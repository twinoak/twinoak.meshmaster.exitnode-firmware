# p1.22-74 — A name of its own on the network

An owner of two boards reported on 22 November that one of them had a new MAC address, and so a
new IP, after an update. The answer given was that this firmware sets no MAC: the station's
address is the chip's own, burnt into its eFuse. That answer is now a **rail** rather than a
reading of the tree — a native test walks `src/` and `lib/` for every call that would choose an
address instead, and fails on any of them.

The half a firmware may choose is the **name**, and each board now announces one of its own:
`meshmaster-` and the last four hex digits of its station MAC, lower case — `meshmaster-2b3c`.
`status`'s `wifi` line prints that name beside the address, in every state, because the moment a
person reads it is the moment they go to reserve an address in their router.

## What changed

**`src/net/Hostname.{h,cpp}`** — two pure functions, host-tested: the name from six bytes, and
those six bytes as `aa:bb:cc:dd:ee:ff`. Nothing of the board is in either; the board passes what
the eFuse gave it, a test passes its own. Added to `[env:native]`'s `build_src_filter`.

**`src/net/WifiLink.cpp`** — `nameThisBoard()`, called from `begin()` **before**
`WiFi.mode(WIFI_STA)`:

```cpp
WiFi.persistent(false);
WiFi.setAutoReconnect(false);
nameThisBoard();               // before WiFi.mode(WIFI_STA), which is the only call that takes it
WiFi.mode(WIFI_STA);
```

**Why there, read off the framework at this repository's pin** (`framework-arduinoespressif32`
3.20017, Arduino core 2.0.17; `framework-espidf` 4.4.7):

| | |
|---|---|
| `WiFi.setHostname(name)` | `WiFiGeneric.cpp:901` → `set_esp_netif_hostname` (L292): it `snprintf`s the name into a static `default_hostname[32]` and **touches no netif at all** |
| `WiFi.mode(WIFI_STA)` | `WiFiGeneric.cpp:1249`. Creates the netifs and starts the driver, then at **L1265** does `set_esp_interface_hostname(ESP_IF_WIFI_STA, get_esp_netif_hostname())` — the one call that puts the buffer on the station's netif |
| and once only | `mode()` returns at its first lines when the mode asked for is the mode in force (L1248-1251), so that push happens at the **first** `WiFi.mode(WIFI_STA)` and never again. `WiFi.begin()` goes through the same `mode()` and so pushes nothing |
| onto the wire | `esp_netif_set_hostname` → `p_netif->hostname` (`esp_netif_lwip.c:1314`), and lwIP's DHCP client writes that into option 12 of its DISCOVER (`dhcp.c:1244`, under `LWIP_NETIF_HOSTNAME`, which is `1` at `lwip/port/esp32/include/lwipopts.h:524`) |

So a `setHostname` after `WiFi.mode()` is a name the network never hears, and that is why the
order is what it is and why there is a test that reads this file and fails if the two lines swap.

The six bytes come from **`esp_read_mac(mac, ESP_MAC_WIFI_STA)`**, which reads the eFuse and needs
no driver; `WiFi.macAddress()` goes through `esp_wifi_get_mac()`, which has nothing to answer with
until `mode()` has run — too late to name anything. The two give the same address: the station MAC
*is* the base MAC (`esp_mac.h`), which is what the core's own default name is built from too.

**`status`** — `WifiLink::describe()` now ends every state's line with `, mac <mac>, name <name>`,
written once after the `switch` so that no state can be the one that forgets it:

```
wifi      connected to Twinoak, 192.168.1.20, rssi -61 dBm (1 connects, 0 drops), mac 34:85:18:1a:2b:3c, name meshmaster-2b3c
wifi      off, wifi.ssid is unset, mac 34:85:18:1a:2b:3c, name meshmaster-2b3c
```

**The boot log** says the same two in one line before the first connect attempt
(`wifi: mac …, name …`), so the bench walk is reading rather than typing.

**The rail** — `test/test_hostname`, in the shape of `test/test_flash_writes`: a walk of `src/`
and `lib/` for `esp_base_mac_addr_set`, `esp_iface_mac_addr_set`, `esp_wifi_set_mac`,
`esp_netif_set_mac`, `ETH_CMD_S_MAC_ADDR` and `setMacAddress`, with its own planted-files test
beside it (four files, three setters seen, three reads left alone). Reads are not forbidden:
`esp_read_mac` is how the name is built. A new bullet in README's *Rails that hold in every task*
states it, and `test_tls_policy`'s two rails tests check that bullet's paths and the suite exist.

## Deviations from the spec or the task

- **The task's premise that every board announced itself as `espressif` does not hold at this
  pin, and this is worth Thomas's attention.** The task names
  `CONFIG_LWIP_LOCAL_HOSTNAME="espressif"` (`sdkconfig.defaults:1464`) as the name boards shared.
  That setting is only lwIP's *fallback for a netif nobody named*, and the Arduino core names the
  station on every run: `get_esp_netif_hostname()` (`WiFiGeneric.cpp:284`) builds
  `CONFIG_IDF_TARGET "-" + mac[3]mac[4]mac[5]` — `esp32s3-1A2B3C` — whenever `setHostname` has not
  been called, and `mode()` pushes exactly that. Those last three bytes are the unique part of an
  Espressif MAC, so **two boards were already two names in a router's list**, and no board of this
  firmware has ever announced itself as `espressif`.

  What follows: this change does **not** close a name collision, because there was none. What it
  buys is a name a person can recognise — `meshmaster-2b3c` rather than `esp32s3-1A2B3C` — and a
  name that is this product's rather than the chip vendor's. It also makes the 22 November report
  harder still to explain by the firmware: neither the address nor the name a board announced
  changed between `v0.6.0` and `v0.7.6`. `FOLLOWUPS.md` already carries that the two addresses
  were never received; this is the firmware side of the same item, and it is now read off the
  framework rather than off `src/net/`.

  `sdkconfig.defaults` is left exactly as it was: the setting is the Arduino core's own
  configuration, `tools/check-sdkconfig.py` holds the file to that on every build, and changing a
  fallback nothing reaches would have been a change for show.

- **Nothing else.** No disagreement with twinoak/meshmaster.dk: every file the task's **Spec**
  line names is in *this* repository (`src/net/WifiLink.cpp`, `sdkconfig.defaults`,
  `docs/console.md`, `docs/field.md`) and all four were read in full, as was the pinned framework
  they describe. A board's name on its owner's LAN is not something the protocol spec speaks about.

## Decisions taken without asking

- **The last four hex digits are `mac[4]` and `mac[5]`**, printed `%02x%02x` so leading zeros are
  kept (`meshmaster-000f`, not `meshmaster-f`). A name that collapsed a zero would be a name that
  does not match the address beside it, which is the one thing this line is for.
- **The MAC is printed `aa:bb:cc:dd:ee:ff`, lower case** — the form a router's lease list and a
  reservation page use, so the two can be compared character by character.
- **Both words are on the `wifi` line in every state, `off` included.** The line is read before
  any WiFi name has been typed — step 3 of the bench walk — and that is when a reservation is
  made. It costs 45 characters on a line `status` prints into a 320-byte buffer; `wifi`'s own
  buffer (160) still holds the longest line with room to spare.
- **One extra line in the boot log** (`wifi: mac …, name …`), before the first connect attempt.
  The task asks only for `status`, but a session cannot see a router, so the walk has to be a
  matter of reading the port.
- **A failed eFuse read says `unknown` rather than six zeroes.** `esp_read_mac` returning anything
  but `ESP_OK` leaves the framework's own name in force, and the line says `mac unknown, name
  unknown` with a `W` line beside it, rather than printing `00:00:00:00:00:00` as though it were
  an address. It cannot happen on a board whose eFuse is programmed; it is one branch, not a
  feature.
- **The rail lists six calls and not an eFuse API.** A raw eFuse write over `MAC_FACTORY` would
  mean forbidding `esp_efuse_write_*` wholesale; this firmware writes no eFuse at all, and the
  file says so where the list is. `esp_iface_mac_addr_set` is the ESP-IDF 5 name and is forbidden
  now so a pin bump cannot bring it in unnoticed.
- **`test/test_hostname` is one suite for both halves** — the name and the rail. They are the same
  question (a board's identity on the network), and the alternative was two suites and another
  minute of PlatformIO relinking.

## Not verified here (and why)

A session cannot join a network, so nothing below has been seen — only built, and read off the
framework's source.

1. **Two boards, one network, two names.** Risskov and Aarhus C on the same router: its list of
   leases should show `meshmaster-xxxx` twice, with two different four-digit endings, where it
   used to show two `esp32s3-XXYYZZ`. This is the one thing the task is for.
2. **`status`'s `wifi` line.** `mac` six octets lower case, `name` `meshmaster-` and the last four
   characters of them, and they agree: the four digits of the name are the last two octets of the
   address. Check it with WiFi **off** too (before `set wifi.ssid`), because that is the state an
   owner reads it in.
3. **The boot log line.** `wifi: mac …, name …` just after `board:` and before
   `wifi: connecting to …`, saying the same two words as `status`.
4. **The name survives.** `erase confirm`, then a reflash, then an `update apply`: the same name
   each time, because it is made from the chip and stored nowhere. There is no `set` for it —
   `set hostname meshmaster-aaaa` should be refused as an unknown key.
5. **A reservation made by the MAC holds.** Reserve the address in the router by the `mac` the
   line prints, reboot the board, and check it comes back to the same IP. This is what
   `docs/field.md` now tells an owner to do.
6. **The name reaches DHCP, not just the netif.** If the router shows a lease's hostname, it
   should already be `meshmaster-xxxx` at the **first** lease after flashing, not after a renewal.
   That is the half of the reading above that only a router can confirm.
