# p1.22-72 — A refused result holds nobody back

On 24 November 2026 a unit posted a result meshmaster.dk turned away for what it said. The
library keeps results until they are taken, oldest first, and `flushResults` returned at the
first post that failed — so that one result was the oldest for three hours and every result
behind it waited, until the kept image filled and dropped it. `IUplink::postJobResult` answered
yes or no, and the server's verdict on a body read exactly like a call that never arrived.

A post has **three** answers now: *taken*, *not reached*, *refused*. A refused result is dropped,
counted, said with the job and the status, marked in what `jobs` remembers, and the flush **goes
on**. A result that was not reached is kept and stops the flush, as it always did.

## What changed

**The seam** (`lib/agent-core/include/agent/IUplink.h`). One more out-parameter:

```cpp
virtual bool postJobResult(long long jobId, const char* body, size_t len, bool& jobsWaiting,
                           int& refusedWith) = 0;
```

| Answer | `return` | `refusedWith` | What the library does |
|---|---|---|---|
| taken | `true` | `0` | forgets the result |
| not reached | `false` | `0` | keeps it, posts it again, **stops the flush** |
| refused | `false` | the **HTTP status** | drops it, counts it, says it, marks it, **goes on to the next** |

An out-parameter and not a new return type, for two reasons. It is the shape its own neighbour
on this interface already has — `postUpdateResult(…, bool& notFound)`, *the one 404 is an answer
and not a glitch* — so a reader of `IUplink.h` meets one idiom and not two; and it carries the
**status**, not a bool, so the log line, the `jobs` mark and the `status` count are the server's
own number rather than something the library had to go and fetch from `lastCall()` afterwards.
An uplink that leaves it 0 always behaves exactly as this interface did before.

**The one function** (`agent/JobEnvelopes.h`, beside the envelopes):
`mm::resultIsTheServersVerdict(int httpStatus)` — **400, 404, 409, 410, 413, 422** are a verdict;
**401, 403, 408, 429**, every **5xx**, 0 (no answer) and every status it does not know are not.
The name is the Walter's own, so the two repositories read the same word.

**The library** (`JobRunner`). `flushResults` drops a refused result, counts it, logs it with the
job and the status, and `continue`s to the next; `postFailures_` does not move and nothing backs
off, because the server is answering. `post()` — the job's own result — never puts a refused body
into the buffer at all, so it is in no claim's `holding` and in no kept image. `resultsRefused()`
and `lastRefusedWith()` are the count and the last status; `Record::refusedWith` is the mark.

**The Heltec's uplink** (`AgentClient::postJobResult`). `postToJob` hands back the status it
already had — 0 when no reply came back — and the one line above decides.

**The console.** `jobs` gains a `refused` line when there has been one, and the job's own line
reads `(refused by the server: http 400)` where it would have read `(not posted)` — which would
have said *still on its way* about a result nobody will ever have. `status`'s `jobs` line carries
`; 1 result(s) refused (last http 400)`.

## Deviations from the spec or the task

**None of substance.** Two readings worth recording:

1. **The task's list and what meshmaster.dk actually answers a result with are not the same set**, and deliverable 2 asked where they differ. Read at `14215c3` in twinoak/meshmaster.dk: the result door is `AgentV1.cs`'s `/jobs/{id}/result` → `AgentProtocolService.ResultAsync` → `RegisterApi.AnswerAsync`, and `AnswerAsync` can answer exactly **400** (`Invalid`, the envelope and the job type's contract), **403** (`Forbidden`), **404** (`NotFound`: no such job, or a result from an exit node that never attempted it) and **409** (everything else, including a `clientId` used for another job) — and 200. So:
   - **413** is real but is not the application's: `HardeningExtensions` sets `MaxRequestBodySize` on Kestrel and on IIS, so a body over the limit is refused by the stack in front of the app and never reaches `AnswerAsync`. It is a verdict on the body all the same — the same bytes are the same size next wake.
   - **410** is answered nowhere in meshmaster.dk today. It is on the list because `actionFor` has had it since task p1.2-10 (the .NET agent's `Definitive`) and because *gone* is as final as *not found*; it costs nothing and it is held by a test.
   - **422** is answered by `IdempotencyMiddleware` (`idempotency-key-reused`) and by nothing on the agent routes, because an agent sends no `Idempotency-Key`. It is on the list for the same reason as 410.
   - **403 is in the server's list and deliberately *not* a verdict**, which is where this function parts from `actionFor`'s `Discard`. A 403 on the agent routes is an exit node whose owner has paused it: its results are perfectly good and go out the moment the owner unpauses, so keeping them is right. `Discard` asks *retry this call now, or back off?* — and a paused exit node should do neither, which is why that list keeps 403 and this one does not.

   Nothing in `spec/API.md` §3 contradicts the list; §3 says what the *body* of each answer is and leaves the statuses to §1's problem-details rule and to the door. No change is owed to meshmaster.dk.

2. **The task calls the Walter's rule "the right rule in the wrong place" and its list is three statuses, not six** (`ModemUplink::resultIsTheServersVerdict`: 400, 404, 409). The library's list is the wider one, because `actionFor` already held 410, 413 and 422 as definitive in this repository and a result is not a special case of that. The Walter's own three are a subset, so nothing it refused before is kept now.

## Decisions taken without asking

- **An out-parameter rather than a new return type**, and it carries the **status** rather than a bool. Reasons above: the idiom `postUpdateResult` already set on this interface, and the words of the log, the `jobs` mark and the `status` line being the server's own number.
- **A status the function does not know keeps the result.** Only the six are a verdict; a 405, a 415, a 451 or anything a later meshmaster.dk invents is *not reached* and is posted again. Keeping is what this library has always done, a dropped result cannot be got back, and the buffer is bounded and counted — so the cost of being conservative is bounded and the cost of being wrong the other way is a reading nobody ever has. A status that turns out to be permanent will show as a result that never goes and a `refused` count that stays 0, which is readable at the console.
- **A refusal is not `resultsDropped()`.** The heartbeat's `resultsDropped` means *the buffer ran out of room*, and a refused result did not. It has a counter of its own, which is at the console and nowhere on the wire — deliverable 5.
- **The count is not in the heartbeat and no follow-up asks for it.** The server knows every result it refused: it refused it, and `AnswerAsync`'s answer is on its own record of the job. There is nothing for the board to tell it that it does not already have, so there was nothing to write for meshmaster.dk.
- **The status is handed from `post()` to the `remember()` that follows it** (`postRefusedJob_`, `postRefusedWith_`) rather than written into the record directly, because at the moment the job's own post is refused the job has no record yet — `remember()` is the line after `post()` at both call sites. The job id is kept with the status and both are cleared when read, so a job that runs again later is never marked from a stale refusal (held by the last half of `AResultRefusedAtItsOwnPostIsNeverKeptAtAll`).
- **The log line names the job and the status and prints no body.** A result is a reading of a repeater and not a secret, but the status is the whole of what a person needs in order to go and read the server's own record of that job.
- **`FakeUplink` gained `failResultsInTurn({…})`** — one fault per result post, in turn — because a flush whose oldest result is refused, whose second is not reached and whose third would be taken needs three different answers from three calls, which one fault and a count cannot give. And `Fault::BadRequest` (http 400), which is the status of 24 November; `Discard` (422) and `NotFound` (404) were already there.

## What the Walter's uplink changes at its next sync

Read in `twinoak.meshcore.walter-firmware` at its current `master`:
`components/agent/modem_uplink.cpp` (`postJobResult` ~L732–798, `resultIsTheServersVerdict`
~L708–710), `components/agent/include/walter_agent/modem_uplink.h` ~L345–352, and
`tasks/phase-18/reports/06.md`.

1. **The signature**, in the header and the definition:
   `postJobResult(long long jobId, const char* body, std::size_t len, bool& jobsWaiting, int& refusedWith)`,
   with `refusedWith = 0` beside `jobsWaiting = false` at the top.
2. **The refusal branch** — today `if (!ok && c.reachable && resultIsTheServersVerdict(c.httpStatus)) { … return true; }`.
   The `return true` was the only way to tell the library *stop keeping this*, and it was a lie:
   the result was not taken. It becomes **`refusedWith = c.httpStatus; return false;`**. Everything
   else in that branch stays as it is — `counters_.results_not_taken`, the `LOG_W`, and
   `gate_->resultNotTaken(jobId, c.httpStatus)`, which settles the journal's `kNotTaken` entry so
   that `resultOwed()` finds it. That entry is the unit's own durable record and is not the
   library's business.
3. **`ModemUplink::resultIsTheServersVerdict` can go** — header and definition — replaced by
   `mm::resultIsTheServersVerdict(c.httpStatus)`. The library's list is the Walter's three and
   **410, 413 and 422** besides, so nothing it settled before is owed now. Its own test of the
   rule (`host_test/agent/test_a_refused_session_reports.cpp` ~L443–450) either points at the
   library's function or goes: `test_envelopes` in this repository holds the list, every status of
   it, and holds it against `actionFor`'s.
4. **`resultWasRefused` / `rememberRefusedResult` / `refused_results_[]` / `kRefusedResults` lose
   the reason they were written.** They exist because the library kept posting a body this uplink
   had answered *taken* for — within the wake from its own buffer, and after a sleep from the
   kept image. The library now drops it at the refusal, so it is never offered again from either
   place. Whether the Walter's **own** owed-result paths (a session result posted from the journal
   after a restart) still want the within-wake guard is its reading and not this report's; the
   sync need not touch them for the library's sake.
5. **The `gate_->withhold(jobId)` path is untouched and still answers `true`.** That is a
   different thing being said — *this job is left to its lease on purpose* — and the three answers
   do not give it a better word. Left exactly as it is; worth a thought at the Walter's end, not
   here.

Nothing else of `mm::IUplink` moved, so the rest of the sync is the ordinary copy.
