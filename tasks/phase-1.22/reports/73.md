# p1.22-73 — What is new is a file of the release

Every task leaves one line in `release-notes/unreleased/`, and until now a release printed them
in one place only: its page on GitHub. That is not where an owner is asked to update an exit
node — meshmaster.dk is. So a release now carries those lines as a **file** of its own,
`WHATSNEW.md`, beside the images and the manifest, and meshmaster.dk's task p4.49-262 keeps it
with the release it imports and draws it on the Firmware tab where the update is offered.

The file is the bullets and nothing else: no heading, no version, none of the standing text the
release's page wraps them in. It is listed in `SHA256SUMS` and it is **not in the manifest and
not signed** — the manifest is what a *board* trusts, its format is the hardware repository's,
and text about a release is no part of what a board verifies before it boots an image.

## What changed

**The shape, in one function** (`tools/release.ps1`). `Test-WhatsNew` holds a text to what the
drawer at the other end can read, and throws **with the line that broke it**:

| | |
|---|---|
| the bound | at most **16 384 bytes**, UTF-8, no byte-order mark, LF |
| every line | a bullet (`- `) or a bullet's continuation (indented two spaces) |
| the markup | `**bold**` and `` `code` `` and **nothing else** of Markdown |

`Find-WhatsNewMarkup` is the last of the three. Code spans come out of the line first, because
anything at all is literal inside one — `heltec_v3`'s underscore, a console line, a path — then
balanced `**bold**`, and what is left has to be prose: a bracket, a tag, a pipe, an underscore,
a stray asterisk or an unclosed code span is named and refused. The reason is at the other end:
meshmaster.dk draws those two and shows everything else as the characters it is made of, so a
link in a line would be read there as its own brackets.

**Three places call it, and none of them is shell:**

- **`-Action notes`** holds the compiled bullets **before it writes the file**, so a release
  stops there and the file is never written;
- **`-Action whatsnew -File <path>`** is new, and holds the file **as it stands**, whoever wrote
  it. It is the step the workflow runs before anything is uploaded, so the dry run's own line
  goes through the same gate, and it prints the file (deliverable 4);
- **`-Action check`** holds the same shape on every pull request, which is where it is cheap.
  `docs/release.md` already promised that a line breaking the format is *a red check and not a
  surprise during a release*; a Markdown link in a line was not caught there before.

`Read-WhatsNew` reads the bytes rather than the text, strictly as UTF-8 and with the line
endings left alone — `Read-Text` would have turned a CRLF file into an LF one and hidden the one
thing the LF rule is there to see.

**The workflow** (`.github/workflows/release.yml`).

- the notes' step ends with `-Action whatsnew`, and its dry-run fallback is now a **bullet**:

  ```
  - **This is a dry run.** Nothing is waiting in `release-notes/unreleased/`, and a real release would refuse.
  ```

  so the file has one shape however it was written. The italics it used to be would have broken
  the markup rule;
- that fallback is now reached **only** when nothing is waiting. Lines that *are* there but of a
  shape no release could publish are red in a rehearsal too, which is what a rehearsal is for;
- `SHA256SUMS` lists `WHATSNEW.md` after the images;
- `gh release create` uploads it beside `manifest.json`.

Nothing else of the run moved. The page's *What's new* and all of its standing text are what they
were, the manifest is built from the four `.bin` files by name as it always was, and the gate
before publishing is untouched.

**The words.** `docs/release.md` §4 is now a table of a release's files with `WHATSNEW.md` in it
and a section on the file — its shape, why the manifest does not list it, and what holds it; §2
says bold and code rather than *emphasis*, because that is what the file allows; §5 and §8 and
the page's own summary table follow. `README.md`'s release paragraph names it too.

   `Read-Note` folds a note's paragraph into a single line first. The rule is in the function

   exercises it today.
3. **meshmaster.dk's `_ReleaseBullets.cshtml` and this rail have to stay in step, and only one
   of them is in this repository.** The markup rule here is the *writer's* half; the drawer's
   half — what it shows and what it escapes — is that repository's task 262, which plants a
   script tag, a link and a table of its own. Neither half trusts the other: a file this rail
   would refuse must still be drawn safely there, and the escaping is tested there.

## Decisions taken without asking

- **A new action rather than a step of shell.** `-Action whatsnew -File <path>` holds the file
  that will be uploaded, whoever wrote it, which is what *held to its shape before the upload*
  asks for and what no amount of checking inside `-Action notes` can give — the dry run's own
  fallback line does not go through `notes`. Every decision of this release stays in a script
  with a self-test, as `tools/release.ps1`'s own synopsis insists.
- **`-Action check` holds the shape too**, on every pull request. `docs/release.md` §2 already
  promised a broken line is a red check and not a surprise during a release, and that promise was
  only true of a note's *own* format — a link, a table or a tag inside a line would have reached
  `master` and stopped a release weeks later. The shape is held on the *compiled* lines, and with
  no line waiting there is nothing to hold.
- **The dry run's fallback is a bullet now.** It said *Nothing is waiting …* in italics, which the
  markup rule refuses. It says the same thing in bold and code, so there is one shape and one gate
  and no exception.
- **A rehearsal is still allowed to be of a release with no lines, and of nothing else.** The
  catch in the notes' step now re-throws anything that is not *nothing to release*: a dry run
  whose waiting lines break the shape goes red, because a rehearsal that passed over it would
  rehearse the wrong thing.
- **UTF-8 is held strictly and a byte-order mark is refused.** The file's shape says UTF-8; a mark
  at the front of it is three characters the drawer would show, and bytes that are not UTF-8 would
  be refused by meshmaster.dk's import ("the notes were not kept and why", its deliverable 1).
  Better to never publish one.
- **Anything is allowed inside a code span.** Without that the rule would refuse
  `` `heltec_v3` ``, `` `set mqtt.iata AAR` `` and every path with an underscore in it, and the
  lines of this firmware's releases are full of them. A code span is literal at both ends.
- **`_underscore_` is markup and is refused, where `docs/release.md` used to allow *emphasis*.**
  The file's shape names bold and code, and an underscore the drawer does not read would be shown
  as itself. That sentence of the page is now bold and code.
- **`WHATSNEW.md` is listed in `SHA256SUMS` after the images, not before.** The images are what a
  person came for, and the gate reads the file by name and not by order.
- **The bound is on the file's bytes and is checked before the lines are.** A file over 16 384
  bytes is refused for being over the bound even if a line in it is also wrong: the bound is the
  thing the other end cannot take at all.
