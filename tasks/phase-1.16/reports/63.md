# p1.16-63 — A table that could not be written

Adding the second application slot was one erase and one write, each asked for once. A board
whose sector would not take the write ran on with no partition table and did not boot again:
the merged image over USB was the only way back, and it costs the key, the token and the WiFi.
At the console somebody read the sentence that said so; asked for by meshmaster.dk nobody did.

While the firmware runs it holds both tables byte for byte and can still write. So now: the new
table three times, then **the old one put back** three times, and only when neither holds does it
say what is true — and then it goes on putting the old one back, once a minute, for as long as it
runs. Three endings, each named, and two of the three leave a board that boots.

## Decisions taken without asking

- **The byte-level sentence of a bad read-back is gone.** `addSecondSlot` used to answer *the
  sector reads 0xNN at 0xNNN where the new table has 0xNN* and nothing else; with three tries the
  first mismatch is no longer the ending, and 200 characters have to carry the ending, what is true
  and what to do. `writeTheTable` therefore returns a plain false at the first thing that did not
  go, and a caller tries again rather than reading a reason — there is nothing else to be done with
  one. Two tests went with it: `AddingTheSlot.AReadbackThatDiffersByOneByteSaysWhatItReadAndDoesNotSayAdded`
  and `AddingTheSlot.AnEraseOrAWriteThatFailsSaysSoAndSaysWhatToDo`. Eleven tests of the new
  endings replace them, including both halves of each.
- **Three tries of each table** (`kTableTries`), because the acceptance criterion's *no more than
  six erases* is exactly three and three. One erase a try, and the erase is not retried on its own.
- **One minute** (`kPutTheTableBackEveryMs`), and the keeper is a plain object stepped from
  `loop()` — no task, no timer, nothing that can run while a job does. It writes at most one sector
  a minute and nothing at all while the sector holds a table.
- **The `AskTable` seam gained a `bool* theSectorHoldsATable`** rather than returning the ending
  enum, which would have put `src/platform` into `src/update`'s header. The ask turns it into one
  of two fixed phrases in the `stuck` entry's note, so no new journal step word exists and the
  page shows the words as they are.
- **`addSecondSlot` has one caller in `main.cpp`** (`addTheSecondSlot()`), so the console's `update
  slot` and the server's own ask both tell the keeper how it ended. Before this the two did the
  same work twice.
- **The warning is its own first line**, `!!` in the ten-column label of this console, in both
  `update` and `status`, rather than a suffix of the `firmware` line beside *on trial*. Two
  unrelated states in one line would read as one.
- **`update slot`'s ending line is printed only when something was written.** On a `two` board, an
  `other` board or a sector that could not be read, nothing was tried and `tries == 0`; the
  sentence is the whole answer there, as it was.

## Not verified here (and why)

No test in this repository can erase a sector, so every line below is Thomas's with a board on the
bench. The three endings above are driven through a scripted 4 kB sector; a real sector that
refuses a write has never been seen by this code.

- **`update slot` on a V3 and on a V4**, from the release of this pile flashed as the plain `.bin`:
  the sentence is *added: app1 at …*, no `ending` line follows it (one try), `reboot`, then `update`
  says `two`, and the settings, the token and the identity are as they were. This is the happy path
  and the only one a healthy board will ever take.
- **`status` and `update` on that same board print no `!!` line** — the keeper is not going, so
  there is nothing there at all.
- **The `!!` line itself has never been printed on a board**, because nothing here can make a real
  sector refuse a write. If it ever appears, it means what it says: leave the board on the power and
  watch the line; it goes away by itself when a write holds.
- **The retry costs nothing on a healthy board**: one erase, one write, one read-back, as before.
  Worth a glance at the serial log of the first `update slot` to confirm one `update slot: added …`
  line and no `Error`-level line beside it.
- **One ask from meshmaster.dk to a `one` board at the desk** (pile 1.15's follow-up, *before a
  board that is not on a desk is asked*): the journal reads `check`, `adding-slot`, then the
  restart and `fetching`. An `adding-slot` that ends `stuck` cannot be provoked on a working board.
- **`CONFIG_SPI_FLASH_DANGEROUS_WRITE_ALLOWED` has still only been built**, not exercised on
  hardware. That was true of task 57 and is true of this one; `docs/field.md` §9 is the page.
