# p1.16-64 — The way back

Two ways back now lead back: `update back` at the console, and a restart where the framework
refuses its own rollback.

The thing that was wrong is one sentence long. *A flash over USB still wins* switches at boot to
an image in the first slot **the record does not know**, and after an update from A to B the
record knows A — it is the version it switched from. So an owner who flashed A again saw the
flasher succeed and the board come up on B, and nothing said a word. The bytes of a slot are the
same whether A was flashed a minute ago or has lain there since the update, so the firmware
cannot tell and does not guess: it says what it found, once, and takes `update back` from a
person instead.

## Decisions taken without asking

- **Deliverable 5's ending is `stuck`, and the record gained a third `Ended`.** The four
  outcomes are `committed`, `rolledBack`, `refused` and `stuck`. It is not `committed` — the image
  did not prove itself. It is not `refused`, which means *nothing was switched*, and something was:
  the board is running the firmware that failed. It is `stuck`, *the board cannot say what
  happened*, which is as close to the truth as the four words come — the board can say what
  happened, in the journal's last entry, and what it cannot say is where it ended up by the
  contract's three other words. So `Ended::Stuck` is new in `UpdateRecord.h` (`fw.up.end` holds
  `stuck`) and `Asked::watchTheTrial` maps the record's three endings to three of the four
  outcomes. The ask's `toVersion` was already the version running when the result is written, so
  it carries the failed image's version with no change.
- **`BootFinding::Stuck`, so the boot's one word is not a lie.** The branch that now ends `stuck`
  used to return `BootFinding::RolledBack`, whose comment reads *the old image is back*. It is not.
  `main.cpp` only prints `bootFindingWord(found)`, so nothing else moved.
- **`update back`'s two console-level refusals are the caller's sentence.** `Updater::goBack` takes
  `const char* elsewhere`: the sentence the console has when meshmaster.dk's ask is in hand or a
  fetch is running. The machine knows neither — `whyTheOtherSlotMayNotBeWritten()` is the arrow
  pointing the *other* way, from this machine to the fetch — and `update apply` already does those
  two checks in `main.cpp` for the same reason. Passing them in rather than leaving them in
  `main.cpp` alone is what makes all seven refusals one test in `test/test_trial`, with
  *nothing was switched* asserted for each.
- **The `back` line of `update` is its own line, not a change to `other`.** `other` is task 59's
  record — what a *fetch* judged — and a board that has taken an update has nothing judged at all
  while still holding a firmware in the other slot. Two different facts in one line would read as
  one. The cost is that `update` now reads the other slot to find its descriptor, which is a pass
  over the bytes there (the same pass `atBoot` has made at every boot since task 60); nothing is
  written and nothing is decided by it.
- **`update back` is not held to the fetched image's hash, as `update apply` is.** `apply` re-reads
  the slot's SHA-256 and compares it with what the fetch judged, because there *is* a judgement to
  hold it to. `update back` has none — its whole subject is bytes no release of this board's named
  — so what stands in for it is the framework's own verify, which `bootOther()` does before it
  writes the boot choice and which refuses an image it would not load, and the descriptor read out
  of the slot. On a board that *does* hold a judged image the two commands overlap and both switch
  to it; the task names no refusal for that and deliverable 1 says it is taken when the framework
  would load it.
- **`refuse()` in `Parser.cpp` gained a fourth argument.** One refusal now names four words.
- **`help` gained `update back` — and `update apply`, which it never had.** Task 60 added the
  command and not its line, so a console that listed `slot` and `fetch` but neither of the two
  commands that restart the board into another firmware would have been odd to add to. Two lines.
- **A boot that has gone back goes on offering `update back`.** After `update back` to A fails its
  trial and the board is B again, the record knows A as `to`, so every boot from then on prints
  *the first slot holds A, which this board has run: `update back` goes back to it*. That is the
  line the acceptance criterion asks for, and `update`'s `last      rolled back: no wifi…` beside
  it is what says the attempt was already made. Suppressing it would mean the firmware deciding
  that a person may not try again.

## Not verified here (and why)

No test here can write a boot choice, boot a second slot, refuse a rollback from the ESP-IDF or
pull the power: all four of the trial's seams are scripted, as task 60 left them. The bench items
below are new with this task and are in `docs/field.md` §9 with the rest, which also carries every
item of tasks 57, 59, 60, 61 and 63 that is still waiting.

On a **V3** and on a **V4**, each with release **B** committed from release **A** (that is, after
one `update apply` or one press on meshmaster.dk):

- **Flashing A's plain `.bin` over USB changes nothing, and the boot says so.** The flasher
  succeeds and the board still comes up on **B**; the log of that boot carries one line naming A
  and `update back`, and `update`'s `back` line names A. This is the thing that was silent before.
- **`update back` commits A inside two minutes.** The board restarts, `status` says *on trial* and
  names A, and `update` ends `last      committed` with A, from B. The identity is the same 64 hex
  characters and the exit node's page shows A.
- **A `update back` whose trial fails ends where it was typed.** From A, with the access point
  **off**, `update back`: the board switches to B, B's ten minutes go by, and the board comes back
  on **A**. `update` then says `rolled back: no wifi…` and names B.
- **`update back` is refused on a board that has never updated.** A `two` board with nothing
  fetched: the other slot holds nothing this firmware would boot, and nothing is switched.
- **An image with no descriptor is seen and said.** A board running from its second slot with any
  pre-descriptor release (or any other application image) in the first: one line at the boot, no
  switch, and `update back` refused.
- **`stuck` cannot be reached from a desk at all.** It needs the framework to answer
  `ESP_ERR_OTA_ROLLBACK_FAILED` for a pending image *and* `esp_ota_set_boot_partition` to refuse at
  the boot after it. Nothing has made a board do either; the journal of the first trial on each
  board generation is what says which bootloader it has (pile 1.15's follow-up, *Which bootloader a
  board in the field has is not known here*), and that reading is the one that matters here too.
- **The reading cost of `update`.** The `back` line reads the other slot's 1.4 MB looking for the
  descriptor. It is the same read `atBoot` has made since task 60 and no session can time it; if
  `update` feels slow at the window, that is what it is.
