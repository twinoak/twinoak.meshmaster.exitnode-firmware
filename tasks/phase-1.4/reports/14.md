# p1.4-14 — The guest door

The door that was shut twice over is open. A `discover` job at class **guest**
is run instead of being answered *unsupported*, and a guest-class job whose
claim carried **no credential at all** logs in **blank** instead of ending
*unauthorized* — the two halves of meshmaster.dk's guest door (its tasks
p4.7-94 and p4.11-111), which the field found on 11 October through repeater 10
(foreign) and exit node 4 on `v0.1.3`: association 9 *discover at guest:
unsupported*, then the *read now* at guest `unauthorized`.

Two decisions, both the server's and both now the board's:

- **`typeAllowsClass`** admits `discover` at `Guest` *or* `Admin`, which is
  `JobTypes.CredentialClasses`' `Discover => [Guest, Admin]`. `acl` and `none`
  stay refused (a login with no password at either is the ACL login, and a
  repeater that has not granted our key an entry answers that with silence —
  task p3.5-40), and `acl.set`, `config.read` and the six writes are admin-only
  as they were.
- **The material of class `guest` with no guest password in the claim is `""`,
  not `nullptr`**: the blank login, the same frame the `acl` login sends.
  `handleLoginReq` compares the password with `_prefs.guest_password`, which
  `NodePrefs()` leaves empty, so a repeater whose owner never set one answers it
  *at guest* (DECISIONS A-4, task p4.5-81) and the job runs on the session it
  opened. The job's log says so in one line:

```
[18:31:02] I jobs: job 9001 discover for repeater 10 "Foreign repeater" (guest)
           no guest password in the claim: the blank login, which a repeater with no guest password answers at guest
           flooded login, for the path its reply comes back along: logged in as guest (flood)
           path of 2 hop(s), learned from the login
           the guest session is open for 600 s: the next job for this repeater logs in again only if it has gone
[18:31:19] I jobs: job 9001: ok after 1 transaction(s)
```

The one case that **is** missing material is untouched: an admin-class job with
no admin password still logs *the claim carried no admin material; nothing to
log in with*, returns `nullptr` and is `unauthorized` with nothing on the air,
because there is no admin login without one. A repeater that *does* have a
guest password answers the blank login with silence, and the two tries of
`ensureSession` end it `unreachable` — which is what the server expects there
(EXIT-NODES §4.1 step 2) and not a fault. The rotation probe (13) never fires on
this path: it needs the `new` candidate *and* a non-blank material, and the
empty door has neither.

The material decision moved to `src/agent/LoginSequence.cpp` as
`loginMaterialFor(job, note, cap)` — host-portable, so every branch of it is a
native test rather than a grep on `JobRunner.cpp`'s text (the deviation below).

## Deviations from the spec or the task

- **The material decision was lifted out of `JobRunner` to a host, as task 13
  lifted the sequence.** The task asks for native tests that *"a guest-class
  `status` job with no credential logs in blank and runs"* and that *"an
  admin-class job with no admin password still ends `unauthorized` without a
  send"*. `JobRunner.cpp` is not in `[env:native]`'s `build_src_filter` (it
  needs Arduino, the radio and the RTC), so with the branch left where it was
  those two could only have been greps on the file's text. `loginMaterialFor`
  is therefore now a free function in `src/agent/LoginSequence.h/.cpp` — the
  password, the blank login, or nothing, and the one line the job's log gets —
  and `JobRunner::loginMaterial` is four lines that call it and log its note.
  Same behaviour, every branch walked natively, and the division is the one
  `ConfigApply.h`/`ApplyOnTheAir` and `LoginSequence.h`/`LoginOnTheAir` already
  make.
  Consequently **`test_credentials`' store-and-file-system grep covers five
  modules rather than four**: the password now passes through `LoginSequence`
  too (by pointer; its note never carries a value), so `LoginSequence.h` and
  `.cpp` joined that list. The rail is the same rail, over one file more.
- **`learned`'s session line names the session's *role*, which is what the task
  asks for; the .NET agent's names its *class*.** `Handlers.cs` logs `the
  {session.Class} session is open…`; the task says
  `permissionName(ctx.sessionRole)`. The board followed the task, and the
  difference is visible only for a session granted above its class (an
  `acl`-class job answered admin, say): there the board says *admin* and the Pi
  says *acl*. The board's reading is the one its own `loggedInAs` already
  reports in the same result, so the line and the data now agree — which is
  worth more than matching a log string. For every job at the guest door the two
  are the same word.
- **`learned`'s below-class line still says "an admin job that follows"**, where
  the .NET agent parameterises it with the job's class. It is unreachable at
  guest — `roleNeededFor(Guest)` is `kPermGuest`, so no accepted login can fall
  below the class — and a `discover` can only be guest or admin here, so the
  word is correct wherever the branch runs. Left alone rather than churned.
- **EXIT-NODES §7's transaction table still says `discover | admin`**, read at
  today's `master` of meshmaster.dk. §4.1's guest door, §7's own `guest` bullet
  (*"A guest login with no password … that is the guest door's empty case"*) and
  `JobTypes.CredentialClasses` all say guest as well, so the table row is the
  stale line and the code is what this firmware followed. One row of §7 in the
  other repository, for the reviewer to open there; nothing here depends on it.
- **Nothing else disagrees.** `spec/EXIT-NODES.md` §4.1 and §7 and
  `spec/DECISIONS.md` A-4 were read in full at today's `master`, and
  `JobTypes.cs`, `AgentProtocol.cs` (the branch that returns a guest job with a
  null credential for a guest pair) and `Handlers.cs` (`LoginMaterial`,
  `DiscoverHandler`, `Learned`) with them. `handleLoginReq`'s two statements are
  as A-4 reports them.

## Decisions taken without asking

- **The log line is the task's wording, not the .NET agent's.** `Handlers.cs`
  logs *"the claim carried no guest password: logging in blank, which a repeater
  with no guest password set answers at guest (task p4.7-94)"*; the task
  prescribes *"no guest password in the claim: the blank login, which a repeater
  with no guest password answers at guest"*. The task won, because it is this
  repository's own instruction and the sentence says the same thing; the job's
  page therefore reads very slightly differently on the two agents, and nothing
  on the server parses it.
- **No new serial (`LOG_*`) line for the blank guest login.** Task 13 added one
  per probe because a bench walk had no other way to see a transaction that the
  job log alone explained. Here the serial console already prints the job's
  class in its opening line (`job 9001 discover for repeater 10 "…" (guest)`),
  which is the whole of what the walk needs to tell this login from an admin
  one; the detail stays in the job's log, where the server shows it.
- **`kLoginNoteCap` is 160 bytes.** The longest of the four lines is 107
  characters, so the cap is the next round number above the worst case with room
  for a sentence to grow; it is a stack buffer on a path that already holds a
  password.
- **`docs/console.md` gained a bench item (19) as well as the sentence the task
  asked for.** The runbook wants a *Not verified here* list precise enough to be
  walked and the firmware printing enough that the walk is a matter of reading;
  the doc's walk is where items 11–17 put exactly that for the earlier tasks, so
  the guest door's first pair went beside them rather than only into this report.
- **No job-type table to correct.** The deliverable says "the job-type table, if
  it lists classes" — `docs/console.md` has no such table (it lists the types in
  the `jobs` command's output and nothing about classes), so only the login-line
  paragraph and the walk item changed.
- **`transactionsFor("discover", Guest)` is 1**, as it already was for every
  class: `src/agent/Airtime.cpp` prices a discover at one and the guest door
  costs no more than the admin one. Nothing to change there.

## Not verified here (and why)

A session cannot put a repeater on the air and cannot hear what one with no
guest password answers a blank login from this board. Every host test above is
a scripted exchange or a parsed claim; the door itself is Thomas's to walk, and
meshmaster.dk's repeater 10 through exit node 4 is the pair waiting for it.
`docs/console.md`'s walk has this as item 19.

1. **The first guest pair at the empty door.** Flash the merge, then on
   meshmaster.dk run the association wizard on a repeater whose owner never set
   a guest password, choosing the second door (*I have the guest password only —
   or none*) with the field **left empty**; repeater 10 is foreign and offers
   that form alone (p4.11-111). The pairing `discover` must now **run**: the
   job's page shows class `guest`, the log `no guest password in the claim: the
   blank login, …`, then `login along the path the server holds (…)` or `flooded
   login, for the path its reply comes back along`, `logged in as guest`, `path
   of N hop(s), learned from the login`, `the guest session is open for 600 s`,
   and the outcome `ok` with `{"path":{…},"loggedInAs":"guest"}`. The old
   failure — association *failed*, *discover at guest: unsupported*, no
   transaction — must be gone. `jobs` on the console counts **1**, `sessions`
   shows one session at class `guest`, tier `guest`.
2. **The pair's probes.** The wizard's verify `status` at class `guest` must
   reuse that session (`session reused (guest, guest, N s old)`) and read; the
   pair goes `active` with `probeClass = guest`. Then the repeater's **Neighbours**
   tab: with the pair active the read asks at `guest` (`ReadingService.ClassOfRead`,
   p4.11-111) and must fill, where before it asked at `acl` and was silent
   through two exit nodes. A *Read now* at guest must be `ok`, not
   `unauthorized`.
3. **A repeater that *does* have a guest password, at the empty door.** The
   blank login is answered with silence by design, so the log must read `login
   (guest) try 1: no reply (…)`, `try 2: no reply (…)` and the job
   `unreachable` at two transactions, with no probe line between them (the
   rotation probe needs a candidate and a non-blank material). The wizard's
   third reading of that silence is meshmaster.dk's to show; from the board it
   must look exactly like a repeater off the air, because that is all the air
   gives.
4. **A guest pair with a password, unchanged.** On a repeater whose guest
   password you do have: the same flow with the password typed, the log showing
   no *blank login* line at all, and `logged in as guest`. This is the path task
   04 already built; it is listed so that the new branch is confirmed not to
   have taken it over.
5. **An admin job with no admin password, still refused dry.** Hard to provoke
   from the UI — the claim refuses such a job before it is handed out — so the
   evidence stays the native test; if it is ever seen in the field the log line
   is `the claim carried no admin material; nothing to log in with` and `jobs`
   must count **0** transactions for it.
6. **08's resume rebases over two more files.** `JobEnvelopes.cpp`'s
   `typeAllowsClass` and `JobRunner.cpp`'s `loginMaterial` / `learned` /
   `runDiscover`, plus `LoginSequence.*`'s new function — its fake repeater is
   the first place the empty door can be answered *at guest* on a host end to
   end, and that is where the discover's three steps should be walked against
   it.
