# p1.5-16 — The library

The portable half of the agent is `lib/agent-core/` now: a PlatformIO library
with a name (`agent-core`), a version (`0.2.0`), a manifest, an ESP-IDF
component file beside it, and a boundary a test walks rather than a list
somebody has to remember. Forty-nine files moved — twenty-eight headers into
`include/agent/` and twenty-one sources into `src/` — and two are new there:
`Log.cpp`, carved out of the board's, and `Version.h`. Every include inside the
library and into it is `<agent/X.h>`, and what is left under `src/` is this
board:
`main.cpp`, the console, the settings, WiFi, the clock, the TLS client and the
root it verifies against, the OLED, the watchdog, and where a log line goes.
`[env:native]` compiles the library **whole**, which means `JobRunner.cpp` and
`AgentLoop.cpp` were compiled by a host compiler for the first time in this
repository's life, with `-std=c++17 -Wall -Wextra -Werror`; `tools/check-library-host.py`
compiles them again with an ESP-IDF consumer's `-fno-exceptions -fno-rtti`.

**The Heltec does the same thing.** All 278 native test cases pass, including
every assertion of the 19 suites that existed before (only the paths they read
moved); both boards build with `-Werror`; RAM is byte for byte 15's and flash is
**+296** bytes on the V3 and **+156** on the V4, all of it the one behaviour-neutral
split this task had to make — the log's formatting is the library's and the
serial port is the board's sink.

## The boundary, and what it actually forbids

`test/test_library` is the rule that replaces 15's list of thirteen named
files. The include rule is an **allow** list, which is the only kind that
survives a new file:

- `<agent/...>` — the library's own, and the only form allowed. A quoted
  include anywhere in the library is a failure
  (`Library.NoFileOfTheLibraryIncludesAnythingWithQuotes`), which is the
  *inward* half of "no relative include crosses the boundary".
- `ArduinoJson.h` — the one dependency.
- a C++ standard header — no dot and no slash in the name, which is exact
  enough: every platform header has an extension or a directory.

The deny list is still written out, so that a failure says *which* rule broke:
`Arduino.h`, anything with `WiFi` in it, `Preferences.h`, `esp_*`,
`freertos/*`, `HTTPClient.h`, `WiFiClientSecure.h`, `Stream.h`, `Print.h`,
`SPIFFS.h`, and MeshCore's tree (`MeshCore.h`, `Mesh.h`, `helpers/*`, any name
with `MeshCore` in it).

The *outward* half is `Library.NothingUnderSrcReachesIntoTheLibraryByARelativePath`:
for every file of `src/`, an include whose basename is one of the library's
headers must be spelled `agent/<name>` exactly, so the board reaches the
library through a consumer's include path like anybody else.

Names, with `//` comments stripped (a comment may say what the library's own
constant stands for — that is 15's rule and it still holds): `Serial`, `ESP.`,
`esp_`, `freertos`, `MAX_PACKET_PAYLOAD`, `MAX_PATH_SIZE`, `PUB_KEY_SIZE`, and
`delay(` — Arduino's free function; the seam's is `delayMs(`, which does not
match it.

**`millis(` needed a rule and not a ban.** The task asks the test to fail on
`millis(`, and a flat ban is impossible: `IPlatform` *declares* `millis()`, and
`JobRunner` and `AgentLoop` each have a one-line private `millis()` over the
seam which every line of their `.cpp` calls without an object — that is the
whole point of 15's platform seam, and 15's own test had to write `::millis(`
to avoid the collision. So the rule is: an occurrence reached through an object
(`->millis(`, `.millis(`, `::millis(`) is fine, and a free `millis()` is fine
only in a file that declares a `millis()` of its own, counting the paired
header of a `.cpp`. A free `millis()` in, say, `ConfigApply.cpp` — which
declares none — fails, and that is Arduino's `millis()`, which is the thing
worth catching.

## How `[env:native]` compiles the library whole

By **the project's own `lib/` discovery**, not by `lib_deps`, and the reason is
in PlatformIO's own source. `GetLibBuilders` collects a builder for every
directory of the project's `lib_dir`; the moment a test file includes
`<agent/Airtime.h>`, the scanner matches it against that builder's
`includeDir` and `CollectBuildFiles` then compiles **every** source of its
`srcDir` — PlatformIO has no per-file dependency inside a library. So the
library is compiled whole by construction, `JobRunner.cpp` and `AgentLoop.cpp`
included. A `lib_deps = agent-core` line would be worse than redundant: a bare
name in `lib_deps` is a *package* to install, and PlatformIO would go to the
registry looking for one.

What a reader cannot see from the `.ini`, though, is whether that is still
happening — so `Library.TheRunnerAndTheLoopAreCompiledAndLinkedOnTheHost` takes
the address of `JobRunner::claimAndRun` and `AgentLoop::loop`. A
pointer-to-member-function is an undefined symbol until the object file is in
the link, so if the library ever stops being compiled here the suite stops
*building*, which is a louder failure than a green run over nothing. (It
touches the two symbols and runs neither: running them against fakes is task
17.)

The same discovery is what the board builds use — `agent-core @ 0.2.0` in both
dependency graphs, 22 `.cpp.o` and one `libagent-core.a` each
(`out/16-boards.log`).

`build_src_filter` lost its hand-kept list of nineteen agent files and is four
lines now: `settings/Keys.cpp`, `console/Parser.cpp`, `ui/DisplayLines.cpp`,
`version.cpp`.

## -Werror followed the files

`platformio.ini`'s `build_src_flags = -Wall -Wextra -Werror` reaches `src/` and
nothing else — which means that moving half of `src/` into `lib/` would have
**quietly dropped this repository's `-warnaserror` from the agent on the board
builds**. So `library.json` carries the same three flags in its `build.flags`,
and the library is `-Werror` wherever it is built, here and in a consumer's
tree.

That is safe to do because of `piolib.py`: `LibBuilderBase.__init__` does
`self.env = env.Clone()`, `process_extra_options` applies the manifest's flags
to *that* clone, and `build()` shares only `CPPPATH`, `LIBPATH`, `LIBS` and
`LINKFLAGS` back to the parent. A `-Werror` in a library manifest cannot leak
into MeshCore's or the framework's build.

And it arrives, which was worth proving rather than deducing. A deliberate
`void werrorProbe() { 1 + 1; }` in `lib/agent-core/src/Backoff.cpp` fails
`pio run -e heltec_v3`:

```
lib/agent-core/src/Backoff.cpp:5:24: error: statement has no effect [-Werror=unused-value]
*** [.pio\build\heltec_v3\lib0f0\agent-core\Backoff.cpp.o] Error 1
```

and the build is green again with the line removed. (The first probe was an
unused *variable*, and it compiled — which is not a hole in this but the
framework's own `-Wno-error=unused-variable`, the demotion `platformio.ini`'s
comment beside `build_src_flags` has described since task 01. `-Wunused-value`
is one of the ones it leaves alone.)

## The 296 bytes

The V3's flash is +296 and the V4's +156; RAM is byte for byte identical on
both, and so is every RAM section (`out/16-sections-master.txt` against
`out/16-sections-16.txt`: only `.flash.text` +208 and `.flash.rodata` +88
differ). Sixteen symbols changed size in all, +117 bytes of them
(`out/16-symdiff.txt`, `out/16-nm-master.txt` against `out/16-nm-16.txt`), and
they are two groups.

**Ours, +57 net**, every byte of it the log split:

| | |
|---|---|
| `mm::serialLogSink` | +24 — new: the board's two lines |
| `mm::logBeginSerial` | +19 — new: sets the sink, calls `logBegin` |
| `mm::logBegin(clock, uptimeMs)` | +15 new, and −10 for the one-argument form it replaces |
| `mm::(anonymous)::uptimeMs` | +10 — new: `return millis();` |
| `mm::logSetSink` | +10 — it existed before and nothing called it, so nothing emitted it |
| `mm::logf` | **−11** — it no longer calls `Serial.print` or the ring itself |
| `mm::JsonWriter::escape` | −4 |

**The framework's, +60**, and not a change to the framework: seven WiFi symbols
(`WiFiGenericClass::mode` +20, `WiFiSTAClass::begin(const char*, …)` +20, and
+4 each on `WiFiSTAClass::begin()`, `WiFiGenericClass::getMode`,
`WiFiScanClass::scanNetworks`, `WiFiScanClass::_scanDone` and
`wifiLowLevelInit`) grew because the image moved under them. Disassembly says it plainly — `WiFiGenericClass::getMode` on
`master` calls the ESP-IDF directly,

```
addi.n  a10, a1, 12
call8   420836ac <esp_wifi_get_mode>
```

and here it cannot, because the callee is now outside `call8`'s ±512 kB reach,
so the assembler takes the address out of a literal instead:

```
addi    a10, a1, 12
l32r    a8, 42000ce0 <_stext+0xcc0>
callx8  a8
```

That is `-mlongcalls` relaxation, three extra bytes of code and four of literal
per call site, and it is what the remaining 179 bytes of `.flash.text` and
`.flash.rodata` are as well: literal pools (`.xt.lit*`), the padding around
them, and string data that shifted. It is the cost of a 1 349 157-byte image
growing at all near a call-range boundary, it would reverse itself the next time
anything shrinks, and no source of the framework's or of ours differs in it.

## The ESP-IDF face

`lib/agent-core/CMakeLists.txt` registers the same 22 sources and the same one
include directory as an IDF component, and `lib/agent-core/idf_component.yml`
carries the version and the one dependency. **Neither is built in this
repository** — there is no ESP-IDF in its toolchain, and the task says as much.
What ran instead:

- `cmake -P tools/check-idf-component.cmake` — a stub `idf_component_register`,
  the component's `CMakeLists.txt` included in script mode (which is the syntax
  check), and then the SRCS it registered held against
  `lib/agent-core/src/*.cpp` **in both directions**: a source added and
  forgotten is a failure, and so is a registered line whose file is gone. It
  also checks `INCLUDE_DIRS` is `include` and that `include/agent/` is there.
  A CI step runs it.
- `Library.TheIdfComponentRegistersEverySourceOfTheLibrary` holds the same
  file-by-file correspondence from the native suite, so a session with no cmake
  still catches the common mistake.

**ArduinoJson is declared as a managed component, not vendored.** The Walter's
own `components/modem/idf_component.yml` takes `dptechnics/walter-modem` from
`components.espressif.com` pinned `"==1.5.0"`, with the resolved version and
hash in the repository's root `dependencies.lock`, and its `CMakeLists.txt`
names the library in no `REQUIRES` because "the component manager adds it to
this component's requirements itself". This library does the same thing with
`bblanchon/arduinojson: "==7.4.3"` — the same version `platformio.ini`'s
`[libs]` pins, which `test_library` holds against the `.ini` so the two cannot
drift. A vendored copy would have been a second ArduinoJson in a consumer's
tree for no gain.

`REQUIRES` is therefore empty: this library needs no component of the
consumer's, which is what the three interfaces are for.

## The log, split

This is the one file the task required to be cut in half, and the only change
in this task that can move a byte of the image.

`Log.h` was on the move list ("the portable macros and `mm::logf`") and
`Log.cpp`'s `Serial` sink was not, and 15's report left the note: *16 moves
`Log` and that test together*. So:

- `lib/agent-core/src/Log.cpp` is everything that makes a line — the level, the
  stamp, the one `vsnprintf`, the 240- and 288-byte statics — and ends by
  handing the finished line to the sink.
- `src/Log.cpp` is the Heltec's sink and nothing else:
  `Serial.print(full); logRing().add(full, len);`, in that order, in a function
  whose parameters are still named `full` and `len` — so
  `LogRing.TheLogWritesEveryLineIntoTheRingAndNothingElseDoes` reads the same
  two lines in the same file at the same path and is **unchanged**.
- `src/SerialLog.h` is the wiring: `logBeginSerial(clock)` sets the sink and
  calls the library's `logBegin`. `main.cpp`'s one `mm::logBegin(&clockForLog)`
  became `mm::logBeginSerial(&clockForLog)`.

Two things about `agent/Log.h` changed, and both are in *Decisions* below: an
unset sink now drops the line instead of printing to `Serial` (a library owns
no port), and `logBegin` takes a second function pointer for the millisecond
uptime the `[+123s]` stamp is made of before the clock is known.

**What a board prints is byte for byte what it printed.** The stamp, the level
letter, the CR LF, the truncation at 288 bytes and the order *port then ring*
are all the same code; what is new is one indirect call through a function
pointer that is always set, and one function pointer read for the uptime where
`millis()` used to be called directly.

## Deviations from the spec or the task

- **The tests' paths moved, and nothing else of them did.** "The 17 test suites
  pass unchanged" cannot mean *not one byte*: **six** suites read a source file
  by path — `test_buffers`, `test_config_apply`, `test_credentials`,
  `test_extend_progress`, `test_rotation_probe` and `test_seams` — and moving a
  file means moving the string that names it. Six `#include` lines also had to
  change spelling or stop resolving (`"Backoff.h"` twice, `"LogRing.h"`, and
  `"mesh/ReplyCodec.h"` three times, now `<agent/...>`), and the other library
  includes were converted from `"agent/X.h"` to `<agent/X.h>` for one spelling
  throughout. 16 test files changed, and
  `git diff test/` is nothing but include lines, path strings and comments:
  **no assertion, no expected value and no test name changed**, and the case
  count went from 270 to 278 only by the new suite. `test_seams`'s header
  comment was rewritten because it said `JobRunner.cpp` "is not in
  `[env:native]`'s build yet", which this task made false; `test_tls_policy`
  needed nothing at all, because `TlsRoots.h` stayed and its scan already
  covered `lib/`.
- **`test_seams` is now partly redundant**, and is kept. Its thirteen named
  files are a subset of what `test_library` walks. It still holds what
  `test_library` does not — which object stands behind which interface, who
  draws the CLI timestamp, the runner's scratch, the extension before
  `unsupported` — so deleting the overlap would have cost a test file's worth of
  risk for nothing. A reviewer who wants the duplication gone should say so;
  this task may not change a test's assertions.
- **`-fno-exceptions` is not one of "the board's flags".** The task says the
  library must compile "with `-fno-exceptions -fno-rtti` (the board's flags)".
  The Arduino-on-ESP32 framework this repository builds with uses
  **`-std=gnu++11 -fexceptions -fno-rtti`**
  (`packages/framework-arduinoespressif32/tools/platformio-build-esp32s3.py`,
  lines 49-53) — exceptions are *on* for the board. The pair the task names is
  the ESP-IDF's, which is the consumer that matters, and it is the stricter of
  the two, so `tools/check-library-host.py` compiles the library with it on the
  host and the report says what the board actually uses. I did **not** add
  `-fno-exceptions` to the board build: it would have changed the unwind tables
  of 22 translation units for no behaviour, against a task whose criterion is
  that the image does not move.
- **The library compiles as `gnu++11` on the board and `c++17` on the host.**
  That is unchanged from `master` — these files were in `src/`, which the
  framework compiles as `gnu++11` — and this task did not add a `-std=` to the
  library's flags, because a library compiled to a different standard than the
  firmware it links into is a real ABI risk and a criterion about image size is
  not the place to take it. A consumer picks the standard; the host build proves
  `c++17` and the board build proves `gnu++11`.
- **`src/console/Parser.cpp`, `src/settings/Keys.cpp`, `src/ui/DisplayLines.cpp`
  and `src/version.cpp` stay in `src/`** although they are host-portable. They
  are the task's own list of what `[env:native]`'s filter keeps, and none of
  them is the agent.
- **`src/SerialLog.h` is a new board file**, which the task did not list. There
  was no other place to declare the Heltec's sink: `src/Log.cpp` cannot declare
  it to `main.cpp` without a header, and putting a board function in
  `agent/Log.h` would have put the board back in the library.
- **For the other repository**: nothing. The two items of this pile's
  `FOLLOWUPS.md` are both tagged for Thomas and neither is tagged `[16]`. The
  second of them offers 16 *or* 17 the choice of dropping `IMesh::uniqueTime()`
  (dead since 15); I left it to **17**, because dropping a method from an
  interface is a behaviour change in a task whose whole acceptance is that
  nothing changed, and 17 is where the fakes that implement `IMesh` are written
  and the cut is free.

## Decisions taken without asking

- **The library's version is `0.2.0`**, in `library.json`, `idf_component.yml`
  and `agent/Version.h`, held against each other by `test_library`. The
  repository's last tag is `v0.1.4`, and the task says "the repository's
  version" — but the library did not exist in `v0.1.4`, and a manifest naming a
  version a consumer cannot pin the library at would be worse than a
  forward-looking one. This pile's `README.md` says its exit criterion is
  Thomas tagging **`v0.2.0`**, and task 19 owns that tag; this is that number,
  written once. If 19 tags something else, 19 moves three lines and the test
  catches the fourth.
- **`AGENT_CORE_VERSION` is a macro in a header of the library's own**
  (`agent/Version.h`), with `mm::kAgentCoreVersion` beside it for code that
  prefers a symbol. The task offered the decision and this is the smallest form
  of it: there is no way to get a number out of `library.json` and into a
  translation unit without an `extraScript`, which would be a build-time Python
  hook in every consumer's tree for a string that changes once a release. The
  test is what keeps the header and the two manifests equal.
- **The firmware's version stays the board's.** `src/version.h` and
  `src/version.cpp` did not move: the release workflow bakes
  `-D MESHMASTER_AGENT_VERSION` into a *board* build, `MESHMASTER_BOARD` and
  `MESHMASTER_MESHCORE_TAG` are the Heltec's, and nothing in the library reads
  any of them (the heartbeat's identity comes in as `HeartbeatIdentity`, which
  is 15's doing). So the library reports its own version and the firmware
  reports its own, and a consumer that reports what it runs reports both.
- **`logSetSink` unset now drops the line.** It used to mean "the serial port
  and the ring", which a library cannot mean. `main.cpp` sets it in `setup()`
  (`logBeginSerial`, third line, right after `Serial.begin` and `board.begin`)
  before anything logs, so no line is lost on this board; `agent/Log.h` says it in as many words.
- **`logBegin` takes a second function pointer**,
  `logBegin(clock, uptimeMs)`, because the `[+123s]` stamp a board prints
  before its clock is known is `millis()` and the library has no `millis()` of
  its own at namespace scope. A null `uptimeMs` stamps `+0s`. The alternative —
  giving `Log` an `IPlatform&` — would have made the log module depend on the
  seam for one unsigned number, and `logBegin` already took a function pointer
  for the clock.
- **`REQUIRES` in the component file is empty** and ArduinoJson is declared in
  `idf_component.yml`, following the Walter's `components/modem`. A managed
  component's name under the ESP-IDF is namespaced
  (`bblanchon__arduinojson`), and naming it in `REQUIRES` by a guessed spelling
  would be a line that breaks on a toolchain nobody here can run; the component
  manager adds it itself, which is what the Walter's own comment says it does.
- **`idf_component.yml` asks for `idf: ">=5.0"`**, a range where every other
  dependency in both repositories is exact. The Walter pins ESP-IDF 5.5.5 in
  its `dependencies.lock` and asks `">=5.5.0"` in its own component; a library
  meant for more than one consumer cannot pin the consumer's framework, so the
  floor is the lowest the library is written for (nothing in it is newer than
  C++11 and the IDF's own component manager is 5.0+) and the consumer's lock
  file decides the version.
- **The reply codec is `agent/ReplyCodec.h`**, not `agent/mesh/ReplyCodec.h`.
  The task names one include directory, `include/agent/`, and a second level
  for one file would be a directory for its own sake.
- **`tools/check-library-host.py` is Python, not a shell script**, like
  `tools/check-partitions.py`: it runs the same way in CI, in the runbook's
  container and on Windows, and on Windows it exits with the container line to
  use rather than pretending to pass.
- **`tools/check-idf-component.cmake` checks the SRCS list both ways.** The
  task asked for a syntax check and nothing more; a stub that records what it
  was given gets the real check — list against disk — for three more lines, and
  a forgotten source in that list would otherwise only be found by the Walter.

## New libraries (with the one-line justification)

None. `lib/agent-core` is this repository's own code, and its only dependency is
the ArduinoJson `platformio.ini` already pins.

## Not verified here (and why)

A session cannot flash a board, and it cannot run an ESP-IDF build.

1. **The ESP-IDF component.** `lib/agent-core/CMakeLists.txt` and
   `idf_component.yml` have been parsed and held against the files on disk and
   never compiled. The first build is the Walter's phase 4, task 01
   (`twinoak.meshcore.walter-firmware`), and that task should expect to find at
   least these: whether `bblanchon/arduinojson` 7.4.3 is on
   `components.espressif.com` under that exact name (the registry was not
   reachable from here and the name was taken from ArduinoJson's own
   documentation of its ESP-IDF support), and whether `REQUIRES` being empty
   survives the component manager adding the managed dependency. Neither is a
   change to the library's code if it is wrong.
2. **The Heltec on the air with the rearranged tree** — the bench walk on the
   next release, and the only thing to walk is the log, because nothing else
   changed:
   - **A log line before the clock.** Power the board on and watch the first
     lines: `[+0s] I ...`, `[+1s] I ...` — the `[+123s]` stamp is the library's
     now and `millis()` reaches it through a function pointer. Then, after
     `wifi on` and the first SNTP answer, the stamp becomes `[HH:MM:SS]` at the
     same moment it used to.
   - **`dump` after a few minutes.** The ring holds the same bytes the port
     printed, in order, and the last line of `dump` is the line the port last
     printed — the sink writes the port first and the ring second, as it always
     did.
   - **`set log.level debug` and `set log.level warn`.** The level is the
     library's state now; a `debug` line appears and disappears as before, and
     `get log.level` reads back what was set.
   - **`log.frames on`** and a `status` job: the `frame tx` and `frame rx`
     lines are `AgentMesh`'s and did not move. Paste one `frame tx` line into
     the next report — 15 asked for it and no report has one yet.
   - **Everything else**: `status`, `server`, `jobs`, `sessions`, `errors`,
     `reboots`, a heartbeat on the exit node's page, a job that logs in. All of
     them are the same code at a different path; a difference in any of them
     would mean a move went wrong, which is what 278 green cases say it did
     not.
3. **The library in a consumer's tree.** `docs/library.md` is task 19's, and
   until a second firmware has compiled against this, "a second firmware can
   take it at a commit" is a claim about a manifest and not an observation.
