# p1.17-65 — A record is read where it lives

0.7.3 did not start. `loadUpdate` built a 2 764-byte `UpdateRecord` and returned it by value into
the member that keeps it, inside `Updater::atBoot`, inside `setup()`: **9 232 bytes on a loop task
that had 8 192**, and a board that restarted for ever straight after `clock: no time yet`.
`loadAsk` had the same shape and ran next in the same `setup()`.

A record is now read into the object that keeps it and emptied in place, the three types can be
neither copied nor moved, the build refuses a frame of ours over 1 024 bytes, the loop task has
16 384, and the board says at boot and in `status` how much of them was never used.

### The functions outside `src/update/` that were over the limit

Four frames of ours were over 1 024 before this task. Two are in `src/update/` and were brought
under (the table above). The other two are **named in `tools/check-frames.py`'s `CEILINGS` with
today's size as the ceiling and a reason**, because bringing either under is not a small change:

- **`mm::Observer::reportNeighbours()`, 1 888 bytes.** 1 780 of them are two arrays of
  `kNeighbourCap` entries — 20 public keys of 65 characters and their 20 field structs — built to
  hand one neighbour report to the slots. The only way under the limit is to make them members of
  the `Observer`, which is 1.8 kB of `.bss` held for the life of a board that has 62 % of its RAM in
  use, to save a frame taken for the few milliseconds a report is built in, once a sweep. It is a
  leaf of the loop task: `formatNeighbours` (720) below it and nothing deeper.
- **`mm::observer::makeToken(...)`, 1 296 bytes.** The JWT is three buffers that have to coexist —
  the claims as JSON (512), the header base64url (64), the claims base64url (512) — and the sizes
  are MeshCore's `JWTHelper`'s own, which that file is a reading of. Shrinking one would mean a
  token *refused* rather than a smaller token, and an exit node that cannot sign in to its broker.
  It runs once per broker connection, with nothing below it but `base64Url`.

Both ceilings are held on both boards, and the rail refuses either function growing by a byte. A
ceiling in `src/update/` is refused whatever it says, and a ceiling of a function this build has no
frame for is refused as stale.

## Deviations from the spec or the task

- **None of substance.** The task file is this repository's own and there is no section of
  meshmaster.dk's spec that this touches: nothing of the contract, the protocol or the stored keys
  and values changed.
- **"The compiler refuses a copy" is as strong as C++17 allows, and no stronger.** Deleting the
  copy and move operations makes every copy, every assignment and every `return` of a *named*
  record a compile error — which is what the four call sites of `loadUpdate` and `loadAsk` did. It
  does **not** forbid `return UpdateRecord();`, a prvalue, which C++17 constructs in the caller's
  own storage with no copy at all; that is not a frame on the callee's stack either, so nothing is
  lost, but the statement in deliverable 2 is worth being exact about. The thing that catches a
  2 764-byte local however it is written is the frame rail, and that is why the two come together.

## Decisions taken without asking

- **`-fstack-usage` and a Python rail, not `-Wstack-usage=1024` or `-Wframe-larger-than=1024`.**
  Deliverable 4 asks which of the compiler's means holds the limit and why. `-fstack-usage` only
  *writes* what each frame came to — `<object>.su` beside every object, one line a function with
  its bytes and whether the compiler could bound it — and `tools/check-frames.py` decides. The two
  warning flags were the obvious alternative and were not taken, for three reasons the task itself
  asks for: a flag has no per-function exception, so the two frames above would have had to become
  `-Wno-error` for whole files; a flag cannot print *the twenty largest frames of ours*, which
  deliverable 7 wants and which is the only way to see the limit coming; and a flag cannot have a
  self-test, which the acceptance criteria ask for. What is **not** lost by choosing the file over
  the flag is the unbounded case: `-fstack-usage` marks a frame `dynamic` without `bounded` when
  `alloca` or an unbounded VLA is in it, and the rail refuses those whatever their counted size —
  the same thing `-Wstack-usage` would have said, read from the same analysis.
- **The flag is in `build_flags` and not `build_src_flags`.** The rail covers `src/` *and*
  `lib/agent-core`, and a `build_src_flags` cannot reach a library; `lib/agent-core/library.json` is
  left exactly as it is, as deliverable 4 asks, because the Walter's firmware compiles that library
  with another compiler. A global flag reaches MeshCore, the Arduino core and the ESP-IDF as well —
  they write their `.su` files too (1 898 of them on the V3) and the rail reads none of them, which
  it proves by deriving the source file from the `.su` file's own place in the build directory
  rather than from the name inside it. **GCC writes only the basename in a `.su` line**
  (`lbasename`), so a function defined in `src/console/StreamOut.h` reads as `StreamOut.h`; that is
  worth knowing before trusting the field, and it cost one wrong first run to find out.
- **`Updater::begin()` and `Asked::begin()` now put the per-boot state back.** The tests simulated
  a restart with `updater = Updater()` and `asked = Asked()`, which a non-assignable member
  forbids. The alternative was placement-new in a test; this is the honest version of the same
  thing — `begin()` is called once per boot, in `setup()`, and it is where a fresh machine belongs.
  `Asked::waiting_` is deliberately not cleared: nothing reads it unless `pending_` says an ask is
  waiting for `step()`, and clearing it would be a 240-byte temporary in `begin()`.
- **`readRelease` empties the caller's `ReleaseInfo` and fills it in place.** It is 872 bytes, and a
  second one of them beside it was most of a frame the rail does not allow. The behaviour that
  comes with that is the one this task is about: a refusal now leaves **nothing** of a release half
  read in the caller's info, where before it left whatever was there. That is a change a test
  states (`TheReader.ARefusalLeavesNothingOfAReleaseInTheCallersInfo`) and `Release.h` documents;
  the one caller in `src/` passes a member it only reads after an `ok`.
- **`findOneDescriptor`'s window is 512 bytes and not 1 024.** A kilobyte of window was a frame of
  1 168. The window only has to hold a whole 96-byte descriptor and overlap the last read by 92
  bytes, so halving it costs twice as many reads of a medium this function already reads whole, and
  nothing else.
- **The boot's line is the last thing `setup()` prints**, after `asked.atBoot()` and before
  `board.onBootComplete()`: the figure a person reads is then what the whole of `setup()` cost,
  which is the deepest the stack has been at that point.
- **`loopTaskHandle` is declared by hand in `src/main.cpp`,** at file scope, because no header of
  the Arduino core declares it and `uxTaskGetStackHighWaterMark(nullptr)` would answer for whatever
  task happened to call. With the handle the answer is the loop task's wherever it is read from.
- **Where the core takes 16 384 from** (deliverable 5 asks): `cores/esp32/main.cpp` defines
  `ARDUINO_LOOP_STACK_SIZE` as `CONFIG_ARDUINO_LOOP_STACK_SIZE` when the Kconfig sets it and 8192
  otherwise, returns it from the weak `getArduinoLoopTaskStackSize()`, and gives that to
  `xTaskCreateUniversal(loopTask, "loopTask", …)` — **in bytes** on this port.
  `Kconfig.projbuild`'s `config ARDUINO_LOOP_STACK_SIZE` has `default 8192`, which is what
  `tools/check-sdkconfig.py` now records as the core's value against this repository's 16384. The
  same weak function could have been overridden in `src/` with `SET_LOOP_TASK_STACK_SIZE`; the
  task asks for the configuration key, and the key is the one a check can hold.
- **The two greps that stand for "no function returns or takes one by value"**, run over `src/`,
  `lib/` and `test/` and both empty:
  `grep -rnE "(UpdateRecord|AskRecord|Journal)[[:space:]]+[A-Za-z_][A-Za-z0-9_:]*\(" | grep -v '&'`
  and `grep -rnE "\((const )?(UpdateRecord|AskRecord|Journal) [a-z]"`. The `static_assert`s are the
  rail that holds from here on; these two are what was checked today.
- **The numbers in `docs/field.md`'s guidance** — *under about 4 000 bytes free* is no margin,
  *over about 8 000* is what 16 384 was chosen for — are mine, not a measurement. Nothing has
  measured a board yet; that is the first bench item and the pile's third follow-up.
- **`env.Action` and not PlatformIO's `VerboseAction`** in `tools/pio/check_frames.py`: the latter
  hands SCons the bare function under `pio run -v`, and SCons then dies in its own `print_cmd_line`
  with `TypeError: unsupported operand type(s) for +: '_Null' and 'str'`. That failed the first
  verbose V4 build (`out/65-v4.log`) and is fixed and commented.
- **No `CHANGELOG.md` entry.** Nothing of `lib/agent-core`'s interfaces, constants or fixtures
  moved; the library is held to the same frame limit by this project's build and by nothing written
  into its manifest. One release note instead (`release-notes/unreleased/65.md`).

## Not verified here (and why)

**Nothing in a session can start an image**, and a PC's stack is not a board's: the whole of this
task is about a number only a running board produces. For Thomas, with the cable in, before
anybody else hears of the release — these are also in `docs/field.md` §9's bench list:

- ⚠ **The plain `.bin` on a V3, and the board starts.** The boot passes `clock:` and reaches
  `stack: loop task: 16384 bytes, the least ever free N`. This is the thing 0.7.3 failed. If it
  restarts for ever instead: **0.7.2's plain `.bin`** brings it back with its key, its token and its
  WiFi, and what the port printed is what to report.
- ⚠ **`status` after ten minutes online: the least ever free.** And again **after an
  `update fetch`**, which is the deepest thing the loop task does — a TLS handshake, a release's
  signature and a 1.4 MB image. Both numbers into this pile's `FOLLOWUPS.md`: they are the only
  measurement of what 16 384 really leaves, and whether it is generous or needed.
- ⚠ **The same two on a V4.**
- ⚠ **Then the bench of pile 1.16's README**, from `update slot` on: this release is what 0.7.3
  announced, so everything 0.7.3 was never walked for is still unwalked.
- ⚠ **That the ten-minute trial and `update back` still behave**, since `Updater::begin()` now puts
  the per-boot state back and `Updater::apply` and `goBack` read the record into the member instead
  of over it. Every one of those paths has a native test and none has run on a board.
- ⚠ **That `findOneDescriptor`'s 512-byte window finds the descriptor in a real 1.4 MB slot** as
  the 1 024-byte one did. The native tests cover it against the fixture images and a scripted
  medium; the board reads flash.
