# p1.13-55 — A batch keeps its id over a sleep

`doObservations` has said it since pile 1.2: a batch built and not yet accepted
*must go out again exactly as it was, under the client id it was built with*,
because the server de-duplicates on that id. The id and the count lived in two
fields of the loop and **nowhere else**, and a board that deep-sleeps wakes
without its RAM. The image a sleep keeps held the adverts and not the batch they
were in, so the unit woke with the adverts and no id, built a new batch of the
old ones and the new, and posted it. The server — which had no id it knew — stored
every advert again. On 16 November 2026 meshmaster.dk took batches of 13, 14,
15, 16, 17 and 18 adverts from the Walter unit in six wakes running, and the
hundred newest rows it held from that unit were **19 different adverts**.

The image is **version 2** now: it carries the pending batch's client id and how
many of the ring's oldest adverts that batch holds. After `restoreKept()` the
first post is the same batch under the same id, the server answers *had it
already*, the ring loses exactly those adverts, and what was heard since follows
as a new batch under a new id.

| | Before | Now |
|---|---|---|
| where the pending batch lives | `AgentLoop::batchId_`, `batchCount_` — RAM | the same two, **and** the kept image (version 2) |
| the first post after a sleep | a new batch of the old adverts and the new, under a new id | that batch, under the id it was built with |
| what the server does with it | stores every advert a second time | *had it already*: nothing stored twice |
| a batch that is no longer whole | posted short, or over other adverts, under the old id — and then **consumed unsent** | the id is forgotten and a new batch is built |
| a version 1 image after the update | — | read, as an image with no batch pending |
| how large an image can be | "about 19.5 kB", added up by hand | `mm::kMaxKeptImageLen`, **19 368** bytes, with a test |
| what a person at the port sees | the ring's depth | and a `batchid` line while a batch waits for an answer |

The Heltec hands the loop no store and loses no RAM: `loop()` touches none of
this and nothing changes for it.

## Where the bytes go

Version 2 appends **one block, last of all**, and takes version 1's `reserved`
header field for the count:

```
  header, 32 bytes
    14   u16  batchCount   how many of the advert records below - the first of them,
                           which are the oldest - are the batch still waiting for an
                           answer; 0 when none is. Version 1's `reserved`
  results, adverts         exactly where version 1 puts them
  batch id, 40 bytes       only when batchCount is not 0: the client id, NUL-terminated
```

Last, and conditional, for three reasons. Every record before it is at the offset
version 1 gives it, so a version 1 image is a version 2 image *minus* this block
and the two formats are one reader. An image with **no** batch pending is the
length it always was, so the wear rule (*no write when the store already holds
this image*) and every existing arithmetic against a small store are untouched.
And the writer need move nothing in `finish()`: `setPendingBatch` holds the 40
bytes back from the first record, so the id reaches the store or the batch is not
kept at all, and no advert is ever written where the id was going to be.

**A batch is written only when the image holds every advert of it.**
`finish()` drops it when `batchCount` would exceed the adverts actually written;
the reader enforces `batchCount <= advertCount` as a structural check; and
`restoreKept` takes the batch only when the ring was empty before it and every
advert of the batch reached the front of it. Three places, because the
consequence of getting it wrong is the opposite of the bug this task fixes: the
server de-duplicates on the batch **row**, so an id over the wrong adverts has it
store none of them and the board consume them unsent.

## Deviations from the spec or the task

**None.** `spec/EXIT-NODES.md` §6 at today's `master` says *every result and
observation batch carries a client-generated id; the server ignores duplicates*,
and §3 says the de-duplication is the batch row's unique `(agent_id, client_id)`
— so a repost under the same id stores nothing, which is what this task rests on,
and a *different* set of items under that id would store nothing either, which is
why a batch that is no longer whole gives its id up rather than being shortened
under it. The task file and the spec agree.

One line of `docs/library.md` was **wrong** for this release and is corrected
rather than deviated from: §9's *what a release may do* table said that a change
to the kept image's layout means `restoreKept()` refuses the image in your store
whole. This change moves the layout and refuses nothing, so the row now says that
a version the library knows is read — naming version 1 at `0.7.2` — and any other
is refused.

## Decisions taken without asking

1. **The batch block is last, 40 bytes, and only there when a batch is pending**, with `batchCount` in version 1's `reserved`. *Where the bytes go is the session's to choose*; the three reasons are above. The 40 bytes are `sizeof AgentLoop::batchId_`, which a `static_assert` in `keepAcrossSleep` holds, because an id that came back cut would be **another batch** to the server.
2. **"No longer whole" is `ObservationRing::oldestSeq()` plus `size() >= batchCount_`**, not the existing `dropped()` counter. `oldestSeq()` is a number that grows only when something leaves the **front** of the ring — a push that found it full, a `consume`, a `clear` — so it answers exactly the question *are these still the adverts the batch was built over?* `dropped()` would also have moved on `dropNewest`, which takes the newest and cannot break a batch, and would have forgotten batches that were perfectly whole.
3. **A batch that is not whole gives its id up; it is never shortened or re-pointed under it.** The alternative — post what is left under the old id — is the silent loss described below.
4. **A version 1 image is read rather than refused**, and version 1's `reserved` is **ignored** rather than read as a batch that version could not have kept. The alternative was a free update that costs a unit the one sleep it was in the middle of, for nothing.
5. **`pendingBatchCount()` and `pendingBatchId()` are public, and `status` prints a `batchid` line while a batch waits.** A session cannot flash a board, so the bench list below has to be readable off the port: the line is what says *the id did not change over the sleep* without a debugger.
6. **The constant is `mm::kMaxKeptImageLen` in `agent/KeptImage.h`**, summed from `ResultBuffer`'s and `ObservationRing`'s own figures rather than written out, so it moves when they do. `KeptImage.h` now includes `agent/ResultBuffer.h` for it; `KeptImage.cpp` already did.
7. **The release note is written** although a Heltec owner notices nothing. The task asks for one, and what a person who runs a *sleeping* exit node notices — their observations stop arriving twice — is exactly what `docs/release.md` §2 wants a line about. **`CHANGELOG.md` is written too**, which is the rarer *both*: the kept image's layout is one of the things §9's table promises a consumer, and the news is that this layout change does **not** refuse the image in their store.
8. **The fake server now de-duplicates on `clientId`**, and `loseTheAnswerToObservations(n)` is how a test says *the server took the batch and the answer never came back*. Modelling the loss as an opt-in on the observations call alone leaves every other fault in the fake meaning what it meant.

## What the loop did before this task, with or without a sleep

The task asks for this, for deliverable 3.

**With a sleep, before this task.** `restoreKept` put the adverts back and
nothing else, so the new boot began with `batchCount_` 0 and `batchId_` empty.
The first post after the sleep was a **new** batch under a **new** id, over the
ring's oldest up to twenty — the adverts the server already had, plus whatever
was heard since. Its count and its items agreed, so **nothing was consumed
unsent**: the cost was duplication at the server, every advert stored again at
every wake, which is the Walter's 16 November and the rows this task was written
for.

**Without a sleep, before this task.** Two shapes, and both of them *lost*
adverts rather than duplicating them. If the ring was full and dropped its oldest
while the batch waited, `buildBatch` still took `count = batchCount_` of the
ring's oldest — by then **different** adverts — and sent them under the old id;
the server de-duplicated on that id, stored nothing, answered 200, and
`ring_.consume(batchCount_)` took them. If `keepAcrossSleep`'s `dropNewest`
trimmed the ring below `batchCount_`, `buildBatch` clamped the count to
`ring_.size()` and kept the id, so a short batch went out under an id the server
held a longer one for — stored nothing, consumed all the same. Either way up to
twenty adverts were consumed unsent and counted **nowhere**: not in
`observationsDropped`, not on the exit node's page. Neither shape has ever been
seen in the wild — a Heltec's ring fills only in an outage long enough to hear
sixty-four adverts while a batch is unanswered — but it was the same fault as the
sleep's, without the sleep, and `forgetBatchIfNotWhole` closes both.

## Not verified here (and why)

A session can build, run the native tests and read the MeshCore source it builds
against. It cannot flash a board, hear a radio or sleep. This change is in
`lib/agent-core/` and a **Heltec exercises none of it** (it hands the loop no
store), so the bench list is short and the real walk is the Walter's, in its own
phase 15 — it takes this library at a release.

1. **The Heltec is unchanged.** Flash `pio run -e heltec_v3 -t upload` on a
   provisioned board and let it run through a few batches. `status` prints the
   same `batch` and `pending` lines it always did; there is **no** `batchid` line
   unless a batch is actually unanswered, and no `kept:` line at all, because
   `setRetained` is never called on this board. Nothing about the image, the
   store or the batch id is in the Heltec's path.
2. **A Heltec with an unanswered batch prints the new line.** Pull the WiFi (or
   point `meshmaster.url` at a port nothing listens on) while adverts are
   waiting, let one batch attempt go out and fail, then `status`: a `batchid`
   line names the id and how many of the waiting adverts went out under it. Bring
   the link back: the next attempt carries **that** id, the batch is accepted or
   answered as a duplicate, and the line is gone. This is the whole of the change
   that a Heltec can show.
3. **The real walk is a sleeping unit** — the Walter, at the release that carries
   this. What to look for on its console: at the end of a wake that could not get
   its batch answered, `kept: N result(s), M advert(s) and K of them as a batch
   still waiting written to the store`; at the boot after the sleep, `kept: the
   batch of K that was waiting for an answer came back with the image`; and at
   the post after that, `observations: K posted, 0 accepted (the server had this
   batch already)`. Then meshmaster.dk's own side of it: the adverts from that
   unit stop repeating across wakes, and its batch count stops growing by one a
   wake for the same adverts.
4. **A store sized by the constant.** The Walter's `IRetained` region and its
   scratch should be `mm::kMaxKeptImageLen` (19 368) or more; at anything smaller
   a wake that keeps a lot says `kept: … do not fit the … bytes of the store` and
   may say `kept: the batch of K … did not fit the image whole`. Neither is a
   fault, and both are a figure on the exit node's page — but which it is on that
   board is a thing to read once with the flash it actually has.
5. **An image written by the firmware as it is today, read by this one.** The
   version 1 fixture in `test_loop` is laid out by hand from the format, which is
   the strongest check a host can make; reading a version 1 image that a *board*
   wrote — flash the Walter at `v0.7.1`, let it keep something, flash this, and
   watch `kept: … read back from the store` with no refusal and
   `keptImagesRefused` 0 in the next heartbeat — is the bench's.
