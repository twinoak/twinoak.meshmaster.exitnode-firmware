# p1.6-20 — Built like a consumer builds it

The library's first consumer built it as an ESP-IDF component on a Linux host
and hit two things no check here could see. Both are closed, and the check that
could not see them now builds the library the five ways a consumer does.

**The Heltec's bytes did not move at all**: both images are byte-for-byte the
same size as `v0.2.0`'s, which is what a rename of a local parameter and a
diagnostic pragma should cost.

## What changed

| | |
|---|---|
| `lib/agent-core/src/ConfigReply.cpp` | `uint32_t& unix` → `uint32_t& epoch` (two uses), with four lines saying why a parameter may not be called that |
| `lib/agent-core/include/agent/Json.h` | **new.** `<ArduinoJson.h>` wrapped in a `-Wmaybe-uninitialized` pragma, for the dependency's own code and nothing else; the two sources that parse JSON include this instead |
| `tools/check-library-host.py` | rewritten: the compiler and its version first; then no identifier of the library is a predefined macro name; then 22 sources × 5 configurations = **110 compiles**, in parallel. `--self-test` runs the name check against planted sources |
| `test/test_library/test_library.cpp` | the include allow list now says `<ArduinoJson.h>` may appear in `include/agent/Json.h` and nowhere else in the library |
| `.github/workflows/ci.yml` | the *library compiles for a consumer* step runs `--self-test` and then the matrix; its comment and the file's header say what the five configurations are and that this runner's GCC is the consumer's |
| `docs/library.md` §2, `docs/upstream.md` | which dialects and levels are proven, as a table, and why both of each are in it |

## The two findings, and how each was closed

### 1. A parameter named `unix`

Reproduced on CI's compiler before anything was changed — `ubuntu:24.04`,
`g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`, which is what
`runs-on: ubuntu-latest` has today:

```
$ g++ -std=gnu++17 -Wall -Wextra -Werror -fno-exceptions -fno-rtti -O0 -c … ConfigReply.cpp
ConfigReply.cpp:41:74: error: expected ',' or '...' before numeric constant
   41 | bool takeTime(…, uint32_t& unix, char* err, size_t cap) {
      |                            ^~~~
ConfigReply.cpp:44:9: error: 'err' was not declared in this scope; did you mean 'errno'?
… (the Walter's fifteen)
```

Renamed to `epoch`, which is the name `Iso8601.h`'s own declaration already uses
(`bool parseUtc(const char* text, uint32_t& epoch)`), so the diff is two lines
and a comment. Nothing else in the library collides: GCC 13.3 on this target
predefines exactly two non-reserved names, `unix` and `linux`, and neither
appears as an identifier anywhere in the 52 headers and sources.

**The grep is a check and not a one-off.** `check-library-host.py` asks the
compiler itself — `g++ -std=<dialect> -dM -E -x c++ /dev/null` in both dialects —
for its predefined macros, keeps the ones with no leading underscore (those are
the ones an identifier can collide with), unions them with the names GCC defines
on targets this runner is not (`i386`, `mips`, `sparc`, `vax`, `sun`, `bsd`), and
holds every identifier of the library against the result. It reads code and not
prose: comments, string and character literals are blanked out first, because
`ReplyCodec.cpp` has a field called `"unixTime"` and `JobRunner.h` a comment
about the `time <unix>` CLI command and neither is an identifier.

Proven both ways (`out/20-host-check-proofs.log`):

```
$ # `namespace mm { int unix = 0; }` appended to lib/agent-core/src/Backoff.cpp
$ python3 tools/check-library-host.py
lib/agent-core/src/Backoff.cpp:28 uses `unix`, which a compiler predefines as a macro:
  in that dialect this file is not code any more. Rename it.
1 identifier(s) of the library are predefined macro names. …
exit=1

$ python tools/check-library-host.py --self-test
  ok    the mistake, as a parameter: flagged unix, unix
  ok    the mistake, as a local: flagged unix, unix
  ok    the mistake, as a member: flagged linux
  ok    a string (unixTime, ReplyCodec.cpp): not flagged
  ok    a comment (time <unix>, JobRunner.h): not flagged
  ok    a block comment: not flagged
  ok    a longer identifier that contains one: not flagged
the name check holds on its planted sources
```

### 2. ArduinoJson's `-Wmaybe-uninitialized`

**It is not plain `-O2`.** On CI's GCC 13.3, every one of the four configurations
the task asked for — `c++17` and `gnu++17`, each at `-O0` and `-O2`, with
`-fno-exceptions -fno-rtti -Wall -Wextra -Werror` — compiles
`ConfigReply.cpp` and `JobEnvelopes.cpp` clean, and so does `-O1`, `-O3`, `-Os`
and each of those with exceptions on. What raises it is the configuration the
first consumer's host tests are actually built in: `-O2` under
**AddressSanitizer and UndefinedBehaviorSanitizer**
(`host_test/CMakeLists.txt`'s `RelWithDebInfo` + `-fsanitize=address,undefined
-fno-sanitize-recover=all -fno-omit-frame-pointer`), where the sanitizers keep
the inlined copy and the optimiser can no longer see through it:

```
In member function '…ObjectData::findKey(…)',
    inlined from '…ObjectData::getMember(…)' at …/ObjectImpl.hpp:16:20:
…/ArduinoJson/Object/ObjectImpl.hpp:36:21: error:
  '<anonymous>.…CollectionIterator::nextId_' may be used uninitialized
  [-Werror=maybe-uninitialized]
   36 |     return iterator();
```

So **that configuration is the fifth in the matrix** — compile only, so it needs
no sanitizer runtime and costs no more than the others — and it is what makes the
fix testable at all. Without it the matrix would be green with the fix and green
without it, which is a check that proves nothing.

The fix is the narrowest of the three the task offered:
`lib/agent-core/include/agent/Json.h`, one header, the pragma scoped to the
include and to one warning name.

**The pragma does reach it.** That was the open question — a middle-end warning
raised after inlining is reported against a location, not against a
preprocessing state, and an `-isystem` include path does not silence this one
(the consumer tried). It works because GCC resolves a late diagnostic against
the pragma state *at the location it reports*, and that location
(`ObjectImpl.hpp:36` and `:43`) is inside the include the pragma brackets.
Proven by removing the pragma from the header and running the matrix
(`out/20-host-check-proofs.log`):

```
  c++17 -O0              22 sources, clean
  c++17 -O2              22 sources, clean
  gnu++17 -O0            22 sources, clean
  gnu++17 -O2            22 sources, clean
  c++17 -O2 asan+ubsan   22 sources, FAILED: ConfigReply.cpp, JobEnvelopes.cpp
```

and clean in all five with it back. It also holds with the ArduinoJson include
path as `-I` rather than `-isystem`, and in both dialects.

**No `-Wno-error` anywhere, and the pin did not move.** `library.json`'s
`build.flags` are untouched, so a consumer still gets every warning of ours as
an error; the exemption is one warning name, in the dependency's own code, in one
header, and `test_library` now forbids a second way into ArduinoJson so the
exemption cannot be bypassed by accident. The pin did not move because there is
nowhere to move it to: `pio pkg show bblanchon/ArduinoJson` says **7.4.3 is the
newest release**, published 2 March 2026, which is what `[libs]`,
`library.json` and `idf_component.yml` already pin. So no changelog to cite, no
three-file pin change, and no board-size question.

## Deviations from the spec or the task

- **The task's four configurations are five.** The fifth is the first consumer's
  own `-O2` under ASan and UBSan, and it is there because the four the task names
  do **not** raise the warning deliverable 3 asks to be reproduced and removed —
  not on CI's GCC 13.3, and not at `-O1`, `-O3` or `-Os` either. Without it there
  is nothing for the fix to be measured against. The four are still all four, and
  all four are clean.
- **`docs/library.md` §8 is the rails section, so *which dialects and levels are
  proven* went into §2**, beside the sentence about the library's own `-std=`
  that it belongs with ("it carries no `-std=` of its own, so the standard is
  yours to choose"). §8 is *The rails you inherit, and must keep* — six promises
  with a test each — and a build-strictness table is not one of them.
  `docs/upstream.md`'s *What is not built here* points at the new table.
- **The grep is not only a grep.** The task says "a grep of the whole library for
  any other identifier a GNU dialect or a target predefines". Asking the compiler
  for its own list is strictly better than hard-coding one, and it is what the
  check does; the hard-coded list is only the names *other targets* define, which
  this runner's compiler will never name. Both are in the check and the failure
  message does not distinguish them.
- **`gnu++11` is not in the matrix, and it is the dialect the board build uses**
  (`framework-arduinoespressif32`'s `platformio-build-esp32s3.py` line 50). It is
  covered by the board build itself, which is CI's other job and compiles the
  whole library in it; the matrix is the two dialects the task named. Worth
  knowing that `gnu++11` predefines `unix` too — the board never saw it only
  because the xtensa target has no such predefine.

## Decisions taken without asking

- **`epoch`, not `unixTime` or `t`.** `agent/Iso8601.h`'s `parseUtc` already
  names that out-parameter `epoch`, and the Walter's reported diff proposed the
  same; the two now read alike.
- **The wrapper header is `agent/Json.h`, in the public include directory.**
  It has to be reachable as `<agent/...>` from the library's sources, and the
  library has one include directory. Nothing of the library's public API includes
  it, so a consumer gets the pragma only if it includes that header itself —
  which it may, and which is the honest way to take ArduinoJson from here.
- **The pragma is `#if defined(__GNUC__) && !defined(__clang__)`.** Clang has no
  `-Wmaybe-uninitialized`, and an unknown warning name in a pragma is itself a
  warning there — which under this library's `-Werror` would be an error in a
  compiler the task puts out of scope. Four lines to not break it.
- **`test_library` tightened rather than a new test.** The include allow list
  already walked every file of the library; `<ArduinoJson.h>` is now allowed in
  `include/agent/Json.h` alone. A new suite for one rule would be a file's worth
  of risk for nothing, and no case count moved.
- **CI runs `--self-test` before the matrix**, the way the partition check's step
  does. A check whose own check runs in CI cannot quietly stop checking.
- **No `CHANGELOG.md` line in this pull request.** `agent/Json.h` is a new public
  header and the `unix` fix is a consumer-visible one — the Walter can drop its
  `twinoak_ours(agent_core c++17)` dialect pin and its two per-file
  `-Wno-maybe-uninitialized` exemptions — but none of the four things
  `CHANGELOG.md`'s own preamble says to write a line for moved (no interface, no
  `MeshReply` constant, no fixture manifest, no version), and the `v0.3.0` section
  is opened by task 23 and closed by 24. **For the reviewer: that section wants
  these two lines**, and this is the only place they are written down.

  `set_source_files_properties(… -Wno-maybe-uninitialized)` for `ConfigReply.cpp`

  of theirs has to change** — the exemptions are harmless now — so it is a
  cleanliness item, not a blocker.
- **The board on the bench: nothing.** No byte of either image moved and nothing
  the board prints changed, so this task adds nothing to the walk of
  `docs/console.md` that 1.5 left for `v0.2.0`.
- **CI's GCC is 13.3.0 *today*.** The check prints the version into the job log on
  every run rather than pinning it, because the point is that it is the
  consumer's compiler and not a chosen one. A GCC 14 runner may raise something
  new; that will be a red build with the version in the log beside it, which is
  the intended behaviour and not a regression of this task.
