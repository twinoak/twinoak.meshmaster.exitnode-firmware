# p1.6-21 — A wake keeps its budget

18 gave a wake four bounds and two of them leaked at the job step. Every job
result went through `JobRunner::post()`, which began by flushing the **whole**
offline buffer under no cap, and none of those posts was counted in
`report.bytesPosted` or in the uplink's seconds: on an LTE plan priced by the
byte, one claimed job could post a day of kept results, and the report would
have said it spent nothing. The leak was in the shape of the code and not in an
arithmetic slip — the loop counted its own calls and the runner's were somebody
else's — so what closed it is a shape: **one ledger, which is the only place in
the library a call to the server is made from**.

`lib/agent-core/include/agent/UplinkMeter.h` is that ledger. It holds the wake's
three bounds (the whole wake's seconds, the uplink's, the bytes of body) and what
has been spent against them; `AgentLoop` owns one and lends it to the
`JobRunner` at `begin()`; every one of the five calls the library makes — the
config, the heartbeat, the claim, every result and every observation batch — is
made through its `spend()`, which reads the clock either side of the call and
weighs the body that went through. A post the budget has no room for is **kept**
in the offline buffer, behind whatever is already there, and the wake says
*kept: budget*: a bound of ours is not a failure of the server's, so nothing
backs off for one, and "offline is normal" (EXIT-NODES §5) is what makes keeping
it an answer and not a loss.

**`loop()` runs the same path with no bounds set**, which is the strongest thing
this task can say about the Heltec: there are not two code paths, there is one
with a bound of zero — "no bound", as everywhere else in the `Budget`. All
fourteen of `loop()`'s cases and the 356 of `master` pass with **no assertion,
expected value or test name changed**; the board's images grew by 1 184 and
1 124 bytes of flash and 32 of RAM, named symbol by symbol below, and nothing
the board prints changed.

`pio test -e native`: **362 cases in 22 suites, all passing**, in the container
`RUNBOOK.md` §2 names. Both boards SUCCESS with `-Werror`. The two leaks were
each reproduced as a failing test before the fix, and the fix was mutation-tested
both ways round (below).

## Acceptance checklist

- [x] **No `IUplink` call in a wake is outside the byte and uplink-second accounting (a test per call kind, and a grep-style test that `JobRunner` has no unbounded flush reachable from `wake()`).**
  Two text tests and one arithmetic one.
  `TheWakesLedger.EveryCallToTheServerInTheLibraryIsMadeThroughIt` reads
  `IUplink.h` for **the list of calls there are** — its virtual methods that are
  not `const`, which is the seven of API §3 and not a list typed into a test —
  and then every line of `AgentLoop.cpp` and `JobRunner.cpp` that calls one of
  them, requiring `spend(` on the same line; it fails if no call site is found at
  all, so it cannot pass by having stopped checking.
  `TheWakesLedger.TheRunnerHasNoUnboundedFlushAndAsksBeforeEveryPost` holds the
  other half: there is **no** `flushResults(size_t…)` any more (the unbounded one
  of the pair is gone, and the one flush there is asks `mayPost(len)` about every
  body), and inside `post()` the queue is flushed before anything of this
  result's goes out, the budget is asked before the send, and the keep says
  *kept: budget*.

  `EveryCallOfAWakeIsInItsUplinkSecondsAndEveryPostedByteInItsBytes`: the fake
  server charges every call 100 ms of the test's clock, so a wake of a config
  call, a heartbeat, a claim and a result is `uplinkMs == 400`, and the wake after
  it — heartbeat, the kept result, the claim, its own result, a batch — is
  `uplinkMs == 500` and `bytesPosted ==` the sum of every body the fake was
  handed, the job step's among them. `elapsedMs` is far larger, which is the
  point: the job's waits on the radio are not the server's seconds.

## What one wake spends, and where it is counted

| | What bounds it | Where it is counted |
|---|---|---|
| the config call | the uplink's seconds | `spend(0, …)`: its body is the uplink implementation's, its seconds are the wake's |
| the heartbeat | the uplink's seconds | the same. A wake that could not say hello learns nothing, so no byte cap stops it |
| the offline buffer | the uplink's seconds **and** the byte cap | `spend(len, …)` per result, oldest first; what does not fit waits with its own timestamps and client id |
| the claim | the uplink's seconds, and the transaction cap decides its `max` | `spend(0, …)` |
| every job's result | the uplink's seconds **and** the byte cap | `post()` → the queue first, then this body if the budget has room; otherwise **kept: budget**, behind the queue |
| a job not run | the same | `reportNotRun` posts through `post()` like any other: the lease is answered now or from the buffer, and never not at all |
| every observation batch | the uplink's seconds **and** the byte cap | a fresh batch is halved until it fits; one already built and refused goes whole or waits (its client id is what the server de-duplicates on) |
| the job on the air | the wake's seconds and the transaction cap | the airtime gate, as before. **Not** the uplink's seconds — a reply wait on the radio is not time at the server |

And two numbers in the report that were not there before: `uplinkMs`, what the
calls took together, and `resultsKept`, how many results this wake could not
carry. `bytesPosted` is now assigned from the ledger rather than accumulated by
two of the six steps, so it is every byte of body the wake posted and not the
bytes of the steps that remembered to add theirs up.

## Deviations from the spec or the task

- **`post()` is lent the budget rather than passed it.** The task says
  "`post()` takes the wake's remaining bytes (and `loop()` passes *no cap*)", and
  the 1.5 review says "pass the wake's `bytesLeft` into `post()`". It is given
  the wake's remaining bytes — through the ledger it is lent at `begin()` — and
  not as a parameter, for two reasons. The first is the deliverable beside it:
  the uplink's seconds have to be counted "through one place, so a new call
  cannot forget", which a parameter cannot do and an object can (and a test can
  then read `IUplink.h` for the calls and the sources for the call sites, which
  is what makes *cannot forget* a build failure rather than a promise). The
  second is that two existing text tests anchor the exact line
  `posted = post(job.id, g_body, len);` — `test_buffers`'
  `TheRunnerReadsTheLeaseBeforeItRunsAJob` and `test_credentials`' wipe test —
  and a task that is about a budget is the wrong one to move the line two other
  suites read the runner's shape by. `loop()` passes no cap by having no cap:
  its ledger's bounds are zero, which is "no bound".
- **The two `flushResults` overloads became one.** 18 left a bounded one and an
  unbounded one, and the unbounded one was the leak: `post()` called it. There is
  now `int JobRunner::flushResults()`, bounded by whatever the ledger says and
  returning how many went through. This is the one source-compatible break of
  the change — a consumer that called `flushResults(bytesLeft, posted)` would
  stop compiling — and nothing in this repository called it but
  `AgentLoop::wakeResults`.
- **"A wake whose cap is zero bytes" is spelled `postBytes = 1`.** The task's
  fourth test asks for a cap of zero bytes; in a `Budget`, `0` is **no bound**
  (18's rule, stated in `AgentLoop.h` and in `docs/library.md` §6, and `loop()`
  depends on it). The case is therefore a cap of one byte, which no result and no
  batch this firmware writes can fit, and the test says so in those words.
- **18's "a result that a wake could not run is posted outside the byte cap" is
  reversed**, which this task asked for: a `reportNotRun` result now goes through
  the same budget as every other post and is kept when it has run out. The
  promise it was protecting is kept a different way — a job claimed is answered
  *now or from the buffer*, never not at all — and the buffer is the spec's own
  mechanism for it (EXIT-NODES §5: "results are buffered and posted later with
  their original timestamps; leased jobs whose lease expired meanwhile are still
  reported"). 18's own report named that decision as a decision; this is the
  other half of it, now that the budget covers the step.
- **The byte cap does not count the config call's, the heartbeat's or the
  claim's bodies**, and `Budget::postBytes` now says so. Those three bodies are
  written inside the consumer's `IUplink` — `postHeartbeat` takes a struct and
  `claimJobs` an integer — so their length is not knowable from inside the
  library; what the library can count is the bodies it writes itself (results,
  batches, and a progress report when something calls for one). Their **seconds**
  are counted like any other call's. A reviewer who wants their bytes too would
  have to move the heartbeat's and the claim's serialisation behind the seam,
  which is a `v1.0` interface change and not this task's.
- **Nothing of meshmaster.dk disagreed.** `spec/EXIT-NODES.md` §5 and §6 were
  read in full at today's `origin/master` (**`2c58e85`**, pile 4.15 included);
  §6's *as built in pile 4.14 (task 121)* is what sizes the claim and is
  unchanged by this task, and §5's *offline is normal* is what a kept result
  leans on. Nothing here is a change to the protocol, so there is nothing for the
  other repository.

## Decisions taken without asking

- **The ledger is a plain object, not an `IUplink` decorator.** A decorator would
  make "every call goes through one place" a compile error rather than a test —
  a new method of `IUplink` would have to be forwarded — but it would put a
  second vtable and an extra indirection on every call the Heltec makes,
  including the accessors `loop()` reads on every pass (`configured()`, `link()`,
  `lastCall()`), to enforce a rule that the two-line text test enforces for
  nothing. The test reads the interface's own list of calls, so adding one to
  `IUplink` and using it uncounted is red.
- **The runner keeps the ledger for its whole life, not for the length of a
  wake.** `AgentLoop::begin()` lends it once. The alternative — lend it in
  `wake()` and take it back — would leave the Heltec on a second code path
  (`meter_ == nullptr`), and the whole claim of this pile is that the board's
  path is the one the tests drive. A runner nobody lent one to is still bounded
  by nothing, which is what `test_runner` and `test_claim` drive directly.
- **A body the server did not take is not counted in `bytesPosted`**, and does
  not come off the byte cap. 18's accounting did the same, the name says
  "posted", and a refused call is a failure that backs the wake off anyway, so
  the cap cannot be eaten by retries inside one wake. On a plan that charges for
  the attempt this under-counts by a failed body; the figure a battery and a plan
  care about is in `uplinkMs` and in `bytesPosted` together, and a wake that
  failed is a wake that stopped.
- **The ledger does not refuse a call.** It times and weighs; what a bound means
  is each step's own business — a batch is shortened, a result is kept behind the
  queue, a job is never put on the air — and a refusal from inside would be
  indistinguishable from a server that said no, which is the one thing that must
  not back off.
- **`WakeReport` gained two members rather than none.** `uplinkMs` is what makes
  "no call is outside the uplink-second accounting" assertable at all (the
  criterion asks for a test per call kind, and the only honest test is
  arithmetic); `resultsKept` is where the report "says *kept: budget*". Both are
  additive, neither is in `WakeState`, so no state version moved and no existing
  test changed.
- **"Kept: budget" is a log line of the runner's and a count in the report, not a
  new console figure.** `JobRunner::resultsKeptForBudget()` is readable and is
  deliberately not printed by `jobs` or `errors` and not in the heartbeat: the
  Heltec can never keep a result for a budget it has not got, so a line about it
  on its console would be a line that always says zero — and `docs/console.md`
  would have had to move for nothing.
- **A job already claimed still runs when the uplink's seconds are spent.** Only
  posting stops. Refusing to run it would need `reportNotRun`, which is itself a
  post, and would turn a job that could have been done into a `failed` for the
  sake of an accounting line; a kept result is an answer, and the next wake sends
  it. What the spent uplink does stop is the claim (18's check, unchanged), so a
  wake with no seconds left takes on no new work.
- **`kNoByteCap` moved** from `agent/AgentLoop.h` to the new
  `agent/UplinkMeter.h`, which `AgentLoop.h` includes: `mm::kNoByteCap` is where
  it always was for anyone who includes either header, and it now lives beside
  the thing that means it.
- **`doObservations` lost its `size_t&` parameter** (it reads the ledger
  instead), and `doPendingResults` counts what the flush returned rather than the
  difference of two queue depths. Both are private, both behave identically on
  the board, and `test_buffers`' reading of `heartbeatIfOverdue` — which greps
  for `doObservations(` — still passes.

None. One new header in the library, `agent/UplinkMeter.h`, and no new

## Not verified here (and why)

Nothing the Heltec does changed and `wake()` is not in its image, so the bench
list is 1.5's and 20's, unchanged. What is genuinely unverified is what a
*metered* wake costs, which no device has run yet.

1. **A wake on a Walter over LTE** — its phase 4. Three things only a real unit
   and a real plan can answer: whether `Budget::postBytes` is the right unit at
   all (the body is what this counts; the plan charges for headers, TLS records
   and retransmissions, so the cap will want a margin, and what that margin is
   is a measurement and not an opinion); whether `uplinkSeconds` is the right
   bound for an attach that took three goes, which is 18's open question and now
   has `report.uplinkMs` to answer it with; and whether a kept result ever waits
   long enough to be dropped from the buffer, which is the next task's subject
   (22, what a sleep keeps) and is where the eight-result bound starts to matter.
2. **A result kept across a *sleep*** is still lost: the offline buffer is RAM
   and the `WakeState` does not carry it (1.5's review, the `[1.6]` item task 22
   has). Everything this task does is inside one boot. A unit that keeps a result
   for budget and then deep-sleeps loses it, and its job stays leased until the
   server's lease lapses — exactly the hole 22 fills. Worth knowing in that order:
   this task makes *keeping* a result the normal answer to a spent budget, which
   makes 22 more load-bearing than it was when the pile was written.
3. **The two new log lines on a board.** They are linked into the Heltec's image
   and unreachable there, so the bench cannot produce one; the first firmware to
   print *kept: budget* is the Walter's.
4. **`extendLease` and `postProgress`** are still called by nothing in the
   library (19's item). They are in the ledger's list all the same — the text
   test reads `IUplink.h` and not a list of the calls that happen to be made —
   so the first caller is counted without anybody remembering to count it.
