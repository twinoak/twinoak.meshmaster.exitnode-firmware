# p1.9-36 — A lighter TLS

Both boards are built with **the ESP-IDF compiled from source under the same
Arduino core**: `framework = arduino, espidf` in `platformio.ini`, core 2.0.17
on ESP-IDF 4.4.7, which is the pair `espressif32@6.11.0` picks by itself when
both frameworks are named (its `platform.py` sets `framework-espidf` to
`~3.40407.0` for a mixed project) — so no platform or package pin moved. The
configuration is a committed `sdkconfig.defaults`: the core's own
`tools/sdk/esp32s3/sdkconfig`, copied whole, with its mbedTLS section changed
and nothing else — `CONFIG_MBEDTLS_DYNAMIC_BUFFER`, the three
`DYNAMIC_FREE_*` keys, asymmetric content lengths of 16 384 in and 4 096 out,
`KEEP_PEER_CERTIFICATE` off, and one key the task did not list,
`SSL_PROTO_DTLS` off, because the dynamic buffers are not available with DTLS
compiled in. `tools/check-sdkconfig.py` holds the file to the core's on every
CI build, names the ten keys with their reasons, refuses any other difference,
refuses a core on disk other than the one the file was copied from, refuses
any insecure esp-tls key, and with `--built` reads the generated
`sdkconfig.<board>` to see that the build really used them. The partition
tables, the flash mode, frequency and size, the merged image's layout and the
certificate bundle are byte for byte what they were; the bootloader is now
built from source with the same header; the native tests are untouched and
green (534 cases). Nothing the firmware does changed, and no file under `src/`
or `lib/` did.

Two things the task could not know from the desk and this build had to
arrange, both in `tools/pio/arduino_component.py` and both with their
reasons written there: the Arduino core, compiled now by the ESP-IDF's
component build, does not see `platformio.ini`, so the board's own defines
(`BOARD_HAS_PSRAM`, `ARDUINO_USB_CDC_ON_BOOT=1` …) and MeshCore's
`pins_arduino.h` for the V4 are handed to it by a pre-script — without them
the V4 would have had no PSRAM and no USB `Serial`; and the project's own
sources search the libraries' include directories before the ESP-IDF's, as the
Arduino-only build did, because on a case-insensitive filesystem
`#include <Mesh.h>` otherwise lands in the ESP-IDF's Bluetooth-mesh
`mesh.h`.

## What was read, and what it settled

- **`MBEDTLS_PLATFORM_MEMORY` and `TlsHeap`.** The ESP-IDF 4.4.7's
  `mbedtls/esp_config.h` defines `MBEDTLS_PLATFORM_MEMORY` with
  `esp_mbedtls_mem_calloc`/`_free` as the standard pair, as the core's did,
  and the dynamic port (`components/mbedtls/port/dynamic/`) allocates every
  buffer with `mbedtls_calloc` and frees it with `mbedtls_free`
  (`esp_mbedtls_dynamic_impl.c:147,208,259,304,372,438`) — the function
  pointers `mbedtls_platform_set_calloc_free` sets, which is
  `src/platform/TlsHeap.cpp`'s wrapper. So the watch sees every allocation,
  the V4's routing to PSRAM still applies to each buffer of 4 KB and over, and
  there are more of them now: a 16 KB in-buffer is taken when a record is read
  and freed when it has been consumed (`__wrap_mbedtls_ssl_read`), a 4 KB
  out-buffer around each write, with an idle stub of a few bytes between
  (`TX_IDLE_BUFFER_SIZE`, `esp_mbedtls_free_rx_buffer`'s 16 bytes). The `tls`
  line's `routed there` count on a V4 will climb faster than "about four per
  handshake".
- **`DYNAMIC_FREE_CA_CERT`: both clients set their CA again on every
  handshake, so it is on.** The option frees `conf->ca_chain` once the server's
  certificate has been verified (`esp_ssl_cli.c:56`, in the
  `SERVER_CERTIFICATE` step) and NULLs the pointer; the object freed is the
  application's. WiFiClientSecure's `start_ssl_client` (core
  `ssl_client.cpp:179-182`) runs `mbedtls_x509_crt_init` and `_parse` on its
  own `ca_cert` and `mbedtls_ssl_conf_ca_chain` for every `connect()`, and
  `AgentClient::exchange` makes a new `WiFiClientSecure` for every handshake
  (`src/agent/AgentClient.cpp:172-178`: `setCACert` for meshmaster.dk's root,
  `setCACertBundle` otherwise); its `stop_ssl_socket` frees `ca_cert` again,
  which `mbedtls_x509_crt_free` makes a no-op because the first free zeroes
  the head (`x509_crt.c:3365`). esp-tls parses `cfg->cacert_buf` into the
  connection's own `tls->cacert` (`esp_tls_mbedtls.c:321-339`) and the bundle
  path attaches a static dummy chain with a verify callback; neither uses the
  **global CA store**, which is the one case that would break (its
  `global_cacert` would be freed by the first handshake and the next
  connection would verify against nothing). `src/net/MqttClient.cpp` sets
  `cert_pem` or `crt_bundle_attach` and never `use_global_ca_store`, so the
  observer's slots are safe too. Renegotiation on a kept connection would need
  the CA again, and mbedtls's client default is renegotiation disabled (a
  HelloRequest is answered with a `no_renegotiation` warning and the
  connection goes on), which neither client changes.
- **`KEEP_PEER_CERTIFICATE` off.** `MBEDTLS_DYNAMIC_FREE_PEER_CERT` makes the
  key unavailable (`depends on !MBEDTLS_DYNAMIC_FREE_PEER_CERT`), so it is
  "not set" in the committed file and absent from the generated one. What it
  would break is `mbedtls_ssl_get_peer_cert` after the handshake, which the
  core's `verify_ssl_fingerprint`/`verify_ssl_dn` use — `src/` makes no
  `verify()` call and reads no peer certificate (a grep is in the report's
  evidence), and `test/test_tls_policy` already forbids `setFingerprint`.
- **DTLS off.** `MBEDTLS_DYNAMIC_BUFFER` `depends on !MBEDTLS_SSL_PROTO_DTLS`
  (the Kconfig: "Dynamic buffer feature is not supported with DTLS"); the
  core's configuration has DTLS on. Nothing here or in the core's libraries
  uses `MBEDTLS_SSL_TRANSPORT_DATAGRAM` (`ssl_client.cpp:159` is
  `TRANSPORT_STREAM`; esp-tls and esp-mqtt are TCP).
- **One configuration for both boards.** The core's precompiled libraries are
  per memory type, and both boards are `qio_qspi` (the V3's board has no
  `psram_type`, so the builder's default `<flash_mode>_qspi`; the V4's says
  so). The `sdkconfig.h` of that type is the one the single `sdkconfig` file
  describes (`CONFIG_SPIRAM_MODE_QUAD`, no `SPIRAM_BOOT_INIT`); the V3's lack
  of PSRAM is found at boot by `psramInit()` as before, and the V4's
  `BOARD_HAS_PSRAM` is a compile define. So the task's "per board where they
  differ" is one file.
- **Flash size.** The core's own configuration says `ESPTOOLPY_FLASHSIZE`
  4 MB with detection on, and the builder warns *Flash memory size mismatch
  detected. Expected 8MB, found 4MB!* on every build. It is left as the core
  has it: the image headers carry the board's size because PlatformIO's
  `elf2image` passes `upload.flash_size` for the bootloader and the
  application alike (the table above: 8 MB and 16 MB in both headers, before
  and after), and the core's precompiled build ran boards of 8 and 16 MB on
  the same 4 MB-with-detect configuration. Changing it would be a key outside
  the TLS section.
- **The certificate bundle is the same.** The ESP-IDF's `cacrt_all.pem` at
  the package generates a 63 739-byte `x509_crt_bundle`; the one embedded in
  the core's `libmbedtls.a` (extracted to
  `out/36-core-bundle/core-x509_crt_bundle.bin`) is those 63 739 bytes
  followed by the 4-byte length word the embedding appends. So the Mozilla
  roots a custom broker or meshmaster.dk's fallback verifies against did not
  move.
- **The app descriptor moved** (`esptool image_info`): project name
  `arduino-lib-builder` → `meshmaster-agent-firmware`, app version
  `esp-idf: v4.4.7 38eeba213a` → `git describe` of this tree
  (`v0.5.0-3-g7fecbb9-dirty` here; at a tag, the tag), ESP-IDF
  `v4.4.7-dirty` → `4.4.7`. Nothing of ours reads it (`status` prints
  `MESHMASTER_AGENT_VERSION`); it is the ESP-IDF's own stamp and now says what
  it should. The stamp carries the compile time too
  (`CONFIG_APP_COMPILE_TIME_DATE=y`, the core's own setting), so two builds of
  one tree differ by those bytes: the clean build and the incremental one that
  preceded it gave images 56 bytes and a hash apart, with the same `RAM` figure.

## Deviations from the spec or the task

- **One key more than the task listed: `CONFIG_MBEDTLS_SSL_PROTO_DTLS` off.**
  The Kconfig makes `MBEDTLS_DYNAMIC_BUFFER` unavailable while DTLS is
  compiled in; the alternative was no dynamic buffers at all. It is in the
  check's allowed list with that reason.
- **`CONFIG_MBEDTLS_SSL_KEEP_PEER_CERTIFICATE` is off** — the task's "if the
  dynamic options need it so": they do (above).
- **`build_unflags = -Werror=all` in `[esp32_base]`.** The ESP-IDF compiles
  its own tree with `-Werror=all`, and PlatformIO's component mode brings that
  flag into every library's compile — MeshCore's own constructors initialise
  members out of order (`-Wreorder`) and failed. Upstream's warnings are not
  ours to fix (the bootstrap's own rule), so the flag is taken back for what
  PlatformIO compiles; `src/` keeps its `-Wall -Wextra -Werror` from
  `build_src_flags`, which is stricter, and the ESP-IDF's components compile
  without a warning either way. The 15 warning lines the bootstrap counted are
  back to being warnings.
- **The task's "if `espressif32@6.11.0` cannot pair the two, find the platform
  release that does"** did not arise: 6.11.0 pairs them itself. **Plan B** (the
  lib builder with the changed config, pinned through `platform_packages`) was
  not needed and is not written beyond this line.
- **The per-board `sdkconfig.defaults`** is one file (above: both boards are
  the core's `qio_qspi` type).
- **`docs/observer.md`'s *What it costs* gains a row marked *expected*** rather
  than new figures, as the task asked; the row says what should move
  (~40 KB per connection at rest, the dip of a call near the old figure) and
  that 37 writes the measured ones. `Board.h` is untouched.

## Decisions taken without asking

- **Where the committed configuration lives: `sdkconfig.defaults` at the root**
  — the name and place both the ESP-IDF and PlatformIO's builder look for by
  themselves (its own staleness check watches that path), so no CMake argument
  names it. The generated `sdkconfig.<env>` beside it is git-ignored, and the
  pre-script deletes it when the defaults are newer, because the ESP-IDF only
  *seeds* a missing one from the defaults and an existing one wins over them —
  without that, a changed default would not reach a working tree that had
  built before. The root is also outside `test/test_tls_policy`'s walk, which
  the core's own `# CONFIG_ESP_TLS_INSECURE is not set` line would otherwise
  trip; the check carries that rail for this file instead (`FORBIDDEN`, with a
  planted case).
- **The core gets the board's defines and MeshCore's `pins_arduino.h` through
  a pre-script and two CMake variables**, not through a copy of the variant
  into the core's tree or a Kconfig: `tools/pio/arduino_component.py` reads
  `build.extra_flags` and `build.variant` from the board definition — the same
  two places the Arduino-only build read — and `CMakeLists.txt` applies them
  to the core's component alone (`target_compile_definitions`, and an
  `-iquote` for the pins header, which a quoted `#include "pins_arduino.h"`
  searches before the component's own directory). The linked images prove it:
  the V4's `firmware.elf` has `Serial` (HWCDC) and `Serial0` and a real
  `psramInit` of 216 bytes; the V3's has `Serial` alone and the 7-byte stub.
  The pins matter for the defaults of `Wire.begin()` and `SPI.begin()` with
  no arguments, which MeshCore does not use (its `ESP32Board.h:48` and the
  radio wrappers name every pin), but the core is compiled with what it was
  compiled with before, and the build log says which header it got.
- **The project's sources search the libraries' directories before the
  ESP-IDF's, through `--include-directory=` in `build_src_flags`.** The
  espidf builder prepends the ESP-IDF's 170-odd include directories and
  appends the libraries' after them for `src/` alone (a library's own
  sources keep their own first); on Windows and macOS that resolves
  `#include <Mesh.h>` to `bt/esp_ble_mesh/mesh_core/mesh.h` and `<Crypto.h>`
  to its `crypto.h` (a scan of every library header against every ESP-IDF
  include directory found exactly those two, `out/36-cmd-AgentMesh-v1.txt`
  being the compile line it read). The pre-script asks PlatformIO's own
  dependency finder for the same list the builder appends (37 directories)
  and adds each as GCC's long spelling of `-I`, which PlatformIO's flag parser
  does not file under `CPPPATH` and therefore leaves in the compiler flags,
  which come before every `-I` on the command line; `build_src_flags` is the
  channel because it reaches `src/` and nothing else — the ESP-IDF's
  components are compiled from the same environment, and a MeshCore directory
  in front of *their* includes would turn the Bluetooth stack's
  `#include "mesh.h"` into MeshCore's. The verbose compile line of
  `src/mesh/AgentMesh.cpp` (`out/36-cmd-AgentMesh-v3.txt`) shows the 37
  entries before the first `-I`. Linux, where CI builds, needs none of this
  and gets it anyway.
- **`src/CMakeLists.txt` registers `src/` by a recursive glob** of `.cpp` and
  `.c`, with no `REQUIRES`: PlatformIO reads the component's source list from
  CMake and compiles the files itself with `platformio.ini`'s flags, so the
  file is the list and nothing else. The root `CMakeLists.txt` is the three
  lines the builder would have generated plus the block for the core.
- **`CONFIG_ARDUINO_VARIANT` stays `esp32s3`** for both boards: the core's
  CMake turns the variant into a directory of its own tree and a macro name,
  and `heltec_v4` is MeshCore's, not the core's. The board's `-DARDUINO_ESP32S3_DEV`
  (the V3's `extra_flags`) and the core's own `-DARDUINO_ESP32S3_DEV` are the
  same define twice, which GCC allows.
- **The CI cache key names `sdkconfig.defaults`** beside `platformio.ini`, in
  `ci.yml` and `release.yml` alike, and the `Build` step is timed into the
  step summary.
- **`.gitignore`** gains `sdkconfig.*` (less `sdkconfig.defaults`),
  `dependencies.lock` and `managed_components/` — the last two are what the
  ESP-IDF's component manager would write if it ever ran here; it did not
  (no `idf_component.yml` in `src/`), and the entries cost nothing.
- **The ESP-IDF's app descriptor** keeps its defaults (project name and
  `git describe`, above) rather than a pinned string: it is the ESP-IDF's own
  stamp, nothing of ours reads it, and at a tag it says the tag.

## Not verified here (and why)

A session cannot flash a board, make a handshake or read a heap; the build,
the checks and the tests are above. The walk is `tasks/phase-1.9/README.md`'s
*Between 36 and 37*, with this build's images (`out/36-after-*`, or the pull
request's artifacts), and these are the things to read:

1. **The bootloader built from source boots.** A *first install* with the
   `-merged.bin` on one board (the web flasher's *Custom firmware*, or
   `esptool.py --chip esp32s3 write_flash 0x0 …-merged.bin`): the board comes
   up, prints its banner at 115200, and `status` says what it said on
   `v0.5.0`. This is the one thing of this task that only hardware can tell:
   the bootloader's header is the same, its configuration is the core's, but
   it is a different binary (13 936 bytes for 15 104, entry `0x403c98b8`). A
   board that stays silent after the flash, or loops in the ROM's
   `invalid header` message, is that; the plain `.bin` on a board that already
   has the old bootloader is the way to tell the bootloader from the
   application.
2. **What the board prints at boot and in `status`** is unchanged — nothing
   under `src/` moved — but the core underneath is compiled afresh: the V4's
   USB `Serial` and its PSRAM (`status`'s `heap` line: `psram free N` on a
   V4, absent on a V3) are the two things the defines above decide, and the
   OLED and the radio are what the pins decide. A V4 with no console over USB,
   or with `psram free 0`, is the pre-script's defines not reaching the core
   (the build log's `arduino_component:` line says what the core got).
3. **The heap at rest, no slot** (`set mqtt1.preset none`, ten minutes):
   `status`'s `heap` and `uplink` lines → the README's row *after 36, V3, no
   slot*. Expected: `free` well above the 71 612 of 2 November, by about the
   two content buffers (~34 KB) plus the certificates (~8 KB) that a kept
   connection no longer holds between records; `uplink`'s *lowest during* a
   reused call near the old 69 232 (the 16 KB in-buffer is borrowed back for
   the reply), and the *handshake* figure the row asks for.
4. **The handshake beside a slot** (`set mqtt1.preset meshview`, an hour, a
   job or two): `get mqtt.status`'s `memory`, `uplink` and slot 1's state,
   `gave way`, and `status`'s `heap` → the row *after 36, V3, one slot*. The
   question of pile 1.8's task 31 — does the server's reconnect handshake fit
   beside an open slot on a V3 — is answered by `min ever` and `gave way`:
   the gate's constants are still 28 October's (`Board.h`, task 37's to
   move), so the slot may *wait for heap* at first until the board has
   measured a call of its own; what matters is whether it then connects and
   stays. **A handshake that fails with an allocation error where `v0.5.0`'s
   went through** would be the dynamic buffers costing a peak the old build
   did not have (the in- and out-buffers are both allocated during the
   handshake, as before, but now from a heap the two idle buffers were just
   returned to — fragmentation is the bench's question).
5. **A V4, two slots, an hour**: the same lines → the row *after 36, V4, two
   slots*. The `tls` line's `routed there` now climbs with every record, not
   only every handshake (each 16 KB read buffer is a PSRAM allocation of its
   own), and `0 fell back` is still the healthy reading; a count of fallbacks
   is a PSRAM that could not serve a buffer in time.
6. **TLS itself.** Every connection still verifies (nothing in `src/`
   changed, `test_tls_policy` green, the bundle byte-identical); the thing the
   configuration could have broken is a *second* handshake on the same
   connection, which neither client makes. A `tls handshake failed` on a
   reconnect after an idle close, where `v0.5.0` reconnected, would be the CA
   freeing (`CONFIG_MBEDTLS_DYNAMIC_FREE_CA_CERT`) reaching something this
   reading missed, and that key alone is the one to turn off and rebuild.
7. **The build on another machine.** This tree built on Windows and the
   checks ran on Linux in the container; CI's Linux build is the pull
   request's. A macOS checkout is the third case-insensitive filesystem and
   was not tried.
