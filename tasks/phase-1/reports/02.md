# p1-02 — an-exit-node-with-no-jobs

Milestone 1. The board is an exit node on meshmaster.dk: it hears adverts,
heartbeats every `pollIntervalS` with the self-description of EXIT-NODES §5,
and posts what it heard to `/agent/v1/observations` in batches — with
`jobTypes: []`, so the server hands it nothing and the routing procedure admits
it for no job. Nothing leaves the radio: `tx` is still 0.

The heartbeat's bytes are the .NET agent's, byte for byte, and a native test
says so against `tests/fixtures/contracts/AgentHeartbeat.json`.

body 8 KB, the batch scratch 4 KB and the rate limiter 0.5 KB; all of it

to leak. The image carries `/agent/v1/heartbeat`, `/agent/v1/observations`,
`onboard`, `heltec_v3` and `observationsDropped` once each, and `tx 0` is still
what `status` will print.

## Acceptance checklist

- [x] **Native tests: the heartbeat and observation batch JSON equal the .NET fixtures byte for byte for the same input.** `test/test_envelopes`: `Heartbeat.TheSameInputMakesTheDotNetFixtureByteForByte` builds the sample `MeshMaster.Contracts`' `ContractsTests` writes `AgentHeartbeat.json` from — the same thirteen job types, the same budget, the same `{"uplink":0}`, the same `2026-09-23T14:00:00Z` — and compares the whole body to the fixture's bytes. **The observation batch has no fixture** (`ObservationBatch` is not one of the four envelopes the .NET test writes files for; see the deviations), so it is held to the record in `Envelopes.cs` instead: `ABatchIsTheRecordsFieldOrderWithTheNullsLeftOut` asserts the exact string for a fully-populated item, `ADirectNeighbourHasAnEmptyPathAndZeroHops` for an empty path, `AnEmptyBatchIsStillAWellFormedBody`, and `ANameFromAStrangerIsEscapedAndNeverBreaksTheBody`.
- [x] **The ring drops the oldest and counts.** `test/test_observations`: `Ring.WhenItIsFullTheOldestGoesAndIsCounted` fills all 64, pushes three more, and checks the three oldest are gone, `dropped()` is 3 and `heard()` is 67; `Ring.ABatchTheServerTookIsConsumedFromTheOldestEnd` checks that consuming a posted batch is not the same as dropping one (`dropped()` stays 0).
- [x] **The batch timer fires at twenty or sixty seconds.** `BatchTimer.ItFiresAtTwentyOrAtSixtySecondsAndNotBefore`: nothing pending is never due; 19 at 59 999 ms is not due; 20 at 0 ms is; 1 at 60 000 ms is.
- [x] **`pio run -e heltec_v3` green.** The log above; `-Werror` on `src/` throughout.
- [x] **The firmware string in the heartbeat matches `status`.** `Heartbeat.TheFirmwareStringIsTheTwoFieldsTheHeartbeatSends` composes `"meshmaster-agent " + agentVersion + " on MeshCore " + companionFirmware` from the two fields the heartbeat sends and compares it to `mm::firmwareString()`, which is what `status` prints. `src/version.cpp` is compiled into the native env now, with `platformio.ini`'s own `[meshcore]` tag and pin, so the test runs against the real strings.
- [x] **A 401 halts the network loop and is visible on console and OLED; a 429 waits `Retry-After`.** The policy is a pure function so that this is a test and not a promise: `ServerPolicy.AFourOhOneHaltsEverything`, `AFourTwoNineWaitsExactlyWhatRetryAfterSays` (17 s → 17 000 ms; no header → a minute; an absurd header → an hour), `AFiveHundredBacksOffFromHalfAMinuteToTen` (the whole 30/60/120/240/480/600/600 ladder, and no reply at all reads the same as a 500), `TheAnswersThatMeanTheRequestItselfIsWrong`. What the loop does with `Halt` is board-only: `halted_` stops `loop()` before anything is sent, `LOG_E` names it, `status`'s heartbeat line and `server` say *halted: http 401, the token was refused*, and the OLED's third line becomes `token revoked/wrong` until `set meshmaster.token` or a reboot. That last step is on the bench list.
- [x] **Never more than 120 requests a minute.** `src/agent/RateLimit.h` is an exact sliding window over the last 120 request times, asked before every call; `RateLimiter.TheNormalLoopNeverMeetsIt`, `TheHundredAndTwentyFirstInAMinuteIsHeldUntilTheWindowMoves` and `ItSurvivesTheMillisecondCounterWrapping` cover it. `server` prints how many of the 120 are spent.
- [x] **The console gains `mesh` and `server`, and `log.level debug` prints each heartbeat's reply in one line.** The two verbs are in the parser (and therefore in `test_console_parser`'s grammar and in the README session the tests replay); `mesh` prints the counts and the last five adverts with names, roles, hops, SNR and RSSI; `server` prints the state, the last heartbeat and the next, the last batch, the ring, the four counters and the request budget. The debug line is `server: heartbeat reply: serverTime ..., budget ..., poll ... s, jobs waiting yes|no`.
- [x] **The OLED's third line is the heartbeat, the fourth the identity.** `hb HH:MM · N adverts` once one has been answered (the middle dot is CP437 `0xFA`, which is the font MeshCore's `SSD1306Display::startFrame` selects with `cp437(true)`); before that it is the config call's line, as in task 01.
- [x] **Docs move with code.** The README has the new **What you should see on meshmaster.dk** section — the row *onboard · Heltec V3*, the page's heartbeat block field by field, and unknown nodes filling up — plus the `mesh` and `server` output in the provisioning session. `docs/console.md` has the two commands, the new OLED line, the debug lines, and two more steps in the bench walk.

## Deviations from the spec or the task

- **`ObservationBatch` has no contract fixture**, so the batch's bytes are held
  to the record in `src/MeshMaster.Contracts/Envelopes.cs` at `master` rather
  than to bytes the .NET test wrote. `ContractsTests` writes files for four
  envelopes only ("the four envelopes of spec/API.md §3 the tests below read
  field by field": `AgentHeartbeat`, `HeartbeatReply`, `ClaimedJob`,
  `JobResultReport`), and `ObservationBatch`, `Observation` and
  `ObservationFields` are not among them. **This is one for the other
  repository**: adding those three to `ContractsTests.Samples` would give this
  firmware the same byte-for-byte hold on the observation feed that it has on
  the heartbeat, and `test_envelopes` would read the file instead of its inline
  expectation — a one-line change here. Same shape as task 01's note about
  `AgentConfig`.
- **The `heard` kind is never sent; every observation is an `advert`.** The
  task says "`onAdvertRecv` (and the packet-heard hook) feeding an observation
  ring". An `Observation` needs a `publicKey`, and on a board the packet-heard
  hook has none to give: a non-advert frame carries a one-, two- or three-byte
  path hash and an encrypted payload, not a key. So the packet-heard hook
  (`Dispatcher::logRx`) feeds the frame counters and the per-packet RSSI, and
  the ring takes adverts only. The one frame type that *does* carry a sender's
  key in clear is `PAYLOAD_TYPE_ANON_REQ` — somebody's login to somebody else —
  and reporting those is not something the task asks for and not something the
  rails invite.
- **`fields.flags` is left out.** `ObservationFields` has a `Flags` the .NET
  agent fills from `ContactInfo.flags`, which is a field of the *companion's
  contact table* and is `memset` to zero for a contact made from an advert
  (`BaseChatMesh::populateContactFromAdvert` at the pin). A board has no
  contact table and an advert carries nothing that corresponds, so the field is
  absent rather than a zero that means nothing. `name`, `lat`, `lon` and `role`
  are all decoded and sent.
- **`companionConnected` is `true` when the radio came up, not unconditionally.**
  The task writes `companionConnected: true`. On this board the radio *is* the
  companion, and a board whose SX1262 did not initialise is an exit node that
  hears nothing — which is exactly what EXIT-NODES §10's "companion
  disconnected while agent online" alert is for. So it reports the truth: true
  in every normal case, false on a board with a dead radio (which also sends no
  `companionPublicKey`, no `companionFirmware` and no `radio` block, because it
  has none).
- **`companionFirmware` is the MeshCore *tag*, `companion-v1.17.1`**, not
  `v1.17.1`. The task says "the MeshCore tag" and that is what `[meshcore].tag`
  holds; the `v1.17.1` in the fixture is what a real companion's
  `RESP_CODE_DEVICE_INFO` answers, and that string is `FIRMWARE_VERSION` in
  `examples/companion_radio/MyMesh.h`, an example this repository does not
  build. The tag is the honest answer and it moves with the pin by itself.
- **The OLED says `token revoked/wrong`, not `token revoked or wrong`.** The
  line is 21 characters of a 6×8 font across 128 pixels; the task's wording is
  22. The console and the log say it in full.

## Decisions taken without asking

- **The ring holds 64 adverts, 7.5 KB.** Task 01 left the heap figure on the
  bench list, so the number is taken from the build instead: the image had
  55 KB of static RAM and 231 KB free at boot, of which ~187 KB survived a TLS
  handshake. Sixty-four entries at 116 bytes is 7.5 KB of `.bss` — three
  batches of the twenty a flush sends, about half an hour of a busy window at
  two adverts a minute — and the whole task costs 27 KB, leaving roughly 160 KB
  free after a handshake. It is a compile-time array: it cannot fragment the
  heap and it cannot grow. If the bench's real figure is smaller than expected,
  `ObservationRing::kCapacity` is the one number to change.
- **An entry stores *when it was heard* as `millis()`, and the timestamp is
  computed when the batch is built** (`now − (millis − heardAt)`). That way an
  advert heard before SNTP or the first heartbeat answered still gets the right
  absolute time once there is one, which is the "buffered and posted later with
  their original timestamps" of EXIT-NODES §5 as far as a board can do it.
- **Only an advert reaches MeshCore's own dispatch.** `AgentMesh::onRecvPacket`
  counts every frame, logs a header line when `log.frames` is on, and releases
  everything that is not `PAYLOAD_TYPE_ADVERT` before calling the base class.
  So no payload is decrypted, no ECDH shared secret is ever calculated, and
  there is no branch of `Mesh::onRecvPacket` left that could compose a reply —
  a stronger statement than task 01's `allowPacketForward() == false`, which
  guards the sending paths but would still have let an `ANON_REQ` addressed to
  our hash cost an ECDH. An advert then gets MeshCore's signature check, its
  replay-timestamp check and its `wasSeen` de-duplication for free, which is
  why observations are not duplicated across routes.
- **RSSI is taken in `Dispatcher::logRx`, not in `onRecvPacket`.** A flood
  frame can wait in the inbound queue for up to a second before it is
  dispatched, and `Radio::getLastRSSI()` has moved on by then; `logRx` runs
  while the number is still the packet's, so it is noted there against the
  packet pointer (16 slots, the packet pool's size) and taken back when the
  packet is dispatched. SNR needs none of this — `Packet::_snr` is the
  packet's own. The .NET agent sends neither (`Observer.cs` passes `null,
  null`): being the radio is how a board can do better, and UI §7's feed has
  columns for both.
- **A name from an advert is bounded at 32 bytes and cut at the last byte that
  is still well-formed UTF-8**, with control characters ending it. It is
  whatever a stranger put in a packet, and it has to survive being a JSON
  string on the way to a page that renders it. 32 is MeshCore's own bound
  (`ContactInfo::name`). The JSON writer escapes `"`, `\` and the C0 controls;
  it does not escape non-ASCII the way .NET's default encoder does, which is a
  difference in bytes and not in value, and cannot arise in a heartbeat, whose
  every field is ASCII and is held against the fixture.
- **A name is never in a log line.** `log.level debug` prints an advert's first
  four key bytes, its role, its hops and its SNR; the name is read on demand
  with `mesh`. The .NET agent does log it at debug, but the rail here says
  nothing the mesh says is logged as text, and a name costs nothing to look up.
- **The JSON is written by hand, not by ArduinoJson.** A twenty-item batch is a
  6 KB document, which ArduinoJson would build on the heap before serialising
  it; the writer here streams straight into the output buffer and answers 0
  rather than half a body if it would not fit. It also puts the number
  formatting under this repository's control: a double is written as the
  shortest decimal that reads back as itself, which is what System.Text.Json
  has done since .NET Core 3.0, and `869.618` through a `float` would have been
  `869.617981` (hence `SettingsStore::numberDouble`). Reading still uses
  ArduinoJson, as task 01 left it.
- **The config call happens once per WiFi link and is no longer retried.** Task
  01's report said "task 02's heartbeat loop replaces this schedule", and it
  does: the heartbeat answers the budget, the poll interval and the clock every
  time, so a failed startup call is noted (and backed off from, if the answer
  earned it) and the loop starts anyway — which is what the .NET agent's
  `StartupBudgetCheckAsync` does. A 401 is the exception: there is no loop to
  start.
- **A batch keeps its client id across a retry, and so does its contents.** The
  id is what the server de-duplicates on, so a batch it took whose answer was
  lost costs nothing twice; and a retry must be the *same* items, or the extra
  ones would be consumed against an id the server already has and never stored.
  A batch the server refuses for good (400, 403, 404, 409, 410, 413, 422) is
  dropped and counted rather than retried forever.
- **`errors` carries the four counters the task names, always.** `overheard` is
  the mesh's own chat — `GRP_TXT`, `GRP_DATA` and `TXT_MSG` counted and dropped
  unread, which is what the field means on the .NET side too;
  `wifiReconnects` is links after the first; `httpFailures` is any call that
  did not come back 2xx, a 401 and a 429 apart; `observationsDropped` is the
  ring's.
- **`X-RateLimit-Remaining` is collected and only ever logged.** The board's
  own ceiling is the sliding window; the header is there for a person reading
  `server` when something is odd.

## Not verified here (and why)

A session cannot flash a board or hear a radio. Everything below is Thomas's,
with the Heltec V3 on USB and a terminal at 115 200 baud; `docs/console.md`
"The bench walk" steps 6 and 7 are the same list.

- **The exit node's page.** After provisioning (task 01's walk), within one
  poll interval `/exit-nodes` shows the row **online** and the transport column
  **onboard · Heltec V3**. On `/exit-nodes/{id}`: agent version `0.0.0-dev` (or
  the tag from a release build), firmware `companion-v1.17.1`, board
  `heltec_v3`, the companion key equal to what `status` prints, the radio line
  `869.618 MHz, BW 62.5, SF8, CR8` and **no** radio warning if the site's
  `network.radio` is the Danish channel, job types empty, queue depth 0, and
  the four error counters.
- **The radio parameters as set on the bench.** `set radio.sf 9`, then wait one
  interval: the page's radio line follows, and the warning appears if the
  network standard is set. Put it back.
- **Unknown nodes within a few minutes at a window.** `mesh` shows adverts
  heard and the last five with names; the log says `observations: N posted, N
  accepted`; `/unknown-nodes` has those keys with the hops, the SNR and the
  RSSI, and a key the register already knows teaches that pair a path instead.
  Check that a name with an accent (a Danish repeater) reads correctly on the
  page — that is the UTF-8 bounding doing its job.
- **`tx 0` after all of it.** `status` must still say `tx 0`: this firmware
  sends nothing on the radio. If it ever says otherwise, that is the bug this
  milestone most needs to catch.
- **The poll interval moving.** A heartbeat reply says 30 s when work waits and
  120 s when none does; with no jobs in the queue `server` should settle on
  `poll 120 s`. If a job is queued for some *other* exit node the log says
  *the server says jobs are waiting; this firmware claims none yet* once, and
  nothing else happens.
- **A revoked token.** Revoke it on the server, wait one interval: the log's
  `http 401` line, the OLED's `token revoked/wrong`, `server` showing *halted*,
  and — the part that matters — **nothing further on the wire**. Then
  `set meshmaster.token <a fresh one>` and watch the loop start again without a
  reboot.
- **A dropped link.** Pull the router's uplink for five minutes: the ring
  fills, `server` shows the pending count climbing, `httpFailures` rising and
  the backoff in the log (30 s, 60 s, 120 s …); when the link returns, the
  backlog goes in batches of twenty and `observationsDropped` is 0 if the
  outage was short. Leave it down long enough to overflow 64 adverts and the
  counter should be non-zero and match what the page's heartbeat block shows.
- **The heap over an hour**, which task 01 also left here. `status` after an
  hour of heartbeating: `free` and `min ever` should be flat. Each call is a
  fresh TLS handshake (`setReuse(false)`, as task 01 left it), so this is the
  measurement that says whether task 06 needs to keep a connection alive.
  Note the figure in the review.
- **The middle dot on the OLED.** `hb 12:03 · 17 adverts` — if the glyph is
  wrong, the font is not CP437 and the byte should become a plain `.`.

One thing a session also cannot check and is worth saying: **the loop blocks**.
A heartbeat is a synchronous HTTPS call of a few seconds during which
`the_mesh.loop()` does not run, so adverts arriving in that window are missed
rather than queued. At a heartbeat every 30 or 120 seconds that is a small
fraction of the time, and task 06 ("a node that stays up") is where a
connection kept alive, or the radio on its own task, belongs.
