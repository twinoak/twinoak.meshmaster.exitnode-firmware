# p1-04 — logins-and-the-config-read

The board logs in with a password now, and puts the entry it had to rewrite back
afterwards. Three job types join the heartbeat's list - `discover`, `acl.set`,
`config.read` - and every one of them carries a repeater's admin password for the
length of the job and no longer: one fixed buffer inside the claimed job, parsed
straight out of the claim's bytes with no copy of its own, wiped when the job
ends whatever it came to, read by exactly one thing (the login packet's
plaintext, which is wiped the moment the packet is encrypted), never a log
argument, never near NVS. `log.frames on` prints the login that carried it with
its encrypted body as one `*` per byte, the .NET agent's redaction of
`CMD_SEND_LOGIN`. Every admin session on a repeater where this exit node holds a
grant ends with `setperm <own key> <granted level>` (task p4.1-60), the cache
follows the level, and `sessions` on the console shows what is held - a key, a
class, a level and an age, no secret.

## Deviations from the spec or the task

- **The password on the wire is ciphertext, so the redaction stars the encrypted
  body.** The task asks for the .NET agent's redaction of "the login frame's
  password bytes". On a cable, `CMD_SEND_LOGIN` carries the password in clear
  after the key and the agent stars those bytes. On the air there are no such
  bytes: the ANON_REQ payload is the destination hash, our public key and the
  AES body (`Mesh::createAnonDatagram`, `src/Mesh.cpp:513-540` at `d9296435`).
  So the board prints the 33 clear bytes as hex and one `*` per byte of the
  body, for a login that carried a password; the ACL login (our key, a
  timestamp, no secret) is printed whole, as task 03 left it. The star count is
  the block-padded body and says less about the password's length than the .NET
  count does, which task 41's diagnostic used; the runner's log says whether
  material was sent at all (`the claim carried no admin material`), which is
  what that diagnostic needed.
- **`unauthorized` at class `acl` and `admin` still cannot come from a refused
  login on stock firmware**, only from a login *answered* below the class or a
  RESPONSE that is not a login-ok: task 03's deviation stands for the three new
  types. A wrong admin password is two silences and `unreachable`, as the .NET
  agent reports it against a real radio too.
- **The restore is not sent into a silence.** The .NET runner sends the restore
  after every job whatever its outcome, so after a job that ended `unreachable`
  it sends one more command into the same silence and drops the session either
  way. Here a job that ended `unreachable` or `timeout` (the lease is spent)
  skips the command, drops the session and says so in the log; the entry is put
  right by the next login from this key, which a blank login answered admin does
  at once (the third rule of EXIT-NODES §7). Same end state, one transaction
  fewer, and nothing sent past a lease.
- **The guest password on a pair with a grant is `unsupported`, not
  `unauthorized`.** The task says the firmware refuses it, belt beside the
  claim's braces, and does not say with which outcome. `canRun` refuses it
  before anything is sent, so the honest outcome is the one that means "this
  firmware does not have what the job asked for" and moves nothing in
  reachability; the sentence names task p4.1-60. The claim never hands it out,
  so this is a branch the field should not reach.
- **A direct neighbour's known path is sent DIRECT now.** Task 03 read a claim
  path of zero hops as "no path" and flooded; the mesh gained `setDirectPath()`
  and a trace to a direct neighbour is the round trip of the repeater's own hash
  at this board's hash size. Not this task's deliverable, but `discover` along a
  known path would otherwise have flooded for every direct neighbour.
- **The contract fixtures did not change**: both sets were already at today's
  `master` (`f518ebd1`), so `tools/sync-fixtures.ps1 -Verify` is the only
  fixture step of this task.

## Decisions taken without asking

- **Where the password lives.** `JobCredential` inside `ClaimedJob`: two
  16-byte arrays, the flags, and `wipe()` through a volatile pointer. The claim
  is parsed with ArduinoJson's **zero-copy** mode (`char*` input), so the
  document points into the client's static body buffer and keeps no copy of
  any string; the job's arrays are filled from it and the body is wiped the
  moment the parse returns, took or not. The jobs are built in place in the
  caller's slots rather than through a local, so no stack frame ever held one.
  HTTPClient's `getString()` is gone from every call: a `BodySink` stream takes
  the reply straight into the caller's buffer, because a `String` is a heap
  copy that nothing wipes and grows by reallocation. What remains that this
  code cannot wipe: the chunk buffer HTTPClient moves bytes through and the TLS
  library's receive buffers - the same shape as the .NET agent's HttpClient,
  and said so in `Credentials.h`.
- **Fifteen bytes of a password go out**, as `BaseChatMesh::sendLogin` sends
  them (`src/helpers/BaseChatMesh.cpp:585`); a longer one is cut at the parse
  and the job's log says it was, without the value or its length.
- **Sender timestamps are one series.** Every REQ tag and every CLI line's
  timestamp comes from the RTC's `getCurrentTimeUnique()`, so what a repeater
  sees from this key is strictly increasing across both kinds - a REQ needs
  `>` its last timestamp, a text `>=` with equal being a retry that runs
  nothing (`MyMesh::onPeerDataRecv`, 676 and 709). A CLI retry is therefore a
  fresh timestamp and the command runs again, which for a `get`, `region` or
  `setperm` is the same answer. The one thing this leans on is the board's
  clock being ahead of the last timestamp the repeater saw from it, which SNTP
  guarantees once a job can run at all.
- **A CLI reply is the first `TXT_MSG` of CLI data from the peer while one is
  awaited**, as the .NET agent reads it: the repeater's reply carries its own
  timestamp and no tag (`temp` at 739-750), so there is nothing to match on. A
  `TXT_MSG` at any other moment is released unread with the mesh's own chat,
  and a `TXT_MSG` of another type (a signed message, say) during a wait is
  dropped. The hazard the .NET agent has too: a late reply to a retried command
  could be taken as the next command's answer.
- **The discover's order and words are the .NET handler's** (task p3.5-39):
  a direct login along the server's path verifies it; silence clears the path
  and the next login floods; a flooded login's reply comes back as a returned
  path and `onPeerPathRecv` learns it; the path-discovery request - the
  flooded base-telemetry REQ the companion builds (`companion_radio/
  MyMesh.cpp:1602-1630`) - is tried once and last, and only when neither login
  was answered or the claim carried no material. `loggedInAs` is the tier the
  repeater granted; a login answered below admin keeps the path and is
  `unauthorized` (task p3.5-41).
- **The config read's order is the .NET handler's actual order**, not the key
  table's: `region` and `region default` first, the `get`s in the list's order
  skipping the two that are not a `get`, `ver` and `board`, the access-list
  request last, then the restore. The default list is the fifteen keys of
  `ConfigReadPayload.DefaultKeys`, the price `n + 2 + r` (18 for the default
  list, 20 with the login and the restore). A claim's list past twenty keys is
  refused by name at the parse; a reply's value past 208 characters is cut
  (the region value is at most a 159-character listing and one line).
- **Silence on the ACL after keys were read is `ok` with the .NET sentence**
  under `raw`, em dash included (`kAclSilentLine`; the writer escapes it as
  `—`, as System.Text.Json does); a reply that is not the layout is the
  .NET's other sentence and no ACL; 23 entries is the full-list line. A `get`
  that did not answer `> …` goes under `raw` as `<command>: <reply>`.
- **The restore's conditions** are the .NET `NeedsAclRestore`: the claim carried
  a level, the level is below admin, and the session in force is admin - which
  covers the admin password and a blank login answered admin alike. It is sent
  once with no retry, confirmed by an `OK`; on `OK` the cache holds an acl-class
  session at the granted level, on anything else the session is dropped and the
  log says the entry may still be at admin. `config.read` sends it itself so its
  result can say what became of it; the runner sends it for every other type
  but `acl.set`.
- **`sessions` on the console** prints the first twelve hex characters of the
  repeater's key, the class, the tier and the age; the header says what a
  session is made of. `jobs` prints the seven types from `kJobTypes` rather
  than a literal.
- **The JSON writer's escaping changed for every envelope**, not only the new
  one: `<>&'+`` ` `` and non-ASCII are `\uXXXX` now, `\n` and its four
  siblings are short. Same values on the server; the bytes of an observation
  with a non-ASCII name differ from before (they now match what the .NET agent
  would have sent). No existing fixture held such a character, so no existing
  test moved.
- **`kDataCap` is 4 608 and `kBodyCap` 6 656**, sized for a default read: fifteen
  values, the ACL's 344 characters, the raw lines and the envelope.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and everything below needs a
real repeater and the admin password of one. With the Heltec V3 on USB, a
terminal at 115 200 baud, and Risskov's page on meshmaster.dk -
`docs/console.md` "The bench walk" steps 11 to 13 are the same list.

- **The association through the board.** Run the wizard with this exit node.
  The `discover` should log `login along the path the server holds (N hop(s)),
  which verifies it: logged in as admin, firmware level 2 (direct)` - or, with
  no path known, `flooded login …: logged in as admin` and a path of the hops
  the reply came back along - and end `ok` with `loggedInAs: admin` on the
  job's page. Then the grant: `session reused (admin, admin, N s old)`, one
  login across the two jobs (the repeater's own `PUSH_CODE_LOG_RX_DATA`, if you
  capture it, should show one ANON_REQ), `cli 'setperm <key>… 1' try 1: ok`,
  `the repeater answered 'OK'`, `the entry set is this exit node's own: the
  session is now read-only`. `sessions` between the two shows the level moving.
  Then the verify at class `acl`: a blank login answered read-only, `ok`.
- **Read the configuration** on the repeater's page. `jobs` should count **20**
  transactions: the login, `region` and `region default`, thirteen `get`s,
  `ver`, `board`, the access-list request, the restore. The Configuration tab
  fills; `regions` shows the map and its default; the `acl` value lists the
  board's key at **3** in that read (the read's own login put it there) and
  `aclRestored` is `true`; the *next* read's list shows it at **1**. The
  `ver` value is `v1.17.1 (Build: …)` whole, as the .NET stores it.
- **`setperm … 1` as the read's last frame.** `set log.frames on` before the
  read: the last `frame tx txt direct …` before the `frame rx txt` that answers
  it must be the restore, and `log.frames` must show the login frame as hex up
  to the key and then stars. An advert in the same window must still print its
  header line and no bytes.
- **A wrong admin password**: two `login (admin) try N: no reply`, `unreachable`
  - stock firmware answers silence, and the job's page says so.
- **A repeater with an empty guest password**, if there is one to hand: the
  blank login lands at guest, the log says `logged in as guest, but this job
  needs read-only: the repeater accepted the login from this exit node's own
  key at a lower level than read-only`, and the result carries `loggedInAs`
  and `needed`.
- **A night of probes with the association `active`.** Status and telemetry at
  `acl`, neighbours every six hours, the daily read at admin: in the morning
  the association has not moved to `needs-regrant`, the ACL entry is at 1, and
  `sessions` shows a read-only session or none - never an admin one. That is
  the whole point of the restore, and only a night can show it.
- **The heap over that night.** `status` in the morning: `free` and `min ever`
  flat. Every buffer this task added is `.bss`; a moving figure points at
  HTTPClient's chunk buffer, which the `BodySink` change now exercises on every
  call.
- **A `region` listing longer than 159 characters**, on a repeater with a large
  map: the `raw` line about the 160-character buffer and no `regions` value.
  Risskov's map is small, so this may not be provokable there.
- **The console during a config read.** Twenty transactions at two a minute is
  about ten minutes during which the heartbeat cannot go (task 03's note on
  the blocking claim, sharper now); the console and the OLED must stay live
  throughout, and the number to watch is how late the heartbeat after the read
  is. Task 06 owns the fix.
