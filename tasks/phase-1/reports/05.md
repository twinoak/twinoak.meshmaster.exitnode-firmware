# p1-05 — the-writes

The board changes a repeater now. Six job types join the heartbeat's list -
`config.apply`, `cli`, `advert.request`, `clock.sync`, `password.set`, `reboot` -
and with them it advertises all thirteen types of API §3, in `JobTypes.All`'s
order. Every one of the six is **one send per command**: a `set` sent twice is a
change made twice, so no write is ever retried, a reply the mesh ate is recorded
as the silence it was and never resent, and the sender timestamps of an apply
and its re-read are strictly increasing (the RTC's unique second, the one series
every tag and every CLI line of this board already came from). The apply's
*policy* - what goes next, what a reply means, which line goes out even after
the sequence has failed - is a host-portable engine (`src/agent/ConfigApply.h`)
that the native tests run against a fake repeater; the board's runner puts its
lines on the air. A `password.set` sends its restore **after** the password
line and drops its session whatever came back, compares the firmware's echo with
what it sent and records `password now: <set>`, never the value; a `reboot`
sends no restore, says why, and is `ok` as *sent* on the silence the firmware
answers it with. `log.frames on` prints a `password` line and the reply that
echoes it as two hex bytes and stars.

## Deviations from the spec or the task

- **A line is confirmed by what it expects, not by `OK` alone.** The task says
  "stop at the first reply that does not start with `OK`"; the spec as built
  since task p4-57 (and the .NET `ConfigApplyHandler` at today's `master`) has
  a line say what its reply must start with - `OK` for a `set`, `OK - loaded`
  for the blank line, `home is now` and `default scope is now` for two region
  lines that do not start with `OK` - and `null` for a line the firmware
  answers with nothing, which is sent without waiting. Built as the spec says:
  the plan's `lines[].expect` is the rule, `OK` when the plan does not say.
- **The re-read of a `regions` entry that was `not-sent` is not made.** A
  region sequence that fails part-way - a line the packet could not be built
  for, or the lease - is `not-sent` as the .NET handler records it, and a
  not-sent key is not read back. My first test expected the read; the .NET's
  reading is the one kept.
- **The region loader's terminator goes out even past the lease.** Task 03
  decided nothing is sent past a lease. A repeater left in load mode reads
  every later CLI command as a region until a blank line arrives
  (`MyMesh::handleCommand`, `examples/simple_repeater/MyMesh.cpp:1196-1230`),
  which is worse than one packet late, so the escape line waits for the
  airtime budget and ignores the lease, and the job is reported `timeout` with
  its data - the result is the only record of what happened on the mesh.
- **The restore is not sent into a silence**, as task 04 built it, and that
  covers a `password.set` whose line got no reply: the .NET sends the restore
  in a `finally` whatever came back. Here the session is dropped, the log says
  the entry may still be at admin, and the next login from this key - a blank
  login answered admin - restores at once (the third rule of EXIT-NODES §7).
- **A plan this firmware cannot hold fails the job, not the claim.** Task 04
  refused a `config.read` past twenty keys at the parse, which fails the whole
  claim. An apply past sixteen commands, sixty-four lines, a 2 KB text pool, a
  96-character command or a 48-character line is refused inside the job by
  name, and the job is reported `failed` at no transaction with the sentence in
  its log; the other job of the claim runs. A server plan built from the key
  table has at most thirteen commands, and a regions map that still fits the
  firmware's 160-character listing (task p4-57's finding: about twenty
  regions) is under fifty lines.
- **A `clock.sync` on a board with no time is `failed` at no transaction.** The
  .NET agent always has a clock; this board has none until SNTP or a server
  reply answers, and `time 0` would be a refusal at best. The sentence names
  the reason.
- **The reply to a `password` line is starred in the frame log.** On the air
  the echo is ciphertext, so its hex reveals nothing; it is starred all the
  same, because the .NET agent logs that reply "as its code alone" and the
  task asks for the same redaction.
- **The contract fixtures did not change**: both sets were already at today's
  `master` (`f518ebd1`); `tools/sync-fixtures.ps1 -Verify` is the only fixture
  step of this task. The spec sections read at `master` differ from the
  pinned commit only in what tasks p4.3-67 and 68 added (the lease per
  transaction, the daily version read), neither of which is this task's.

## Decisions taken without asking

- **The engine is host-portable and the runner is its exchange.** The
  acceptance criteria name four things a native test must show about an
  apply, and none of them can be shown on a host if the sequencing lives in
  `JobRunner`. So `runConfigApply(plan, exchange, outcome, reRead)` is a pure
  walk over an `ApplyExchange` - one line on the air, the next timestamp, the
  regions read, the log - and `JobRunner::ApplyOnTheAir` is that interface
  over the mesh, the budget and the lease. The fake in the tests models
  MeshCore's `getCurrentTimeUnique()` (`src/MeshCore.h:108-114`: the second,
  or one above the last handed out) and the .NET fake's three silences.
- **One timestamp series.** The engine takes every sender timestamp from the
  exchange, which on the board is `mesh_->uniqueTime()` - the same
  `getCurrentTimeUnique()` every REQ tag and every other CLI line use - and a
  retry of a re-read `get` takes the next one from the same series. A second
  series would have let the restore's `setperm` after an apply carry a
  timestamp below the apply's last line, which the repeater drops as a replay.
- **A line the firmware answers with nothing is one transaction**, as the .NET
  counts it (`OnceAsync` counts the `CliSendAsync` too), and it is given a
  quarter second of the mesh's loop to leave the radio before the next is
  queued, because the loader resolves a line's parent by indent against a
  stack and order matters. At the default budget a forty-line region load is
  therefore about thirteen minutes on the air; the server leases an apply at
  forty seconds a transaction (task p4.3-67).
- **The escape line's own reply changes nothing**, and the .NET's "the
  companion did not send" is "the packet could not be built" here, in the
  reply of a `not-sent` command, because there is no companion between this
  board and the radio.
- **A `cli` command is trimmed and bounded at 120 characters** (`CliPayload.
  MaxLength`); a longer one, an empty one or one with a line break is
  `failed` before anything is sent, as the .NET handler does it. Nothing else
  is judged: the blocked list is the server's, and the firmware sends what it
  is handed.
- **The candidate of an unverified credential logs in afresh.** The claim's
  `credential.candidate` (`new` or `old`, task p4-55) is a word, not a value;
  when it is present the runner drops any session it holds for that repeater
  before the job, and the log says so - the server reads the job's outcome as
  the verdict on exactly that material.
- **The new password is refused at fifteen bytes.** `char password[16]` in
  `NodePrefs` at `d9296435`: a value the repeater would cut is a lock-out, so
  a sixteenth byte fails the job before anything is sent, with the sentence,
  and `JobCredential.newPasswordCut` is the flag the runner refuses on.
- **`password.set` wipes the reply buffer once the echo is compared**, before
  the restore's own reply could overwrite it, and the restore's log line and
  the result never carry it: `password now: <set>` when the echo matches,
  `password now: <a different value>` when it does not (a firmware that cut
  it), the reply verbatim only when it is not the echo at all.
- **A `reboot` is `ok` on silence and on a reply that is not a hard error**, a
  hard error is the one failure, and the session is dropped either way - the
  .NET handler's three cases.
- **`ConfigApplyResult`'s three computed properties are written** - `sent`,
  `ok`, `allOk` - because System.Text.Json writes a record's computed
  properties and the fixture carries them; `CliResult`'s `answered` and
  `isHardError` the same.
- **`driftS` is never sent.** `ClockSyncResult.DriftS` is what a firmware that
  says how far the clock was off would report; this one does not, and the .NET
  handler passes null too. The writer takes it so the fixture (which has one)
  can be matched byte for byte.
- **`transactionsFor("config.apply", …, n)` is `2n + 1`**, `TransactionCosts.For`'s
  arithmetic, and an unknown plan is priced as one command.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and every write here is a
change to a repeater on a mast: nothing below should be tried against a
repeater that is not ten metres away with a cable beside it. With the Heltec
V3 on USB, a terminal at 115 200 baud, and meshmaster.dk's
`tasks/phase-4/FIRST-APPLY.md` in the other hand - `docs/console.md` "The bench
walk" steps 14 to 17 are the same list.

- **`FIRST-APPLY.md` step one through the board (a harmless key).** Untick
  everything but `advert.interval`, confirm. The log: `apply plan <hash>: 1
  command(s), single attempt, stop at the first refusal or silence`, `'set
  advert.interval 120' try 1: ok`, `re-read 'get advert.interval' try 1: ok`,
  `re-read 'ver' try 1: ok`, `applied 1 of 1 command(s) …; re-read 1 of 1
  touched key(s)`, then `restore: cli 'setperm <own key> 1': ok`. `jobs` must
  count **5** (the login, the set, two gets, the restore); the job's page shows
  the reply verbatim and *before → read back*; `get advert.interval` on the
  repeater's console says what MeshMaster says.
- **The refusal** (step two): `set tx 10` from the console is refused by the
  server before any job exists - nothing reaches this board, which is the
  point. Then `set advert.interval 15`: the `cli` job's log says `the repeater
  refused 'set advert.interval 15': Error: interval range is 60-240 minutes`,
  the result carries it verbatim with `isHardError: true`, and the job is
  `failed`.
- **The partial plan** (step three): the desk cannot arrange it (the editor
  refuses every value the firmware would), so the check is that it cannot. If
  a value does get through, write down the firmware's exact words: the whole
  outcome rule here is *starts with `OK`*, and this is the one chance to see
  the real strings.
- **One send per command, on the air.** With `set log.frames on` during the
  apply, every `set` prints exactly one `frame tx txt direct` line, and
  `status`'s `tx` equals what `jobs` counted. That is the rail this task is
  named for, and it is one line to read.
- **The small jobs** (step four): `advert` → `OK - Advert sent`, and `mesh`
  hears the advert within the minute; `time <unix>` → `OK - clock set: HH:MM -
  D/M/Y UTC`, and the repeater's `clock` on its own console agrees, or `(ERR:
  clock cannot go backwards)` recorded as `failed` with the reply. **Reboot**
  only with the cable in: the log says `no restore on this session …` then
  `reboot sent; the firmware does not answer one`, the job is `ok` as *sent*,
  the page says *awaiting the next status read*, and *Read now* confirms it by
  the uptime. Whether a real `_board->reboot()` really leaves this board with
  silence is what the first real reboot shows.
- **A rotation on a test repeater** (never Risskov first): the log order
  `cli 'password <new>' try 1: ok` → `the repeater confirmed the new admin
  password` → `restore: cli 'setperm <own key> 1': ok` → `the session is
  dropped`; `jobs` counts **3** through an acl pair; `sessions` shows none for
  that repeater; the next admin job logs in with the new password. With
  `log.frames on` the `password` frame and its reply print as two hex bytes
  and stars. Then the two silences the fake models - the command eaten, the
  reply eaten - which only a radio can produce: the row goes `unverified` and
  the next admin job's claim carries `candidate`, and this board must log
  `the claim carries the new candidate …: logging in afresh with it`.
- **The transaction counts** against EXIT-NODES §7's rows: an apply of `n`
  commands is `2n + 1` plus the login and the restore; `cli`, `advert.request`,
  `clock.sync` one plus the login and the restore; `password.set` one plus the
  login and the restore; `reboot` one plus the login and **no** restore. `jobs`
  prints them; none has ever been counted on the air.
- **Regions, last** (step five), and only after everything above passed: the
  plan's sequence printed on the apply panel is what goes out, one line every
  budget gap, the silent lines logged `sent (direct), no reply expected`, the
  blank line answered `OK - loaded N regions` with N equal to the plan's
  count. The three things only a radio can settle are task p4-57's: whether the
  lines arrive in order, whether a lost region line is common, and how big a
  real Danish map is. A repeater whose `region` listing fills the 160-character
  buffer cannot have its regions applied at all, and the tab says so first.
- **The heap over a day of writes.** `status`'s `free` and `min ever` should
  not move: every buffer this task added is `.bss`. The claim body is 6 KB now
  and is read through the same `BodySink`; a moving figure points at
  HTTPClient's chunk buffer, as in task 04.
- **The console during a long apply.** A forty-line region load at the default
  budget is about thirteen minutes during which the heartbeat cannot go (task
  03's note, sharper again); the console and the OLED must stay live
  throughout. Task 06 owns the fix.
