# p1-06 — a-node-that-stays-up

The board keeps itself alive now. A task watchdog sits on the loop that is also
this firmware's network task, fed through every wait a job takes so that a
thirteen-minute region load is not mistaken for a wedged one and a TLS call
that never returns is. What the server was away for is kept in RAM — the
observation ring as before, and a new bounded buffer of job results, oldest
dropped and counted, posted late with the bytes and the client ids they were
written with. A job whose lease ran out before it started is not put on the air
at all: the server has given it back to the queue, and a transaction for
somebody else's lease is worse than none. Both retries of this firmware — WiFi
and server — back off on the same doubling sequence with **jitter** on the
wait, so a houseful of boards that lost the same router do not come back at the
same second, and the OLED's third line says which of the two is missing. After
twelve consecutive unanswered calls *with the link up* — about an hour and a
half — the board restarts itself, having written why into RTC memory first;
`reboots` prints the last five reasons, `errors` prints every counter the
heartbeat carries, and `dump` prints the last four kilobytes of the log, which
is the same bytes the port already printed. And there is a second board:
`heltec_v4`, with MeshCore's board definition vendored (a consumer of the
package cannot point `boards_dir` inside one) and a transmit power of 10 dBm,
because the V4's power amplifier makes that 22 at the socket.

## Deviations from the spec or the task

- **"The task watchdog on the main loop and the network task" is one task here,
  and that is the honest reading.** This firmware has one thread: the Arduino
  loop task runs the mesh, the console, the OLED *and* every HTTPS call to
  meshmaster.dk. There is no second task to watch, and creating one (a network
  task, or the radio on its own) is a re-architecture, not a watchdog. So the
  watchdog is on that task, at 90 seconds — past the worst legitimate call
  (a 30 s handshake, a 10 s connect, a 15 s read) and nowhere near a job's own
  waiting, which feeds it. The report says so rather than pretending there are
  two.
- **The bounded number of consecutive failures is counted only against a live
  WiFi link.** The task says "a reboot on a wedged TLS stack after a bounded
  number of consecutive failures". A router that is off is not a wedged stack
  and a reboot does not fix one, so the count is of calls that failed while
  `wifi.connected()` — which is the condition under which "the stack is wedged"
  is the remaining explanation. Twelve of them is about an hour and a half at
  the backoff.
- **The heartbeat now goes from inside a long job.** Not in the task's
  deliverables, but tasks 03, 04 and 05 each ended by handing it here: a claim
  is run to the end before `claimAndRun` returns, so a `config.read` of twenty
  transactions at two a minute is ten minutes and a region load is thirteen,
  during which the heartbeat could not go and the exit node's page said *quiet*
  and then *offline* while the board was working perfectly. `online` is a
  heartbeat within three poll intervals (EXIT-NODES §10), which at the server's
  own 30 s is 90 seconds — so *every* multi-transaction job used to take the
  board off the page. The job's own waits are where the time is, so the pump
  that keeps the console and the OLED alive through them sends the heartbeat
  that is due, and only that: no claim and no observation batch happen inside a
  job. `StayingUp.TheHeartbeatGoesFromInsideALongJob` holds that shape.
- **The Heltec V4's transmit power fallback is 10 dBm, not 22.** The task asks
  for the V4 target; a target whose default output is 12 dB over what the board
  is meant to emit is not one. MeshCore's `variants/heltec_v4/platformio.ini`
  sets `LORA_TX_POWER=10` with the comment *"If it is configured as 10 here,
  the final output will be 22 dbm"*, and `variants/heltec_v4/LoRaFEMControl.cpp`
  turns the external amplifier on for every transmission
  (`setTxModeEnable`). So `radio.tx`'s fallback is a compile-time define
  (`MESHMASTER_TX_DBM_DEFAULT`, 22 for the V3 and the host build, 10 for the
  V4); the *range* is unchanged, because `MAX_LORA_TX_POWER` is 22 on both.
  This is the only setting whose default is the board's rather than the
  channel's, and `docs/field.md` §9 says so to whoever carries a board out.
- **The spec read at today's `master` (`9fb3661`) agrees with the task.**
  EXIT-NODES §5 and §10 and `docs/ops/agent.md` say what this task built:
  "offline is normal", results buffered and posted later with their original
  timestamps, leased jobs whose lease expired still reported, the board's
  offline buffer a RAM ring and not a journal, and `online`/`quiet`/`offline`
  derived against the poll interval. Nothing in them contradicts the task file.
  `docs/ops/exit-node-field.md` is the *Pi agent's* field page and is about the
  agent→companion cable, which a board does not have; `docs/field.md` here is
  the board's equivalent and says so rather than duplicating it.

## Decisions taken without asking

- **The result buffer is a byte arena with an index, not a ring of fixed
  slots.** Results are 300 bytes to 6 KB depending on the type, so eight slots
  of `kBodyCap` would be 53 KB of RAM for a queue that is almost always empty.
  Twelve kilobytes and eight entries costs 12 KB and holds two of the largest
  results this firmware writes, or a dozen small ones — and the realistic depth
  is **two**: a claim hands over at most `kClaimMax` jobs and a claim only
  happens after a heartbeat the server answered, so results pile up only for
  the jobs that were already running when it went away.
- **A result larger than the whole arena is refused and counted as a drop.**
  Dropping everything else to make room for one result that cannot fit would
  lose more than it saves; nothing this firmware writes is that large anyway
  (`kBodyCap` is 6.6 KB).
- **The offline buffer is posted before the claim and after the heartbeat**,
  which is the order `docs/ops/agent.md` §4 gives in as many words. It is also
  the order `post()` uses inside a claim, so the server never sees a job's
  results out of order.
- **A lapsed lease is refused inside `runJob`, not in `claimAndRun`.** It keeps
  the anchor `Outcome outcome = runJob(job, ctx, dataLen);` that task 04's
  credential test holds, and it puts the decision where every other "can this
  job run at all" decision already lives, one line above `canRun`.
- **The jitter is ±25 % of the step, and the step is unchanged.** Full jitter
  (a wait uniformly between zero and the step) would spread the herd further
  but makes the log unreadable and the first retry sometimes instant; a quarter
  either way is enough to break a synchronised houseful and the log still says
  both numbers (`next attempt in 88 s (the 120 s step, jittered)`). The
  sequence itself stays the documented 30/60/120 … so the existing tests and
  `docs/console.md` remain true.
- **`dump` prints the ring through a callback, not into a buffer.** Four
  kilobytes printed from a four-kilobyte copy would be eight; the ring hands
  its one or two runs straight to `Stream::write`.
- **The log ring drops the first partial line.** After a wrap the oldest bytes
  are the tail of a line whose beginning is gone; printing it would put half a
  sentence at the top of every `dump`. The first byte printed is the one after
  the first newline.
- **The reboot log is five entries in RTC memory with no magic beyond a
  version word.** RTC slow memory survives a software reset, a panic and a
  watchdog reset and is cleared by a power cut, which is exactly the
  distinction a person at the board wants: *this board crashed* versus *this
  board lost power*. `reboots` says which. The struct is plain data with no
  initialisers, because `RTC_NOINIT_ATTR` means "do not touch this at boot".
- **`healthTick()` refreshes the clock and the uptime in RTC memory every
  pass**, so a crash entry can be timed: the panic handler cannot write the
  log, but the last tick before the crash is within a loop of it.
- **The heartbeat's two new counters are `resultsDropped` and `reboots`**, the
  camelCase the other four use, and `reboots` counts only the restarts this
  firmware asked for — a power cut or somebody pulling the USB cable is not an
  error of this board's. The count lives in RTC memory so it survives the
  restart it counts.
- **The OLED says `no wifi: no server` rather than `no wifi`.** Line one
  already has the link's own detail; line three is the exit node's line, and
  when the link is down both are missing, which is what somebody standing at
  the window needs to be told in one glance.
- **`reboot` on the console notes its own reason** (*asked for on the
  console*), so `reboots` after a deliberate restart does not report a
  mysterious `Software reset`.
- **The V4 environment takes MeshCore's `heltec_v4_oled` flags**, not the TFT
  or the bare variant: the OLED is what `src/ui/Oled.cpp` draws on and what
  `docs/field.md` describes. A V4 with the TFT would be a third environment and
  is not this task's.
- **The V4's Arduino *variant* directory is not vendored**, only the board
  JSON. `-I ${meshcore.dir}/variants/heltec_v4` puts its `pins_arduino.h` on
  the include path (which is how MeshCore reaches its own — its board JSON
  names a variant the framework does not ship either) and `MC_VARIANT` compiles
  its sources into the MeshCore library through upstream's `build_as_lib.py`.
  So the one thing copied is the one thing that cannot be referenced.

## Not verified here (and why)

A session cannot flash a board, hear a radio, pull a power lead or wait a week.
Everything below is Thomas's, with `docs/field.md` open — §5 and §6 of that
page are the same list in the order a person would walk them, and
`docs/console.md`'s bench walk step 18 is the short form.

- **The watchdog, which has never fired.** The one thing that cannot be
  rehearsed from a desk: that `esp_task_wdt_init(90, true)` plus
  `esp_task_wdt_add(nullptr)` on the loop task really panics and reboots, and
  that the board then comes up with `reboots` saying *Task watchdog reset*
  timed from the last tick. A `while (true) {}` typed into `doReboot` for one
  build would prove it in ninety seconds; it has not been done here because
  the image that ships should not be the one with the loop in it.
- **RTC memory across the four resets.** `reboots` after (a) `reboot` on the
  console — *asked for on the console*; (b) the RST button — the board's own
  name for it; (c) a re-flash — the log should survive, because a flash is a
  software reset; (d) pulling the USB cable — *log empty: the RTC memory did
  not survive*. That last one is the one that proves the other three mean
  something.
- **The deliberate reboot.** Point `meshmaster.url` at a host that accepts TCP
  and never answers (or block the server at the router with the WiFi still up)
  and leave it an hour and a half: twelve `server: next attempt in …` lines
  with the steps 30, 60, 120, 240, 480 and then 600, each *jittered* by up to a
  quarter, then a restart whose reason is `12 server calls in a row got no
  answer, with wifi up`. Then put the server back and check the next heartbeat
  carries `reboots: 1`. **Pull the WiFi instead and it must never reboot** —
  that is the other half of the condition and the more important one.
- **The buffers under a real outage.** With a job in flight, pull the router's
  uplink: `jobs` shows the result under `buffer`, `server` shows the ring
  filling, and the log backs off. Put it back: `jobs: N result(s) that waited
  went through`, the job's row on the server fills in and the page says the
  result was late. Then leave it down long enough to overflow — 64 adverts at a
  busy window is minutes, eight results is longer — and check
  `observationsDropped` and `resultsDropped` on the exit node's page match what
  `errors` says.
- **A lapsed lease on a real claim.** The desk cannot arrange one. The way to
  provoke it is a `config.read` of the default list (twenty transactions, ten
  minutes at the default budget) claimed together with a second job: the second
  should be reported `timeout` at **0 transactions**, with
  `the lease ran out before this job started` in its log and no frame on the
  air for it — `log.frames on` and `status`'s `tx` are the check. The server's
  side of it is that the job comes back to the queue and is re-routed.
- **The heartbeat during a long job.** The change that matters most for the
  page: run a `config.read` of the default list and watch the exit node stay
  **online** throughout, with `server` showing heartbeats continuing at the
  poll interval while `jobs` counts transactions. Before this task it went
  quiet. The number to write down is how much the heartbeat's own few seconds
  push the job's transactions apart — it should be none, because it happens
  inside a wait that was going to be spent waiting.
- **The OLED's third line, in all four states.** `no wifi: no server` with the
  router off, `no server: retry Ns` counting down with the router on and the
  server blocked, `hb HH:MM · N adverts` normally, `token revoked/wrong` after
  a revoke. And that the button still wakes the display through all of it.
- **`dump` on a board that has been up a week.** That four kilobytes really is
  about fifty lines, that it starts at a line boundary, and that nothing in it
  is a secret. Read it once with `log.frames on` having been on for a while —
  that is the log level that puts the most in the ring, and the frame lines are
  where a redaction bug would show.
- **The heap over the week.** `status`'s `free` and `min ever` should be flat:
  the 16.6 KB this task added is `.bss` and nothing new is on the heap.
- **The Heltec V4, end to end.** Nothing about that board has been on a bench
  from this repository. In order: flash `heltec_v4`'s merged image; `status`
  must say `board heltec_v4` and `tx 10 dBm`; the OLED must come up on the same
  I²C pins (`PIN_BOARD_SDA=17`, `SCL=18`, `PIN_OLED_RESET=21` — the reset pin
  is new on this board and is the likeliest thing to be wrong); the user button
  on GPIO 0; the radio's `P_LORA_RESET=12`, which the V3 does not have. Then
  hear an advert, register it as a second exit node and check the page says
  *onboard · Heltec V4*. **Measure the output** if there is anything to measure
  it with: 10 dBm at the chip should be about 22 at the socket, and if it is
  not, `radio.tx` is the knob and `MESHMASTER_TX_DBM_DEFAULT` is where the
  default lives.
- **A week at the window**, which is phase 1's exit criterion and the one
  nobody can shorten. `docs/field.md` §8 is the list to read on the seventh
  day.
