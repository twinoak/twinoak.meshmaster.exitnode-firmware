# p1-03 — the-read-jobs

The board claims and answers jobs. A heartbeat that says `jobsWaiting` is
followed by `POST /agent/v1/jobs/claim {"max":2}`, and every job it hands over
runs on the air at the budget's pace and posts its result: `status`,
`telemetry`, `neighbours`, `trace`. `jobTypes` in the heartbeat is those four
and nothing else, so routing sends nothing else.

Each handler is a direct call into MeshCore's mesh layer — a blank-password
login as ourselves, `REQ_TYPE_GET_STATUS`, `REQ_TYPE_GET_TELEMETRY_DATA`,
`REQ_TYPE_GET_NEIGHBOURS`, `REQ_TYPE_GET_OWNER_INFO` and a trace packet — and
the reply arrives in `onPeerDataRecv`, `onPeerPathRecv` and `onTraceRecv`. The
bytes those replies carry are parsed by `src/mesh/ReplyCodec.cpp`, which is
held to the **transcribed frames of meshmaster.dk** (a second fixture set,
copied here by the same script as the contracts), and the result JSON is held
to the .NET agent's bytes.

## Deviations from the spec or the task

- **`BaseChatMesh` is not used, and the reply does not arrive in the callbacks
  `MyMesh` has.** The task says each handler is "a direct call into MeshCore's
  mesh layer — the same functions the companion firmware runs when a phone asks
  — and the reply arrives in the callbacks `MyMesh` already has". The functions
  are `BaseChatMesh::sendLogin`, `sendRequest` and the companion's
  `onContactResponse`; deriving from `BaseChatMesh` to get them would bring its
  contact table (350 slots), its forty channels, its sixteen connections, and —
  the reason this is a deviation and not a preference — **four code paths that
  put a packet on the air by themselves**: the message ACK, the signed-message
  ACK, the reciprocal path return and the path-return retry. This firmware
  sends one packet per transaction and nothing else, and the cheapest way to
  keep that true is not to compile the paths that would break it. So
  `AgentMesh` stays a `mesh::Mesh` and the four calls are written out of
  MeshCore's own primitives — `createAnonDatagram`, `createDatagram`,
  `createTrace`, `sendDirect`/`sendFlood` — which is what `BaseChatMesh`'s two
  senders are made of, three lines each; the replies arrive in `Mesh`'s own
  `onPeerDataRecv`, `onPeerPathRecv` and `onTraceRecv`, which is the layer the
  companion's `onContactResponse` is called *from*. `docs/upstream.md` has the
  table a bump re-reads.
- **`log.frames on` prints the frames of a job as hex, and no others.** The
  task says "prints every mesh frame as hex on the console — with the same
  redaction the .NET agent's `--log-frames` has, and never a message's text".
  Two kinds of frame cannot be printed as hex without breaking a rail task 01
  and task 02 set: an **advert** carries a stranger's name in clear (task 02
  decided a name is read on demand with `mesh` and never logged), and the mesh's
  own **chat** is other people's conversation, counted and dropped unread. Both
  keep the header line they had. What is printed as hex is a job's own frames,
  both directions — the login, the request, the reply, the trace — which is what
  the .NET agent's `--log-frames` exists for (a capture), and the payload of
  every one of them is ciphertext on the air anyway.
- **A job whose credential class needs a password is answered `unsupported` at
  no transaction.** The claim is atomic and the server decides the class, so a
  `guest`- or `admin`-class job can arrive at a board whose whole repertoire is
  a login carrying its own key. It is recognised before anything is sent and
  reported `unsupported` with a sentence, which is the outcome that means "this
  firmware does not have what the job asked for" and — the reason it is not
  `failed` — the one outcome that moves **nothing** in the server's reachability
  (EXIT-NODES §3), which is right for a transaction that never happened. Task
  04 is where the class stops being refused.
- **At class `acl`, a key the repeater's ACL does not hold reads as
  `unreachable`, not `unauthorized`.** Stock firmware answers a login it will
  not take with silence (`handleLoginReq` returns 0 at `simple_repeater/
  MyMesh.cpp:110`), so two tries and nothing back is all the board can see, and
  it cannot tell that from a repeater that is off the air. The .NET agent
  behaves the same way against a real radio — its `unauthorized` at that class
  comes from the fake companion, which answers a refusal that stock firmware
  never sends. `unauthorized` is reported here only when the repeater *answers*
  something that is not a login-ok, or answers below the class the job asked
  for, and then the tier travels in `LoginBelowClassResult` as task p4.1-60 asks.
- **A trace result carries the whole round trip and this board's own hash**, not
  the outward half. That is what the .NET `TraceHandler` posts (every hop of
  `trace.Path`, then `HashOf(self)` with the final SNR), and the server takes
  the outward `(count - 1) / 2` from it when it stores reachability (task 24).
  Halving it here would throw away the SNR of the return legs, which is a
  measurement and not an artefact.
- **The contract fixtures' recorded commit moved** from `71ba9a6e` to
  `f518ebd1` (today's `master`), because the companion set had to be fetched
  from a commit and the two sets are synced together. **No contract fixture's
  bytes changed**; only `MANIFEST.txt`'s source line did.
- **`tools/sync-fixtures.ps1` grew a second set.** It had a `-SourcePath`
  parameter that nothing read; it now has `-Set contracts|companion|all` and a
  `MANIFEST.txt` per directory, and `-Verify` (which CI runs) checks both.

## Decisions taken without asking

- **A claim takes two.** `{"max": 2}` is the task's own number and it is the
  right one for a board: one transaction is on the air at any moment anyway,
  and two is the `status`+`telemetry` pair the server schedules in one slot and
  claims together. A claim happens once per heartbeat that said work was
  waiting, so a queue of six is drained over three intervals rather than in one
  burst — which is also what the budget would have done.
- **The lease bounds the job's work, and a slot past it is not taken.** Before
  every transaction the runner asks the budget how long until the next one may
  go; if that lands past `leaseUntil` the job stops there and is reported
  `timeout`, which is what the .NET runner reports when its lease cancellation
  fires. The air is better spent on the next job than on one the server has
  already moved on, and the result is still posted.
- **The session cache is what makes a claimed pair one login**, and
  `groupWith` is read, logged and otherwise not needed: the cache is keyed by
  the repeater's public key, so two jobs for one repeater share a session
  whether or not the server grouped them. Ten minutes of lifetime, the .NET
  agent's own default (`AgentOptions.SessionLifetimeSeconds`); four slots, which
  is more than a claim of two can use.
- **A RESPONSE, a PATH or a TRACE reaches MeshCore's dispatch only while a job
  is waiting for its reply**, and only from the one peer whose hash matches
  (`searchPeersByHash` answers for that key alone). Outside that window they are
  released with everything else, so no ECDH is ever calculated for a stranger —
  which is task 02's property kept rather than given up. `onPeerPathRecv`
  returns **false**: the path it taught is kept and used for the rest of the
  job, and no reciprocal path is sent.
- **Six pages of neighbours, 54 entries.** The firmware answers nine a page and
  each page is a transaction; a repeater with more zero-hop neighbours than this
  is not one an exit node's budget should be paging through, and the result says
  how many it has so the server can see the difference. A page that never comes
  back after some already did is still a reading: what was heard is reported
  rather than nothing.
- **One pending result, kept and retried.** A result whose POST did not get
  through keeps its `clientId` and is sent again before the next claim; the
  server de-duplicates on that id and takes a late result anyway (API §3), so
  retrying costs nothing and losing a reading costs a transaction. That one
  pending result is the heartbeat's `queueDepth`, which is therefore 0 or 1.
- **The job's log is a kilobyte and keeps its tail**, and the envelope bounds it
  again at the 4 000 characters API §3 allows, from the end — what a job did
  last is what a reader of its page wants. Nothing that could need redacting
  ever reaches it: this firmware holds no password.
- **The runner blocks, and pumps the console through it.** A board has one
  thread; a transaction is a send and up to sixteen seconds of waiting, and the
  budget's gap is twenty more, so a `status`+`telemetry` pair at the default
  budget is about forty seconds during which the heartbeat cannot go. The
  console, the OLED and the clock are pumped throughout, so the board is still
  one a person can type at, and the mesh is pumped by the wait itself so adverts
  are not missed. Task 06 ("a node that stays up") is where a second task or a
  kept-alive connection belongs; this is noted there as it was in task 02.
- **`clientId` is `<jobId>-<32 hex>`**, the shape `$"{job.Id}-{Guid.NewGuid():N}"`
  gives on the .NET side.
- **Eight-byte neighbour prefixes, newest first.** The prefix length is the
  agent's own (`NeighboursHandler.PrefixLen`), and it is what makes nine a page:
  a reply carries 126 bytes and a row is 13 of them.
- **The JSON writer moved to a header of its own** (`src/agent/JsonWriter.h`)
  rather than being copied: three files now write envelopes with it, and the
  bytes the fixtures hold are made in one place.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and **every one of these needs a
real repeater**: nothing in this task can be proved against anything but the
firmware's own source until a job goes out over the air. With the Heltec V3 on
USB, a terminal at 115 200 baud, and a repeater the exit node is associated with
— `docs/console.md` "The bench walk" steps 8 to 10 are the same list.

- **The association.** Associate Risskov with the board's key on meshmaster.dk
  (the wizard, as with the Pi). The grant is an `acl.set`, which is task 05's,
  so it has to be made from the Pi or by hand for now — this board cannot send
  the `setperm` that creates its own entry. Until the key is in the repeater's
  ACL, every `acl`-class job here is two silent logins and `unreachable`; that
  is the deviation above, and it is the first thing to check.
- **Read now.** On the repeater's page, press **Read now**: within a poll
  interval the log shows `jobs: 2 claimed`, a line per job and
  `job <id>: ok after N transaction(s)`, and the readings are on the page. The
  four job types each `ok` at least once is the phase's exit criterion.
- **The transaction counts against EXIT-NODES §7.** `jobs` on the console
  prints them: a `status`+`telemetry` pair at class `acl` must be **4** (one
  login, two status requests — the reading and the owner info — and one
  telemetry), a `neighbours` read one plus one per nine neighbours, a `trace`
  one and no login. `status`'s `tx` must equal the sum of what `jobs` counted,
  because one packet per transaction is the rail — a larger `tx` is the bug this
  is here to catch.
- **The SNR the board hears against the Pi's.** The same repeater read from
  both: `lastSnr` in the status result and the per-hop SNRs of a trace should
  agree within a dB or two, and a large difference is an antenna or a placement
  finding rather than a firmware one.
- **The firmware version.** An `acl`-class status read costs the second,
  owner-info request and the result's `firmware` field should be `v1.17.1` from
  a repeater at the pin. If it is absent, the second request went unanswered and
  the log says so.
- **A trace with and without a path.** With no path known the job is
  `unreachable` at **no transaction** and the log says *run discover first*;
  after a `discover` from the Pi teaches one, the trace returns the round trip
  and the page's per-hop SNR chart fills. A companion built for three-byte path
  hashes would be `unsupported`, which this board cannot provoke — its own
  `PATH_HASH_SIZE` is 1.
- **The budget's pace.** At the default 2 a minute with a 20 s gap, a claimed
  pair takes about forty seconds and `jobs` shows the seconds waited. Raise the
  budget on the exit node's page and watch the next claim run faster; the
  console must stay usable throughout (that is the pump).
- **A result the server did not take.** Pull the uplink while a job runs: the
  result is kept, `jobs` says *(not posted)*, `server` shows
  `queueDepth` 1 in the next heartbeat, and it goes through on the next claim.
- **`log.frames on` during a job.** The login, the request and the reply should
  each print one `frame tx`/`frame rx` line with the bytes; an advert in the
  same window must print its header line and **no bytes**. That is the rail, and
  it is the one thing here a person can check in a minute.
- **The heap over an hour of jobs.** `status` after an hour: `free` and
  `min ever` flat. Everything this task added is `.bss`, so the figure should
  not move at all; if it does, the suspect is `HTTPClient`, not the runner.
- **A repeater that is off the air.** A job for one: two logins, silence,
  `unreachable`, three transactions at most, and the server re-queues it for the
  next exit node rather than failing it.

One thing worth saying that is not a bench item: **a claim blocks the
heartbeat**. `claimAndRun` runs every job of the claim before it returns, so at
a budget of two a minute a pair of jobs can push the next heartbeat a minute
late. The server measures health against the interval it last answered
([EXIT-NODES §10](https://github.com/twinoak/meshmaster.dk/blob/master/spec/EXIT-NODES.md#10-exit-node-lifecycle-and-health)),
so a claim that takes longer than the poll interval is visible there. Task 06 is
where that belongs; the number to watch on the bench is how late the heartbeat
after a claim actually is.
