# p1-01 — the-board-speaks

The build is ours now. `src/` is an application - a serial console with its
settings in NVS, WiFi with backoff, SNTP with the server's time as the
fallback, an HTTPS client that verifies meshmaster.dk's chain against a bundled
ISRG Root X1 and makes `GET /agent/v1/config` with the token, an OLED, and the
mesh in companion role with an identity and nothing sent - and MeshCore's stock
companion example is no longer built. Three decisions every later task
inherits are written down in the code that makes them: where the token lives
(`src/settings/Store.h`), how the server's certificate is checked
(`src/agent/AgentClient.h`), and what the serial console will and will not
print (`src/Log.h`, `src/console/Console.h`).

## Deviations from the spec or the task

- **"With the chain verified against a bundled ISRG Root X1 *and* the core's certificate bundle."** The arduino-esp32 2.0.17 client verifies against one or the other in a handshake (`ssl_client.cpp` takes a root PEM before it looks at the bundle), not both at once. So: ISRG Root X1 first, always; if and only if the handshake fails with `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` (-0x2700, the chain no longer ends at X1), the same call is retried once against the core's bundle, the choice is remembered for the session, and `status` prints which root verified. Both are verification. Today's live chain (`meshmaster.dk ← YR1 ← Root YR ← ISRG Root X1`, checked with `openssl s_client` on 2026-09-28) verifies against X1 alone. The bundle is the one `libmbedtls.a` of the framework carries (`_binary_x509_crt_bundle_start`, ~64 KB, the Mozilla roots as of the core's 2024 release), reached by its link symbol; nothing is vendored.
- **`grep ... of the tree finds only the test that forbids it`** is met for code and cannot be met literally for `tasks/`: the task file itself quotes the grep. See the checklist item.
- **`AgentConfig` is not among the contract fixtures**, so its parser is held to the record in `Envelopes.cs` rather than to bytes the .NET test wrote. If `MeshMaster.Contracts` ever adds a round-trip fixture for it, `test_config_reply` should read that file instead of its inline sample - a one-line change, noted here for the other repository.
- **The firmware string.** The task writes it as `meshmaster-agent <version>+<sha> on MeshCore <tag>`; `MESHMASTER_AGENT_VERSION` already is `X.Y.Z+<sha7>` in a release build (the bootstrap's `release.yml`) and `0.0.0-dev` locally, so the string is `meshmaster-agent <that> on MeshCore <tag>` with no second `+<sha>`. The MeshCore tag and pin reach the code as `MESHMASTER_MESHCORE_TAG` / `_PIN` defines interpolated from `[meshcore]` in `platformio.ini`, so a bump moves them by itself; `status` prints the tag and the first eight characters of the pin.
- **Three companion-example defines left the flag block** with the example: `BUILD_EXAMPLE`, `MC_UI_FLAVOR` and `ENABLE_USB_INTERFACE` (the example's serial companion interface, which would only mislead). `MAX_CONTACTS`/`MAX_GROUP_CHANNELS` stay - harmless, and MeshCore's own. `densaugeo/base64` stays too, corrected in its comment: `build_as_lib.py` compiles every `helpers/*.cpp`, and `BaseChatMesh.cpp` includes it whether the application uses it or not.

## Decisions taken without asking

- **The token lives in NVS**, namespace `meshmaster`, key `mm_token`; the passphrase beside it as `wifi_pass`. NVS keys are 15 characters at most, so the console names (`meshmaster.token`) map to short NVS keys in the table. The WiFi driver's own habit of persisting credentials in its NVS namespace is turned off (`WiFi.persistent(false)`), so there is one copy on flash. Flash encryption is documented as the owner's choice (`docs/console.md`), not assumed. For the call, the token goes NVS → a stack buffer → the `Authorization` header and the buffer is wiped; `HTTPClient` keeps its own copy of the header line until `end()`, which is the one copy this code cannot wipe - the same shape as the .NET agent's `HttpClient`.
- **What the console echoes.** Typed characters are echoed (a terminal with local echo off is usable), except that once a line begins `set wifi.pass ` or `set meshmaster.token ` the value echoes as asterisks. `set` answers `ok <key>` and never the value; the log has no redactor because nothing that could need one is ever an argument.
- **`log.frames on` means a header line per received frame** - payload type, route, hop count, payload length, SNR, RSSI - and never a payload byte, hex or text. The .NET agent's `--log-frames` is a capture file of companion frames; a board has no file and the rail says no text, so this is the board's version of it. Frames of the mesh's own chat are counted under their type (`status` shows `grp-txt`, `txt`) and dropped unread.
- **`erase confirm` forgets the settings and keeps the identity.** The server holds the companion key; a new key would flag the exit node as *companion changed* and suspend admin routing (SECURITY §6), which is not what "forget my WiFi" should do. The word is `confirm`; `erase` alone says so.
- **A `set` takes effect at once**: `wifi.*` drops and rejoins, `meshmaster.*` re-reads the URL and token and calls the server again, `radio.*` reprograms the SX1262 (`setParams`/`setTxPower`, as the companion does live on `CMD_SET_RADIO_PARAMS`), `log.*` applies. No reboot is part of provisioning.
- **Value rules.** `meshmaster.url` must start `https://` and be `host[:port][/path]` in URL characters; a trailing slash is stripped before `/agent/v1/config` is appended. `meshmaster.token` must start `mma_` and be base64url after it (API §3 as built: the server's prefix), 12..128 characters. `wifi.pass` is 8..63 characters; **an open network is joined when `wifi.pass` is unset**, with a warning. `wifi.ssid` may contain spaces (the value is the rest of the line, trimmed). Radio ranges are MeshCore's (`MyMesh::begin`'s `constrain` calls): 150..2500 MHz, 7.8..500 kHz, SF 5..12, CR 5..8, -9..22 dBm; the fallbacks are the Danish channel 869.618 / 62.5 / 8 / 8 / 22. Lines over 200 characters, control characters and non-ASCII are refused.
- **The clock.** SNTP against `0/1/2.pool.ntp.org`, UTC, started on every WiFi connection. "No time" is a clock before 2025-01-01 (MeshCore's `ESP32RTCClock` starts at 15 May 2024 on a power-on, and a software reset keeps the time, which `status` reports as `(rtc)`). The config reply's `serverTime` sets the clock when there is no better source and it disagrees by more than five seconds - the .NET `AgentClock`'s tolerance; once SNTP has answered it wins, and a server time more than five seconds off is logged and not taken.
- **The config call** runs once per WiFi connection, 1.5 s after the link comes up, and on failure is retried with backoff (30 s doubling to ten minutes). Task 02's heartbeat loop replaces this schedule. The call is blocking (a few seconds cold); the console waits.
- **The radio failing to initialise does not halt the board** (MeshCore's example halts). The console stays up, `status` says `radio init failed`, no identity is made (the identity comes from radio noise, as in `radio_new_identity()`), and the next boot tries again.
- **MeshCore's headers are system headers for our `-Werror` build**, through `src/mesh/MeshCoreHeaders.h` and its `#pragma GCC system_header`. `-isystem` was tried first and cannot be used: PlatformIO passes MeshCore's directory with `-I`, GCC then drops the `-I` and searches it after every other `-I`, and the ESP-IDF tree's `bt/esp_ble_mesh/mesh_core/mesh.h` shadows `Mesh.h` on Windows' case-insensitive file system. `#warning` directives are reported from system headers all the same (RadioLib's "God mode active", present in every MeshCore build), so `-Wno-error=cpp` keeps that one a warning; every other warning in `src/` is still an error.
- **Two libraries pinned that were floating.** `Adafruit SSD1306` and `Adafruit GFX Library` arrived transitively in the bootstrap build; `src/ui/Oled.cpp` and MeshCore's `SSD1306Display.cpp` draw on them, so they are pinned at the versions the bootstrap had resolved (below).
- **The native env compiles four files of `src/`** (`test_build_src = yes`, `build_src_filter` names them) and gets `ArduinoJson` and `PROJECT_DIR`; the rest of `src/` needs a board.
- **The OLED** uses MeshCore's `SSD1306Display` from the variant and its `MomentaryButton` on GPIO 0 (PRG); on for five minutes after boot or a press, then off; a 1 Hz refresh while on. Line four is `id <8 hex>  agent`.
- **Docs.** `docs/console.md` is the command and key reference, what the port prints and does not, the OLED, and the bench walk; `README.md` has the flashing lines (`pio run -t upload`, the `esptool.py ... write_flash 0x10000 firmware.bin` line for CI's artifact, the merged image at `0x0` for a release), the provisioning session the test replays, and the rails. `docs/upstream.md` now says the examples are not built and where our sources reach MeshCore's headers.

## Not verified here (and why)

A session cannot flash a board or hear a radio; everything below is Thomas's,
with the Heltec V3 on USB and a terminal at 115 200 baud. `docs/console.md`
"The bench walk" is the same list with what to look for.

- **Flash and boot.** `pio run -e heltec_v3 -t upload`, then the banner
  `meshmaster-agent 0.0.0-dev on MeshCore companion-v1.17.1`, `type 'help'`,
  the `>` prompt. The OLED shows four lines. `status` shows a 64-hex identity,
  the radio line with the Danish channel, `wifi off`, `no time`,
  `server not configured`, a heap figure.
- **Provision**, as the README session: `set wifi.ssid`, `set wifi.pass`
  (asterisks on the echo), `set meshmaster.url https://meshmaster.dk`,
  `set meshmaster.token` with a token from `/exit-nodes/new`. Watch
  `wifi: connected`, `clock: ... from sntp`, `server: GET ...`,
  `heap: N free after the call`, `server: config ok: agent <id> "<label>",
  transport onboard ...`. The OLED's third line becomes `config ok HH:MM:SS`.
- **The heap after the TLS handshake**: the `heap:` log line and `status`'s
  `after the tls call N` - the number every later task budgets from. Note it
  in the review.
- **The root**: `status` says `root ISRG Root X1`. The fallback to the core's
  bundle cannot be provoked without a server whose chain does not end at X1;
  a `set meshmaster.url https://<some other https host>` shows what a chain the
  bundle verifies but X1 does not looks like (`the certificate chain did not
  verify against ISRG Root X1; trying the core's bundle`, then an HTTP status
  from that host).
- **A wrong token** → `server: http 401`, the OLED `http 401`, `status` the
  same with the time; a missing header is the server's 400.
- **WiFi backoff**: pull the router's uplink or change `wifi.pass` to a wrong
  one: attempts every 5, 10, 20, 40 ... s up to five minutes, the OLED
  `wifi: retry Ns`; then the link comes back by itself when the network does.
- **NTP blocked** (UDP 123 dropped at the router, then reboot): `no time`
  through the WiFi join, then `clock: ... from the server (corrected by ... s)`
  on the config reply.
- **`wifi`** lists networks with channel, RSSI, security; **`erase confirm`**
  forgets the settings and a reboot shows the same identity; reflashing keeps
  both settings and identity.
- **Frames**: after an hour at a window, `status` shows `rx N (advert ...)`
  and **`tx 0`**; `set log.frames on` prints one header line per frame and
  nothing of a payload. A repeater or companion nearby should show adverts
  counted.
- **The button**: after five minutes the OLED is off; PRG turns it on.
