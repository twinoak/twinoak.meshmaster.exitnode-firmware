# p1.15-56 — A listing says how many there were

A repeater's neighbour list is read nine to a page, and the library has said for
two piles what it does when a page does not come back: *a page that never came
back after some already did is still a reading: the server gets what was heard
rather than nothing at all*. The job ends `ok`, the log says *the list stops at 9
of 17*, and the result is nine neighbours.

The server cannot read a log. Nine neighbours that are the whole list and nine
that are where the list stopped were **the same bytes**, so it took the nine for
all there were, opened `neighbour_lost` for the other eight, halved the count on
the chart, priced the next listing at one page, and found the eight again as new
at the listing after that. Thomas, on meshmaster.dk: *often only half the
neighbours come back*.

The count was in every page of the reply all along and was thrown away. Now it is
in the result:

```json
{"neighbours":[{"prefix":"a1","lastHeardS":42,"snr":7.25},{"prefix":"7f","lastHeardS":3600,"snr":-2.5}],"total":17}
```

| | Before | Now |
|---|---|---|
| a whole list of nine | `{"neighbours":[…9…]}` | the same, and `"total":9` |
| a list that stopped at a lost page | the same bytes as above | the same nine, and `"total":17` |
| a list cut at `kMaxNeighbours` | 54 entries, nothing said | 54 entries, and the repeater's own 60 |
| a repeater with no neighbours | `{"neighbours":[]}` | `{"neighbours":[],"total":0}` |
| where the count was | the job's log, which the server never reads | the log **and** the result |

Nothing else moved: the pages asked for, the two tries a request has, the order,
every line of the log and the outcome of every case are what they were. A job
whose **first** page is not answered still ends `unreachable` with no result at
all.

`total` is the figure of the **last page that was read**, so a repeater that
heard a new neighbour between two pages is reported at its newer count. It is
written whenever the job ends `ok`, and it is the one thing in this release that
can stop a library consumer's tree compiling: `mm::writeNeighboursResult` takes
it as its third argument (`CHANGELOG.md`).

**The fixture waits here.** `NeighboursResultTotal.json` is made by
meshmaster.dk's task 239, which may reach its `master` after this lands, so it is
written here from the line that task carries, into `tests/fixtures/contracts-ahead/`
— a directory the sync does not touch and `MANIFEST.txt` does not list.
`tests/fixtures/contracts/` is not edited and no sync was run. The first item of
`FOLLOWUPS.md` is what ends that arrangement.

## Deviations from the spec or the task

**None of substance.** meshmaster.dk's task 239 was read from its `master` today
and its deliverable 1 is the line this task carries, byte for byte. Two things
worth the reviewer's eye, neither a disagreement:

- **`NeighboursResult.json` is unmoved and `JobResultReportAtGuest.json` with
  it.** That envelope fixture carries a listing in its `data` member, written
  before the count existed — what meshmaster.dk calls an *unsaid* listing. It is
  a copied fixture and cannot be edited here, so the envelope test that is held
  to it byte for byte now builds that `data` as the fixture's own bytes instead
  of through `writeNeighboursResult`. What that test is for is the **envelope** —
  `loggedInAs` last, after the log — and the envelope has not moved; the writer
  is held byte for byte by three cases of its own.
- **`total` is always written, never left out.** The .NET record's member is
  nullable, because a listing from an exit node that predates this release has no
  count at all. This firmware has one for every `ok` listing, so there is no case
  in which it would write *unsaid*, and the writer takes a plain `int` rather
  than a sentinel nobody would pass.

## Decisions taken without asking

- **The waiting fixture gets a directory, a `README.md`, a `.gitattributes` line
  and a macro of its own.** `tests/fixtures/contracts-ahead/` is named by the
  task; the rest follows from it. The `-text` attribute is there for the same
  reason the copied tree has one — the file is bytes to be compared, not text for
  git to normalise — and `AHEAD_FIXTURES_DIR` (`platformio.ini`'s `[env:native]`)
  is how the tests find it without assuming a working directory, as
  `FIXTURES_DIR` is. All four go together when the sync brings the real file.
- **The count of the *last page read*, with no arithmetic over it.** The
  alternative was the largest count any page gave, or the first. The task says
  *the count the repeater gave in the last page that was read*, and that is
  literally what `runNeighbours` already held in `total`; a page that came back
  empty is a page that was read, so a repeater whose count rose between the pages
  is reported at the newer figure.
- **Three faults on `FakeMesh`, keyed to the page and not to the send.**
  `silenceTheNeighboursPageFrom`, `truncateTheNeighboursPage` and
  `sayTheNeighbourTotalFromPage`. `beSilent` counts every send and cannot say
  *the second page*, because the login and the first page were answered; the page
  is read off the request's own offset, so a page asked a second time is the same
  page and both of its tries behave alike. None of them is a new answer of the
  repeater, so the fake's citation manifest is unchanged.
- **A page that cannot be parsed is a page with fewer than four bytes, and the
  test turns the repeater's padding off to get one.** `parseNeighboursPage`
  refuses exactly one thing — a reply shorter than `total(i16)`, `returned(i16)`
  — and the cipher block's zero padding means no reply on the air is ever that
  short. `setPadding(false)` is the fake's existing knob and the test says why it
  is used. The branch it covers is defensive and stays that way.
- **The release note is about the listing and not about the server's use of it.**
  What meshmaster.dk makes of `total` is its task 239 and may land after this
  release; the line says what the listing now carries and what it stops costing.

## Not verified here (and why)

No test here can hear a radio. Everything below wants a board and a repeater that
really has neighbours.

- **A real `neighbours` job against a repeater with more than nine neighbours.**
  Flash, let meshmaster.dk queue a `neighbours` job for a repeater with ten or
  more, and read the posted result: it must carry `total` after the array, equal
  to the number of entries when every page came back. The job's log prints the
  pages as it always did, so the serial console (`dump`, and the result on
  meshmaster.dk) is enough to read the walk.
- **A listing that really stops short.** The case this task exists for cannot be
  staged on the bench without a lost page; on the air it happens by itself. When
  it does, the result has fewer entries than `total` and the log says *the list
  stops at N of M* — the two must agree. If meshmaster.dk's task 239 is deployed
  by then, the Neighbours tab says *9 of 17: the list stopped short* above the
  list.
- **A repeater with more than 54 neighbours**, if one exists on this mesh: 54
  entries and the repeater's own count, which is the only way the server learns
  the list was cut.
- **The fixtures, when meshmaster.dk's pile 4.42 is merged.**
  `.\tools\sync-fixtures.ps1 -Commit master`, and
  `tests/fixtures/contracts-ahead/NeighboursResultTotal.json` must be the copied
  file byte for byte. It is the first item of `tasks/phase-1.15/FOLLOWUPS.md`,
  and it is the only check that the two ends agree on this wire.
