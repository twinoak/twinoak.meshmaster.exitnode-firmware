# p1.15-60 — Switched, proved, or back

Task 59 leaves a judged image in the slot that is not running. This boots it, and
decides whether it stays.

A firmware that boots is not yet a firmware that works. So a switched image runs
**on trial**: ten minutes from its boot to show three things — the mesh started,
the WiFi joined with the clock set off the network, and a heartbeat answered
`2xx` — and if it does not, the old image runs again without anybody's help.

```
> update apply
apply     switching; the board restarts now
[12:06:02] I update: switching: 0.7.2+4a4e791 to 0.8.0+1a2b3c4, 1446640 bytes, in app1
... the board restarts ...
[12:06:31] I update: proving: on trial for 10 min; a reset ends it and the bootloader undoes it
> status
firmware  meshmaster-agent 0.8.0+1a2b3c4 on MeshCore companion-v1.18.0 (81dbae59) - on trial
> update
trial     on trial, 9 min 2 s left: mesh yes, wifi and clock yes, heartbeat not yet
          0.8.0+1a2b3c4, switched to from 0.7.2+4a4e791 at 2026-11-20T12:06:02Z; the bootloader undoes it if this boot does not end
[12:06:48] I update: committing: mesh, wifi and the clock, and a heartbeat answered 17 s into the trial
> update
last      committed: 0.8.0+1a2b3c4, from 0.7.2+4a4e791, switched at 2026-11-20T12:06:02Z
```

**The undoing is the bootloader's, not the application's.** With
`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` — the Arduino core's own default, and so
this firmware's, which `tools/check-sdkconfig.py` holds by **not** having to list
it — the bootloader marks an image that is still pending-verify at a reset as
aborted, which makes its `otadata` entry invalid, and the other entry is then the
one it boots (`bootloader_utility.c` and `bootloader_common_loader.c` at the
pinned ESP-IDF 4.4.7: `ota_select_invalid` is true for `ABORTED`). So a crash, the
watchdog and a power cut during the trial all have the same end and nothing in the
application has to notice. What the application does is **not** mark the image
valid until all three conditions have been seen — which is why
`verifyRollbackLater()` is defined `true` in `src/platform/BootChoice.cpp`: the
Arduino core would otherwise mark a pending image valid before `setup` ran
(`cores/esp32/esp32-hal-misc.c`, `initArduino`, where it is a weak symbol).

**Three files may now decide what a board boots, and no fourth.** Task 57 named
`src/platform/TableFlash.cpp` for raw flash and task 59 added
`src/platform/OtaSlot.cpp` for the OTA writer. The third is
`src/platform/BootChoice.cpp`, which holds the call that sets the boot partition
and the two that write the running image's verdict into `otadata`;
`test/test_flash_writes` fails the build when one of them is anywhere else, and
also when any file but that one defines `verifyRollbackLater()`.

**Two files of new portable code, both host-tested.** `src/update/Trial.cpp` is
the machine — the switch, the trial, the undo and the boot that finishes the
record — on four seams: `BootSlots` (the slots, the boot choice, the two marks),
`TrialConditions`, `TrialClock` and `DeliberateRestart`, plus task 59's
`SlotSink` for the slot's bytes. `src/update/UpdateRecord.cpp` is the record and
its journal. `test/test_trial` drives all of it across two and three scripted
boots: a store that is a map and outlives a "reboot", a clock that moves only
when a test says so, and a restart that **returns** so that a test can look at
what was left behind. The bytes in the slot are task 58's own fixture release, so
the hash that is re-read before a switch and the descriptor that is read out of
the first slot are a release's real ones.

### The other deliverables

- **Deliverable 5, the record.** Nine keys in the one NVS namespace the settings
  live in — `fw.up.state`, `.from`, `.to`, `.sha`, `.at`, `.slot`, `.end`,
  `.why`, `.jr` — written by the firmware and typed by nobody, exactly as task
  59's five are (`SettingsStore::getRecord/putRecord`; `get` does not print
  them, `help` does not list them, `Keys.h` has no row for them). The state is
  written **last** on the way in and cleared **first** on the way out, which
  `TheRecord.TheStateIsWrittenLastOnTheWayInAndClearedFirstOnTheWayOut` reads
  key by key, and `.AHalfWrittenOneIsNotARecord` holds the three half-written
  shapes that read as nothing in hand. The journal is `at`, `step` and `note`
  inside meshmaster.dk's `FirmwareJournalBounds` (40 entries, 2 000 characters),
  and the step words are the contract's own: `switching`, `proving`,
  `committing`, `rolling-back`, `restored`.
- **Deliverable 1, what waits in RAM.** `AgentLoop::postWhatWaits()` is new in
  the library (one addition, nothing moved): the results the offline buffer
  holds and one observation batch, **one try each**, and it returns what went
  out. The switch calls it after the boot choice and before the restart, and the
  ordering test reads that. `CHANGELOG.md` and `docs/library.md` §6 carry it.
- **Deliverables 8 and 9, the words.** `update apply` on the console; `update`
  gains a `trial` block (each condition and the minutes left) and a `last` line
  (`committed`, or `rolled back` with what was missing, with the versions either
  side and when the switch was made); `status` says *on trial* in its first line
  while it is. `README.md` has the paragraph on which slot a board runs from and
  a new rail; `docs/field.md` §9 has the section, a transcript and four more ⚠
  bench items; `docs/console.md` has the `update apply` row and the two amended
  ones; `release-notes/unreleased/60.md` is the one line (377 characters).

## Deviations from the spec or the task

- **The trial's boot clears task 59's record**, which deliverable 7 (*nothing
  else is written*) does not list. It has to be cleared by somebody: from the
  moment the new image is running, `fw.slot.*` describes the slot the board was
  switched *from*, and leaving it would make `update`'s `other` line say the
  running firmware is waiting in the other slot and let `update apply` try to
  switch to the image it just came from. It is cleared at the one boot that
  knows the switch happened (`beginTrial`), with one call of task 59's own
  `saveRecord`, and the test asserts it.
- **A `switching` record that comes back as the same image ends *rolled back***,
  with *the switch was never taken*. Deliverable 5 allows two endings and this is
  neither a commit nor a trial that ran; the Walter's machine calls the same case
  a rollback reason (`kSwitchNotTaken`, `self_update.h`), and task 61 is what
  decides whether the server hears `rolledBack` or something else about it.
- **A trial cut short on a board whose bootloader does not undo ends the same
  way**, by this firmware's own hand: the record's `rolling-back` entry names the
  reset, the boot choice is set back and the board restarts, and the boot after
  that finishes the record. Deliverable 4 asks for the undo *when the conditions
  fail*; a reset is the one thing that ends a trial without them being decided,
  and leaving the new image running unproven for ever would be the only other
  answer.
- **A commit whose `markValid` is refused rolls back instead, but only on a board
  whose bootloader marks the image pending.** There the bootloader would undo the
  image at the next reset whenever that came, so going back now with a record
  that says why beats being undone later by nobody; where the bootloader does not
  mark it pending, nothing would undo it and the record ends `committed` with the
  refusal in the journal's note. `TheTrial.AFrameworkThatWillNotMarkAPendingImageValidSendsItBackInstead`.
- **`update fetch` is refused while an update is in hand**, which is not in the
  task. The slot a fetch writes is the slot holding the image the board would go
  back to: a fetch during a trial would leave a board with nothing that is known
  to work. `Updater::whyTheOtherSlotMayNotBeWritten()` is the sentence and
  `TheTrial.TheOtherSlotMayNotBeWrittenWhileAnUpdateIsInHand` is the test;
  `update apply` is refused while a fetch runs for the same reason.
- Nothing else. The spec sections the task names are this repository's own pages,
  the pinned ESP-IDF and Arduino core on disk, and the Walter's `self_update.h`
  read as the model; they agreed with the task throughout.

## Decisions taken without asking

- **An image in the other slot is known by its version, not by its hash.**
  Deliverable 6 asks for *an image that the record does not know*. The record
  keeps the version it was switched from and the version it was switched to, and
  a version is `X.Y.Z+<sha7>` — the commit is in it — so comparing versions tells
  a flash over USB from the image the board came from, from the one running, and
  from one already tried and rolled back, which are the three cases the
  deliverable names. Hashing 1.4 MB at every boot from the second slot to learn
  the same thing would cost a second of every boot. The hash **is** re-read
  before a deliberate switch (deliverable 1), where it is read once and on
  purpose.
- **The descriptor of an image in the other slot is read over the image's own
  length**, which the framework's own reading of its header gives
  (`esp_image_verify`, as `esp_ota_set_boot_partition` itself uses). Scanning the
  whole 3.1 MB partition would find the tail of whatever was there before and
  refuse a perfectly good image as *two descriptors*.
- **The oldest journal entries are dropped when a bound is reached**, not the
  newest. What the first line says — the versions and the moment of the switch —
  is in the record's own fields as well, so the oldest line is the one line that
  is said twice; the end of a journal is what an outcome is read against.
- **The journal is kept as the one text it is stored as**, `<at>|<step>|<note>` a
  line, rather than as 40 structs: 40 structs of a bounded step and note are four
  kilobytes of `.bss` on a board with 60 % of its RAM in use, and the text is
  2 520 bytes. `Journal::readFrom` reads the stored value straight into that one
  buffer and compacts it in place, so there is no second buffer anywhere and
  nothing of this is on the stack.
- **The trial is measured from `atBoot()`**, which `setup()` calls as early as
  the clock allows — after `agentClock.begin()` and before the WiFi, the server
  and the console — so that a board switched to a new image is on trial from
  within a second or two of the reset, and nothing that follows is started twice.
- **`Updater::step()` is called from the job pump as well as from `loop()`.** A
  `config.read` of twenty-one transactions is eleven minutes and a region load is
  thirteen; without it a working image could miss its ten minutes because the
  board was busy doing exactly what it is for.
- **`postWhatWaits()` is called for the switch and not for a rollback.** The task
  asks for it where a person asked for the restart; a rollback's restart usually
  happens *because* the server could not be reached, and one more TLS attempt
  there would cost seconds and post nothing.
- **The three conditions are latched, not sampled.** Each is remembered with the
  millisecond it was first seen, so a WiFi link that comes up and drops again
  inside the window has still been seen — the trial asks whether the image *can*
  do the job, not whether it is doing it at the tenth minute.
- **`Updater::begin` takes a `Seams` struct** rather than ten positional
  pointers: every one of them is a pointer to an interface, and two of them the
  wrong way round would still compile.
- **The boot that follows a trial finishes the record, and the trial image does
  not.** The trial image writes `rolling-back` and the reason and leaves the
  phase at `trial`; the next boot — whichever image it is — writes `restored` and
  the ending. A power cut between those two leaves a record the boot after it
  still finishes.

## Not verified here (and why)

No test in this repository can write a board's boot choice, boot a second slot or
pull a board's power, so the whole of the board half is the bench's. The list is
in [`docs/field.md`](../../../docs/field.md) §9 as ⚠ items, in the words a person
at a window would use. It needs **a second release to update *to***, imported on
meshmaster.dk and served to the board, so it comes after the pile's *Afterwards*
list. On a **V3** and on a **V4**, both saying `two`, with release A running and
release B fetched:

1. **⚠ `update apply` commits B inside two minutes.** `status`'s first line says
   *on trial* and names B, `update` shows the three conditions going `yes` one
   after another, and inside two minutes `update` says `last committed` with B
   and with A as the version it came from. The identity is the **same 64
   characters**, and the exit node's page shows B.
2. **⚠ With the access point switched off, ten minutes later the old one is
   back.** The board restarts by itself and B runs again; with the WiFi back,
   `update` says `rolled back: no wifi…` and names the release it tried.
3. **⚠ The power pulled one minute into a trial is the same ending.** At power-up
   the **old image runs** — the bootloader did it, not the application — and
   `update` says `rolled back` with *restarted during the trial* and the reset's
   own reason.
4. **⚠ A flash over USB still wins.** With the board running from the second
   slot, the plain `.bin` of any release through the web flasher: after the flash
   the board restarts once more by itself and **that release runs**.

Five things no test here can reach at all, and what is in their place:

- **The bootloader's rollback has never run.** That a reset during a trial ends
  it is read out of the pinned
  `components/bootloader_support/src/bootloader_utility.c` and
  `bootloader_common_loader.c` — a `PENDING_VERIFY` entry is rewritten `ABORTED`,
  `ota_select_invalid` is true for `ABORTED`, and the other entry is then the one
  `bootloader_common_get_active_otadata` returns — and nothing more. Bench item 3
  is what proves it on a board. It is also the one place where this firmware
  depends on a bootloader it does not update
  (`tasks/phase-1.15/FOLLOWUPS.md`).
- **`verifyRollbackLater()` has never been linked over the core's own.** It is a
  weak symbol in `cores/esp32/esp32-hal-misc.c` and the definition in
  `src/platform/BootChoice.cpp` is the strong one; both boards build, and
  `test/test_flash_writes` holds that exactly one file of `src/` and `lib/`
  defines it. What proves it on a board is bench item 2: an image that is marked
  valid before `setup` runs could never roll back for want of WiFi.
- **The ESP-IDF's boot choice and the two marks have never been called.**
  `src/platform/BootChoice.cpp` is read against the pinned
  `components/app_update/esp_ota_ops.c` and nothing more; the host tests drive
  scripted slots. Two consequences worth knowing at the bench:
  `esp_ota_set_boot_partition` verifies the image itself and refuses one it would
  not load, so a slot that was spoiled by a refused fetch cannot become the next
  to boot; and `esp_ota_mark_app_invalid_rollback_and_reboot` answers
  `ESP_ERR_OTA_ROLLBACK_FAILED` when there is nothing in the other slot to go
  back to, which this firmware then says in the record rather than pretending.
- **A board whose bootloader does not mark an image pending has not been found.**
  Deliverable 4's board is a real one — a Heltec that came from other firmware
  and was upgraded with a plain `.bin` — but there is none on the bench, and the
  host tests script the state the framework would report. `FOLLOWUPS.md` already
  carries the item.
- **The ten minutes have never been waited out on a board.** The window is one
  constant (`kTrialMs`) and `FOLLOWUPS.md`'s *constants* item carries it; the
  host tests move a clock rather than a board.
