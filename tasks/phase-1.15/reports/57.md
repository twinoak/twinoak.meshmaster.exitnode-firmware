# p1.15-57 — A second slot

`app1` was taken out of both tables in October — *this firmware does no OTA, so
the second application slot was never written* — and its flash left unallocated.
Owners have now asked for an update they can start from meshmaster.dk, and an
update needs a slot to be fetched into. So the slot is back:

| | offset | size | what it was before |
|---|---|---|---|
| V3, `meshmaster_8MB.csv` | `0x350000` | `0x320000` | unallocated (`0x345000`–`0x66FFFF`) |
| V4, `meshmaster_16MB.csv` | `0x660000` | `0x630000` | unallocated (`0x655000`–`0xC8FFFF`) |

Not one other line of either table moved by a byte, and neither did `nvs`: the
slot is **not** where the framework's default has `app1`, because `nvs` is there
now. It is 64 kB aligned, above `nvs`, and ends exactly where `spiffs` begins;
the 44 kB between `nvs`'s end and the boundary stays unallocated, because an
application partition has to be aligned.

**A board in the field does not get this table by being upgraded.** The MeshCore
web flasher erases the whole board before it writes a merged image, which costs
the key, the token and the WiFi, so no board is asked for one: it takes the
release as the plain `.bin`, which keeps the table it has, and the firmware
writes the one sector itself when a person types `update slot`. For that it has
to recognise a board's own table by its bytes, so both tables are kept as files
(`meshmaster_<size>_one_slot.csv` is what every merged image from `v0.2.0` to
`v0.7.1` wrote) and both are carried in the image as arrays.

```
> update
table     one
app0      0x010000, 0x330000 bytes
app1      none: this is the table boards were flashed with before the second slot existed
          type `update slot` to add it, then `reboot`; the settings and the identity are untouched
> update slot
added: app1 at 0x350000, 0x320000 bytes. Type `reboot`; the table is read at the next boot
```

| The sector holds | The word | `update slot` |
|---|---|---|
| a table with an `app/ota_1` entry — the new one, or the framework's default | `two` | says the slot is there and where; writes nothing |
| this board's one-slot table, byte for byte, `0xFF` above it | `one` | erase, write, read back, compare |
| anything else | `other` | refuses in a sentence; says to flash a merged image over USB |

The write needs the ESP-IDF's guard against writing the partition table turned
off for the whole image, so **one file may erase or write raw flash** —
`src/platform/TableFlash.cpp`, which holds the address and the length as
constants of its own and refuses every call outside that one sector — and a
native test walks `src/` and `lib/` and fails when a second file holds one of
those calls. That is a new rail in `README.md`.

## Deviations from the spec or the task

- **"the one key changed" is two keys.** `CONFIG_SPI_FLASH_DANGEROUS_WRITE_*`
  is a Kconfig `choice` of three bools (`ABORTS`, `FAILS`, `ALLOWED`), so moving
  off the core's default writes two lines: `ABORTS` goes from `y` to not set and
  `ALLOWED` from not set to `y`. Both are in `tools/check-sdkconfig.py`'s
  allowed list, with one reason between them that says it is one choice. There
  is no way to write it as one key.
- **"differs by the `app1` line and by nothing else" is held over the data
  lines**, not over the whole file. The one-slot files must say what they are
  and that nothing is built with them, so their comment headers are their own.
  The test strips comments and whitespace and then demands exactly one extra
  line, the `app1` one, with every other line identical and in the same order —
  and `tools/check-table-bytes.py` holds the two files' *bytes*, which comments
  do not reach, against the firmware's arrays and the merged image.
- Nothing else. The spec sections this task names are this repository's own
  pages and they agreed with the task throughout.

## Decisions taken without asking

- **The word is decided by the entries, not by the table's MD5.** A sector is
  `two` when it parses and holds an `app/ota_1` entry, and `one` when it is this
  board's one-slot table byte for byte. The MD5 entry is not verified: the
  bootloader checks it before it boots the image that would be doing the
  checking, so a running firmware's sector is MD5-valid by construction, and
  carrying an MD5 implementation to re-derive that would be weight for nothing.
  A sector that is corrupt in any way is `other`, and `other` is never written.
- **`one` requires the `0x400` above the entries to be `0xFF` too.** The sector
  is 4 kB and `gen_esp32part.py` writes `0xC00` of it; a merged image leaves
  `0xFF` above that and so does an erase. Comparing only the entries would call
  a sector with something else up there *the table boards hold*, and then write
  over it.
- **The slot's position** is the task's, and the 44 kB below it
  (`0x345000`–`0x34FFFF` on the V3) stays unallocated rather than being given to
  `nvs` or `spiffs`: either would move a partition, which `boards/README.md` has
  forbidden since task p1.2-11.
- **The tables are committed as bytes, not generated at build time.** A
  generated array would move with the csv and the check of deliverable 8 would
  then compare a file with itself. `tools/check-table-bytes.py --write`
  regenerates them, and CI holds them against `gen_esp32part.py` and the merged
  image, so an edited table file with a stale array is a red build.
- **A board build carries its own board's two tables and no more** (`0xC00`
  each, selected by `HELTEC_LORA_V3`/`V4` in `TableBytes.h`); the host build has
  no board and carries all four, because the tests read both boards'.
- **`update` and `update slot` and nothing between them.** `update slots`,
  `update now`, `update confirm` are all one refusal that says what to type: the
  second command erases flash and a near miss must not reach it.
- **The one file bounds its own calls.** `TableFlash.cpp` takes an offset inside
  the sector, never an address, and refuses anything that does not lie wholly
  inside it — so with the ESP-IDF's guard off, what remains is a file whose
  every call can be read in a minute.
- **One log line.** `update slot` writes its own result to the log ring at
  `warn` when it added the slot, `info` otherwise, so `dump` carries it.

## Not verified here (and why)

No test in this repository can write a board's partition table, boot from a
second slot or pull a board's power, so everything below is the bench's. The
list is in [`docs/field.md`](../../../docs/field.md) §9 as ⚠ items, in the words
a person at a window would use. **On a V3 and on a V4**, each provisioned and
running the release before this one, then upgraded with **this release's plain
`.bin`** (never the merged one):

1. **⚠ `update` says `one`**, and `status` shows the same 64 hex characters it
   showed before the upgrade.
2. **⚠ `update slot` says *added*** with `app1`'s offset, then `reboot`; after
   it, `update` says `two` and prints both slots' offsets and sizes.
3. **⚠ Nothing else moved**: `status` shows the same 64 characters, the WiFi
   comes up by itself, and the exit node's page on meshmaster.dk shows a
   heartbeat **with the token it already had**.
4. **⚠ A board flashed with this release's merged image** through `esptool`
   says `two` on its first `update`, with no `update slot`.
5. **⚠ `update slot` typed on a `two` board** says the slot is already there,
   names its offset, and writes nothing.

Two things that cannot be rehearsed at all and are written down instead:

- **A power cut during the write** leaves a board whose table sector is erased
  or half written; it needs a merged image over USB (`esptool`, which erases
  nothing outside what it writes — never the web flasher) before it boots again.
  It is the only moment in this pile that can leave a board needing a cable, and
  `README.md`, `boards/README.md` and `docs/field.md` all say so.
- **A board with flash encryption or secure boot** would refuse this write.
  Both are the owner's choice in `README.md` and out of scope here; phase 1.15's
  `FOLLOWUPS.md` already carries the item.

One thing the ESP-IDF's source settled rather than the bench: the table is
written **out of a `const` array in flash**, with the cache disabled, which
would normally be a crash. `esp_flash_write` asks
`host->driver->supports_direct_write(buffer)` first and copies a non-DRAM source
through a 32-byte stack buffer when it does not
(`components/spi_flash/esp_flash_api.c`, ESP-IDF 4.4.7 as pinned), so the array
may stay in flash.
