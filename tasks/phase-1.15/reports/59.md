# p1.15-59 — An image is fetched and judged

Task 57 gave a board a second application slot and task 58 gave the firmware a
reader of a release. This joins them: given a release's `base` on the configured
server, the manifest and its signature are fetched and checked — 1, 2 and 3 —
**before one byte of an image is asked for**; then the image's `ota` file is
fetched in ranges straight into the slot that is not running, and what the slot
now holds is judged from the bytes themselves. At the end the other slot holds a
judged image, or holds nothing this firmware will ever boot.

**Nothing is switched here.** The running firmware and the boot choice are as
they were, and `esp_ota_set_boot_partition` is in no file of this tree —
`test/test_flash_writes` now fails the build if it appears anywhere at all.

```
> update fetch 12
fetch     /agent/v1/firmware/12: the manifest and its signature first, then the image in pieces; the steps follow
[12:03:11] I fetch: manifest.json: 1612 bytes
[12:03:12] I fetch: checks 1, 2 and 3 passed: twinoak-exitnode-firmware 0.8.0+1a2b3c4: the image exit-node.heltec_v3.868, 2 file(s)
[12:03:13] I fetch: range 0-65535: http 206, 65536 bytes (65536 of 1446640 held)
...
[12:03:52] I fetch: checks 4 and 5 passed: ... the one descriptor at 0x1189C agrees with it
[12:03:52] W update: fetched 0.8.0+1a2b3c4, 1446640 bytes, sha 4f2a91c0b7d2e5a8... (41021 ms, 25 request(s); the last call left 118 kB of heap, lowest 94 kB)
> update
other     holds 0.8.0+1a2b3c4, 1446640 bytes, sha 4f2a91c0b7d2e5a8..., fetched from /agent/v1/firmware/12
```

**Four files of new code, three of them behind seams.** `src/update/Fetch.cpp`
is the engine and is host-portable: the server is behind `ReleaseHttp`, the slot
behind `SlotSink`, the record behind `RecordStore`, and `test/test_fetch` drives
all of it against a scripted server, a slot that keeps what is written to it and
a record store in memory. `src/update/SlotRecord.cpp` is the record. The board's
three halves are `src/platform/OtaSlot.cpp` (the ESP-IDF's OTA writer) and
`src/update/FetchSeams.cpp` (the server over `AgentClient`, and the record over
NVS).

**Every request of a fetch goes down the one path every other call goes down.**
`AgentClient::getStreamed` is a method of the existing client, not a second one:
the kept connection, the verified chain, the `Authorization` header that
`exchange()` builds and **no other file of `src/` or `lib/` builds**, and
`X-Agent-Version`. Nothing of the token is in the engine, in the seams, in the
console or in a log line. The one thing a 1.4 MB file needed is a body that is
*streamed* into a sink instead of filling a buffer.

**The loop stays alive.** `step()` makes at most one request and returns, so the
mesh, the console, the observer and the watchdog all get their turn between two
ranges — and the slot is opened with `OTA_WITH_SEQUENTIAL_WRITES` rather than
with the file's length, so the nine seconds of flash erase that 1.4 MB costs is
spread over the ranges instead of happening in one call.

### The other deliverables

- **Deliverable 3, the record.** Five keys in the one NVS namespace the settings
  live in — `fw.slot.state`, `.ver`, `.sha`, `.len`, `.base` — written by the
  firmware and typed by nobody: `get` does not print them, `help` does not list
  them and `Keys.h` has no row for them (`SettingsStore::getRecord/putRecord`,
  documented there as *records*, not settings). The state is written **last** on
  the way in and cleared **first** on the way out, so a power cut in the middle
  of either leaves *nothing judged* and never a record that half agrees with the
  slot: `TheRecord.AHalfWrittenOneReadsAsNothingJudged` removes each of the four
  parts in turn, and `.RoundTripsAndSaysNothingJudgedWhenItIsCleared` holds the
  round trip, a 63-character hash, an upper-case one, and that forgetting it
  forgets all five keys.
- **Deliverable 4, a word and a number.** `fetched` with the version, the hash
  and the bytes; `fetch`; `check` 1 to 5; and `slot`, which is this task's one
  added word (see *Decisions*). `TheWords.AreTheOnesTaskSixtyOneWillPost` holds
  all five spellings, including `running`.
- **Deliverable 5, the loop.** One request a `step()`, and `step()` is called
  from `loop()` only while a fetch is running. Nothing is held in RAM but one
  range's bytes on their way through the sink and the manifest and its signature,
  both bounded here (4 kB and 160 bytes, refused in a sentence rather than
  overrun — `BeforeAFile.AManifestLongerThanThisReaderHoldsIsCheckTwo`). **The
  two figures the deliverable asks for are the bench's**, because no session can
  measure them: the firmware prints both at the end of every fetch — how long it
  took in milliseconds, and what the last call left of the heap and the lowest it
  saw during it (`AgentClient::lastCost()`, which task p1.8-30 already measures
  exactly for mbedtls's share). The ⚠ item in `docs/field.md` asks for them by
  name.
- **Deliverables 7 and 8, the words.** `update fetch <release id>` and a new
  `other` line on `update`; `docs/console.md` has a row for each and
  `docs/field.md` §9 a section, a transcript and seven ⚠ bench items.
  `release-notes/unreleased/59.md` is the one line (380 characters).

## Deviations from the spec or the task

- **A `Content-Range` whose total is not the manifest's size is reported as
  check 4, not as a failure.** The task's criterion asks for *a file one byte
  longer* to end `check` 4, and §5's check 4 is *the downloaded file's size and
  SHA-256 are the manifest's* — so a server that answers `bytes 0-4095/4097`
  has already failed that check, on its own word, and is refused there rather
  than after 1.4 MB has been fetched to reach the same conclusion. The Walter's
  `core/net/download.h` calls the same case `kWrongFile`; this firmware gives it
  the number the task asks for. It is not retried either way.
- **The ESP-IDF's own verdict is reported as check 5.** It is not one of
  section 5's five checks, and deliverable 4 allows only 1 to 5. Check 5 is the
  closest true thing — *the file holds what it says it does* — and the sentence
  names the framework: *the image is the manifest's bytes and the framework will
  not boot it*. A refusal there spoils the slot like any other.
- **A file longer than the slot is refused at check 3**, before it is asked for.
  §5's check 6 is about a `swd` file's `app_region` and this product publishes
  none, but its rule — *a manifest cannot widen what may be written* — is the
  same rule, and check 3 is where this reader decides whether there is an image
  for this board it can take. The refusal names both figures.
- **`test/test_flash_writes` now names a file per call rather than one file for
  all of them.** Writing the other application slot is the `app_update`
  component's business, not raw flash, and its calls are bounded by a *partition*
  where `TableFlash.cpp`'s are bounded by an *address*. So the rail is two files
  and no third — `src/platform/TableFlash.cpp` for the raw-flash calls,
  `src/platform/OtaSlot.cpp` for the OTA writer — and a call of one of them in
  the other is as much a failure as it turning up anywhere else. The walk's
  self-test plants six files and must report exactly the four calls that are in
  the wrong place. `README.md`'s rail and `tools/check-sdkconfig.py`'s reason for
  `CONFIG_SPI_FLASH_DANGEROUS_WRITE_ALLOWED` both say so now.
- **`AgentClient`'s private `CallExtras` was renamed `FirmwareExtras`**, because
  `test/test_seams` greps `AgentClient.h` for `struct Call` to prove the `Call`
  record is the library's and `struct CallExtras` matched it. The rail is right
  and the name was the accident.
- **A firmware route does not become "the server's last answer".**
  `AgentClient::lastCall()` is what `AgentLoop` reads of its own call a line
  later (`agent/ServerPolicy.h` decides whether to halt on it), so twenty-odd
  ranges of an image passing through would be answering a question nobody asked.
  The heap cost *is* kept, because it really is what the last call cost and the
  fetch's own line prints it.
- Nothing else. The spec sections the task names — `unit-protocol.md` §4 read
  from today's `master` of meshmaster.dk, `FIRMWARE-MANIFEST.md` §5 from the
  synced fixture set — agreed with the task throughout.

## Decisions taken without asking

- **A fifth ending word, `slot`.** Deliverable 4 lists `fetched`, `fetch` and
  `check`, and deliverable 6 asks for a refusal before any request when there is
  no second slot. *No second slot* is not *the release could not be had*: the
  release is fine, the board is not ready, and what a person must do about it is
  `update slot` and a reboot rather than anything to do with the server. So it
  is its own word, and **task 61 has one more word to carry**. Its sentence is
  the slot's own and says which of the four reasons it is: the table word is
  `one`, the table is `other`, the table could not be read, or the sector says
  `two` and this boot has not read it yet.
- **64 kB a range, three tries a file, 4 kB of manifest.** A range is a request
  on the kept connection with no handshake, so a smaller one costs round trips
  and a larger one costs more when a connection drops: 64 kB is 23 ranges for
  the 1.4 MB this firmware is, and a fraction of a second of WiFi each. Three
  tries are **three in all and not three per range** (the task's words), so a
  link that drops three times during one file ends the fetch and the next
  `update fetch` begins again. The manifest bound is 4 kB against today's 1.6 kB.
  All three are in `tasks/phase-1.15/FOLLOWUPS.md`'s *constants* item.
- **`OTA_WITH_SEQUENTIAL_WRITES`, not the file's length.** With the length,
  `esp_ota_begin()` erases every sector the image will fill before it returns —
  some nine seconds of flash erase for 1.4 MB, in one call, with the mesh and the
  console waiting on it. With sequential writes each write erases only the
  sectors it is about to fill, so the erase is spread over the ranges and no
  single piece of this fetch holds the loop for long. Read out of the pinned
  ESP-IDF's `components/app_update/esp_ota_ops.c` (`need_erase`), not remembered.
- **Checks 4 and 5 are run on bytes read back out of the slot**, not on the
  bytes as they went past on the way in: what is judged is what would be booted.
  The pinned `esp_ota_write` writes straight through when flash encryption is off
  (the 16-byte hold-back is inside `if (esp_flash_encryption_enabled())`), so a
  read back before `esp_ota_end()` sees what is really there.
- **Every ending but *fetched* spoils a slot that was opened**, not only the ones
  the task names: a 404 halfway through a file, a 416, a redirect and three
  failures all leave the slot's first sector erased. A half-written image that
  nothing can boot is the one safe state, and task 60 then has one answer and not
  two.
- **The record is cleared the moment a fetch starts**, before the first request,
  because the slot is about to be written over and whatever it held is no longer
  there. A fetch that is refused therefore always leaves *holds nothing this
  firmware will boot*, whatever it held before.
- **A release id is digits, 1 to 10 of them, and no leading zero** — `0` and
  `007` are both refused. It becomes a path this board asks the server for, so
  the parser refuses anything else before a path is built from it, and
  `releaseIdIsSane` applies the same rule again in the engine. `base` is a path
  on the configured server and never a URL of its own; the engine names no host.
- **The step lines go to the log, and `update fetch` prints one line and
  returns.** A fetch cannot be waited for at the console without starving the
  loop, and the log *is* the serial port on this board — so the port shows each
  step as it happens and `dump` still has them afterwards.
- **`SettingsStore` grew `getRecord`/`putRecord` rather than two rows in
  `Keys.h`.** A row in `Keys.h` would make these settable and printable from the
  console, which they are not: nobody types what the other slot holds. They are
  in the same namespace, so `erase confirm` forgets them with everything else —
  which is right, and `Store.h` says why.
- **`Accept: */*` on a firmware route**, where every other call sends
  `application/json`: a `.bin` is not JSON.

## New libraries (with the one-line justification)

None. The hashing is MeshCore's `rweather/Crypto` (already a dependency, and
already what task 58's reader hashes with), the signature check is MeshCore's
`lib/ed25519`, and the fetch is `HTTPClient` over the `WiFiClientSecure` this
firmware already makes every call on.

No test in this repository can reach the network, write a board's application
slot or pull a board's power, so the whole of the board half is the bench's. The
list is in [`docs/field.md`](../../../docs/field.md) §9 as ⚠ items, in the words
a person at a window would use. It needs **a release of this firmware imported

*Afterwards* list, not before it. On a **V3** and on a **V4**, both saying `two`:

   show the manifest, the signature, *checks 1, 2 and 3 passed*, the ranges and

Four things no test here can reach at all, and what is in their place:

- **The ESP-IDF's OTA writer has never been called.** `src/platform/OtaSlot.cpp`
  is read against the pinned `components/app_update/esp_ota_ops.c` and nothing
  more: the host tests drive a fake slot. Two consequences worth knowing at the
  bench. `esp_ota_write` refuses the **first** write when byte 0 is not `0xE9`
  (`ESP_ERR_OTA_VALIDATE_FAILED`), so on a board a file whose first byte was
  corrupted ends `fetch` — *the other slot refused the bytes at 0* — where a
  host test ends `check` 4; both are refusals and neither leaves a bootable
  image. And `esp_ota_begin` refuses the running partition outright, which is a
  guard this firmware adds nothing to.
- **A board with the framework's default table has not been tried.** It is
  `two` by task 57's word, so a fetch will take it; which of its two slots
  `esp_ota_get_next_update_partition` names is the framework's business.
  `FOLLOWUPS.md` already carries the item.
- **A board whose WiFi drops mid-fetch.** The resume is tested against a
  scripted drop; a real TLS connection going away mid-body is the bench's. A
  fetch that a **restart** interrupts begins again, which is out of scope and in
  `FOLLOWUPS.md`.
- **Neither half has read a release the other made.** This task's scripted
