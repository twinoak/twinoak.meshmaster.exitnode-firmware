# p1.15-61 — The server asks

Tasks 57, 59 and 60 let a person at the console add the slot, fetch a release, switch
to it and watch it proved or undone. This lets a person on meshmaster.dk do the same
with one press.

**It is not a job.** A job belongs to a repeater and this is about the exit node
itself, so the server asks in the reply to this board's heartbeat — in every reply
from the moment somebody pressed until the result is recorded — the board does the
steps in order by itself across two restarts, and posts **one** result to
`POST /agent/v1/updates/{id}/result` until the server takes it.

```
[12:03:10] I update: check: table one, 0.7.2+4a4e791 running
[12:03:10] I update: adding-slot
[12:03:10] W update slot: added     app1 at 0x350000, 0x320000 bytes; reboot for it to take effect
... the board restarts ...
[12:03:41] I update: update 17 is in hand at `adding-slot` and goes on from there
[12:03:41] I update: fetching: 0.8.0+1a2b3c4, 1446640 bytes
[12:04:22] W update: fetched 0.8.0+1a2b3c4, 1446640 bytes, sha 4f2a91c0b7d2e5a8...
[12:04:22] I update: switching: 0.7.2+4a4e791 to 0.8.0+1a2b3c4, 1446640 bytes, in app1
... the board restarts ...
> update
asked     update 17 in hand at `proving`: release 9, 0.8.0+1a2b3c4, 1446640 bytes
          no job is claimed until it has ended; 0.7.2+4a4e791 is what was running
[12:05:11] I update: committing: mesh, wifi and the clock, and a heartbeat answered 17 s into the trial
[12:05:11] I update: update 17 ended committed: the result goes out at the next heartbeat
[12:05:31] I server: the result of update 17 was taken
```

**The library carries the two members and the post, and nothing of an update.** One
more optional heartbeat member behind a provider, exactly as the observer's is; one
more member on `HeartbeatReply`; one more call on `IUplink` — **with a body**, which
is the one way a call can be added to that seam without breaking every tree that
pins it. A consumer that hands the loop no `IUpdateProvider` writes no member, reads
no ask, holds no claim, makes no call and sends the heartbeat it sent before **byte
for byte**; the Walter builds unchanged and updates itself by a job of its own.

**One file of new portable code.** `src/update/Ask.cpp` is the machine — the ask, the
steps, the record that outlives the restarts, the journal that becomes the result's,
and the result's bytes — on six seams: `AskTable` (task 57's word and its one write),
`AskFetch` (task 59), `AskTrial` (task 60), and task 59's `RecordStore` with task 60's
`TrialClock` and `DeliberateRestart`. `test/test_update_ask` drives all of it across
two and three scripted boots: a store that is a map and outlives a "reboot", a table
whose word a test sets, a fetch that answers whatever ending a test gives it, a trial
that keeps task 60's own record the way task 60 keeps it, and a restart that
**returns** so that a test can look at what was left behind.

## Deviations from the spec or the task

- **A fetch is not begun until the server can be reached**, which the task does
  not say. An ask at `fetching` that a restart interrupted begins again at the
  next boot — `FOLLOWUPS.md`'s own rule — and at that moment the WiFi has not
  joined: the three tries a file gets would be spent in three passes of the loop
  and the ask would end `refused`/`fetch` for nothing. So `AskFetch::ready()` is
  a seam of its own (the board: started up, the server configured, the link up)
  and the step waits at `fetching` until it answers.
  `TheRefusals.AFetchWaitsForTheLinkRatherThanSpendingItsTries` and
  `.AFetchThatARestartInterruptedBeginsAgainAtTheNextBoot` are the two tests.
- **A different `id` while one is in hand, or while the result of the one before
  it has not been taken, is not taken now** — it is logged and left, and the
  server asks again in its next reply, which it does *in every reply until it has
  the result*. The task says what the **same** `id` does in both states and is
  silent on a different one; the board holds one ask and one result at a time, so
  taking a second would mean losing a result that deliverable 6 says must survive
  until it is taken. `TheSameId.ADifferentIdIsNotTakenWhileOneIsInHandOrItsResultWaits`
  holds it, including that the second ask **is** taken once the first result has
  gone.
- **A refusal and a `stuck` add one journal entry of their own**, whose step is
  the outcome's word and whose note is the sentence — `refused: the table is
  `other`…`. Deliverable 3 asks for one entry per *step*, and an ending is not a
  step; but a refusal's journal would otherwise be the `check` entry alone and the
  server keeps the journal as it came, so the reason would be nowhere a person can
  read it. A commit and a rollback add none: task 60's own last entry already says
  it, which is why the contract's sample ends at `restored`.
- **A switch the framework refused ends the ask `stuck`, not `refused`.** There is
  no refusal word for it: the release was fetched and judged, so it is none of the
  five, and `stuck` is *the board cannot say what happened* with the framework's
  own sentence in the journal. The same for a fetch that ends `slot` (which the
  table word should have caught) and for a table that is not `two` after the slot
  was written, which deliverable 3 names `stuck` itself.
- **An ask for another product is refused by the fetch's own check 2**, not at
  `check`. It is out of scope as a feature and there is no refusal word for it;
  the manifest's product is check 2 of `FIRMWARE-MANIFEST.md` §5 and it is checked
  **before one byte of an image is asked for** (task 59), so such an ask costs two
  small requests and ends `refused`/`check` 2 with the product named. A word of
  this task's own would have been a sixth refusal the server does not know.
- **An `update` object in a reply that is not of the shape is dropped and the rest
  of the reply is still taken** (`HeartbeatReply::updateRefused`, which the loop
  logs). Refusing the reply whole would make a member the server is free not to
  send at all into a failed heartbeat, a backoff, and in the end an exit node the
  page reads as offline. The ask comes again in the next reply, so the cost of
  dropping one is thirty seconds.
  `UpdateAskReply.AnUpdateThatIsNotOfTheShapeIsDroppedAndTheReplyIsStillTaken`
  holds all eight ways to be malformed.
- **`update fetch` and `update apply` are refused at the console while an ask is
  in hand**, in a sentence, as task 60 refuses them during a trial and for the
  same reason: the ask is doing those steps itself.
- Nothing else. The spec sections the task names are this repository's own pages,
  the library's headers and tasks 56 to 60's reports; meshmaster.dk's task 244 is
  not on its master yet, so the contract is the five lines the task carries and
  they are in `tests/fixtures/contracts-ahead/` byte for byte.

## Decisions taken without asking

- **The heartbeat's `id` and `step` are written while the ask is *in hand*, and
  not while its result is merely waiting.** The contract says *only while an
  update is in hand*; once the ask has ended the result's post is what tells the
  server, and the member is the table word alone. So the server never sees a
  `step` that contradicts a result it already has.
- **`step` is the newest entry of the journal, wherever that journal is.** Before
  the switch it is this ask's own (`check`, `adding-slot`, `fetching`); from the
  switch on it is task 60's record's (`switching`, `proving`, `committing`,
  `rolling-back`, `restored`), which is why the heartbeat says `proving` during
  the trial without this task writing that word anywhere. `kStepSwitching` and
  `kStepProving` moved out of `Trial.cpp`'s anonymous namespace into `Trial.h` so
  that there is one spelling of each and not two.
- **The result's journal is this ask's entries followed by task 60's record's**,
  appended at the moment the ask ends and only when that record **is** this ask's
  switch (its `to` is the version asked for and its `from` is what was running
  when the ask was taken). Without that test a refusal would carry the journal of
  whatever update the board made last month.
- **Two versions are the same release when the part before the `+` matches**, and
  the build metadata only when both sides carry it. The server's catalogue may
  hold `0.8.0` where the image says `0.8.0+1a2b3c4`, and `current` would never
  fire on a plain `strcmp`; two builds of the same version are still different,
  because the commit is part of a release.
- **The ask is taken from `loop()` and never from the pump inside a job.**
  `onUpdateAsk` is called from inside the heartbeat, which this firmware also
  sends from inside a long job (`heartbeatIfOverdue`), and taking an ask writes
  flash and restarts the board. So the ask is kept in RAM and `Asked::step()`
  takes it one pass later — which is also what makes *a job that was running when
  the ask came is finished first* true for nothing: a claim runs to its end before
  `loop()` looks at anything else.
- **`holdsJobs()` holds the claim and nothing else.** `claimDue_` is **not**
  cleared while it is held, so the claim the server asked for is made as soon as
  the ask has ended; and the branch does not `return`, so the observation batch
  still goes out — a board in the middle of an update is still an exit node, and
  what its radio heard is not the update's business.
- **The journal comes to the library's writer through an interface
  (`mm::UpdateJournal`) and not an array.** Forty entries of a bounded step and
  note are four kilobytes of structs on a board with 62 % of its RAM in use, and
  this firmware keeps them as one text already (task 60's `Journal`). The two
  strings are borrowed and overwritten at the next call, which the writer allows
  because it writes each entry before it asks for the next.
- **A result's body buffer is 2 048 bytes, and a journal too long for it is
  shortened from its oldest end.** Forty entries at the contract's bounds come to
  about 3 900 bytes and a real result is seven entries and under five hundred, so
  the choice is between two kilobytes of `.bss` that are never used and a result
  that is not posted at all. `resultToPost` drops the oldest entries until the
  body fits and says in the log that it did
  (`TheResultsPost.AJournalTooLongForTheBodyIsShortenedFromTheOldestEnd`); the end
  of a journal is what an outcome is read against.
- **An `id` of 0 is not an ask.** `loadAsk` reads a record with no id as *no ask*,
  which is what makes a half-written record safe to read; the server's ids are
  rows of its own table and are never 0.
- **The 404 is an answer and not a failure.** `doUpdateResult` calls
  `succeeded()` for a 200 and `noteFailure` for anything else **except** the 404,
  which earns no backoff and no counter: the server has told the board something
  definite and asking again would be asking a question that has been answered.
- **The table word is read out of the sector once a boot and remembered.** The
  heartbeat asks for it every thirty seconds and the sector is four kilobytes of
  flash; writing the slot forgets it, and the boot after that reads it again.
- **The provider is handed over whether or not the board has a release key**, and
  answers `false` when it has none. The alternative — not calling
  `setUpdateProvider` at all — would have the same effect on the wire and would
  put the decision in `main.cpp` instead of in the one file that owns it.
