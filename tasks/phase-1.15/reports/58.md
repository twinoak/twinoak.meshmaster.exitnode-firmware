# p1.15-58 — A release says what it is, and is signed

A release of this firmware was, for each board, two images and `SHA256SUMS`.
Nothing in it was signed and an image did not say inside itself what it was: a
person read the file's name and flashed it. A board that fetches its own
firmware has no person reading names, and neither has MeshMaster's catalogue.
So a release now carries the three things the repeater's and the Walter's do:

| | |
|---|---|
| `manifest.json` | every published file with its size, its SHA-256, the board, the band and the address it loads at. `tools/release/build_release.py` writes it **from the files themselves** — no size, no hash and not even the `ota` load address is typed; that comes from `app0` in the table the environment names |
| `manifest.json.sig` | `ed25519 <key id> <base64>`, one line: one signature over the manifest's bytes, made in the release job with the `RELEASE_SIGNING_KEY` secret. One signature covers the whole release |
| the descriptor | 96 bytes in each image — role **32** (`exit-node`), slot `0xFF`, link 0.0, the version, the board, `868` — placed by the build and checked in CI for both boards, in the application image and in the merged one |

And the firmware got the keys and the code to check all three: `src/update/`,
which the native tests build whole and which contains no ESP32 call.

```
> update
image     exit-node heltec_v3, band 868, version 0.8.0+1a2b3c4
keys      1 release key trusted: 73efdd383a957596
table     two
app0      0x010000, 0x330000 bytes
app1      0x350000, 0x320000 bytes
```

**`FIRMWARE-MANIFEST.md` is the hardware repository's, and it does not know this
product.** Its reference implementation, `spec/tools/manifestref.py`, lives
there and in the Walter's checkout of it — not here. So the document is
transcribed again, as `tools/release/manifest.py`, with the three values this
pile chose on 18 November (`twinoak-exitnode-firmware`, `exit-node`, the byte
32), and what holds the transcription to the reference is not a promise: the
specification's fixtures are now a synced set here, and
`tools/release/test_release.py` re-derives **every** signature, descriptor and
canonical form `index.json` records and refuses a difference. The firmware's
reader is a third implementation, in C++, held against the same fixtures.

**Three readers of §4, one set of bytes.** `manifest.py`'s `make_descriptor` is
what the build places in the image (through `tools/pio/release_headers.py`),
what the manifest is written beside, and what `tools/check-descriptor.py`
checks — so the descriptor inside a file and the entry above it cannot come from
two different ideas of the specification.

## Deviations from the spec or the task

- **The specification's reference implementation is re-implemented, not
  imported.** `spec/tools/manifestref.py` is the hardware repository's and is
  not in this tree; the synced fixture set carries `FIRMWARE-MANIFEST.md` and
  the generated fixtures but not the generator. It also knows nothing of this
  product: `PRODUCTS`, `ROLES` and the role byte 32 would all have to be edited
  there. So `tools/release/manifest.py` is the document transcribed again, and
  the three refusals that would otherwise be a comment are tests:
  `test_release.py` re-derives every signature, every descriptor and every
  canonical form of `index.json` with it. A difference between this file and the
  reference is a red build here, which is the strongest thing available without
  a shared package.
- **"the other board's `ota` file under this board's name and hash" is held with
  the *other* file's hash.** Read the other way — this board's hash over the
  other board's bytes — check **4** refuses it, and check 5 is never reached. The
  case the criterion is about is a file swapped *and its hash swapped with it*,
  which is what a manifest written over the wrong files looks like, and then the
  only thing left to catch it is the descriptor inside the image. That is the
  test, and it fails at check 5 naming `heltec_v4`.
- **The manifest carries `upstream`.** §2's optional `upstream` object is
  written, with MeshCore's name, the `[meshcore].tag` and the pin, because this
  firmware is built on MeshCore exactly as the repeater's is and the field costs
  nothing. The task does not ask for it; nothing reads it yet.
- **The version `0.8.0` in the task is not typed anywhere.** `VERSION` says
  `0.7.2` today (the notes pull request of `v0.7.2` is still open), and the
  manifest's `version` is whatever the build was given — the release workflow's
  `-D MESHMASTER_AGENT_VERSION`, which comes from `VERSION`. Which number the
  first signed release carries is `VERSION`'s and Thomas's; the pile's README
  already asks him to merge that pull request first.
- **The descriptor's reserved bytes are not checked, and its strings are checked
  a little harder than the reference checks them.** Bytes 80–91 are *reserved,
  zero* in §4's table and this reader does not look at them: the crc already
  covers them, and a later schema that gave them a meaning would be refused for
  nothing. Its strings must be zero-terminated inside their field — §4's own
  words, which the reference does not enforce — and printable ASCII, because they
  end up in a line a person reads.
- Nothing else. The sections the task names agreed with the task throughout.

## Decisions taken without asking

- **Ed25519 twice, and no new library.** The firmware verifies with MeshCore's
  `lib/ed25519`, which it already carries for its identity and which is already
  compiled into every environment. The tooling signs with
  `tools/release/ed25519ref.py`, RFC 8032 §6's own reference implementation in
  the standard library — not `cryptography`, which would be a compiled wheel on
  every runner that touches a release. Both are proved on RFC 8032's first test
  vector before they are trusted with a release, and the Python one reproduces
  the reference implementation's signatures over the specification's manifests
  **byte for byte**, which is a stronger check than a test vector.
- **The two generated headers go into the source tree, git-ignored.** With
  `framework = arduino, espidf`, `src/` is compiled from the CMake code model and
  an include directory added to the SCons environment does not reliably reach it
  (`tools/pio/arduino_component.py` is a page about that). A header beside the
  file that includes it needs no include path at all, so
  `src/update/generated/trust_keys.h` and `image_descriptor.h` are written there
  by a `pre:` script of every environment and are in `.gitignore`.
- **The descriptor's bytes are made by Python at build time, not by `constexpr`
  C++.** The crc has to be right *in the file*, so it cannot be computed at run
  time; a `constexpr` computation would need a C++ standard the board build does
  not promise. Generating them from `manifest.py` has a better property anyway:
  the bytes in the image and the bytes the manifest is written beside come from
  one function.
- **`update` reads the descriptor, which is also what keeps it in the image.**
  `--gc-sections` collects a `const` array nothing refers to, so the one line
  that proves the descriptor is there on a bench is also what makes sure it is.
- **The test key is allowed in `keys/release-keys.txt` for a test build and
  refused for a release build.** That is what makes the criterion above
  demonstrable in one file, and it is the same loader either way: the release
  gate and `tools/gen-trust-table.py` both call `load_keys`, which takes
  `test_build` from who is asking. `[env:native]` is the only test build, and it
  gets the key from the fixtures rather than from that file in the ordinary case.
- **The reader is bounded, and says so when a manifest outgrows it.** Four files
  an image, 96 characters a file name, and the refusal is check 3 — *says more
  about itself than this reader holds* — rather than a truncation nothing
  notices. A manifest for another board is not read into memory at all.
- **The firmware does not require the canonical form.** §2 calls it "a
  convention for diffs, not a requirement", so only the release gate insists on
  it; a board checks the signature over whatever bytes it was given.
- **The sync copies the firmware set byte for byte, through base64.** The other
  two sets are normalised to UTF-8 with LF on the way in; a signature is over a
  file's bytes, so one line ending changed would make every signature in the
  directory fail, and a `.bin` would be corrupted outright. The contents API's
  own base64 is the one way through `gh` that no byte is touched, and
  `.gitattributes` keeps git out of them afterwards. Their `MANIFEST.txt` and
  `README.md` are not copied: those two are each repository's own.
- **`SHA256SUMS` still covers the images only.** The manifest's own hash would
  add nothing — the signature is over its bytes — and the gate holds
  `SHA256SUMS` against the manifest, so the two cannot drift.

## New libraries (with the one-line justification)

None. The signing is `tools/release/ed25519ref.py` (RFC 8032's reference
implementation, standard library only, proved on the RFC's first test vector),
and the verifying is MeshCore's `lib/ed25519`, already a dependency.

## Not verified here (and why)

A session cannot flash a board, and **nothing here fetches anything** — this
task made the three things a release carries and the code that checks them, and
task 59 is what first reads a release off the network. So the bench list is
short, and it is one new ⚠ item in
[`docs/field.md`](../../../docs/field.md) §9 beside task 57's:

1. **⚠ `update`'s first two lines on a released image**, on a V3 and on a V4:
   `image  exit-node <board>, band 868, version X.Y.Z+<sha7>` — the board's own
   name and the version `status` prints — and `keys  1 release key trusted:
   73efdd383a957596`. Neither *carries no descriptor this firmware can read* nor
   *no release key in this build* may appear on a released image: the first would
   mean the build did not place the 96 bytes, the second that the board trusts
   nobody and would take no update at all.
