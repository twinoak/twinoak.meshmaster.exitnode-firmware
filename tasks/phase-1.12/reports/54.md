# p1.12-54 — The release says what is left

On 13 November the button published `v0.7.1` correctly and the run ended **red**,
with a summary that offered two causes — a setting switched off, or `master`
changed while the run was publishing — neither of which had happened. What had
happened is what happens at *every* release: `master` requires
`build (heltec_v3)` and `native tests`, so the job cannot merge its own pull
request.

**A release that published is now a green run** whose summary's first line names
the one pull request left for a person. Red is kept for the two endings where
nothing is waiting for anybody because something really failed.

| | Before | Now |
|---|---|---|
| pushed, opened, not merged | red, *its pull request is not merged* | **green**, *vX.Y.Z is published; pull request #N is left for a person to merge* |
| the cause it names | a switched-off setting, or `master` moving | the checks `master` requires, and the `ci` run GitHub holds for a maintainer's approval |
| not pushed / not opened | red, the same sentence for both | red, each with its own first line and sentence; the setting stays where it *is* the cause |
| where it is decided | shell in `release.yml`, untestable | [`tools/release.ps1 -Action outcome`](../../../tools/release.ps1), nine new self-test cases |
| what the pull request says | *No check runs on this pull request* | which checks `master` requires, that the run is held for approval, and the two ways to finish |

Nothing a person who runs an exit node notices changes, so there is **no line in
`release-notes/unreleased/`** (`docs/release.md` §2). Nothing was published and no
tag was pushed by this task.

## What the run says now, in the ending every release has

```
### v0.7.2 is published; pull request #61 is left for a person to merge

The release is out and nothing needs undoing. What is left is the pull request that
files its notes and moves the version on: #61, from `release/v0.7.2`. This job cannot
merge it, and that is every release - `master` requires `build (heltec_v3)` and
`native tests` before a merge, and GitHub holds the `ci` run of a pull request raised
with the job's own token for a maintainer's approval (*1 workflow awaiting approval*),
so neither check reports by itself.

Either way of finishing it is right:

- approve the run on the pull request and merge it when it is green;
- merge it without waiting: the commit touches the release's own files and nothing
  else - `VERSION`, the three manifests, `CHANGELOG.md` and `release-notes/`.

Until then the next press refuses with *the tag v0.7.2 already exists* - which is the
point: the version has not moved (docs/release.md).
```

and, because a green run is glanced at rather than read,
`::warning::v0.7.2 is published; pull request #61 files its notes and moves the version on, and is left for a person to merge`
on the run itself.

## The shape of the step

`release.yml`'s last step no longer decides anything. It walks as far as it gets,
keeps four facts, and hands them to one place:

```powershell
./tools/release.ps1 -Action outcome -Tag $env:TAG -Branch $branch -Number $number `
  -Pushed:$pushed -Opened:$opened -Merged:$merged -Because $because
exit 0
```

Pushed or not, opened or not, merged or not, in; the exit code and the summary's
first line, out. `outcome` throws for an ending that is a failure, which is what
turns the step red; `exit 0` is the rest, explicitly, because the runner ends a
`pwsh` step with `$LASTEXITCODE` and the last `gh pr merge` of three attempts
that were *meant* to fail would otherwise decide it. (On 13 November that
leftover is also why the exception read `could not be merged (0)`: the code it
printed came from the `gh pr view` after the merge, not from the merge. Each
attempt's own answer is captured now and printed.)

Everything that used to `throw` inside the step — the move, the stray-file guard,
the commit — now sets `$because` and falls through to the same place, so there is
exactly one exit from that step and one writer of its summary.

## Decisions taken without asking

- **`$script:MasterRequires` is a constant in `release.ps1`, and the only copy of
  `master`'s required checks in the tree.** The job cannot read branch protection
  — that needs admin rights its token does not have, and a release's last step is
  the wrong place to find out — so the two names are written down once, with a
  comment saying they are a repository setting. Both the summary and the pull
  request's body read them from there, so they cannot drift apart from each other;
  they can drift from `master` if Thomas changes the rules, which is the follow-up
  already open in `FOLLOWUPS.md` and the one thing that would also make the job
  able to merge its own pull request.
- **The pull request's body moved into `release.ps1` too** (`-Action pr-body`,
  written to `out/notes-pr.md` and passed as `--body-file`, as the Walter's is).
  It names the required checks, so it wanted the same constant; and a text with a
  test is what deliverable 4's rail needed, rather than a grep over a YAML file
  for a sentence that is gone.
- **A green ending also writes `::warning::`.** The deliverable asks for the
  summary's first line; a release that leaves something for a person should say so
  where a run is glanced at and not only where its summary is read. The Walter's
  `waiting` does the same. A merged ending writes neither.
- **Three merge attempts are still made, and still take their twenty seconds**,
  even though *cannot merge* is now the expected answer. They are what the day
  `master` asks for no check needs, and twenty seconds is nothing beside a release
  that takes five minutes. The comment above the loop says that three answers of
  *2 of 2 required status checks are expected* is the ordinary ending and not an
  error.
- **The summary names the pull request as `#N`**, which is what the number is for
  a reader; the branch is named beside it, since that is what a person needs if
  the pull request was never opened.
- **Two sentences elsewhere were corrected rather than left standing**, because
  this task is about a run saying what is true: `release.yml`'s gate comment and
  `docs/release.md` §5 both said *no check runs on that pull request* as a flat
  fact. A `ci` run **is** started and then held for approval, and the reason the
  `ci is green` gate needs `ci-commit` is the narrower one — a commit that a *run
  of this workflow* puts on `master` with the job's own token gets no run of its
  own. The gate's behaviour is untouched; only what the comment claims.
