# p1.18-67 — The stack line, where the words say

Task 65 wrote the loop task's `stack` line into `get mqtt.status` and wrote *in `status`* into two
documents. `status` now prints it, from the same function the boot log and `get mqtt.status` print
it from, and the words name the command each `stack` line is in. One line of C++ and one printf;
the rest is the words and the tests that hold them.

**What a person sees.** `status` has a `stack` line, between `heap` and `uplink`:

```
heap      free 136580, min ever 97212, largest block 73716; after the tls call 136580
stack     loop task: 16384 bytes, the least ever free 10112
uplink    connection kept since 12:03:14 (root ISRG Root X1); …
```

`get mqtt.status` is untouched and still has its three: the loop task's, for scale, and the
observer's two tasks' below it. The boot's line is untouched.

**Where it lives.** `src/main.cpp`'s `printStatus` calls `mm::platform::loopStackLine` into the
`line` buffer it already has for `wifi`, `time`, `server` and the rest — so the function's frame is
**592 bytes, exactly what it was** (the rail's listing, `out/build-67-v3.log`), and no third place
formats either number. `src/platform/LoopStack.h`'s header comment names three callers where it
named two; `test/test_loop_stack` reads `src/main.cpp` function by function and says which command
prints which line.

## Decisions taken without asking

- **The line goes between `heap` and `uplink`**, not at the end. Both lines are this board's own
  memory, so a person reads the heap and the stack together, and the `uplink` and `log` lines keep
  the last word as they had it. Nothing before it moved.
- **It is printed into `printStatus`' existing `line` buffer** (`char line[320]`, already shared by
  `wifi`, `time`, `server`, `heartbeat`, `jobs`, `flood`, `observer` and `uplink`) rather than into
  a `char stack[96]` of its own, as `printMqttStatus` uses. The longest shape of the line is 60
  characters; the buffer is 320; and the alternative adds 96 bytes to the frame of a function on
  the loop task for nothing. `printStatus` is 592 bytes before and after.
- **`get mqtt.status` keeps the loop task's line.** The task's deliverable 2 asks for it, and it is
  what the observer's two numbers are read against: a slot task's 1 560 bytes free of 6 144 means
  something different beside a loop task with 10 112 free of 16 384. The duplication is one line in
  two commands, from one function, held by a test.
- **6 144 bytes comes from the firmware, not from a transcription.** `src/net/MqttClient.h:67`,
  `static constexpr uint32_t kTaskStackBytes = 6144;`, is the number `printMqttStatus` prints and
  `MqttClient` creates the task with, and Aarhus C printed `slot 1 task: 6144 bytes, the least ever
  free 1560` on 20 November (`tasks/phase-1.17/FOLLOWUPS.md`). `docs/observer.md` had it right;
  `docs/console.md`'s sample was written by hand with 8 192, which is what the loop task had before
  0.7.4 and never what a slot had. The sample's `the least ever free 1560` is that same reading.
- **The sample's loop task figures stay 16 384 / 11 240** in `console.md`, `field.md` and now
  `observer.md`, so that the three documents show one board and not three. The real reading, 10 112
  on Aarhus C, is in pile 1.17's `FOLLOWUPS.md` where the measurements are collected, and this
  report's own example above uses it.
- **The test reads function bodies, not the whole file.** `functionBody(text, signature)` cuts from
  a signature to the next closing brace in the first column, which is how `test_receiver` reads a
  function of the pinned MeshCore, and an empty body is an `ASSERT` and not a pass — a renamed or
  deleted command fails the test rather than slipping through it. This is what would have caught
  task 65: a count of two calls in the file could not see that both were in the wrong command.

## Not verified here (and why)

A session cannot flash a board or hear a radio. With a V3 or a V4 on the bench, after the flash:

- ⚠ **`status`, and the line.** Between `heap` and `uplink`:
  `stack     loop task: 16384 bytes, the least ever free N`. This is the whole of the task — on
  0.7.4 there is no such line — and the N is the number pile 1.17's `FOLLOWUPS.md` is waiting for.
  **Read it twice**: some minutes after a power-on, and again after an `update fetch`, which is the
  deepest thing the board does.
- ⚠ **`get mqtt.status` still has three.** `loop task:` first, then `slot 1 task: 6144 bytes, …`
  and `slot 2 task: 6144 bytes, …`, with the same loop task figures `status` just showed. A slot
  that has had no event says `nothing measured yet`; that is not a fault.
- ⚠ **The boot log is as it was**: `stack: loop task: 16384 bytes, the least ever free N` as the
  last line before the board is up, and its N is a little larger than `status`' later one, never
  smaller.
- ⚠ **Nothing else of `status` moved.** The `heap` line is above the new one and the `uplink` and
  `log` lines below it, in that order, and every other line reads as it did on 0.7.4.
