# p1.10-44 — An empty `get` reply is a value

A key whose value is the empty string is answered `"> "` by `CommonCLI::handleGetCmd`, which
`JobRunner`'s `trimInPlace` makes `">"`. `mm::cliReplyValue` wanted `'>'` *and* a space, so that
reply was not a `get` reply to it: the key went into the snapshot's `raw` list and out of its
`values`. A bare `>` is now the **empty value**, which is how the .NET agent has read it since
meshmaster.dk's task p4.23-165 (`CliReplies.ValueOf`). Nothing else of reply parsing moved.

The function reads, after the leading whitespace it already skipped:

```c++
  if (reply[0] != '>') return nullptr;
  const char* after = reply + 1;
  const char* end = after;
  while (isSpace(*end)) end++;
  if (*end == 0) return end;  // the reply's own terminator, which is the empty string
  return *after == ' ' ? after + 1 : nullptr;
```

`end` walks to the terminator only when everything after the `>` is whitespace, and the pointer
returned is then the reply's own NUL — the empty string, with the same lifetime every other return
of this function has. When something non-blank follows, the decision is the old one, byte for byte:
one space after the `>`, or it is not a reply this reads.

**Read against the firmware it parses**, not against a memory of it:
`.pio/libdeps/heltec_v3/MeshCore/src/helpers/CommonCLI.cpp:701-800` at the pin
(`81dbae592ffad40b4212bc0b37e82b38da08f4bc`, companion-v1.18.0) is `handleGetCmd`, and every key it
knows is printed with one `sprintf(reply, "> %s", ...)` — `guest.password` at line 709 straight from
`_prefs->guest_password`, and `owner.info` at 730 writing `'>'`, `' '` and then the characters there
are. Neither has a floor: an unset one is `"> "`.

**Where it is visible.** `JobRunner::runConfigRead` (`JobRunner.cpp:1037`) and `runConfigApply`'s
re-read (`ConfigApply.cpp:391`) are the two callers. A key with an empty value now reaches the server
in `values` / `reRead` as `""` instead of in `raw` / `reReadRaw` as `get guest.password: >`. That is
the point: meshmaster.dk reads an **empty** `guest.password` as *this repeater has no guest password*
and clears the stored one, and through this firmware that answer never arrived as a value, so a guest
password taken off a repeater stayed stored on the server until somebody cleared it by hand. Nothing
was ever stored *wrongly* — absent is read as "not known", never as "none" — so this closes a gap and
does not fix a fault. Neither caller compares a re-read value locally; both only write it out, so the
server settles it.

## Deviations from the spec or the task

None. Two things were read expecting a disagreement and found to agree:

- **`cliReplyValue` and `CliReplies.ValueOf` now answer the same for every input the firmware can
  produce.** The .NET one trims *both* ends before it asks, so it also strips a value's trailing
  whitespace (`"> off "` → `"off"`); this one strips leading whitespace only and leaves the trailing
  to `trimInPlace`, which both callers run on the reply first. After that trim the two are the same
  function, and the test says so where it can (`"> off "` → `"off "`, noted as `trimInPlace`'s job
  and not this one's). Making `cliReplyValue` trim its own tail would have been *something else about
  reply parsing moving*, which deliverable 1 forbids.
- **`kDefaultConfigKeys` is still `ConfigReadPayload.DefaultKeys`**, key for key and in order
  (checked against today's `master` of meshmaster.dk, `src/MeshMaster.Contracts/Payloads.cs:97-98`).
  p4.23-165 did **not** add `guest.password` to the default list; it reads the key with an explicit
  list in the claim, which this firmware already honours (`job.hasConfigKeys`). So there is no list to
  sync here, and `test_config_read`'s pin of that literal stands.

- **A reply that is only whitespace, or empty, is still not a value** (`""`, `"   "` → nullptr).
  There is no `>` in it, so the firmware did not answer a `get` with it, and the .NET side agrees
  (`""` trims to `""`, which is neither `"> "`-prefixed nor `">"`). It is tested, so the distinction
  between *no reply* and *an empty answer* cannot be lost later by accident.
- **A tab after the `>` is not the prefix's space** (`">\tx"` → nullptr, as before). `handleGetCmd`
  prints exactly one space and never a tab, so no firmware reply is affected; only the all-whitespace
  tail is read loosely, because `trimInPlace` and the air can both leave a `"\r\n"` behind.
- **No `docs/` page changed.** Nothing moved in what the board prints, what it needs on the bench or
  how it is flashed. `CHANGELOG.md`'s *Unreleased* carries the consumer-visible line, as tasks 38–43
  of this pile each did.

## Not verified here (and why)

A session can build and run the host tests; it cannot flash a board or hear a radio. The bench list is
short, because this is one function and the suite exercises it against the firmware's own literal:

1. **A repeater with no guest password, read with `guest.password` in the claim's key list.** On
   meshmaster.dk, run a `config.read` against a repeater through this exit node with the key list
   containing `guest.password` and the repeater's guest password **unset**. The result should carry
   `"guest.password": ""` under `values` and **no** `get guest.password: >` line under `raw`, and the
   server should settle the stored guest password to *none* (that half is meshmaster.dk's p4.23-165).
   Before this task the same read put the key in `raw` and left the stored password alone.
2. **The same read with a guest password set.** The value should be the password, unchanged — and note
   that a configuration read is not a redacting path, so it arrives as text: that was so before this
   task too, and nothing here moved it.
3. **An unset `owner.info`**, if the claim asks for it: the same `"> "`, so the same empty value. It
   is not on the default key list, so it takes an explicit list to see.
4. **A `config.apply` whose re-read covers a key whose value is the empty string**: the re-read should
   carry the key in `reRead` as `""`, not in `reReadRaw`.
5. **A regression glance at an ordinary read**: a 16-key default `config.read` should look exactly as
   it did — the keys a v1.18.0 repeater answers `??:` to are still raw lines, `ver` and `board` are
   still the extras, and the ACL is still the last value.

The serial console needs nothing new to walk this: `jobs: job N: cli 'get guest.password'` is already
printed per transaction, and the snapshot that goes up is what the result's `values` shows on the
job's page.
