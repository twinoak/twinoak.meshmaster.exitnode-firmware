# p1.10-50 — Nothing of ours left behind

A login with the admin password writes this exit node's key into the repeater's
ACL **at admin** and saves it to flash (`handleLoginReq`). Task p4.1-60 ends such
a session with `setperm <own key> <granted level>` where we hold a grant — and
where we hold **none**, nothing had ever taken that entry off. Three ways in, all
of them real: the ACL door's own discover on a flow that stopped before its
grant (meshmaster.dk's associations 14 and 6 today), the daily configuration read
of a **guest** association's primary, which is planned at admin, and a one-off
admin job through an exit node whose pair is parked, failed or absent.

meshmaster.dk's p4.33-191 makes the claim say so: `acl: 0` beside the admin
password means *you should hold nothing here*. This firmware is the half that
acts on it. The session's last command is then `setperm <own key> 0` instead of
the restore — the same one line, sent **once** and read back with the blank login
of task p1.10-48, where a check answered at **guest** is the confirmation that the
key is off — and after it the session is **gone with the entry**, because on stock
firmware the entry *is* the session. A job that ended in silence sends nothing and
says the key may still be at admin; a `reboot` and an `acl.set` on our own key
send nothing, for the reasons they already gave.

## Deliverables, one by one

1. **`acl: 0` on an admin claim.** `JobRunner::restoreAcl` is still the one place
   the session's last command is decided, and the level's value is what it reads:
   the gate changed from `job.aclLevel < kPermReadOnly` to `< kPermGuest`, and
   `const bool removal = job.aclLevel == kPermGuest` is what the rest of the
   function branches on. The line is `setperm <own key> 0` through the same
   `writeOwnEntry` the grant and the restore use (task p1.10-48), so it is sent
   once and its silence read back with a blank login; the `what` the log and the
   console print is `removal: cli 'setperm <own key> 0'`. It goes **after the
   job's own lines**, wherever the restore goes — `runClaimed` for the twelve
   types, inside `runConfigRead` for the read's own result, after the password
   line for a `password.set` — and none of those call sites changed. Confirmed,
   the session is **dropped** rather than cached at level 0: the entry is the
   session, and taking the entry off takes the session with it.
2. **A job of another class changes nothing**, and nor does the local door. Two
   clauses, each with one line in the job's log; the decisions below say why each
   is there when no claim meshmaster.dk sends can reach it.
3. **The price.** Nothing moved, and the report of that is the point: the clause
   in `transactionsOf` reads `job.hasAclLevel` and `kTransactionsForAclRestore`
   is the line and its check. `Airtime.h`'s comment on that constant and
   `transactionsOf`'s own now say that a level of 0 is the removal and is priced
   there, so the next reader does not have to work it out from the absence of a
   change. `LoopTest.AWakePricesTheRemovalOfOurOwnKeyAsItPricesTheRestore` holds
   it from the outside.
4. **The fixtures**, at `299df66`. Three files moved and they are p4.32-187's, not
   191's.
5. **The words**, as the checklist lists them.

## Deviations from the spec or the task

- **`tools\verify.ps1` does not exist in this repository.** The last acceptance
  criterion names it, as tasks 47, 48 and 49 did, and there is no such script in
  `tools/`. What it stands for was run by hand: the native suite in a container,
  `pio run -e heltec_v3`, and the four other steps of CI's native job. Either the
  script should be written or the criterion should say what these three reports
  say; that is the reviewer's call. This is the fourth task in a row to record it.
- **The sync brought meshmaster.dk's p4.32-187 timeouts with it, and the library's
  own defaults were left alone.** Deliverable 4 asks for the fixtures at 191's
  commit; 191 changed none, and what lies between the old pin and the new is
  p4.32-187's doubling of `perHopMs` and `loginMs` in the three claim fixtures.
  `ClaimedJob`'s defaults in `agent/JobEnvelopes.h` are still 4 000 and 8 000,
  because they are what the library assumes for a claim that carries **no**
  `timeouts` member and meshmaster.dk always carries one — the firmware has read
  both off the claim since phase 1. `test/support/Jobs.h` keeps 4 000 and 8 000
  too: they are the test's own numbers (`withTimeouts` is there for a test that
  cares), and bumping them would move the simulated clock under every wait in
  three suites for no behaviour this task changes. `docs/library.md` §3.3 now says
  both numbers and which is which. If the reviewer wants the defaults to follow
  the server, that is a task of its own and it belongs with a look at
  `JobDefaults.Transaction`'s lease arithmetic.
- **`aclRestored` carries the removal's outcome, and no new field was added.**
  meshmaster.dk's `ConfigReadResult` is unchanged by 191, so the only member a
  read has for its last command is `aclRestored`: `true` where the key came off,
  `false` where the line could not be confirmed, absent where there was nothing
  to send. Its own documentation is *what became of the exit node's own ACL entry
  after this read*, which is true of a removal word for word, and the server reads
  the field in one place only — `AssociationService.AclSnapshotAsync`, for an
  **`acl`** pair's own read, which is exactly the claim that never carries 0
  (`JobCredential.ForAcl(grant ?? proving ?? ReadOnly)`). So nothing on the server
  reads it as a restore that happened. The alternative was to report nothing,
  which would have left the acceptance criterion's *the result says what became of
  it* to the job's log alone.
- **An `acl.set` for somebody else's key still sends nothing**, as it did before
  this task: `runClaimed` skips the restore for the whole `acl.set` type, not only
  for our own key. The spec's sentence is about our own key (*an `acl.set` on our
  own key sends no second `setperm`: the command is the level*), so a level-0
  claim beside an `acl.set` for a **stranger's** key leaves our entry at admin
  until the next admin job. That is what `TransactionCosts.Restores` prices on the
  server — it excludes `acl.set` and `reboot`, as 191's decision 4 says — so the
  two halves agree, and the next admin job through that exit node takes the key
  off. Unchanged, and named here because the task's deliverable 1 phrases the
  exception as *not for an `acl.set` on our own key*.
- **The spec and the task agreed otherwise.** API §3's `credential.acl`
  paragraph, EXIT-NODES §4.3 (*Our own logins*, *Revoke*) and §7 (*And where the
  key should hold nothing, that last command is its removal*) say exactly what
  this implements, including the two exceptions the **server** holds (an admin
  fallback pair, and the box link) and the price being `TransactionCosts.AclRestore`
  for a `guest` pair as well as an `acl` one. Nothing in 191's report asks anything
  else of this firmware.

## Decisions taken without asking

- **The removal is an admin-class job's alone.** The restore's gate is the
  *session's* role, not the claim's class, because a blank login answered admin
  is the third rule of §7 — and that is the one job that could otherwise reach a
  level-0 line with no admin password behind it. Such a login is no evidence that
  this key should hold nothing (it is evidence that an earlier session died before
  its restore), and the task's deliverable 2 says that case is not this task's to
  judge. So `job.credentialClass != CredentialClass::Admin` refuses it with one
  line in the log. The server cannot send such a claim — `acl: 0` rides beside an
  admin password and an `acl`-class claim carries the level its own login expects
  — which is why the clause is a guard and not a branch anybody walks.
- **And never over a local door.** A unit logs in to its own repeater as the
  repeater it **is**, so `setperm <own key> 0` there is the repeater asked to
  forget itself — the job meshmaster.dk's p4.25-170 refuses to queue — and
  nothing on the other side of that line could put it back: no login takes an
  entry off, and the admin entry a unit's own CLI needs is the one being deleted.
  The claim cannot carry a level over that link (`localDoor ? null`), and the
  restore's own comment says a local job that *does* carry one is restored like
  any other. For level 0 that reasoning does not hold, so `mesh_->answersLocally()`
  is asked and the line is refused with a sentence. It is the one place in this
  task where following the claim would be worse than refusing it, and the walk
  item says that if the line ever appears in a log, the server is the half to fix.
- **One function, two names for one line.** `restoreAcl` keeps both the restore
  and the removal rather than a second method beside it: it is the same line, the
  same `writeOwnEntry`, the same place in the job and the same return value, and
  a second function would have duplicated the four gates and the silence branch.
  What differs is said in words at each branch — the log sentences are the
  removal's own, because *the next login from this key will put it right* is true
  of a restore and false of a removal.
- **The removal's silence says what will take the key off, not what will put it
  back.** The restore's remedy is the third rule of §7 and it costs nobody
  anything; a removal has none of that kind, so every unconfirmed branch names the
  job that will try again — the next admin job through this exit node, which for a
  guest primary is tomorrow's configuration read and for a parked pair is
  meshmaster.dk's revoke. Nothing in the result claims the key came off unless a
  reply or the blank login said so.
- **A confirmed removal drops the session and reports `aclRestored: true`.** The
  first is the firmware's own reading (`applyPermissions` deletes the `ClientInfo`
  the login filled, so there is no session left to keep) and it is what `runAclSet`
  already did for a level-0 line on our own key. The second is in the deviations.
- **The level-0 case of a `reboot` gets its own sentence** rather than the
  restore's. The restore's reason ends *the next login from this key puts the
  entry back*, which is not true of a removal: the key waits at admin until an
  admin job can end with its last command. The old sentence is still printed word
  for word for a claim that carries a level above 0, so the test that reads it is
  unchanged.
- **No new fault knob in the fake, and no new citation.** Task p1.10-48 taught
  `FakeMesh` what `applyPermissions` does to a level-0 entry and where
  `onPeerDataRecv` sends the reply afterwards, so the two readings this task needs
  — the "OK" that comes home and the one addressed to another key — are already
  there and are reached by granting two keys in the right order. `test/support`
  is untouched by this task.

against. It cannot flash a board or hear a radio, so this list is Thomas's with
the board on the bench. It is `docs/console.md`'s walk item **26**, and it wants
meshmaster.dk's p4.33-191 **deployed** first: until the server is running it, no
claim carries `acl: 0` and nothing of this task is reachable.

   repeater with a **guest** association through this exit node and the admin
   password stored — whose configuration probe is planned at admin, which is the
   case that leaves an entry behind every day. `get acl` on the repeater's own
   console first: our key absent, or at `03` from an earlier admin job. Press
   *Read the configuration*; the log must end with `removal: cli 'setperm <own
   key> 0'` and then the repeater's `OK`, or the check at guest and *this exit
   node's key is off it, so the line ran*. `jobs` must count **21**, or 22 with

   `sessions` must show none for that repeater. The read's own `acl` value still
   lists us at `03`, which is why `aclRestored` is in the same result.
2. **The reading of `applyPermissions` for our own entry, again.** Walk item 24 of
   task p1.10-48 is still unwalked and this task now sends the same line on a
   second path: if a level-0 line for our own key *is* answered when our entry is
   not last in the table, `test/support/FakeMesh.h` is wrong and
   `AConfigReadThatHoldsNoGrantTakesTheKeyOffAndTheReadSaysSo` is testing a fault
   that cannot happen (the behaviour would be right either way — an `OK` confirms
   it too — but the fake and the walk should agree).
3. **The three that send nothing.** A `reboot` of the same repeater (`no restore
   and no removal on this session`, and `get acl` still listing us at `03`
   afterwards); a job that ends `unreachable` with the repeater's power pulled
   mid-job (*no login takes an entry off*); and a *Revoke*, whose `acl.set` must
   still be the **one** line of walk item 24 and never two.
4. **The line that must never appear.** A *Read the configuration* of a unit's
   **own** repeater over the box link must send no `setperm` of any level. If
   `no removal over the local door` is ever in a log, the server sent a level over
   that link and meshmaster.dk is the half to fix.
5. **A fleet's worth of the price.** One more transaction a day per repeater whose
   primary is a guest pair, and one per one-off admin job through an unassociated
