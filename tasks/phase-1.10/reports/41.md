# p1.10-41 — No password for a local login

The library decided **what to log in with before it knew the job was local**. At
`admin` with no password in the claim, `loginMaterialFor` answered `nullptr` —
*nothing to log in with* — and `ensureSession` reported `unauthorized` without
sending anything. Every CLI job of a unit's own repeater is `admin`-class, and
the door at the other end of that seam answers the login *itself, at admin,
whatever it carried*. So the question is now asked **first**: for a job the mesh
answers without the air the material is the **empty string at every class**, and
a unit configures its own repeater with no admin password stored on
meshmaster.dk at all.

That is the refusal of 7 November 2026 — job 22016, the scheduled `config.read`
of a re-registered repeater, *no admin password stored*, for a radio whose
settings had been lost and whose admin password is therefore a random one nobody
knows (S-13). It is the item *An admin job for the unit's own repeater needs a
password nobody reads* of `twinoak.meshcore.walter-firmware`'s
`tasks/phase-8/FOLLOWUPS.md`, whose **Fix** reads *skip the material check for a
job the local door will answer* — which is what this is, one line earlier in the
function than the check it skips.

**This board loses nothing and changes nothing.** The Heltec has no local door,
`AgentMesh` keeps `answersLocally()`'s default `false`, and every path through
the material decision on this firmware is the path it was — down to the log
line. Four files of code, two of words, two of tests.

## Decisions taken without asking

- **The door is an argument of the material decision, not a branch in the
  runner.** `loginMaterialFor` gained a `bool answeredLocally` as its **second**
  parameter, with no default, so that the one caller must answer the question and
  every branch of the decision stays walkable on a host (`test_rotation_probe`,
  where it now runs twice: through the door and on the air). The alternative — an
  `if (mesh_->answersLocally()) material = "";` in `JobRunner::loginMaterial` —
  would have put a branch of the policy back on the board, where no native test
  reaches it; `GuestDoorOnTheBoard.TheRunnerTakesItsMaterialFromThePolicyAndSendsNothingWhenThereIsNone`
  now greps for the call *and* for the absence of such a branch. The cost is a
  **signature change in a public header**, which is a compile error for a
  consumer that calls the function itself. None does: `JobRunner` is its one
  caller in this tree and in the Walter's vendored copy, and `CHANGELOG.md` says
  so in as many words.
- **The material is `""` at every class, and a password the claim carried is not
  sent at all.** The door does not look at it (`localLogin` ignores its
  `password` argument), so sending it would be a password on a wire for no
  reason; and the claim's password is still never logged, still wiped with the
  credential, and now goes nowhere it did not go before — strictly fewer places.
  The one shape where a claim carries material for a local job *and* means it is
  a `password.set`, whose **new** value rides in the credential and goes out as a
  CLI line as it always did (meshmaster.dk decrypts the pending value first and
  hands it with no login material beside it); that path is untouched.
- **No cut line for a local job.** A password longer than fifteen bytes is cut,
  and said so, for a login that *goes out*. A local job sends none, so there is
  nothing cut and nothing to say — `ALocalJobGetsNoCutLineBecauseNothingOfThePasswordIsSent`
  holds both halves, the silence through the door and the cut line on the air.
- **One line, and it names the class.** The task asks for a note *answered by the
  board, no password needed*; the line is that sentence plus `: the empty material
  at class <class>`, because the class is what the decision was about and the same
  line is now printed for `admin`, `guest`, `acl` and `none`. It sits next to
  task 40's *this mesh answers for this repeater without the air* line, which says
  why the job is not paced; this one says why it needed no password. Neither takes
  a value as an argument.
- **`restoreAcl` was re-read and not changed.** The comment is the deliverable: a
  reader who wonders what the door does to the restore now finds the answer
  beside the gate, and the test holds both sides of it. Changing the gate to
  mention the door would have been a second place to get `hasAclLevel` right.
- **The fake stays a stock repeater, and a local admin session comes through its
  ACL.** `FakeMesh` is this repository's second reading of MeshCore, with every
  answer cited to a fixture or to a function of the pinned firmware
  (`Citations.EveryAnswerOfTheFakeCitesAFixtureOrAFirmwareFunction`). The local
  door's login reply is the **Walter's** behaviour, not MeshCore's, and the
  manifest has no citation form for it — so the fake was *not* taught to answer
  every login at admin. A test that wants a local admin session says
  `mesh.grant(self(), kPermAdmin)` and gets the same answer by the stock route:
  `handleLoginReq`'s first statement answers a blank login at the level the ACL
  holds the key at. That is why task 40's
  `A34LineReadThroughTheLocalDoorWaitsForNoBudgetAndSpendsNone` gained that one
  line — its claim's password is no longer what opens the session — and the
  comment there says so. Its pacing assertions are untouched and still pass to the
  figure.
- **The fake records *whether* a login carried material, never what.** `Send`
  gained `bool withMaterial` and the fake `loginsWithMaterial()`, which is how a
  test sees that the claim's password stayed where it was. A recorder of the
  value itself would have been a second copy of a password in the harness for no
  extra proof.
- **`docs/library.md` §3.5 is new rather than a row added somewhere.** The
  material decision was documented only in the header's comment and in
  `docs/console.md`'s sentence about what a job's log prints; the library's page
  described the login's *failures* (§3.4) and not what it carries. A consumer
  implementing `answersLocally()` has to know that the login it is handed may be
  the blank one at `admin`, so the whole decision is now one table on the page
  that consumer reads, and the new row is first in it because that is the order
  the function decides in.
- **`docs/console.md` was not changed.** It is this board's console, and this
  board has no local door: none of these lines can appear on a Heltec. Its
  sentence *An **admin** job whose claim carried no admin password is still
  `unauthorized` with nothing sent at all* stays exactly true here, which is the
  same reason task 40 left that page alone.
- **The row and the entry say "unreleased".** A release task gives a change its
  version; this task is not one, so §3.2's row and §3.5 point at `CHANGELOG.md`
  for the version, as tasks 39 and 40 did.

## Not verified here (and why)

A session cannot flash a board or hear a radio — and, as with task 40, there is
something more: **nothing of this change is visible on this board at all.** The
Heltec keeps `answersLocally()`'s default, so `answeredLocally` is false at every
login this firmware makes and every branch of the decision is the branch it was.
The bench list is therefore in two halves: what proves the exit node is
unchanged, and what proves the change works, which needs a Walter.

**On the exit node (that nothing moved):**

1. **An `admin` job still needs its password, and says the same thing when it has
   none.** Queue a `cli` for a repeater whose stored admin password is **not**
   set (or clear it on meshmaster.dk for one job): the result must be
   `unauthorized` at **0 transactions** with *the claim carried no admin
   material; nothing to log in with* in the log and **nothing on the air** — the
   board's frame log (`agent frames`) must show no login. A job that suddenly
   runs would mean this board picked up a local door it has not got.
2. **An ordinary `config.read` through the exit node is unchanged.** The same
   transaction count, the same `aclRestored`, the same *waiting 20 s for the
   airtime budget* lines, and the same `setperm <own key> 1` as the session's last
   command. The job's log must **not** contain *answered by the board, no password
   needed*; that line belongs to no job of this board.
3. **A guest job with no guest password still logs in blank** (`no guest password
   in the claim: the blank login …`) and a cut password still says it was cut.
   Those two lines are the neighbours of the new one and the easiest way to see
   that the decision's order did not shift under them.

**On a repeater-v2 unit's Walter (that the change works), once its pile 9 syncs
this library — this is its task 05's bench, listed here because it is what this
task is for:**

4. **The read that was refused.** Job 22016's shape — a scheduled `config.read`
   of the unit's **own** repeater — with **no admin password stored on
   meshmaster.dk at all**. The claim must come down with no credential, the job
   must come back `ok`, its log must carry *answered by the board, no password
   needed: the empty material at class admin* and **no** *nothing to log in
   with*, and `LinkMesh::linkCounters()`' `local_jobs` must have moved while
   `client_tx` has not. This is the one that matters: before it, the job never
   left the server.
5. **A fresh radio, whose admin password nobody knows.** The whole point of the
   task: provision a radio with a random admin password (S-13), register it, and
   run `cli`, `config.apply` and `clock.sync` of it **through its own unit** with
   nothing stored. Each must log in blank and run. A refusal here is the server's
   version gate (`TheUnitsWalterIsOlder`), not this change.
6. **A password typed for one job still rides.** Under prompt custody,
   meshmaster.dk hands a one-shot value even for a local pair. A `password.set` of
   the unit's own repeater must still **set** the new value over the console CLI
   while logging in with nothing — the value in the credential, no material
   beside it.
7. **Nothing is restored on the unit's own repeater.** No `setperm <own key> …`
   may appear on the console of a local job, and the radio's access list must be
   what it was after one. A `setperm` there would mean a level reached the claim,
   or the restore was keyed to the session.
8. **A job for a repeater that is *not* the unit's own still needs its password.**
   The same unit, a neighbouring repeater over the air, at `admin` with nothing
   stored: still `unauthorized`, still nothing sent. This is the one that catches
   a door left open — a `setOwnKey` that matches too much, or an `answersLocally()`
   that stays true after the `endJob`.
9. **The guest and acl classes through the door are unchanged in effect.** They
   logged in blank before this task too, so a local `status` must read exactly as
   it did on 0.1.1 — same outcome, same data — with the new line as the only
   difference in its log.
10. **The wake does not refuse it.** Task 40's named follow-up, unchanged by this
    one: `AgentLoop::wakeJobs` still prices a 34-transaction local read as
    `n × (minGapSeconds + loginMs)` and can report *wake budget* at no
    transaction on a short wake. If the bench sees that, it is that follow-up and
    not this change.
