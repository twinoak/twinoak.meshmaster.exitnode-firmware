## Deviations from the spec or the task

- **The task says the notes "still describe v0.6.0"; the heading said *since
  v0.5.0*.** Both are the same thing — v0.6.0's notes are *What's new since
  v0.5.0* — and nothing follows from it but the wording of this line.
- **The notes' *What's new* is nine bullets and an opening sentence, not five.**
  `release.yml`'s comment above the block said *This release's own five lines*,
  which was v0.6.0's count written into a comment that is about the block and
  not about a number; the comment now says *This release's own lines*. Thirteen
  tasks do not compress to five bullets without dropping a report, and the task
  asks for *the rest, one line each*.
- **Tasks 40–43 are one bullet between them, not four.** The task says *then the
  rest, one line each*. These four change nothing on a Heltec — every one of
  their reports says so in its own words — so four lines of a release note for a
  person running an exit node would each have had to say *and this does nothing
  on your board*. They are one bullet that says it once, names all four changes,
  and says whose board they are for. Nothing of them is left out.

## Decisions taken without asking

- **The bootloader warning stays, reworded.** Pile 1.9's bench step 4 (a first
  install from 0x0 with the merged image) is optional and there is no record of
  it anywhere in this repository: pile 1.9's FOLLOWUPS is empty, and report 37
  lists it as bench item 3, unwalked. The sentence could not stay as *new in
  this release* — it is v0.6.0's bootloader now — but dropping it would be
  claiming a walk nobody made, which is what deliverable 2 forbids. It now says
  whose bootloader it is and that no first install from 0x0 with it is on
  record.
- **`## Unreleased` stays, saying *Nothing yet*.** 37's decision, kept.
- **The thirteen per-task bullets stay under the v0.7.0 heading rather than
  being rewritten into a summary.** They are what each task wrote about its own
  change for a consumer of the library, and v0.5.0's section has the same shape:
  the four questions first, the detail under them. What this task added above
  them is the pile-wide answer, which is the thing a pin has to read and which
  no single task could write.
- **`docs/library.md` §9 moved with the fixture bump**, because its two
  sentences name a commit per tag and would otherwise have said `v0.6.0` was the
  newest. *Docs move with code*, and the manifest is the code here.
- **The notes do not mention the two claim timeouts doubling** (`perHopMs`
  8 000, `loginMs` 16 000, which came across in 50's fixture sync). It is
  meshmaster.dk's own change, already live on the server since its 4.32, and
  nothing a person flashing this board does or sees; `CHANGELOG.md` carries it,
  because a consumer that prices a lease has to know.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and **nothing of this release
has been on the air**: the thirteen tasks are host-tested and contract-tested
and no session of any of them opened a serial port. The list below is the
pile's bench list gathered in one place, Thomas's with `v0.7.0`'s images. The
walk items are `docs/console.md`'s.

1. **The four that matter, in the order they bite** —
   **item 22** (47): a repeater slow enough to answer late, two *Read the
   neighbours* inside a session's lifetime; `login (acl) try 1: refused` must
   never appear again and the association must stay `active`.
   **item 23** (48): a grant whose "OK" misses its 16 s wait — *no answer, and
   this line cannot be asked twice*, *the entry check (blank login): answered at
   read-only*, 3 transactions, `ok`, and `get acl` on the repeater listing this
   board at `01`.
   **item 24** (48): a revoke of a key that is **not** last in the repeater's
   table, which is the reading of `applyPermissions` that
   `test/support/FakeMesh.h` stands in for and that nobody has tried.
   **item 26** (50): a guest primary's daily `config.read` — the log ending in
   `removal: cli 'setperm <own key> 0'`, **21 transactions** (22 with the
   check), and then `get acl` not listing this board's key at all.
2. **The two walks FOLLOWUPS already holds** (45, 46): the owner info at `acl`
   and at **guest** on somebody else's repeater, and **item 21**, an `acl` login
   answered at guest that still returns the neighbours with `loggedInAs`. AAR_LH
   through Risskov is the first pair that matters. Both halves are now live —
   meshmaster.dk's 180 and 181 deployed on 13 November, this firmware tagged
   after it.
3. **Item 25** (49): the sentence at the top of a *Read the configuration*
   (*every console line of this job carries the firmware's two-character
   prefix*), that the read is still the repeater's own configuration key for
   key, and that a region map still loads and still comes back whole.
4. **The first install from 0x0 with a `-merged.bin`**, still unwalked since
   pile 1.9 and the reason the notes carry the bootloader bullet. A spare board,
   not FD9B: it should come up and print its banner at 115200.
5. **A V3 with two slots up for an hour**, and **a V4 with two**, both still
   open from 37's list. Nothing of this release touches the observer, so these
   are v0.6.0's items carried forward, not this one's.
6. **That nothing else changed.** `v0.7.0` should boot, publish and report
   exactly as `v0.6.0` did but for the version string and the four changes
   above; `status`, `get mqtt.status` and the heartbeat should read as they
   read on `v0.6.0`.
