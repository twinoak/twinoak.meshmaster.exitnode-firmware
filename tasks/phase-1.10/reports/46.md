# p1.10-46 — A guest answer the job can use

A login at class `acl` answered at **guest** says the ACL entry this exit node's
key was granted is gone or demoted — and for two job types this firmware answers
whole to a guest login, it no longer costs the reading as well. AAR_LH,
10 November 2026: jobs 25169 and 25177, both *Read the neighbours*, ended
`unauthorized` with `{"needed": "read-only", "loggedInAs": "guest"}` without the
request the repeater would have answered ever going out. meshmaster.dk's
p4.30-180 stopped the server creating such jobs where it can and said what an
agent does with one that still happens; this is agent-core's half.

`MyMesh::handleRequest` was read at the pin (`81dbae59`,
`examples/simple_repeater/MyMesh.cpp`) rather than quoted: `REQ_TYPE_GET_STATUS`
checks **no permission at all** and its line is commented *guests can also access
this now*; `REQ_TYPE_GET_NEIGHBOURS` checks none either; `REQ_TYPE_GET_TELEMETRY_DATA`
forces `perm_mask = 0x00` for a guest sender, so that reply is the base channels
and none of the sensors; and `REQ_TYPE_GET_ACCESS_LIST` is `sender->isAdmin()`.
So `status` and `neighbours` are served whole at guest and `telemetry` is not.

**First:** `master` of meshmaster.dk has `tasks/phase-4.30/reports/180.md`, so
this task ran rather than stopping.

## Deviations from the spec or the task

- **`config.read` at class `acl` is `unsupported` here, not `unauthorized`.**
  The task's second test bullet asks for `config.read` *after the same login*, as
  the .NET agent's `GuestIsEnoughTests` has it. This board never reaches a login
  for that pair: `canRun` (`agent/JobEnvelopes.h`, `typeAllowsClass`) refuses an
  `acl`-class `config.read` at the claim, at no transaction and with nothing
  sent, because a `get` is a CLI line and `onPeerDataRecv` drops a text message
  from anybody below admin. That is the server's own rule too
  (`JobTypes.CredentialClasses`: `ConfigRead => [Admin]`, narrowed in its task
  p3-34 for this very reason), so no such job is created. The bullet is
  therefore tested **twice**: at `acl`, where the refusal is the claim's and
  earlier than the login, and at `admin`, where a login answered at guest is the
  below-class refusal it always was (`{"loggedInAs":"guest","needed":"admin"}`).
  Nothing of the spec disagrees; the .NET agent's case is defence in depth for a
  job the server does not make, and this board's is stricter.
- **One assertion was added to an existing login-class test.**
  `RunnerTest.ALoginAnsweredBelowTheClassIsUnauthorizedWithTheTierItGranted` now
  also says the envelope carries **no** `loggedInAs` — the tier is the refusal's
  data and nothing else. Its outcome, its data and its existing assertions are
  untouched. No other existing test was touched at all.
- **The spec and the task agreed otherwise.** API §3, EXIT-NODES §7 (*And guest
  is enough to read with*, and the guest bullet's reading of `handleRequest`) and
  180's report say the same thing this implements, and the field is on the
  envelope where 180 put it.

## Decisions taken without asking

- **A second context flag rather than reusing `grantedBelowClass`.**
  `ctx.grantedBelowClass` means *the login was refused below its class*: it is
  what writes `LoginBelowClassResult` as an `unauthorized`'s data and what a
  `discover` reports its tier from. A job that **ran** must not be able to carry
  that refusal record as well, so the new fact is its own flag
  (`ctx.ranBelowClass` / `ranBelowClassRole`), read only by the envelope's
  `loggedInAs`. The .NET agent keeps the same two fields apart for the same
  reason (`GrantedBelowClass`, `RanBelowClassAs`).
- **The field is reported whatever the outcome.** `JobRunner.cs` upstream reports
  `LoggedInAs: ctx?.RanBelowClassAs` from the context and not from the outcome,
  and this does the same: a read that got its guest session and then lost the
  request reports `unreachable` with `loggedInAs: guest`. What the login was is a
  fact about the login, and a silence afterwards does not unsay it — the server's
  `AclLoginFellShort` reads the tier on an `ok` and on a refusal alike, so a
  third reading would be the only one that lost the evidence.
- **The predicates live in `agent/JobEnvelopes.h`**, beside `canRun`,
  `typeAllowsClass` and `readsOwnerInfo` — the file that already holds the
  claim's job-type-and-class rules, on a host, where every branch is a native
  test. `servedWholeAtGuest` is split out from `guestIsEnough` as
  `JobTypes.ServedWholeAtGuest` is split from `GuestIsEnough.Covers` upstream, so
  the two halves of the rule can be read and tested separately.
- **`guestIsEnough` masks the role byte itself** (`grantedRole & kPermRoleMask`),
  although both callers pass an already-masked role: the low two bits are the
  role and the rest of the permission byte is not, and a predicate that reads a
  raw `ClientInfo::permissions` must not answer by accident.
- **The price did not move.** `transactionsFor` is untouched: a guest-answered
  read spends what that read spends, and the extra login of a grouped pair is the
  session rule's — the refusal cost the same second login before this task, so no
  estimate a battery spends against got smaller.
- **The log line names the type and the tier and no password**, in the job's log
  where the bench and the job's page both read it, and it cites `task p4.30-180`
  so that the sentence can be traced to the decision. The serial log gets
  nothing new: the job's own result line already says `ok`.

## Not verified here (and why)

A session can build, run the host tests and read the MeshCore source it builds
against. It cannot flash a board or hear a radio, so this list is Thomas's with
the board on the bench. It is `docs/console.md`'s walk item **21**, and every
step of it is readable off the serial console (`jobs`, `sessions`) and off the
job's page on meshmaster.dk.

1. **The reading that was lost, kept.** A test repeater with **no guest
   password** and an `active` `acl` pair with this exit node: take the entry away
   from the repeater's own console (`setperm <this exit node's key> 0`) and press
   *Read the neighbours*. Expect `ok` at **2 transactions**, the neighbour list
   on the page, the log's `logged in as guest, below the read-only this job asked
   for … so the read runs at guest (task p4.30-180)`, and the association moved to
   `needs-regrant` with the fallbacks offered — the same move the `unauthorized`
   made, with the reading kept. This is the change's whole point and it has never
   gone out on the air.
2. **The same for a status read**, at 3 transactions, with the battery reading
   and the owner info landing on the page (the owner-info request is also one
   `handleRequest` checks no permission for, which pile 1.10's task 45 read the
   same way — so this item walks both tasks' readings of that function at once).
3. **`telemetry` still refused**, on the same repeater and right after: expect
   `unauthorized` with `{"loggedInAs": "guest", "needed": "read-only"}`, a
   **second** login in `jobs` (the guest session is invisible to the class that
   asked for more), and **no** telemetry request on the air. If a telemetry
   request *is* sent, this rule leaked past the two types.
4. **A repeater that has a guest password**, entry removed: the blank `acl` login
   is answered with **silence** there, so the read must be `unreachable` after two
   tries and not `ok` — the other half of EXIT-NODES §7's reading, and the case
   where nothing about the entry is learned at all.
5. **The pair's own verify step.** Re-grant from the page and let the flow run:
   its `status` at `acl` is one of the two types, so an entry the firmware does
   not honour arrives as an `ok` with a battery reading. Watch that the pair does
   **not** activate on such a read and that the fallbacks are offered — that is
   the server's half (180), and this board's `loggedInAs` is what it reads.
6. **A grouped claim on the air.** The status+telemetry pair the default
   schedules claim together, with the entry gone: the status should be `ok` with
   the tier and the telemetry `unauthorized`, two logins between them, and the
   airtime budget's pacing unchanged.
7. **The Walter's local door.** A local job is answered at admin whatever the
   login carried (`LinkMesh::localLogin`), so this rule never fires for one; it
   is worth one look after the Walter's next agent-core sync that a unit's own
   repeater's reads still carry no `loggedInAs` at all.
