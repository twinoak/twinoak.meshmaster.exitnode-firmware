# p1.10-39 — A trace of two bytes

A trace to a **direct neighbour** now goes out at this board's own width — two
bytes a hop — where `runTrace` filled in `1`. That one byte is why job 20005 of
5 November reported a hop `86` that `8620`, `8621` or `8623` could all have
sent: a trace packet states its hash size once and every repeater on the way
matches *its own* hash over `1 << (flags & 3)` bytes
(`Mesh::onRecvPacket`'s `PAYLOAD_TYPE_TRACE` arm, `Mesh.cpp:58` at the pin —
`self_id.isHashMatch(&pkt->payload[i + offset], 1 << path_sz)`), so at one byte
three repeaters answer to the same address. The rail *path hashes are two bytes
or more, never one* (D-33) now holds in the last place this firmware chose a
width.

**The library is told the width instead of knowing it.** `IMesh` gained
`floodPathHashSize()` — the path-hash width every flood of that mesh originates
— and `runTrace` asks it for a direct neighbour, both for the repeater's hash on
the way out and for this board's own on the way home (the way home follows by
itself: the self hop is rendered at `trace.hashSize`, which is the width the
reply's own flags state). `AgentMesh` answers `kFloodPathHashSize`, the fake
answers 2 and can be told otherwise, and **the interface's default is 2** —
`virtual uint8_t floodPathHashSize() const { return 2; }` — so a consumer's tree
compiles untouched and a mesh that overrides nothing is never one byte either.
That is the same choice meshmaster.dk's .NET agent makes on its side
(`src/MeshMaster.Agent/Handlers.cs:962` at `origin/master` `c973268`:
`path.IsDirect ? ctx.Client.PathHashSize : path.HashSize`, and
`CompanionClient.PathHashSize` is the companion's own `PathHashMode + 1`).

**Nothing else picks a width.** A trace along a path the claim carried keeps
that path's width, as it did: `pathToBytes` reads the width out of the hex hops
and the library never widens one, because the extra byte of a narrow hop belongs
to no node. The whole of `src/` and `lib/agent-core/` was grepped for another
one-byte width and there is none to fix — the two near misses are both a width
**read** and not a width chosen, and both are left alone:
`ReplyCodec.h`'s `TraceReading::hashSize = 1`, which `parseTrace` overwrites from
the reply's flags on every call before anything reads it, and
`Observations.h`'s `HeardAdvert::pathHashSize = 1`, which is the width an advert
*arrived* at (`AgentLoop.cpp:440` renders the hops at it). `AgentMesh`'s
`sendFlood(..., kFloodPathHashSize)` and `beginJob`'s pass-through of the claim's
width are unchanged.

Four files of code, three of words (`README.md`'s rail, `docs/library.md`'s
`IMesh` table and its rails table, `CHANGELOG.md`'s *Unreleased*, where this is
an addition to `IMesh` and therefore an answer to the first of the four
questions a pin asks), and four tests.

## Decisions taken without asking

- **The interface's default is `2`, not `1`.** The convention
  (`CHANGELOG.md`, `v0.5.0`) is that an addition to `IMesh` is `virtual` with a
  body so that a consumer compiles untouched, and the obvious "compiles to the
  same behaviour" default would have been `1`. That would have left the bug in
  every mesh but this board's, and the rail is a rail: *never one, wherever this
  firmware chooses a width*. So the default is the rail's width, and the comment
  on the method says override it only to say **wider**. A consumer whose mesh
  really does flood at one byte sees a direct neighbour's trace prefix widen from
  two hex digits to four, which is in `CHANGELOG.md`'s *Unreleased*.
- **A width the mesh answers is not clamped, only used.** If a mesh answered 3,
  `isTraceableHashSize` already refuses it before a packet is built and the job
  is `unsupported` with nothing sent — the existing arm, whose log line reads
  *this path is built of 3-byte hashes, and a trace packet can carry only 1, 2,
  4 or 8*. The wording says "path" where for a direct neighbour it is the mesh's
  own answer; it cannot happen on this board (`kFloodPathHashSize` is 2) and
  rewording a line a test greps for a wider case than this task owns seemed the
  larger change. Named here so a consumer who hits it knows where it came from.
- **The fake's width is settable, defaulting to 2.** `setFloodPathHashSize()`
  exists so that a test can show the library *asking* rather than assuming;
  without it, a `2` in the library and a `2` in the fake are indistinguishable.
  Test support only, and the default is what the task asks for.
- **`docs/library.md`'s new row says "unreleased" where its neighbours say
  "since `0.5.0`".** The release task is what gives a method its version — that
  is what `p1.8-35` did for `floodScope()` — and this task is explicitly not a
  release, so the row points at `CHANGELOG.md` for the version instead of
  inventing `0.6.1`.
- **No new test for the interface's default value as such.** Proving `2` through
  the interface would have meant a second mesh implementation in a suite, where
  `Seams.TheMeshTellsTheLibraryTheWidthItFloodsAt` greps the default body out of
  the header in one line; the behaviour of a mesh that *does* answer is held by
  the two runner tests.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and the thing this task changes
is what goes out on the air. The bench, with the exit node that produced job
20005 (Ov3t|Master, `e4f3…`):

1. **Trace a direct neighbour and read the prefixes.** Queue a `trace` for
   DK_8620_Kjellerup_V_R03 (`8623…`) from the exit node that has it as a direct
   neighbour — the server must know it as a direct path, which is what job 20005
   was — and read the job's page. The hops should be **two** and their prefixes
   **four hex digits**: `8623` with its SNR, then `e4f3` with the SNR this board
   measured on the packet coming home. A `86` anywhere in that result means the
   firmware on the board is older than this change.
2. **The right repeater answers.** This is the whole point and only the bench can
   see it: with `8620`, `8621` and `8623` all within earshot, the 8.5 dB of job
   20005 may have been any of them. Trace `8623` twice at two bytes and the hop
   should be `8623` both times, with an SNR that does not jump between the three
   radios. If `8620` or `8621` ever appears instead, the addressing is still
   ambiguous and that is a finding worth a follow-up.
3. **A trace along a multi-hop path is unchanged.** Job 20003's route
   (`8623 → 8801 → 8623 → e4f3`) came from a path the server sent; run it again
   and the prefixes should keep **that path's** width, two hex digits where the
   path was learned at one byte. Nothing in this task widens a learned path, and
   a trace of it that suddenly reports four-digit prefixes would mean it did.
4. **A repeater whose own floods are one byte still answers.** The width in the
   packet is the originator's and every hop matches its own hash at it
   (`Mesh.cpp`'s trace arm), so a repeater configured at `path.hash.mode=0`
   should answer a two-byte trace exactly as it answered a one-byte one. Worth
   one trace against such a repeater if the mesh still has one.
5. **Nothing else of a job moved.** The thirteen types, their transaction counts
   and their results are the host suite's and are green; the bench only has to
   see a job still complete.
