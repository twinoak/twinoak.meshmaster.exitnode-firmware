# p1.10-42 — A wait counts the sleep

A wait the server asked for is a number of seconds of **real** time. Until this
task `restore()` re-based what was left of it against the new boot's `millis()`
and the sleep in between counted for nothing, so a board that wakes for five
seconds at a time spent a 30 s hold five seconds at a time — and each of those
wakes sent nothing at all, because *a wait the server asked for is still
running*.

That is what the first repeater-v2 unit did on the night of 8 November 2026: 56
wakes since 20:37, one every fifteen minutes, and meshmaster.dk heard from it on
about every sixth. Its own console had the arithmetic in it —

```
agent state: restored across the last sleep (1 restored, 0 saved, 0 refused)
  version 1; backoff 30000 ms, 1 consecutive failure(s) for 1436464 ms, hold 0 ms left
  counters: 31 heartbeat(s), 31 http failure(s), ...
```

— one failed call bought about ninety minutes of silence at fifteen-minute
wakes, about six hours at the Walter's usual hour, and about a day at the
backoff's two-minute ceiling. The wait was meant to be seconds.

`restore()` now takes a **second argument**: how long the board was away, on a
clock that ran through the sleep. The caller measures it, because the only clock
this library has is `millis()` and the sleep kills it. One argument still means
*no time passed*, so **this board changes by not one byte of behaviour** — the
Heltec never sleeps and never calls `restore()` at all — and the Walter, whose
pile 10 task 01 measures the time away, keeps today's behaviour until it does.

Two files of code, three of words, one of tests.

## Acceptance checklist

- [x] **A hold or a Retry-After loses the time a board was away; one argument
  behaves as before (tests).**
  `bool restore(const WakeState& state, uint32_t awayMs = 0)`
  (`lib/agent-core/include/agent/AgentLoop.h`), and in
  `lib/agent-core/src/AgentLoop.cpp`:
  ```cpp
  const uint32_t owedMs = saved.holdForMs > awayMs ? saved.holdForMs - awayMs : 0;
  holdUntil_ = now + owedMs;
  ```
  `holdForMs` is the one field both waits are saved in — `noteFailure`'s
  `BackOff` branch and its `WaitRetryAfter` branch both set `holdUntil_`, and
  `state()` saves what is left of it — so **one subtraction is both rules** and
  there is no second code path that could disagree with the first. Nothing below
  zero: a sleep longer than the wait leaves nothing owed, and `retrySeconds()`,
  which is what `report.sleepAtLeastS` carries back to the caller, is 0.
  The default argument is the whole of the compatibility: `restore(s)` is
  `awayMs == 0`, `owedMs == saved.holdForMs`, and the line it took is the line it
  takes.
  Four of the six new cases in `test/test_loop` are this criterion:
  `AHoldTheSleepOutlastsIsSpentAndTheNextWakeHeartbeats`,
  `ASleepShorterThanTheHoldLeavesTheRestOfItOwedAndTheWakeSendsNothing`,
  `ARetryAfterTheServerNamedLosesTheTimeAwayToo` and
  `RestoreWithOneArgumentIsExactlyTheFiguresItAlwaysWas` — listed one by one
  under *Tests* below.
- [x] **The reboot guard on a sleeping board is read and reported; the Heltec's
  behaviour is unchanged.**
  `failingForMs` gains the time away as well, because the run of unanswered
  calls lasted through the sleep and the guard's ninety minutes are ninety
  minutes of real time:
  ```cpp
  const uint64_t failing = static_cast<uint64_t>(saved.failingForMs) + awayMs;
  const uint32_t failingForMs = saved.consecutiveFailures == 0
                                    ? 0
                                    : static_cast<uint32_t>(failing > UINT32_MAX ? UINT32_MAX : failing);
  firstFailureAtMillis_ = now - failingForMs;
  ```
  **What that does to the guard, read end to end.** The guard
  (`AgentLoop.cpp`, the `BackOff` branch) fires on `consecutiveFailures >=
  kRebootAfterFailures` (12) **and** `failingForMs >= kRebootAfterFailingMs`
  (90 min) **and** the link up. On a board that sleeps, the second of those three
  was effectively unreachable before this task: `failingForMs` only ever
  accumulated the milliseconds the wakes themselves were awake — a few hundred
  per wake — so twelve failures read as *failing for about a second* and the
  guard never spoke. It now reads the truth, and on a unit with a server away
  for a night it will fire. **That is nothing worse than today**, for a reason
  that is in the library and a reason that is in the consumer:
  - in the library, *the guard is told and not taken in one-wake mode* (task
    p1.5-18): inside `wake()` it sets `report.rebootWanted` and `rebootWhy` and
    writes one `LOG_W`, and `platform_->rebootForHealth` is **not** called. The
    `else` branch that calls it is `loop()`'s, which a sleeping board never
    drives. So the honest figure buys a flag and a log line and cannot restart
    anything.
  - in the consumer, the Walter keeps that door shut twice over
    (`components/agent/include/walter_agent/walter_platform.h`): its
    `rebootForHealth` journals the request, raises the unit's own attention for
    the wake record and `status`, and hands the board to the supervisor rather
    than restarting it — and in one-wake mode the library never calls it, which
    is why its `selfReboots()` is 0. Nothing in the Walter's tree acts on
    `report.rebootWanted` beyond reading it: `grep -rn "rebootWanted"` over that
    repository is the vendored library's own declaration and the two lines of
    `AgentLoop.cpp` that set it, four host-test assertions, and two sentences of
    prose — `walter_platform.h`'s and `tasks/phase-4/reports/04.md`'s.
  A deep-sleeping board boots fresh at every wake anyway, so the one thing a
  reboot would buy — a stack unwedged — is what the sleep already does.
  `TheRebootGuardOnASleepingBoardReachesItsNinetyMinutesOnlyWhenTheSleepCounts`
  holds both halves of it. It is also called out in `CHANGELOG.md`, because it is
  the one consequence of this change a consumer could be surprised by.
  **The Heltec:** `grep -rn "restore(" src/` is empty — this firmware calls
  neither `state()` nor `restore()`, drives `loop()` and never sleeps, so its
  behaviour is unchanged by construction and not by assertion. `AgentLoop`'s only
  other reader of `holdUntil_` and `firstFailureAtMillis_` is untouched.
- [x] **The comments and `docs/library.md` say the rule; the build and the host
  suite green.**
  - `WakeState`'s own comment (`AgentLoop.h`) now says that `restore()` re-bases
    a duration against the clock it finds **after the time the board was away is
    taken off it**, and why, with the unit of 8 November as the example.
  - `restore()`'s declaration says the whole contract: who measures `awayMs` and
    why it cannot be the library, that the hold is what is left and never less
    than nothing, that a backoff and a Retry-After are the same rule, that
    `failingForMs` is longer by it, and that the default is *no time passed*.
  - `docs/library.md` §6 step 7 — *Across a sleep*, which is where the page
    explains `WakeState` — has the rule in a paragraph of its own, including the
    *never more than really passed* rule a caller measures by, and the symptom
    the old behaviour produced. The `millis()` row of §5, the code example of §6,
    §10's *what a bump may change* table and §11's `millis()` row point at it.
  - `docs/host.md` says what a test of the rule needs (`LoopTest::woken()`, and
    that the `restore()` call is the test's own), since that page is the one that
    explains how a sleep is tested here.
  - `CHANGELOG.md` *Unreleased* has the consumer's entry: the signature, the

  - `pio test -e native` in the container of `RUNBOOK.md` §2: **28 suites, 560

## Tests

Six new cases in `test/test_loop/test_loop.cpp`, under a heading of their own
(*A wait counts the sleep*), and one new fixture helper. The task asked for five;
the sixth is the reboot guard, which the acceptance criteria ask to be *read and
reported* and which is cheaper to hold than to argue about.

`LoopTest::woken()` is a boot after a sleep that only the `WakeState` survives: a
fresh `AgentLoop` and `JobRunner` over the same fakes, with no store, so what the
test hands `restore()` is all that comes back. It deliberately does **not**
restore anything itself — unlike `LoopTest::boot()`, which does — because the
call being measured is the caller's: one argument is *no time passed*, two are
the sleep.

## Deviations from the spec or the task

- **The task's figures in deliverable 3 are a one-call wake; a wake is two
  calls.** *"`restore(s, 10000)` after a 30 s hold: 20 s still owed"* — but one
  wake against a server that is away fails **twice**, at the config call and at
  the heartbeat, so the backoff it ends on is the second step and the hold is
  60 s jittered (57936 ms in the run that caught this), not 30 s. The case
  therefore asserts the arithmetic on what `state()` actually saved —
  `retrySeconds() == (holdForMs - awayMs) / 1000`, with `holdForMs` bounded to
  the second step's jittered range — which is the rule the task is about, exactly,
  and not a round number that depends on how many calls a wake happens to make.
  The *30 s hold* of the goal text is still the real-world figure: one failed
  call, in `loop()` or in the first wake of a boot, is the 30 s step.
- Nothing else. `WakeState`'s layout, `kVersion`, every other field and
  `state()` itself are untouched, and no spec section disagrees with the task
  file.

## Decisions taken without asking

- **A defaulted second argument rather than a second method.** `restore(s,
  awayMs)` with `awayMs = 0` is one implementation and one rule; a
  `restoreAfterSleep(s, awayMs)` beside `restore(s)` would be two entry points
  that could drift, and the Walter's own pile 10 task 01 already names
  `restore(state, awayMs)`. The cost is that a consumer's tree keeps compiling
  while the meaning of the call it makes has changed — which is the dangerous
  kind of change — so it is in `CHANGELOG.md` and in a row of `docs/library.md`
  §10's table, which is exactly the watch that table exists for.
- **The time away is added to `failingForMs` only while something is failing.**
  `state()` already saves `failingForMs` as 0 when `consecutiveFailures` is 0, so
  `restore()` mirrors it: a board that was holding on a `Retry-After` — which is
  not a consecutive failure — does not come back with a phantom run of failures
  fifteen minutes long. It would have been harmless (the next first failure
  re-bases `firstFailureAtMillis_` anyway), but a figure that means *how long the
  present run of failures has lasted* should not be non-zero when there is no
  run.
- **The add saturates.** `failingForMs + awayMs` is computed in 64 bits and
  clamped to `UINT32_MAX`, so a board that has been failing across fifty days of
  sleeps reads as *still failing* rather than wrapping round to *just started*.
  One line, and it makes the guard's input monotone.
- **The *still owed* line is written only when something is owed**, which the
  task asks for, and its **text is unchanged**: *N s of a wait the server asked
  for is still owed from before the sleep*. How much the sleep took off is the
  caller's to print — the Walter's pile 10 task 01 deliverable 4 puts it in
  `agent state` — because the caller is the only one of the two that knows both
  numbers, and a second library line at every wake is the noise that hid this
  bug in the first place.
- **No `WakeState::kVersion` bump.** The struct's layout is byte for byte what it
  was, so the blob already in a unit's NVS restores rather than being refused.
  Bumping would have cost the first consumer the backoff across one sleep for no
  reason.

## Not verified here (and why)

A session can build and run the host suite; it cannot flash a board or hear a
radio. Nothing in this task changes the Heltec's behaviour, so the bench list is
short and is really the **Walter's**, once its pile 10 task 01 has synced this
and measured the time away:

1. **The unit stops being quiet.** With a server that fails once — pull the
   SIM's data, or point `server.url` at a host that refuses — the next wake after
   the sleep should **send**, not report *a wait the server asked for is still
   running*. On the console: `agent state` right after a boot, and the library's
   line *N s of a wait ... is still owed from before the sleep* should appear only
   when the sleep was shorter than the hold. At fifteen-minute wakes and a 30 s
   hold it should never appear.
2. **The heartbeat count tracks the wake count again.** The symptom was 31
   heartbeats against 56 wakes. After the sync, over a night, those two numbers
   should be within a wake or two of each other unless the server is actually
   away.
3. **The reboot guard, now that it can speak.** With the server away for two
   hours of wakes, the Walter's wake record and `status` should show the
   attention raised and the reason (*N server calls unanswered in M min, wifi
   up*) — **and the unit must not restart**: `selfReboots()` 0, the supervisor
   untouched. This is the one new behaviour on a bench, and it is the reason it
   is in the changelog.
4. **A `Retry-After` the server really names.** A 429 from meshmaster.dk with a
   long `Retry-After` across one sleep: the unit should come back owing the
   remainder and not the whole, and should not call before it.

On the Heltec itself there is nothing to walk: it drives `loop()`, never sleeps,
and never calls `restore()`. The firmware it builds from is in
`out/heltec_v3-build.log`.
