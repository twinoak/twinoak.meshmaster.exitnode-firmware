# p1.10-49 — A console reply belongs to its line

A console reply carries **no tag**. `onPeerDataRecv` answers a CLI line with a
`TXT_MSG` of the repeater's own clock, and the sender timestamp the line went out
with is nowhere in it — so the first text of CLI data from the peer while one was
awaited was the answer, whatever it answered. Replies arrive later than this board
waits (task p1.10-47, and meshmaster.dk's task 187 has the numbers), so the reply
to `get name` could arrive while `get radio` was awaited and be stored as the
radio. A configuration read is thirty such lines in a row, and nothing would have
shown the swap: a `get` answers a value and not the key it belongs to.

The firmware has a tag for it, and it is upstream's own. `handleCommand` reflects
a two-character prefix and a `|`, so `a7|get name` is answered `a7|> …`. Every
console line of a job now carries one, **counted out per line and per try**, and
only a reply that starts with it is that line's answer: another prefix or none is
a late reply, dropped with a line in the job's log while the wait runs to its
end. Where it cannot be told that the repeater reflects one, the line goes
exactly as it went before.

## Deliverable 1 — where the prefix can be used, and since when

The task asks for this in the report **before any code**, so it is here first. All
of it is `git log`/`git show` over the pinned tree on disk
(`.pio/libdeps/heltec_v3/MeshCore` at `81dbae59`, `companion-v1.18.0`).

**Which firmware reflects it.** Four, and they are the four call sites of the
same four lines: `examples/simple_repeater/MyMesh.cpp:1235-1239`,
`examples/simple_room_server/MyMesh.cpp:937`,
`examples/simple_sensor/SensorMesh.cpp:453` and
`examples/companion_radio/MyMesh.cpp:2082`. The repeater's is the one that
matters here, and it reads:

```cpp
  while (*command == ' ') command++; // skip leading spaces

  if (strlen(command) > 4 && command[2] == '|') { // optional prefix (for companion radio CLI)
    memcpy(reply, command, 3);                    // reflect the prefix back
    reply += 3;
    command += 3;
  }
```

It sits **after** the `region_load_active` branch returns (same file, 1199-1231)
and **before** `setperm`, `get acl`, `discover.neighbors` and
`_cli.handleCommand` (1241-1285), so every command a repeater answers over the
air goes through it — and no line sent while the repeater is loading regions does.

**Since when.** Commit `1209d54d`, *various changes for CLI support via companion
radio*, 27 February 2025, which added exactly those lines to
`examples/simple_repeater/main.cpp`'s `handleCommand` (`git show 1209d54d --
examples/simple_repeater/main.cpp`). It has been there continuously since, moving
file twice without changing (`e32fea07` into `CommonCLI`, `9cecbad2` back out to
the call sites, `f2e8fb02` into `MyMesh.cpp`). The first **repeater release** that
carries it is `repeater-v1.0.0a` of 5 March 2025; `git tag --no-contains
1209d54d` names only `rep-v6` and `room-v6`, the two tags of the week before.

**What a repeater that does not reflect it makes of `a7|get name`.** It runs it.
At `rep-v6` (`git show rep-v6:examples/simple_repeater/main.cpp`) `handleCommand`
skips leading spaces and goes straight to the command compares, so `a7|get name`
matches none of them and falls out of the last `else`:

```
Unknown: a7|get name (commands: reboot, advert, clock, set, ver, password, start ota)
```

An **answer**, not a silence — so an unprefixed firmware does not merely fail to
help, it turns every read into an error line. (A `rep-v6` repeater is in any case
not an exit-node target: it has no `ClientACL` — `setperm` and the access list
arrived in `9cecbad2` of 8 July 2025 — and its login reply is twelve bytes with
`reply_data[7] = 0 // FUTURE: reserved` where this firmware reads the entry's
permission byte.)

**What tells the two apart: the login's `FIRMWARE_VER_LEVEL`, and nothing
looser.** The level is in the repeater's login reply only since `c2159634`,
*Login response payload: now includes FIRMWARE_VER_LEVEL*, 25 September 2025 —
released in `repeater-v1.9.0` (28 September 2025) at level 1, and raised to 2 by
`69a71d0e` of 12 January 2026 (`repeater-v1.12.0`). That is **seven months after
the prefix**, so:

| what the login reply says | what it means for the prefix |
|---|---|
| level ≥ 1 | the firmware is `repeater-v1.9.0` or newer, which is newer than `repeater-v1.0.0a`: **it reflects the prefix** |
| level 0, or no level byte at all | either older than the prefix (`rep-v6` and before) or between the two releases (`v1.0.0a`…`v1.8.1`, which reflects it) — and **the two cannot be told apart**, so the line goes bare |

So `mm::kCliPrefixVerLevel` is **1**, and that is the whole of the test. Nothing
looser was used, and there was one looser thing to be tempted by: `ver` answers
the version text. It is a **console reply**, which is the very thing being
matched — reading it to decide how to match it is the circle this task is about,
and it would cost a transaction before the first `get` besides.

## Deliverables, one by one

1. **Where the prefix can be used.** Above, before the code.
2. **Every console line carries one, and only a reply with it is the answer.**
   `JobRunner::nextCliPrefix` draws it — per line **and per try**, from a series
   seeded by `platform_->random()` on the job's first console line and dying with
   the job — and `cliLine` puts it on the wire text. `JobRunner::awaitCliReply` is
   the whole of the wait: `awaitText` in a loop to the line's own deadline, and a
   text that does not start with this attempt's prefix gets one line in the job's
   log, one on the serial console and another round with the remainder. Eight
   drops a wait, as task 47's login has, and the drops do not extend the wait.
   The reply that *is* this line's reaches `Scratch::cliReply` with its prefix
   taken off, so `cliReplyValue`, `cliReplyIsConfirmed`, the apply engine and the
   password echo see exactly what they saw before. The reading of the firmware is
   `agent/CliReplies.h`'s three functions, beside the two that were already there.
3. **Where it cannot be told, the line goes as it does today.** The login's
   `FIRMWARE_VER_LEVEL` is what tells them apart and `kCliPrefixVerLevel` is 1 —
   the table in deliverable 1 is why, and the *why nothing looser* is there too.
   Three more kinds of line go bare, and each is a reading of the pinned source
   rather than a preference (`cliLineTakesPrefix`, and `docs/library.md` §3.8 has
   the table): a line of two characters or fewer, because `strlen(command) > 4`
   is `handleCommand`'s own condition and the region loader's terminator is one
   space; `region` and `region def …`, whose reply is
   `RegionMap::exportTo(reply, 160)` — the whole of the repeater's reply window,
   which the prefix is reflected into the front of; and a line nobody awaits a
   reply for, because the reflected prefix **alone** is a non-empty reply
   (`if (text_len > 0)`) and prefixing a silent line would put a packet on the air
   for every region in a map. An escape line — a line that ends a mode
   `handleCommand` reads before it reads a prefix — is refused for the same reason
   as the terminator, explicitly and not by its length.
4. **A password never leaves differently.** `sensitive` is unchanged and so is
   everything it does: the frame's body is printed as stars, the echo is compared
   and recorded redacted, the one plaintext copy is wiped before the packet is on
   the air. Two things were needed to keep it true with a prefix in the way.
   `Scratch::line`, the buffer the prefixed line is built in, is **wiped after the
   exchange** exactly as `Scratch::secretLine` is — it is the second buffer of the
   runner that can hold a secret, and it says so. And `AgentMesh::await` no longer
   clears `sensitiveAwait_` when a wait ends: the library may now wait more than
   once for one line's reply, and each of those waits is the same line's, so the
   flag is the last `sendCli`'s and is cleared by `endJob`. Without that the
   second wait of a dropped `password` reply would have printed the next frame's
   body as hex rather than as stars.
5. **The words.** `docs/library.md`'s new **§3.8** (*The prefix a console line
   carries*), with the table of the four kinds of bare line and the paragraph on
   the reused session; `docs/console.md`'s job-log section (the sequence as the
   page prints it, and what the serial console says) and bench walk item **25**,
   which is the *Not verified here* list below; `CHANGELOG.md`'s *Unreleased*,
   because a consumer that calls `IMesh::sendCli` through an `IJobExtension` now
   sees three characters at the head of the text it is handed.

- **A prefix is not put on every console line, and two of the exclusions are
  wider than the task's wording.** Deliverable 2 says *every console line carries
  one*; deliverable 3 gives the firmware-level exclusion by name. Two more were
  needed, both read off the pinned source and both in `cliLineTakesPrefix` with
  the reasoning beside them:
  - **a line nobody awaits a reply for, and the region loader's own lines.** The
    reflected prefix is written into the reply buffer *before* the command runs,
    so a command that answers nothing still answers three characters and
    `if (text_len > 0)` sends them. Prefixing the loader's lines would therefore
    put a packet on the air for every region in the map — and worse, the loader's
    branch of `handleCommand` returns before the prefix is read at all, so a
    prefixed region line would be loaded as a region named `a7|dk` and the
    one-space terminator would stop being blank and never end the load. The
    terminator is excluded twice over (it is one character, and it is an escape
    line);
  - **`region` and `region def …`.** Their reply is the whole of the repeater's
    160-byte reply window and the prefix comes out of the front of it. See the
    FOLLOWUPS item below: prefixing those would not merely truncate the map, it
    would write two bytes past `onPeerDataRecv`'s `temp[166]`.
- **A `cli` job whose line the firmware answers with nothing now gets an empty
  answer rather than a silence.** `runCli` sends whatever line the server handed
  it. If that line is one the firmware answers with an empty reply — `region
  load` is the only one at the pin — the reflected prefix makes the reply three
  characters, so the job is `ok` with an empty `reply` where before it was
  `unreachable` with the command recorded. It is the more honest of the two (the
  line did run), meshmaster.dk sends no such `cli` job, and `region load` through
  a `cli` job would leave the repeater in load mode whatever this task does. Named
  here because it is the one outcome in the tree that a prefix can change.
- **`AgentMesh::await` no longer clears `sensitiveAwait_`.** Deliverable 4's
  requirement made this necessary rather than optional; `endJob` clears it and
  every `sendCli` sets it, so its meaning is now *the sensitivity of the last line
  sent* and the header says so. Nothing else of `AgentMesh` moved but comments.
- **One source-text test moved with the call it holds.**
  `Seams.TheMeshDrawsTheCliTimestampAndHandsItBack` asserted the literal
  `mesh_->sendCli(command, sensitive, tag)` in `JobRunner.cpp`, and the call is
  now `mesh_->sendCli(line, sensitive, tag)` - `line` being the command with the
  prefix on it. The fact the test holds is unchanged (the mesh draws the
  timestamp and the runner hands none in), so the string was updated and one
  assertion added beside it: `nextCliPrefix` is called **before** the send in the
  same lambda, so the prefix on the wire is the one drawn for that attempt. It is
  the only existing test in the tree whose text had to change.
- **`FakeMesh` had to learn the difference between a silence and an empty
  reply.** Three of the fake's answers were *the handler wrote nothing*, which
  before this task was indistinguishable from *nothing came home*: `silenceLine`,
  the reboot, and the misaddressed "OK" of a level-0 `setperm` on our own key

  prefix on the line the two part company — the first really is a three-character
  reply — so each of the three now returns before the reply is built, and

  `ACliLineIsSentOnceAndNeverRetried`,

## Decisions taken without asking

- **A counter, not a random byte, and seeded per job.** Two consecutive lines
  must never share a prefix, because the reply this rule exists to catch is the
  reply to the line *immediately before*; a random byte a line would collide one
  time in 256. A plain counter from zero would instead make line one of every job
  the same two characters, and a reply to the last line of one job can still be in
  the air when the next job for that repeater begins — so the counter's **start**
  is `platform_->random()` and it dies with the job. 256 distinct values is far
  more than a job's lines: the longest is a 34-line `config.read`.
- **The rule is in the library, and `AgentMesh` filters nothing.** The same
  decision task 47 took and for the same reason: the Walter has its own `IMesh`
  and hands every text through, so a rule in `src/mesh/AgentMesh.cpp` would not
  hold for it. `takeText` got a comment saying where the rule is and why it is not
  here. Nothing is asked of an implementor — §3.8 ends with *For your `IMesh`: do
  nothing*.
- **Eight drops per wait, and a wait the drops do not extend.** Verbatim from
  task 47's login wait, because it is the same shape of problem and two different
  bounds would be two things to remember. A reply past the deadline is not awaited
  again, and a mesh that somehow handed the same text back for ever cannot hold
  the loop: both are bounds on a board with one thread and a watchdog.
- **One sentence in the job's log per job, not per line.** A thirty-line read
  would otherwise spend a third of its kilobyte of log saying the same thing
  thirty times (and task p1.10-38 drops whole entries from the front when it
  fills, so it would cost the read's own lines). `Context::cliPrefixNoted` keeps
  it to the first console line, and it says which of the two things happened —
  the lines carry a prefix, or this job was not told the firmware level.
- **No byte of a dropped reply is printed**, in the job's log or on the serial
  console. A console reply can be the echo of a `password` line, and the rail is
  that no reply's bytes are ever a log line's argument. The line names the command
  and the attempt and nothing else, which is also enough for the bench: the
  question there is *did it happen*, not *what did it say*.
- **The reply is stripped where it is taken, not where it is read.** `g_cliReply`
  is the one buffer every CLI reply lands in and a dozen callers read, so the
  prefix comes off in `awaitCliReply` and no caller changed. The alternative —
  every reader skipping a prefix — is a dozen places to forget.
- **`cliLineTakesPrefix` reads the command's text rather than taking a flag from
  the caller.** It was tempting to thread a *prefixed* parameter through `cliLine`
  and `ApplySend`, but the apply's lines come from the **server's plan**: a
  `region def …` in a plan would reach `cliLine` with whatever flag the engine
  guessed, and a call-site flag could not catch it at all. One text rule in one
  place, cited to the two `exportTo` calls it is about, catches every caller
  including the ones that do not exist yet.
- **`SessionStore` was left alone**, so a job that reuses a session sends its
  lines bare. The level is kept per job on purpose (task p4.30-181's
  `JobContext.FirmwareVerLevel`), and widening it to the session would change the
  owner-info gate that reads the same two fields — task p1.10-45's decision, not
  this one's. It is the one case where the protection is absent, so it is a
  FOLLOWUPS item with what would close it rather than a sentence in a report
  nobody reads twice.
- **The fake's `Send::text` is the line as the repeater *ran* it**, with
  `Send::prefix` beside it. Forty-six existing `timesSent(...)` assertions mean
  *the command*, and they still do; a test that wants the bytes on the air joins
  the two. `linePrefixes()` and `prefixOf(line, nth)` are what the new tests read.
- **One new fake knob, line-keyed and counted, with how many waits it misses.**
  `deliverTheNextLineRepliesLate(line, times, waits)`: `waits = 2` is what makes a
  reply miss its own wait *and* its line's retry and turn up in the **next line's**
  wait, which is the only timing that produces a swapped value. It reuses task
  47's `late_` list rather than adding a second mechanism.

## Not verified here (and why)

A session can build, run the host tests and read the MeshCore source it builds
against. It cannot flash a board or hear a radio, so this list is Thomas's with
the board on the bench. It is `docs/console.md`'s walk item **25**, and the thing
that makes it unusual is that **nobody has seen the fault it fixes** — 47 and 48
were field cases with job ids, and this one is a reading of the firmware that
could not have shown itself.

1. **The sentence at the top of a read.** *Read the configuration* of any
   repeater: its log must begin `every console line of this job carries the
   firmware's two-character prefix`. If it says instead that the job *has not been
   told the repeater's firmware level*, that repeater is older than
   `repeater-v1.9.0` and its reads are unprotected — note which one it was, and
   the FOLLOWUPS item about a reused session is the other way a read can say it.
2. **The read is still the repeater's configuration.** This is the one that
   matters, and it needs no fault to be staged: compare `name`, `tx` and `freq` on
   the job's page against `get name`, `get tx` and `get freq` on the repeater's own
   console. A value that belongs to the key above it is the fault; the point of
   the walk is that there must not be one.
3. **The drop, when a repeater is slow.** The same repeater as walk item 22 — far
   enough away, or busy enough, that a reply sometimes misses its 16 s wait. When
   a line goes unanswered and the next is answered quickly, the log should carry
   `a console reply that does not carry this line's prefix arrived instead;
   dropped, and the wait goes on`, and the serial console the same in one line. A
   repeater that answers inside its wait every time prints none of these, and that
   is the common case: the walk is *watch for it*, not *make it happen*.
4. **A regions apply really loads.** *Apply* a region map from meshmaster.dk, then
   `region` on the repeater's own console. A region named `a7|dk`, or a load that
   never ended, would mean a prefix reached the loader — which is what
   `handleCommand` reads before it reads a prefix, and the reason the loader's
   lines go bare. `OK - loaded N regions` must still be in the result.
5. **A repeater with a full region map.** The `region` of a *Read the
   configuration* must come back whole **and must not reboot the repeater**: those
   three characters would have come out of the same 160-byte buffer the map is
   written into, two of them past the end of it. This firmware never asks for it
   with a prefix (`region` goes bare), so the walk is a check that it does not —
   and the FOLLOWUPS item is the upstream half, which a phone through a companion
   radio can still reach.
6. **A `setperm` whose "OK" is lost, again.** Walk item 23 unchanged, with one
   thing added: the two rounds now carry different prefixes, so a late "OK" from
   round one cannot confirm round two. Nothing on the page changes; what must not
   appear is a confirmed grant whose line never arrived.
7. **The Walter.** It has its own `IMesh` and takes this at its next `agent-core`
   sync; nothing of its link needs to change, which is the third deliverable. Two
   things to look at there: a local job's lines are answered inside the link and
   cannot be late, so the prefix buys nothing and costs three bytes a line — and
   the door's own repeater must still reflect it, which it will, because it is
   MeshCore at a level the login reports. If the door ever answers the login
   itself with a level of its own invention, that is the number this rule reads.
