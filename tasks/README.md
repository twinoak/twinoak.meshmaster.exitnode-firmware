# Tasks — how the firmware gets built

## Two repositories

The spec says *what*, and it is **not here**. It lives in
[`twinoak/meshmaster.dk`](https://github.com/twinoak/meshmaster.dk) — `spec/`,
`docs/`, the server, the .NET agent and the protocol this firmware speaks —
and it stays there, because the protocol has two ends and one of them is the
server's. This repository holds the board's end: the firmware, its toolchain,
its tests, its releases, and the tasks that build it.

| | twinoak/meshmaster.dk | this repository |
|---|---|---|
| the spec | `spec/`, `docs/` | read from there, by link, at a commit |
| the protocol | defined, and the server's side implemented | spoken |
| the contract fixtures | generated by `MeshMaster.Contracts`' tests | copied, `tools/sync-fixtures.ps1` |
| MeshCore | not used | a dependency, pinned (`docs/upstream.md`) |
| the driver | `tasks/run-all.ps1` | the same, in PlatformIO |
| a release | a person pressing *Run workflow* | a person pushing a tag `vX.Y.Z` |

A task file links into meshmaster.dk at the commit the bootstrap ran from
(`fbf4625`), so a link is a **snapshot**: the file it points at may have moved
on. When a task's reading of the spec and today's `master` of meshmaster.dk
disagree, today's `master` wins and the disagreement goes in the report. The
one thing that is never read by link is the agent contract — that is copied,
byte for byte, into `tests/fixtures/contracts/`.

## Conventions

- **One task, one branch, one PR.** Branch `task/p1-01-the-board-speaks` for
  `tasks/phase-1/01-the-board-speaks.md`. The PR description is the task's
  acceptance checklist, ticked.
- **Read before writing.** Every task lists the spec sections it implements,
  as links into meshmaster.dk. The agent reads those sections in full before
  touching code; the spec wins over the task file if they disagree, and the
  disagreement gets noted in the PR.
- **Read the firmware you build against.** MeshCore is on disk after a build,
  under `.pio/libdeps/<env>/MeshCore`, at the commit `[meshcore].pin` names. A
  claim about what the companion firmware does is checked against that source,
  never against a memory of it.
- **Verification is part of the task.** A task is done when its verification
  commands pass locally and in CI, not when the code "looks right".
  `pio run -e heltec_v3` and `pio test -e native` are implicit in every task,
  and `-Werror` on our own sources means a warning is a failure.
- **No scope creep.** If a task needs something a later task owns, stub it
  behind a seam and say so in the PR. If it needs something the spec lacks,
  the spec is in the other repository: say so in the report and let the
  reviewer open it there.
- **Small, deliberate dependencies.** Libraries are pinned to an exact version
  in `platformio.ini`'s `[libs]`; adding one needs a one-line justification in
  the PR. Not one of them may be native-only or unbuildable on a host: the
  native tests have to keep working.
- **Secrets never in the repo.** The board is provisioned over its serial
  console and keeps its token in NVS; no WiFi password, no agent token and no
  repeater password is ever a build flag, a fixture or a log line.
- **Docs move with code.** A task that changes what the board prints, what it
  needs on the bench or how it is flashed updates `docs/` in the same PR. A
  task that changes behaviour the *spec* describes says so in the report, for
  the other repository.
- **Leave the evidence.** Build logs, `.bin` files and test output stay on
  disk in `out/` after the run (git-ignored), so a reviewer can inspect them
  instead of trusting the PR text.

## Unattended runs

`tasks/run-all.ps1 -Phase N` runs the tasks of a phase in order, each in a
fresh headless session (`claude -p --dangerously-skip-permissions`) that
follows [`RUNBOOK.md`](RUNBOOK.md): branch, implement, verify, write
`phase-N/reports/NN.md`, open a PR, wait for CI, merge. A task counts as done
when its report exists on `origin/master`; the first task that does not land
stops the run (`phase-N/logs/STOPPED.md`), and `-From NN` resumes. Review
findings go into `phase-N/FOLLOWUPS.md`, tagged with the task that must pick
them up. Merging never releases; a release is a person pushing a tag.

`-Phase sync` is the same driver over `tasks/sync/`: one task per MeshCore bump
that CI could not swallow, written by `tools/new-sync-task.ps1` from
`tasks/sync/TEMPLATE.md`. [`docs/upstream.md`](../docs/upstream.md) is the
page that explains when that happens and what is automatic instead.

**Models.** A task file's `**Model:**` line names the model that implements it;
the driver passes it as `--model`. Phase 1 names Fable for the three tasks
whose mistakes would be security mistakes (01, 04, 05) and Opus for the rest.
Review of every report and diff is Fable's regardless of who implemented.
Change a line to change a model.

## Layout

```
tasks/
  README.md            this file
  RUNBOOK.md           what one unattended session does, for every phase
  run-all.ps1          the driver: one session per task, in order
  phase-1/             the onboard exit node - see phase-1/README.md for order, models
                       and the exit criterion
  sync/                MeshCore bumps that needed a session (docs/upstream.md)
```

## What a session can and cannot check

It can **build** (`pio run -e heltec_v3`), run the **native** tests
(`pio test -e native`), and read the MeshCore source it builds against. It
cannot flash a board or hear a radio. Every task therefore ends with a *Not
verified here* list that is Thomas's to walk with the board on the bench.
