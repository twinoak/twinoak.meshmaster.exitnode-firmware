# p1.8-30 — The uplink holds its line

The uplink keeps **one** TLS connection to meshmaster.dk between calls. The
handshake happens at the first call and again only when the connection is gone:
the server closed it, a call failed, the WiFi link was remade, the root to
verify against changed, or a `set meshmaster.*`. A kept connection that turns
out dead under a request is remade once, inside the same call. Nothing the loop
sees changes - the `Call` record, the backoff, the reboot guard and the 401 halt
are untouched, and the existing suites say so - and `status` gains an `uplink`
line: the kept connection and since when (or why not), handshakes against calls,
and what the last call cost the heap.

**The server's side, measured.** From this PC on 31 October 2026, one TLS
connection to `meshmaster.dk:443`, one `GET /agent/v1/config` (401, no token,
`Transfer-Encoding: chunked`, no `Connection` header), then silence:

```
11:39:23 probe 1: one request to /agent/v1/config, then idle up to 420 s
11:39:23 connected: TLSv1.3 TLS_CHACHA20_POLY1305_SHA256, cert verified against the system store
11:39:23 /agent/v1/config -> HTTP/1.1 401 Unauthorized in 23 ms
11:41:30 closed by the server after 127.7 s idle (EOF)
11:41:30 probe 2: request, wait 30 s, request again on the same connection
11:42:01 second request after 30 s idle: answered on the same connection
11:42:01 probe 2: request, wait 100 s, request again on the same connection
11:43:41 second request after 100 s idle: answered on the same connection
```

(`out/uplink-idle-probe.py` and its log, git-ignored; Python's `ssl` on one
socket, because `curl --keepalive-time` sets TCP keepalive and says nothing
about when the far end closes.) So meshmaster.dk holds an idle connection for
**128 s** - IIS's default `connectionTimeout` of 120 s plus its tick - which is
longer than the idle heartbeat's 120 s. The heartbeat is timed from the end of
the previous call (`AgentLoop.cpp`, `nextHeartbeatAt_ = millis() + poll`), so
at 30 s with work and at 120 s idle the connection is normally still there; a
job, a hold or a backoff in between outlasts it and the next call handshakes
again, which is one `uplink: handshake N for call M (the server closed it)` line
and not a failure. The board does **not** fall back to a connection per call:
the finding is that the server keeps it long enough, by about eight seconds at
the idle interval. Neither `docs/ops/release.md` nor `spec/HOSTING.md` names
the figure (HOSTING §1 says the *app pool's* idle stop was not measured, which
is a different timer; re-checked against today's `master` of meshmaster.dk);
this is the measurement the task asked for.

## What changed

- **`src/agent/KeepAlive.h`, `.cpp`** (new, host-portable): the rule. A
  `Transport` is the wire (`connected()`, `close()`, `exchange(root)`); the
  policy reuses while the client sees the connection alive and it was made
  against the root the call wants, closes and handshakes otherwise, remakes a
  kept connection once inside the call when the request over it got no reply
  and no TLS error, never retries a fresh connection's failure (the loop's
  backoff owns that), keeps nothing after a failure, and keeps what the client
  still has after a success (nothing, if the server said `Connection: close`).
  Counters: calls, handshakes, reused, reopened; and why there is no kept
  connection, in words.
- **`src/agent/AgentClient.cpp`, `.h`**: the `WiFiClientSecure` and the
  `HTTPClient` outlive the call. The HTTP client is made once in `begin()`
  (`setReuse(true)`, the same timeouts, the two collected headers); the TLS
  client is made at each handshake and deleted when the connection is gone, so
  every handshake starts from a client with no history - its `lastError()`,
  the root it was given. `AgentClient` is the `Transport` (privately) and the
  request's parameters are bound before `KeepAlive::call()`. A WiFi link remade
  since the last call (`WifiLink::connects()` moved) drops the kept connection
  before the request rather than letting the request find out; `reconfigure()`
  drops it too.
- **What a call costs**: `mbedtls_platform_set_calloc_free()` installs a
  wrapper of mbedtls's allocator once, in `begin()` - this core has
  `MBEDTLS_PLATFORM_MEMORY` on with `esp_mbedtls_mem_calloc`/`free` as the
  standard pair, behind function pointers, and `mbedtls_platform_set_calloc_free`
  is a defined symbol of its `libmbedcrypto.a` (checked with `nm`). While a call
  is in flight every allocation mbedtls makes samples the free heap right after
  it: **exact for mbedtls's share**, which is the handshake and the two 16 KB
  content buffers. Four explicit samples (before, after the status line, after
  the body, after) catch the rest, and if the board's minimum-ever moved during
  the call the lowest is that, exact for everything. `status` prints `last call
  N free before, lowest N during, N after`; the config call's `heap:` log line
  gained `lowest N during`.
- **`src/main.cpp`**: the `uplink` line after `heap`.
- **`test/test_keepalive`** (new, 12 tests): reuse while alive with one
  handshake for five calls; the server's close replaced without a failure; a
  kept connection dead under the request (send failed, connection lost, read
  timeout) remade once inside the call; a failure after the reopen reported as
  the call's and the next fresh failure not retried; a verification failure
  never retried here; the root change forcing a new handshake and back; the
  server's `Connection: close` believed; a drop on purpose; a 401 and a 503
  keeping the connection; the words.
- **`test/test_library`**: `src/agent/` now holds five files; the boundary test
  names them and says why KeepAlive is the board's and not the library's.
- **`platformio.ini`**: `agent/KeepAlive.cpp` in the native build filter.
- **`docs/console.md`**: the `uplink` line, field by field; the `uplink:` log
  lines and their reasons; the server's 128 s; the bench walk's step 4 and 10.
  **`docs/field.md`** §6: what a kept connection means for a router that drops
  idle sessions, and §8's week-at-the-window check. **`docs/observer.md`**: the
  sentence that said the uplink handshakes at every call.

**Read against the framework it builds against** (arduino-esp32
`3.20017.241212`, the core `platformio.ini` names), in the second session,
because the host test fakes the wire and these are the four things the fake
assumes:

- `HTTPClient::beginInternal()` calls `clear()` - the request headers added
  per call (`Authorization`, `X-Agent-Version`, `Accept`, `Content-Type`) do
  not pile up across calls on the one client.
- `HTTPClient::connect()` reuses a connected client when `_reuse` is set, and
  `end()` → `disconnect()` keeps the socket when `_reuse && _canReuse`;
  `_canReuse` is reset from `_reuse` at every reply and cleared by `HTTP/1.0`
  or `Connection: close`, which is the `NotKept` case the policy believes.
- `HTTPClient::returnError()` stops the client on any error, so a failed
  request never leaves a half-dead connection for the policy to reuse.
- `WiFiClientSecure::connected()` is a zero-length `read()` →
  `available()` → `data_to_read()` → `mbedtls_ssl_read(…, NULL, 0)` on a
  socket `ssl_client.cpp` sets `O_NONBLOCK` before connecting and never sets
  back: the probe returns at once, sees a close the server sent, and
  `available()` stops the client when it does. A reused call does not wait
  on the probe.

## Deviations from the spec or the task

- **The task's "or from a wrapper of mbedtls's allocator if this core lets one
  be set"**: it does, and that is what is used - plus the samples and the
  minimum-ever, so that what mbedtls does not allocate (lwIP's segments,
  HTTPClient's 1 KB chunk buffer and its Strings) is not missed. Said in
  `docs/console.md` and in the header comment.
- **`src/agent/` is no longer "the TLS client and the root and nothing else"**
  (`test_library`'s boundary). KeepAlive is portable so the host can test it,
  but it is about HTTPClient's codes and WiFiClientSecure's probe - this
  board's uplink, not the library's seam - so it lives beside AgentClient, like
  `observer/Connection.cpp` lives beside the observer, and the boundary test
  names it. Putting it in `lib/agent-core` would have made a board detail part
  of the library's contract (`docs/library.md`, the IDF component, the
  manifest) for no consumer that wants it.
- **A read timeout on a kept connection is treated as a dead connection** and
  the request is remade inside the call, which the task's "a call that finds
  the connection dead" could be read either way on. The silent case - a router
  that dropped the idle session without a reset - is exactly a write that
  succeeds and a reply that never comes, and it is the case the task's docs
  deliverable is about. The cost is a double submission when the server did get
  the first copy and was merely slow past 15 s: the heartbeat is idempotent,
  observations and results carry client ids the server de-duplicates on, and a
  claim re-sent to the same agent leases it what it already leased - all of
  which the loop's own retry after a failure would have done anyway, only
  later. A read timeout on a *fresh* connection is reported as before, with no
  retry here.

## Decisions taken without asking

- **The TLS client is `new`ed per handshake and `delete`d when the connection
  is gone**, rather than kept as a member and reconnected. `WiFiClientSecure`
  keeps `_lastError` from its last `connect()` and never clears it; a kept
  object that once failed verification against the ISRG root and then connected
  via the bundle would report `-0x2700` for every later dead-connection failure
  and send `AgentClient::call()` to the other root for nothing. A fresh object
  per handshake has no such history, and its `stop()` on deletion frees
  mbedtls's context, the parsed chain and both content buffers - the memory a
  failed call must give back. Between calls the kept client holds those (about
  the handshake's steady share), which is the trade the task asked for: `heap
  free` at rest will read lower than `v0.4.0`'s by that share, and `lowest
  during` a reused call will read far higher. The bench row for the README
  wants both numbers.
- **A remade WiFi link drops the kept connection before the request.** lwIP
  aborts the old sockets when the interface's address changes, so the probe
  would see it anyway on a new DHCP lease; on the same lease it might not, and
  a request would then wait out the 15 s timeout and reopen. `WifiLink::connects()`
  moving is a cheaper and surer signal, and the log says `uplink: the WiFi link
  was remade; the kept connection goes with it`.
- **The allocator wrapper is global and stays installed.** mbedtls has one
  allocator for the process; the observer's esp-mqtt tasks share it. While a
  call is in flight their allocations are sampled too, which is right - what is
  wanted is the free heap at its lowest moment, whoever asked for the bytes -
  and the two shared variables are volatile with a non-atomic compare: a lower
  figure lost to a race between two tasks is at worst one sample, never a wrong
  number. Outside a call the wrapper costs one load of a flag per allocation.
- **`HTTPClient::collectHeaders()` is called once, in `begin()`**, not per
  request: it `new`s the header table each time it is called, and the client
  now lives for the board's life. `sendRequest()` clears the collected values at
  every request, as before.
- **`uplink:` log lines are `info` for a handshake and `debug` for a reuse**,
  so that at the default level the log says how often the connection is remade
  and why, and nothing per call.
- **The idle probe is a script in `out/`, not a tool in the tree.** The task
  asked for the measurement and the report; the report quotes the log and says
  how it was made. If it is wanted again, `tools/` is the place and a
  follow-up the way.
- **For the RUNBOOK, found in the second session:** the container's
  `pio test -e native` and a host `pio run` must not run at the same time. The
  container installs the newest PlatformIO, the host has 6.2.0, and each wipes
  `.pio/build/` when it finds the other's `project.checksum` - a host build
  started beside the container died with `.sconsign311.dblite: No such file`
  and was re-run after the container had finished. Run them one after the
  other; a line in RUNBOOK §2 would save the next session the same ten minutes
  (not changed here: the runbook is not this task's).

## Not verified here (and why)

A session cannot flash a board or reach WiFi; everything below is Thomas's, on
the bench, with the observer off (the README's *Between 30 and 31*):

1. **Flash this image on the test node** (`pio run -e heltec_v3 -t upload`, or
   the merged image), open the console, `status` within a minute: the `uplink`
   line says `connection kept since HH:MM:SS (root ISRG Root X1); 1 handshake(s)
   for 1 call(s)` (or 2 for 2, if the heartbeat went already) and the first
   call's `lowest … during` - the handshake's peak, which should be about the
   80 KB dip of 28 October below `free before`.
2. **Ten minutes later, `status` again**: calls in the dozens, handshakes still
   a handful (the idle heartbeat at 120 s should mostly reuse: the server
   closes at 128 s; a few `the server closed it` handshakes are expected when a
   call lands late), `reopened in-call` 0 on a home router with an ordinary TCP
   idle timeout, and the last call's `lowest during` well above the first's.
   **Paste the `heap` line and the `uplink` line into the README's *Measured*
   table as the row *after 30, no slot*.** That row is what task 31 sets the
   gate from; note that `free` at rest now includes the kept connection's
   share, and that `lowest during` of a reused call is the steady cost.
3. **The log at `info`**: `uplink: handshake N for call M (why)` only at
   handshakes; the config call's `heap: … (… before, lowest … during)` line.
4. **A WiFi drop**: power the router off and on; after `wifi: connected` the
   next call logs `uplink: the WiFi link was remade; the kept connection goes
   with it` and `handshake N … (dropped on purpose)`, and the loop's counters
   move as they did before (`errors`).
5. **A `set meshmaster.token …`** (the same token again is fine): the next call
   handshakes with `dropped on purpose`.
6. **The 401 halt** (a wrong token for a minute): `server: http 401`, the halt,
   the OLED's fourth line - unchanged; `status`'s `uplink` line still says
   `connection kept` (a 401 is a reply) until the fix and the reboot.
7. **The in-call reopen** needs a router that drops an idle TCP session in
   under two minutes, or a NAT whose table is flushed by hand; if one is at
   hand, a call after the drop should take about fifteen seconds longer and
   log `the kept connection was dead under the request; reopened inside the
   call`, with no failure in `errors`. Not reproducible on the bench otherwise;
   the host test covers the rule.
