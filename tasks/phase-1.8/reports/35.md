# p1.8-35 — v0.5.0

What 29–34 made is released as **v0.5.0**: the notes `release.yml` writes have
v0.4.0's shape — the flasher at <https://meshcore.io> with *Custom firmware*, the
table of merged against plain `.bin`, the console set-up, *On a Heltec V3, set
MeshView only* — plus this release's own five lines, what an upgrade keeps, and
what the firmware now **says** when a second broker slot is set on a V3.
`CHANGELOG.md` has a v0.5.0 section answering the four questions, and
`agent-core` is **0.5.0** in all three manifests.

No pre-release (Thomas, 1 November: *only a few people use it, and they know the
state of the firmware*). Nothing of what the firmware does changed in this task:
both images come out at **task 34's byte counts exactly**, which is the evidence
that this is a release and not a change.

## Deviations from the spec or the task

- **The report is finished in two commits, and the second is a second pull
  request.** Criterion 1 asks the report to quote the release workflow's run and
  its checksums; that run does not exist until the tag is pushed, and the tag
  goes on a `master` that already carries this report. So this pull request
  carries everything that can be verified before the tag, and a second,
  markdown-only pull request appends *The release, as published* and ticks the
  three boxes above. One task, one branch for the substance; the second branch
  touches nothing but `tasks/phase-1.8/reports/35.md`.
- **The *What's new* section is version-specific prose inside a generic
  workflow.** `release.yml` writes the notes for **every** future tag, so a
  `## What's new since v0.4.0` left in place would be wrong in v0.6.0's notes.
  The whole *Setting it up* section is already version-specific prose that 31,
  32 and 33 edited as they shipped their features, so the smallest decision
  consistent with the file was to put the section there with a comment saying
  the task that ships a tag rewrites it, and to leave the durable per-tag record
  to `CHANGELOG.md`. A generator that read the notes from a file per tag would be
  a mechanism this task was not asked for, and a follow-up if a release is ever
  cut by somebody who has not read this report.
- **Four new settings, not three.** Deliverable 1 names `set flood.scope`,
  `set mqtt.neighbors on|off` and `discover.scopes`. `mqtt.neighbors.interval`
  (12–336 hours, default 24) is a fourth setting task 33 added; the upgrade
  bullet names it with its default, because *the new settings start at their
  defaults* is a promise that has to be complete to be worth anything.
  `discover.scopes` is a command and not a setting, so it is not in that list.
- **`docs/library.md` gained two table rows that belong to task 32.** *Any change
  to what the firmware does* is out of scope and this is a page, not behaviour;
  but the v0.5.0 CHANGELOG's answer to the first of the four questions is
  `floodScope()` and `setFloodMode()`, and the page that question points a
  consumer at did not document them. Two rows, no behaviour.

## Decisions taken without asking

- **The *Unreleased* section is replaced, not kept beside v0.5.0.** One section
  per tag is the file's own rule, and task 34 said in its report that it wrote
  *Unreleased* only because 35 tags. Everything it recorded is in the v0.5.0
  section.
- **Five bullets, not five lines of one paragraph.** *in five lines* read as one
  line per thing 30–34 left behind, which is what the task's own *Goal* lists;
  each bullet names the console line or the `status` line a reader can check it
  with.
- **The V3 refusal is quoted as a fenced block.** The phrase carries a colon and
  a semicolon and sits inside a sentence; a reader on the bench is comparing it
  with what the console answered, so it is on a line of its own, exactly as the
  firmware prints it.
- **`out/35-release-notes-rehearsal.md` is produced by parsing `release.yml` and
  running its own step**, not by copying the heredoc into a script by hand: a
  rehearsal of the notes is worth having only if the thing rehearsed is the thing
  that runs. The parse is also what caught a hand-indented heredoc inside a YAML
  block scalar on the first attempt — the body had been written at column 0,
  which would have ended the block scalar and broken the workflow.
- **No pre-release and no `--latest` flag.** `gh release create` in the workflow
  passes neither `--prerelease` nor `--latest`; GitHub marks the newest
  non-prerelease release *Latest* by itself, and v0.5.0 is newer than v0.4.0.
- **`out/release-notes-v0.4.0.md` is left on disk** for Thomas to delete, as the
  task asks; it is git-ignored and was not copied into the tree.

## Not verified here (and why)

A session cannot flash a board or hear a radio. The walk is the README's
*Afterwards* for pile 1.8, and what it finds goes into a **v0.5.1**:

1. **A V3, one slot, an hour beside the uplink.** Flash
   `meshmaster-agent-heltec_v3-v0.5.0-merged.bin` on a fresh board, or the plain
   `.bin` over a v0.4.0 one, set MeshView only, leave it an hour, then `status`'s
   `heap` line — **`min ever`** is the number — and `get mqtt.status`'s `memory`,
   `uplink`, `tls` and `stack` lines. Task 31's *Not verified here* 1 and 2 are
   the detail, including the three outcomes of a handshake with the slot up and
   what each one means for `kHeapFloorBytes`.
2. **A V4, both slots**, with the `tls` line's *routed there* climbing and `0
   fell back` (task 31's 4). That is the one thing of this pile that can fail on
   hardware alone.
3. **A V3 upgraded from v0.4.0 with `mqtt2.preset meshmapper` stored.** The notes
   promise `slot 2 meshmapper: off (this board has memory for one broker; a V4
   carries two)` on `get mqtt.status` and one slot everywhere else. This is the
   upgrade path the notes' new bullet points at, and the only way an upgrade to
   this release looks different from the one before it.
4. **`discover.scopes` on FD9B**, then its MeshView page: *Direct neighbours*
   with TwinOak Risskov's scopes, and Battery, Noise floor and TX/RX filled
   rather than *—* (task 33's one unticked criterion).
5. **A flooded login to a repeater with no stored path**: `status`'s `flood` line
   counting a scoped answer, and the job's log saying `(flood, scope dk)` on
   try 1 (task 32's walk).
6. **The version string on a board.** `status` and the heartbeat should say
   `0.5.0+<sha7>` for the tagged commit, which is also what the notes' second
   line says. Checked against the published notes below, not on a board.
7. **The upgrade keeping the settings** — WiFi, the token and the board's key
   across a plain `.bin` — which the notes promise and no session can test. The
   promise is the partition table's, and the check that keeps it there is task
   p1.2-11's.
