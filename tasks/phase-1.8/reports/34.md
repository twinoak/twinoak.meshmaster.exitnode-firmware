### The commits that mattered

Of the 266, the ones this firmware had to answer, from their diffs:

- **`35142a88` (#1896) — robust time on ESP32.** `ESP32RTCClock::begin` seeded
  15 May 2024 on a power-on and left the clock alone on every other reset; now
  it seeds **1 March 2026** (`RTC_TIME_MIN`) on any reset that has no valid RTC
  backup, restores the backup when it has one, and `tick()`/`setCurrentTime`
  keep that backup — the last time this board ran at — in `RTC_NOINIT` memory
  across a crash, a watchdog or a brownout. This firmware's
  `kEarliestPlausibleTime` was **1 January 2025**: with the new seed above it, a
  fresh power-on would have been read by `AgentClock::begin` as *kept by the RTC
  across the reset*, `hasTime()` true, and the first heartbeat, lease check and
  result timestamps dated March 2026 until SNTP answered. **The floor is now
  1 November 2026** (`src/net/Clock.h`, with the reason beside it), so the seed
  is *no time* as it was, and a restored backup — a genuine time this board was
  set to — is *kept by the RTC*, which is what that source meant. The enum's two
  comments say so. (The eight-month corner: a board that ran on the seed alone
  for eight months would cross the floor — and would have been an exit node that
  never reached SNTP or the server for eight months first.)
- **`41588d80`, `b4f7e941` — `CommonRadioPrefs`**, and **`f722794e`, `0c3fe356`**
  (`set af`, `agc.reset.interval` validated): the CLI row above. Citations moved;

- **`01f9293b` (#3568) — a transport code of 0 is un-scoped**, and **`f19733e4`

## The two new behaviours, where they touch us

- **A transport code of 0 is un-scoped** (`01f9293b`, #3568): `RegionMap::findMatch`
  (`src/helpers/RegionMap.cpp:191`) answers its wildcard for
  `transport_codes[0] == 0`, so a repeater forwards such a flood where the pin
  dropped it. **32's code already reserves 0 and FFFF**: `reserveTransportCode`
  (`src/mesh/TransportScope.cpp:55-59`) turns a 0 into 1 and an FFFF into FFFE,
  it is applied to every code `transportCodeFor` computes (`:73`), and
  `test_flood_scope` holds both edges (`0x0000 → 0x0001`, `0xFFFF → 0xFFFE`) and
  two thousand payloads that never produce either. So no scoped flood of this
  board is read as an unscoped one — and that is now *why* the reservation
  matters, which `TransportScope.h` and `docs/upstream.md`'s scope row say. An
  **unscoped** flood of ours (`flood.scope *`, or the second try under
  `flood.unscoped retry`) is `ROUTE_TYPE_FLOOD` with no codes at all, which is a
  different route type and not a code of 0; unchanged.
- **A hidden repeater answers no node discovery** (`f19733e4`, #3538):
  `isHiddenNode()` is `advert_interval == 0 && flood_advert_interval == 0`, and
  on a repeater the local interval is zeroed by `CommonCLI::savePrefs` on the
  first manual `set`, so `flood.advert.interval 0` alone is what hides one.
  33's sixty-second discovery misses such a repeater; its adverts, if it sends
  any (a manual `advert`), still put it in the table through `onAdvertRecv`.
  Said in `docs/observer.md`'s *Neighbours*, in one sentence, and in
  `docs/upstream.md`'s discovery row.
