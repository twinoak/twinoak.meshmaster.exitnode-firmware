# p1.8-32 — A scope of its own

Every flood this firmware sends now carries a **transport code** for the region
`flood.scope` names — `dk` out of the box, the Danish standard's — and the
**second** flood of a transaction drops it while `flood.unscoped` is `retry`, so
that a repeater with no region map is still found. `status` counts which shape
was answered, per flooded transaction since boot, and the heartbeat carries the
same three figures to meshmaster.dk (`AgentHeartbeatFlood.json`, whose task
p4.20-151 had merged by the time this ran).

Thomas, 31 October: *are our exit nodes not using scopes at all?* They were not:
every flood was a plain `ROUTE_TYPE_FLOOD` with no codes. They are now, and the
number that says the day the unscoped try stops earning its airtime is
`status`'s `flood` line and the heartbeat's `answeredUnscoped` — a figure, not a
guess.

Nothing a bench has to type: `dk` is the fallback, and only an installation
outside the Danish standard sets anything.

**Read against the firmware it builds against** (MeshCore at `d9296435`, on disk
under `.pio/libdeps/*/MeshCore`), because every number above is upstream's:

- `TransportKeyStore::getAutoKeyFor` hashes **the name as it is given** and keeps
  the first `sizeof(key)` bytes; the `#` is the *caller's*. `RegionMap::
  getTransportKeysFor` adds it for a region stored without one (`tmp[0] = '#'`),
  and the companion's own default scope does the same
  (`temp.getAutoKeyFor(0, "#" DEFAULT_FLOOD_SCOPE_NAME, key)`). So a public
  region's key is SHA-256 over `#` and the name, and `floodScopeKey` hashes
  exactly that.
- `TransportKey::calcTransportCode` finalises the HMAC straight into a
  `uint16_t`, which on an ESP32-S3 is the first two bytes little-endian. Ours
  takes the two bytes and assembles them, which says the same thing on both ends
  of this protocol without depending on the endianness of whatever compiles it.
- `Mesh::sendFlood(packet, delay, path_hash_size)` sets `ROUTE_TYPE_FLOOD`;
  `Mesh::sendFlood(packet, transport_codes, delay, path_hash_size)` sets
  `ROUTE_TYPE_TRANSPORT_FLOOD` and copies both codes. `sendDirect` has one
  overload and it takes a path. There is no way for a direct send of ours to
  carry a transport code.
- `MyMesh::sendFloodScoped` leaves `codes[1] = 0` with upstream's own REVISIT
  beside it (the sender's return region is not expressed yet), and so do we.
- On the repeater: `MyMesh::onRecvPacket` matches a `ROUTE_TYPE_TRANSPORT_FLOOD`
  against the region map and a `ROUTE_TYPE_FLOOD` against the wildcard, and
  `allowPacketForward` refuses a flood with no region behind it and one past
  `flood.max.unscoped` hops. `sendFloodReply` sends a reply **in the request's
  own scope** (`mesh::chooseReplyScope`), which is why nothing of ours has to ask
  for one: a scoped login's reply comes back scoped by itself.
- `RegionMap::is_name_char` is `c == '-' || c == '$' || c == '#' || (c >= '0' &&
  c <= '9') || c >= 'A'`, and `RegionEntry::name` is `char[31]`. Ours is that
  less `$` and less a `#` anywhere but the front.
- The Danish standard, re-read on today's `master` of meshmaster.dk
  (`src/MeshMaster.Core/Configuration/dk.json`): default scope `dk`,
  `flood.max.unscoped` **15**, 425 region names of which the longest is
  `dk-fyn-kerteminde` at seventeen characters — well inside the thirty this
  setting takes.

## Deviations from the spec or the task

- **The log line's shape is the parenthesis, not the prefix.** The task shows
  `login (guest) try 2: unscoped`; D-47 shows the .NET agent's
  `login (Guest) try 2, unscoped: ok`. This firmware's lines already end with
  `(direct)` or `(flood)` — the shape the packet went out in — so the scope went
  **there**: `login (guest) try 1: no reply (flood, scope dk)` and
  `login (guest) try 2: logged in as admin (flood, unscoped)`. One word in one
  place, every send that can flood, and no line of the existing shape disturbed.
  `exchange`'s `no reply` line, which said nothing about how the packet went,
  gained the same parenthesis.
- **A transaction is a retry loop, and `runDiscover` is one of them whole.** The
  task's *where a transaction floods twice within one attempt (the login's two
  tries, a discovery that is repeated)* reads naturally as the login sequence and
  the discover handler, and that is what the two `FloodTransaction` guards mark.
  The **blank login** of the rotation probe sits inside the login's transaction,
  so on the one path that probes it is that transaction's second flood and goes
  unscoped, and the second try is its third. That is the task's rule applied as
  written — *the second flood goes unscoped* — rather than a rule about try
  numbers, and it is what makes `runDiscover` work at all.
- **`get flood.scope` prints the key.** The task asks for "the name and the
  transport code of an example payload"; the key is printed beside them, because
  it is the thing a bench can actually compare between two boards and because
  D-47 says in so many words that a public region's key *is public by
  construction*. No rail is bent: there is no secret in a hash of a region name,
  and a private region — the one kind whose key is a secret — is refused by
  `set`.
- **The example payload is this repository's own choice**, since the task names
  none: payload type 0 and the eight bytes `00`..`07`, fixed in
  `src/mesh/TransportScope.h`, documented in `docs/console.md` and held by a
  test. For `dk` the key is `4a447e7539b0418bd14cf28aa8241529` and the code is
  `0x234b`.
- **MeshCore's `TransportKeyStore.cpp` is not compiled by the native tests**, so
  the acceptance criterion's *computed in the test from the library* is met by
  the library it **hashes** with rather than by calling upstream's function: its
  header pulls in `Arduino.h`, `Packet.h` and `IdentityStore.h`, and the last of
  those does not even define `FILESYSTEM` off a board. What the tests do instead
  is stronger than a pasted constant in both directions — an independent HMAC
  built from the library's plain SHA-256, two published standard vectors, and the
  pinned source's own text read off disk — and it is written down in
  `test/test_flood_scope`'s header comment.
- **`status`'s line has a clause the task did not ask for.** The task's text is
  `flood: scope dk, answered scoped N / unscoped M / none K since boot`; the line
  ends with the rule in force (*the second flood of a transaction goes
  unscoped*, *every flood is scoped (flood.unscoped never)*, *every flood goes
  out with no transport code (flood.scope \*)*), because the three counts cannot
  be read without knowing which of the three a board is doing.

## Decisions taken without asking

- **Where the rule lives, and where the arithmetic lives.** The *rule* — which
  flood of a transaction drops the scope, and what the three counts are — is
  `lib/agent-core`'s, because it is policy with no board in it and every branch
  of it had to be walked on a host; the *arithmetic* is `src/mesh/`'s, because it
  is MeshCore's hash of MeshCore's packet, and the library may include nothing of
  MeshCore (`test_library`, `test_seams`). The seam between them is two methods
  on `IMesh`: the mesh says what scope it floods in, and is told scoped or
  unscoped per send.
- **rweather/Crypto rather than a SHA-256 of our own.** A copy of the algorithm
  in this tree would be a second implementation that could drift from the one
  the repeater runs, and a transport code the two ends disagree about is a flood
  nobody forwards. The board already links this library (MeshCore hashes with
  it), so the only cost is the host build — three of its translation units,
  added the way `lib/ed25519` already is, from the same pinned release.
- **`FakeMesh` says nothing about scope by default.** `floodScope()` answers
  nullptr, as `IMesh`'s own default does, so every suite written before this task
  sends the heartbeat it always sent and `test_loop`'s three *the heartbeat it
  always was* tests still mean what they meant. A test of the scope says
  `setFloodScope("dk")`. The board's own default is `dk`, in the key table where
  a default belongs.
- **The heartbeat's `flood` is written whenever the mesh reports a scope**, which
  on this board is always — the key table's fallback is `dk`, so there is no
  state in which a Heltec says *the companion's own*. `scope: null` is reachable
  only for an implementation that answers nullptr, and `Envelopes.cpp` writes it
  as the absence of the member, which is what the contract asks for.
- **A value the mesh is handed that the key table would not have taken is
  treated as `*`.** `setFloodScope` validates again rather than trusting its
  caller: a key made out of nonsense is a flood no repeater forwards, and an
  unscoped flood at least still travels. The console cannot produce such a value;
  an NVS blob written by an older or a broken image can.
- **A transaction answered on a *direct* send after a flood counts as
  `unanswered`.** The case is a flood that was silent, a re-login that taught a
  path, and the next attempt answered directly. The flood was not answered, and
  the flood is what these figures measure; the header says so where the rule is.
- **`ConsoleHost` gained a generic `keyNote` hook rather than a `floodScope`
  one**, so that the next key whose value needs a sentence beside it is one
  `strcmp` in `main.cpp` and not another function pointer in the struct.
- **`reserveTransportCode` is its own function.** Upstream's reservation is two
  branches inside `calcTransportCode` that no payload can be made to reach on
  purpose. Lifting it out makes it a test (`0x0000 → 0x0001`,
  `0xFFFF → 0xFFFE`) instead of a hope, and the loop beside that test checks two
  thousand payloads never produce either.
- **The frame log is unchanged.** `log.frames on` prints a packet's header as it
  did; the transport codes are set by `Mesh::sendFlood` *after* `logFrame` has
  run, so printing them would have meant moving the log line or reading the
  packet twice. The job's log says the shape of every send, which is the same
  information in the place a person reads it.
- **`CHANGELOG.md` is not touched.** It has one section per **tag** and this pile
  releases in task 35, which its own task file already asks for `CHANGELOG and
  agent-core 0.5.0`. What that section has to record from here: `IMesh` gained
  `floodScope()` and `setFloodMode()`, **both with defaults and therefore
  additive**; `Heartbeat` gained `flood` and `HeartbeatFlood` is new, also
  additive and left out when unset; and the contract fixtures' manifest commit
  moved `67c2a4c` → `42e4d45`, **by addition only** — two files appeared and no
  existing fixture's bytes changed, which is the question that breaks a consumer
  silently.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and **every number above about
what a repeater does with a scope is read off upstream's source, not off the
air**. The walk, with the images of task 35 (or `pio run -e heltec_v3 -t upload`
from this branch):

1. **`get flood.scope` on two boards.** Both print
   `flood.scope unset (dk)` and then
   `scope     dk: key 4a447e7539b0418bd14cf28aa8241529 (sha-256 of "#dk", first 16 bytes; public by construction), example payload -> transport code 0x234b`.
   The same two values on both; a board that prints others is not flooding the
   same region.
2. **`status`** at boot: `flood     scope dk, answered scoped 0 / unscoped 0 /
   none 0 since boot; the second flood of a transaction goes unscoped`, and the
   log said `flood: scope dk, the second flood of a transaction unscoped` once at
   start-up.
3. **A scoped flood that is answered.** Press *Discover* for a repeater this exit
   node holds no path to **and whose own console's `region` lists `dk` with
   `F`** — a repeater that follows the Danish standard. The job's log should read
   `flooded login, for the path its reply comes back along: logged in as … (flood,
   scope dk)`, and `status`'s `flood` line should move to `answered scoped 1`.
   *This is the step that proves the transport code is right*: a wrong code is a
   repeater that forwards nothing, and the job would be `unreachable` instead.
4. **A scoped flood that is not, and the unscoped try that is.** The same
   *Discover* against a repeater with **no region map** (`region` on its console
   lists the wildcard alone). Try 1 should be silent and say
   `(flood, scope dk)`, try 2 should answer and say `(flood, unscoped)`, and the
   count should move to `answered unscoped 1`. If a repeater with no region map
   answers the **scoped** try as well, that is worth a report: it would mean a
   stock repeater's wildcard match is looser than
   `MyMesh::onRecvPacket`/`allowPacketForward` read.
5. **`set flood.unscoped never`** and repeat step 4: both tries should say
   `flood, scope dk`, the job should be `unreachable`, and the count should move
   to `none 1`. Then `set flood.unscoped retry` again.
6. **`set flood.scope *`** and repeat step 3: every line should say
   `flood, unscoped`, the repeater should answer as it always did, and the count
   should move to `answered unscoped`. `get flood.scope` should print
   `* : every flood goes out with no transport code at all`. Then
   `set flood.scope dk`.
7. **`set flood.scope dk-aarhus`**, and `get flood.scope`: a different key and a
   different code. On a repeater whose region map holds `dk` but not
   `dk-aarhus`, the scoped try should now be the silent one — the inverse of
   step 3, and the clearest single proof that the code is per region.
