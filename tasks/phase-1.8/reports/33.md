# p1.8-33 — Its neighbours and their scopes

An exit node now publishes the observer firmware's `neighbors` message — the
repeaters it hears at **zero hops**, each with its SNR, when it was last heard
and the flood regions it answers an anonymous regions request with — to every
connected broker slot once a day, which is what MeshView draws its *Direct
neighbours* section from; its status message carries the noise floor, the air
time and the battery MeshView showed as *—*; and `discover.scopes`,
`mqtt.neighbors`, `mqtt.neighbors.interval` and the `nbr:` line of
`get mqtt.status` are the observer firmware's own names for all of it.

Around it, the exit node's rules: the table is a fixed array of twenty and the
report a static buffer, so the heap pays nothing until a client copies the
report into its outbox — and that copy is what task 31's gate is asked about
before the report is offered; every request of the sweep waits for the
**jobs' own airtime gate** and is counted on it; nothing of the sweep goes on
the air while a job is open or in flight; a query is synchronous and bounded by
the observer firmware's timeout, so a claimed job waits for at most the one
query on the air; and the sweep's frames are decoded exactly as a job's are,
with the peer set for the query and forgotten after it.

  dated by its own timestamp and never poses as fresh, which is why retaining
  where the preset allows is safe.

## Deviations from the spec or the task

- **`discover.scopes` prints the table and starts a cycle; it does not block
  for the cycle.** The task's "runs one cycle now and prints the table": a cycle
  is sixty seconds of discovery and then one request per neighbour at the
  budget's pace — ten minutes for twenty — and a console that blocks for that is
  a console nobody can type `status` at. So the command prints the table as it
  stands (each neighbour with its SNR, RSSI, age and what the last cycle found
  for it) and starts the cycle in the main loop's background, as the observer
  firmware's own `discover.scopes` does (`OK - neighbor discover started (N
  neighbors)`); the log says how it went and `get mqtt.status`'s `nbr:` line has
  the phase. A second `discover.scopes` while one runs says so and starts nothing.
- **The node discovery is a transaction on the budget too.** The task names the
  regions requests as the transactions; the discovery is one more packet on the
  air per cycle, and it goes through the same gate for the same reason.
- **`heard_secs_ago` is never null.** The observer firmware writes `null` for an
  entry heard before its clock was set; this table stamps entries on the uptime
  clock, which is set from boot, so the age is always known. CoreScope reads
  either.
- **`battery_mv` is left out under a volt.** Both Heltecs always read the ADC
  pin, and a board on USB with no battery reads noise there; the observer
  firmware publishes whatever the ADC says. A volt is this firmware's own line,
  in `main.cpp` beside the read.
- **The first periodic cycle runs five minutes after the sweep is switched on,
  and a periodic cycle runs only while a broker slot is connected.** The observer
  firmware fires as soon as its bridge runs. Five minutes lets the table hear a
  round of adverts and the slots have their handshakes before the sweep's first
  request, and a report with nowhere to go is airtime spent for nothing. A
  manual cycle runs regardless, as its does.
- **The window's control frames are let through to MeshCore's dispatch.**
  "`onRecvPacket`'s release of everything else stays as it is" — it does, with
  one addition: for the sixty seconds a discovery is open, a `PAYLOAD_TYPE_CONTROL`
  frame goes to `Mesh::onRecvPacket`, whose control arm reads it (plaintext, no
  decryption, no shared secret) and releases it whatever it was. Outside the
  window it is released here as before.

## Decisions taken without asking

- **Where it lives: `src/observer/Neighbours.{h,cpp}`**, host-portable, with
  the mesh behind a seam (`NeighbourLink`) that `AgentMesh` implements and the
  test fakes — the same shape as `Connection.h`'s `Client`. The rails of
  `test_observer` (no network names, no `LOG_`, no `Serial.`) hold over the new
  file; the Observer logs through `logf` as it did.
- **A query is synchronous, and that is the whole of "a claimed job waits for at
  most the one query".** The sweep sends a regions request and waits for its
  reply inside `queryRegions`, pumping the console, the OLED and the connections
  as a job's wait does; a claim is made from the main loop, which is blocked for
  the query's few seconds and no longer. The reverse — a job open, the sweep
  waiting — is `busy()`: `JobRunner::openJob()` from the claim to the end, or a
  peer set in the mesh. And a cycle's end, which builds the report, waits for
  `busy()` too, so the report is never built on a job's stack.
- **The sweep's requests go through `JobRunner::gate()`**, made non-const for it:
  one budget for the board, not two. The task's "a transaction on the exit node's
  own airtime budget (`Airtime.h`)" read as that.
- **"Published one at a time" is: the next slot is handed the report only when
  the previous slot has taken it and its own outbox is empty.** The client copies
  a message into its outbox (`esp_mqtt_client_enqueue` with `store`), and ten
  kilobytes is more than `kOutboxBytes` by itself, so the usual bound would never
  let the report through; an empty outbox is the bound instead, and the gate is
  asked once, before the first hand-over, for one copy on top of the uplink's
  next call.
- **The report's gate** is `free ≥ report + the uplink's dip + the floor + the
  margin` and `largest block ≥ report + 256` — task 31's arithmetic less the slot
  that is already open, plus the outbox's item. Skipped is skipped for the whole
  cycle; the next cycle builds a new report.
- **A slot that leaves `connected` before taking the report counts as failed**,
  and `nbr:`'s `last` is `ok` when at least one slot took it, `failed` when none
  did, `no slot` when none was connected with a neighbours topic, `skipped (heap)`
  when the gate said no.
- **A manual cycle runs while `mqtt.neighbors` is off** and publishes if a slot
  is connected (the observer firmware's "Neighbors publish after
  `discover.scopes`, or every interval when `mqtt.neighbors` is on"); turning the
  setting off drops a *periodic* cycle where it stands and leaves a manual one
  to finish. A changed interval counts from the last cycle's end.
- **The snapshot keeps 256 characters of scopes per entry** — CoreScope's bound
  and the task's — though a reply can carry about 172 (a payload is 184 bytes
  less the datagram's overhead and the eight-byte prefix). 1.6 KB of static RAM
  for the literal bound; a later pile can shrink it with the wire's figure.
- **`queried_neighbors` counts requests actually sent** (`send_failed` is not
  one), as the observer firmware's `neighbor_discover_queried_count` does; a
  responded neighbour's table entry is re-stamped as heard now, as its
  `touchNeighbourHeard` does.
- **The report's `self.default_scope` is `flood.scope`** read off the mesh (`*`
  when unscoped), and `self.scopes` is `""`: an exit node forwards no flood and
  has no region map, which is what a repeater with none answers.
- **`discover.neighbors` is not a command here.** The observer firmware has it
  as a bare table refresh; this firmware's cycle does its own, and one command
  that does the whole thing is what the task asks for.
- **The log says what the sweep does, as counts and keys**: the discovery sent,
  each regions request's outcome with the scopes it got (a region name is public
  by construction, D-47), the report built with its size and counts, and each
  slot's hand-over. Never the report's bytes (`test_connection` holds it).
- **`CHANGELOG.md` is not touched**, as task 32 left it: one section per tag,
  and task 35 writes 0.5.0's. What it has to record from here: `IMesh` is
  unchanged; `JobRunner` gained a non-const `gate()` (additive); two keys and one
  console command; the heartbeat is unchanged (the task's out-of-scope line).

## Not verified here (and why)

A session cannot flash a board, hear a radio or reach a broker, and **every
number above about what a repeater answers is read off the pinned source, not
off the air**. The walk, with this branch's images (`out/33-heltec_v3-firmware.bin`,
`out/33-heltec_v4-firmware.bin`, and CI's artifacts):

1. **`discover.scopes` on FD9B** with one slot connected. The line
   `neighbours N heard at zero hops (table of 20); nbr: …` and the table — TwinOak
   Risskov should be in it with its SNR and RSSI — then `cycle starts now: 60 s
   of node discovery …`. On the log within the minute: `neighbours: node
   discovery sent (zero hop, repeaters); taking answers for 60 s` and, for each
   repeater that answers the discovery, `neighbours: <key> answered the node
   discovery, snr …`. Then one `neighbours: regions request to <key>: responded,
   scopes dk,…` per neighbour, twenty seconds apart (the budget's gap), each one a
   `frame tx anon-req direct` and a `frame rx response direct hops=0` with
   `log.frames on`. **This is the step that proves the request is right**: a
   repeater that does not answer is `timeout`, and `timeout` for every neighbour
   is the request's shape (or its scope: a regions request is anonymous and
   unscoped, so it is not that) and not the air. Then `neighbours: report built
   (N bytes, …), going to 1 slot(s)` and `observer: slot 1 meshview: the
   neighbours report (N bytes) is handed to the broker`.
2. **MeshView's page for FD9B**: *Last /neighbors Report* no longer *never*;
   *Direct neighbours* with TwinOak Risskov and its scopes; *Battery* (a volt or
   more, or *—* on USB with no battery), *Noise floor* and *TX/RX* filled within
   one status interval (five minutes). If the page shows the report but no scopes
   for a neighbour whose console's `region` lists `dk` with `F`, the names are
   being read wrongly — `readRegionsReply` and the log line of step 1 say what
   arrived.
3. **The gate.** `get mqtt.status`'s `nbr:` line after the cycle: `last ok …`.
   `status`'s `heap` line: `min ever` after the cycle and after the next
   MeshMaster call, on a V3 with one slot — the report's outbox copy (up to
   10 KB) is the peak this task adds, and the figure for the *What it costs* row.
   If `nbr:` says `last skipped (heap)` on a V3 at rest, the gate's arithmetic is
   asking for more than the board has with a slot up, and the margin in
   `heapAllowsReport` is the constant to discuss.
4. **A job during a cycle.** Press a read on meshmaster.dk while the `nbr:` line
   says `running (query …)`: the job should run (its log as ever) and the next
   regions request should follow it by the budget's gap; `jobs`'s transaction
   count and the sweep's log lines should interleave and never overlap.
5. **A day later**: `nbr: next in …` counting down from 24 h, and the second
   cycle on the log at the hour; `status`'s `min ever` still above the floor
   (16 384) — the task's own criterion for a V3 with one slot.
6. **`set mqtt.neighbors off`**: `nbr: off (mqtt.neighbors off)`, no cycle at
   the hour; `discover.scopes` still runs one. `set mqtt.neighbors.interval 12`:
   `nbr: next in …` moves to twelve hours from the last cycle.
7. **A V4 with two slots**: the report handed to slot 1 and then to slot 2 on
   the log, one after the other, and MeshMapper's broker holding it retained.
8. **The timeout on the air.** `queryTimeoutMs()` at SF 8 / 62.5 kHz is a few
   seconds (300 + the CAD window + 360 + two full-packet air times); a repeater
   that answers late — `timeout` on the log followed by a `frame rx response`
   that nothing takes — is a timeout too short for this channel, and the
   observer firmware's arithmetic, not this firmware's, to raise with its author.
