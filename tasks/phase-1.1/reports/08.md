# p1.1-08 — The host harness

The firmware's protocol side had only ever run as native unit tests, one function
at a time. It now runs **whole**, on Linux, against a fake repeater written from
MeshCore's own source: thirteen job types, one cycle, claim → air → result →
settled, in seventy-two seconds and with no radio anywhere near it.

It earned its keep on the first run. Two faults in this firmware that no native
test could have found, because both live in the wiring *between* files, and both
would have been discovered with a board on a bench and a day gone:

1. **Every login reply was dropped.** `handleLoginReq` prefixes its reply with
   the **repeater's** clock, not with the sender's timestamp that every other
   reply in the file reflects back. `AgentMesh::sendLogin` returned its own
   timestamp as the tag to match on, so `takeResponse` dropped every login reply
   for having "another tag" — and **every job that needs a session would have been
   `unreachable`**.
2. **The server's budget never reached the airtime gate.** `AgentLoop::doConfig`
   took it from the config reply and never passed it on, and `doHeartbeat` only
   passes one on when the reply's *differs from that field*. Invisible in
   production, where the gate's own default is also the server's; plain the moment
   an owner raises an exit node's budget.

Both are fixed, each with the finding written beside the fix.

**What it does not prove.** Not one byte went on any radio. Timing on the air,
SNR, interference, the real region loader and the first second of a cold SX1262
are not here. `docs/host.md` says so in its first paragraph and so does the
program's own log line; the bench list of every phase-1 report is still the bench
list.

### `HostMesh` against `FakeCompanion.cs`

Written from `examples/simple_repeater/MyMesh.cpp` and `src/helpers/CommonCLI.cpp`
at `d9296435`, deliberately not from the other fake, so that the two could
disagree. They do, in six places.

| # | Where the two differ | Which it is |
|---|---|---|
| 1 | **A login reply carries no tag of the sender's.** `handleLoginReq` writes the repeater's own `getCurrentTimeUnique()` into the reply's first four bytes; `handleRequest` reflects the sender's timestamp and calls it "kind of like a 'tag'". `FakeCompanion` cannot see this at all — it answers over a cable with `PUSH_CODE_LOGIN_SUCCESS`, which carries no tag by construction. This firmware matched a login reply by tag and dropped every one. | **This firmware's bug.** Fixed: `sendLogin` leaves `tag` 0 and the reply is matched on nothing, as the .NET agent matches its push code. |
| 2 | **A blank login to a repeater whose guest password has never been set is answered *guest*.** The firmware's ACL lookup and its password comparison are two separate `if`s, so the empty string is compared with `_prefs.guest_password` — which `NodePrefs()` leaves empty. `FakeCompanion` reads it as an `if / else if` chain, so a blank password never reaches the comparison and a key the ACL does not hold is refused (or silent under a knob). | **A .NET-side misreading.** FOLLOWUPS `[meshmaster.dk]`. It changes what an `acl` probe reports through a revoked pair: `unauthorized` at guest, not `unreachable`. |
| 3 | **The replay rule is not modelled on the .NET side at all.** `onPeerDataRecv` keeps a `last_timestamp` per client: an *equal* CLI timestamp is a retry and runs nothing, a lower one is dropped, a `REQ` needs strictly more. `HostMesh` keeps it and the harness proves the apply engine's fresh second per line matters; `FakeCompanion` keeps no such state. | **A .NET-side gap.** FOLLOWUPS `[meshmaster.dk]`. |
| 4 | **`StrHelper::ftoa` truncates seven digits; `FakeCompanion.Ftoa` rounds six.** `get lat` on a repeater at 56.41 answers `> 56.4099998` from the firmware and `> 56.41` from the .NET fake. A snapshot stores the string and drift compares strings. `HostMesh` ports `_ftoa` from the source. | **A .NET-side approximation.** FOLLOWUPS `[meshmaster.dk]`. |
| 5 | **Nothing is padded on the .NET side; everything is on the air.** A reply is one AES datagram whose plaintext MeshCore zero-pads to sixteen bytes (`Utils::encrypt`), so a board reads the reply **and one to fifteen zero bytes**. `FakeCompanion` sends the exact bytes, because over a cable the frame carries its own length. `HostMesh` pads. The consequence is this firmware's and not anybody's bug: a **48-byte legacy `RepeaterStats`** (4 + 48 → 64) and a current 56-byte one (4 + 56 → 64) both arrive as 60 bytes, so `parseRepeaterStats`' length-based version detection reads the padding as a real reading of zero. Over a cable the .NET agent can tell them apart; on a board nothing can. | **Neither fake is wrong: the two transports differ.** A limitation of the board, written down here and in `Not verified here`. |
| 6 | **The default `config.read` list is fifteen keys here and sixteen there.** `agc.reset.interval` is in `ConfigReadPayload.DefaultKeys` and not in `kDefaultConfigKeys`. Found because the harness's 20 transactions and §7's 20 are the same number reached two different ways. | **This firmware's divergence from the spec**, left for a reviewer: what a default read costs is the lease arithmetic's business, not a harness task's. FOLLOWUPS. |

A seventh difference was mine and lasted ten minutes: the first draft of
`HostMesh` read the neighbours request's public-key prefix length from
`payload[7]` instead of `payload[6]`, so every page came back three entries long
with somebody else's bytes in the prefixes. The harness found it on its first
cycle, which is the argument for two readings in one sentence.

## Deviations from the spec or the task

- **Acceptance criterion 3 cannot be met by a script, and that is the task's one
  unmet criterion.** The task asks `tools/host-run.ps1` to register an exit node
  "through the API with a `config`-scoped token", associate a repeater "through
  the wizard's API", and queue a cycle including an apply and a rotation.
  meshmaster.dk closes every one of those doors to a token on purpose:
  - `POST /api/v1/me/tokens` answers **501**: a token is issued in the web UI and
    nowhere else.
  - A personal access token **cannot re-authenticate**, so every *gated* action
    answers `reauth-required` to one, for ever (`spec/API.md` §2, decision D-26).
    Gated: `POST /repeaters/{id}/associations` (and `/advance`, `/retry`),
    `POST /repeaters/{id}/apply`, `POST /repeaters/{id}/cli`,
    `POST /repeaters/{id}/credentials/rotate`. Verified against the live stack:
    `{"type":"reauth-required", …, "detail":"… A personal access token cannot
    provide one: do it in the web UI."}`
  - **Session cookies are not accepted on `/api/v1`** at all.
  - There is no ungated job-creating door either: `POST /repeaters/{id}/jobs` and
    `GET /jobs` of `spec/API.md` §4's resource map are **404** on this build.

  So *every* way of queueing a job on meshmaster.dk is a Razor page posted with a
  session behind a fresh second factor. A script *can* drive those pages — this
  session proved it by hand with `curl`: signed in as the seed admin with a TOTP
  code computed from the published secret, and minted a `read, jobs, config`
  token from `/account/tokens/new`. `tools/host-run.ps1` does **not**, for a
  reason worth stating: Windows PowerShell cannot hold that session at all,
  because the application's cookies are `Secure` unconditionally and .NET's
  `CookieContainer` will not send a `Secure` cookie over plain HTTP. Driving the
  pages from a script is a different deliverable — brittle against every UI change
  and a decision about going round a trust boundary — and it is not one to take
  unasked in an unattended session. The script therefore does everything outside
  the boundary, asserts it, and **prints the four clicks with the assertion for
  each**, the way a *Not verified here* list does. Per `tasks/RUNBOOK.md` §5 this
  is a stop condition: the branch is pushed and the PR is open, and
  `tasks/phase-1.1/logs/STOPPED-08.md` says what is missing.

  What a run against the live stack *does* prove, right now
  (`out/host-run-session.log`, the stack at `bdaf526`): the stack answers; the
  token answers; the register holds the repeater whose key the scenario uses; the
  agent token answers `/agent/v1/config`; the program talks to the real server
  over plain HTTP and takes its **chunked** answers (see below); the exit node's
  record stores the companion key, all thirteen job types, the radio parameters
  and the six error counters; the journal carries no password. Eleven assertions.
  The three that fail are two meshmaster.dk findings and the gated association.

- **The real server answers `Transfer-Encoding: chunked`, which the first
  `HostClient` refused.** Found on the first run against the stack: ASP.NET Core
  does not buffer a JSON answer to measure it, so there is no `Content-Length`.
  The board never had to know — `HTTPClient` joins the chunks for it. The host
  client joins them now. Nothing of this reaches the stub, which answers with a
  length, so this is a thing only the stack could have found.

- **The exit node is the seeded one, not a newly registered one.** Registering
  one is gated (above), and the seeded `seed: Risskov window` is an exit node of
  the admin's with a published token. The scenario's `exitNode.publicKey` is
  deliberately **that exit node's own** `companionPublicKey`, so the heartbeat
  reports what the server already holds: a different key is stored, flagged,
  audited and **suspends admin routing** through the exit node
  (`spec/SECURITY.md` §6), and a harness must not leave that behind.

- **No disagreement found between the task file and today's meshmaster.dk
  `master`** on anything the harness implements. The six differences above are
  between the firmware's reading of MeshCore and the .NET fake's, which is what
  the task asked for.

## Decisions taken without asking

- **Two interfaces, named for what they are.** `src/mesh/MeshPort.h` and
  `src/agent/ServerPort.h`. `MeshCounters`, `MeshReply`, `SendResult` moved into
  the first and `Root`, `Call`, `Outcome` into the second, so the structs belong
  to the interface and both implementations fill the same ones. `AgentMesh` and
  `AgentClient` now inherit them and are otherwise untouched. `MeshReply`'s two
  array bounds are **ours** — `kMaxReplyDataLen` 184 and `kMaxMeshPathBytes` 64,
  MeshCore's values written down — with a `static_assert` in `AgentMesh.cpp` that
  the two agree, so a pin bump that moved either is a red board build and not a
  quiet overrun on a host (`docs/upstream.md`'s rule, applied).
- **Five board-only files are replaced rather than abstracted.** The Arduino core
  (`src/host/arduino/`: `Arduino.h`, `Stream.h`, `Preferences.h`, `esp_system.h`),
  WiFi, the clock and the watchdog are a second *implementation* of the same
  declaration, chosen by `build_src_filter`, not a third interface each. That
  keeps `MeshPort` and `ServerPort` the two seams the task asked for and leaves
  `src/settings/Store.cpp` — the key table, the fallbacks, the numeric parsing —
  compiled and exercised rather than stubbed.
- **The host's clock is real time, not a virtual one.** It would be tempting to
  make the airtime budget instant, but a claim's lease is real seconds on the
  server's clock and a board that waited faster than the world would read every
  lease as lapsed. So the harness waits: the stub answers a loose budget (60 a
  minute, no gap) and a cycle is a minute, and against the stack the budget is the
  server's own and a `config.read` takes the ten minutes it takes. The pacing
  arithmetic is exercised either way, at its own scale.
- **`http://` is checked on the resolved address, every call, not on the
  spelling.** The first draft refused any host that was not a literal private
  address, which also refused `host.docker.internal` — the one name a container
  needs to reach a stack on the workstation's loopback. So the rule moved into
  `openSocket`: every address the name resolves to has to be loopback or RFC 1918,
  **all** of them, so a name that answered with a private address and a public one
  is no way round it. `https://` is still refused outright: there is no TLS stack
  in that build, and a run that looked like production would be talking to
  nothing.
- **The URL is not a setting.** `meshmaster.url` still means "https://, verified"
  on the board *and* in the host build, and the console still refuses anything
  else; the harness's endpoint arrives as `--url` and lives in the client. There
  is one scheme rule in this firmware and the harness does not touch it.
- **`setBoardName()` in `src/version.h`.** The heartbeat's `board` is the
  compile-time `MESHMASTER_BOARD`, and a harness standing in for a Heltec V3 has
  to be able to say so. One function, called from the host program's argument list
  and from nothing else; `nullptr` puts the compile-time name back.
- **`acceptAnyPassword`, for the compose-stack scenario alone.** meshmaster.dk
  will not tell a script what password it stored for a repeater — revealing a
  credential is gated — so a fake that insisted on the real value could not be
  logged into from a real claim at all. The flag is `false` in the CI scenario,
  where the passwords are the scenario's own, and `src/host/HostScenario.h` says
  exactly what it gives up: that the password the server holds is the one the
  repeater has, which is the server's business and what the rotation step checks.
- **The stub is the test runner, not just a server.** It starts, runs the program
  as a child, and asserts — on what the agent posted and on what the fake saw. A
  stale recording fails naming the job, the field and both values, which is what
  the task asked "fails loudly with the field that differed" for.
- **The journal is attributed to jobs by the result's `transactions` count.**
  Exact for every path today (one `spend()` per frame, one entry per send), and
  the 82 = 82 of this run is the check. A job label through `beginJob` would make
  it exact by construction; that is an interface change and is in FOLLOWUPS rather
  than taken here.
- **`[env:host]` is excluded from the board builds in one place.** `[esp32_base]`
  gains `build_src_filter = +<*> -<host/>`, so `#include <Arduino.h>` inside
  `src/host/` can only ever find the shim and a board image can never carry a line
  of the harness.
- **A `Check` whose argument is not a boolean is reported, not thrown.**
  `tools/host-run.ps1` lost two debugging rounds to PowerShell's parameter
  shadowing (`$record` against `-Record`, `$journal` against `-Journal`: a local
  with a parameter's name *is* that parameter, and an array assigned to a
  `[string]` has a `.Count` of 1 for ever). Both are renamed and there is a
  comment at the top saying why, so the next person does not pay it again.

## New libraries (with the one-line justification)

**None.** The host client is a few hundred lines of POSIX sockets rather than
libcurl, precisely so that this line can say none: a harness is not a reason to
add a dependency the board does not have, and `[env:host]`'s only `lib_deps` is
the `ArduinoJson` the native tests already pin.

## Not verified here (and why)

A session cannot flash a board or hear a radio, and this task's whole point is
how much can be checked without one. What is left is therefore short, and two of
the four are new:

1. **The four clicks of acceptance criterion 3.** `tools/host-run.ps1` prints
   them with the assertion for each, and `logs/STOPPED-08.md` repeats them. In
   order: start the association (`/repeaters/1` → Associate, exit node 1, ACL
   read-only) and re-run the script — it must reach **active**; *Read now* — the
   jobs page must show a `status` job **succeeded** with 2 transactions the first
   time and 1 after; the Config tab's Read, Derive and Apply of one key — the
   snapshot must end with `aclRestored: true` and the change history must have a
   `device`-scope row for the key; the Credentials tab's Rotate — the stored
   credential must be the new one. Each needs a second factor within ten minutes,
   which is the whole reason a script cannot do it.
2. **A 48-byte legacy `RepeaterStats` cannot be told from a 56-byte one on this
   board.** The cipher block's padding makes both 60 bytes after the tag, so
   `parseRepeaterStats` reads `rxAirtimeS` and `recvErrors` as real readings of
   zero from a repeater that does not send them. The harness proved the arithmetic
   (row 5 of the table); what nobody can prove without one is whether any repeater
   on this mesh is still old enough to send 48. The `status` of such a repeater is
   where it would show: two counters at exactly zero while everything else moves.
3. **The login fix is proved against the fake, not against a radio.** The fake
   answers a login reply prefixed with its own clock, exactly as the source says
   the firmware does, and the agent now reads it. Walk step 8 of
   `docs/console.md` (*Read now*) is where the real one is proved: a `status` job
   that comes back **`ok after 2 transaction(s)`** rather than `unreachable`. If
   it is still `unreachable`, the login reply's first four bytes are the thing to
   put `log.frames on` against.
4. **Everything else on the phase-1 bench list is untouched by this task.**
   `tasks/phase-1/FOLLOWUPS.md`'s first open item is still the whole of it.

Nothing here went near the token, NVS, the frame log or the one-send-per-command
rail, and the TLS rail is stronger than it was: the grep that forbids an insecure
setting is joined by one that forbids a plain-HTTP address outside `src/host/`,
and by a test that the host client refuses anything but a private address.
