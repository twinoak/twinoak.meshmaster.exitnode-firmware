## Deviations from the spec or the task

- **"against the fake" (acceptance criterion 2) could not be walked here.** The
  fake mesh that answers as stock repeater firmware does is task 08's
  deliverable; `JobRunner` needs a board (`millis`, the radio, MeshCore) and is
  not in `[env:native]`'s `build_src_filter`. The task's own *deliverable* text
  asks for what was done instead — "the native test for the status result covers
  both" — so the rule, the transaction arithmetic and the result bytes are held
  natively, through the real claim parser, and whether the second request is
  actually absent from the air is task 08's harness and the bench.
- **The task says `tasks/run-all.ps1` should be given "the branch delete after a
  merge that meshmaster.dk's copy has". It has no such thing.** Both drivers were
  read: meshmaster.dk's `tasks/run-all.ps1` at `master` has no branch delete
  either, and in both repositories the delete lives in `tasks/RUNBOOK.md` §4
  (`gh pr merge --merge --delete-branch`) — which this repository already had
  when phase 1 left five branches behind, so the instruction that exists is not
  the one that failed. The intent ("so the next phase does not leave them") is
  what was implemented, in the place that actually goes wrong: the driver asks
  again *after* the session, which is the case of a session cut off between the
  merge and the delete.
- **No disagreement found between the task file and today's meshmaster.dk
  `master`** on the version flag.
  `StatusPayload.ReadsVersion(class, version) => class == Acl && (version ?? true)`,
  and the fixtures' README spells out that absent means *read it* and that an
  implementation ignoring the field is correct and merely spends one transaction
  more per read. The firmware now matches the .NET `StatusHandler` line for line.

## Decisions taken without asking

- **`origin/master` was one commit behind local `master`** (`1c8e73d`, Thomas's
  own, adding the phase-1.1 task files) where the runbook assumes master is up to
  date. It was pushed as a fast-forward before branching, so that this PR's diff
  is this task's work and nothing else. Nothing was rewritten.
- **Where the flag lives.** `ClaimedJob.statusVersion` (default `true`, so a
  claim that says nothing behaves as every claim did before) plus one free
  function `readsFirmwareVersion(job)`, rather than a nullable pair. The server
  keeps the rule in one static method for exactly the reason its comment gives —
  three places must not spell it three ways — and a bool with a `true` default
  says "absent is read it" in the type itself.
- **The type bound is in the rule.** `readsFirmwareVersion()` answers `false` for
  any type but `status`, so a later handler cannot inherit the flag by accident;
  the payload is read for a `status` job and no other in the first place.
- **`AgentConfig.json` arrived with the sync**, which closes the upstream half of
  the review's last open box ("`AgentConfig` has no contract fixture (01) —
  meshmaster.dk's side"). `test_config_reply` now parses that file beside the
  shape it already checked, and the file header's "there is no fixture for it" is
  gone. Ten lines, and the box is true on both sides.
- **The inline observation expectation was not simply deleted.** The fixture's
  sample is two decimals and north-east of Greenwich; the old inline test also
  carried six decimals and a western longitude, which is a real advert and the
  only exercise `formatE6`'s negative branch had. That case stays as
  `Observations.APositionIsThePlainDecimalOfTheAdvertsMicrodegrees` — a `find` on
  two fields, not a second copy of the whole body.
- **The branch delete refuses more than it deletes.** Ancestry is checked against
  `refs/remotes/origin/master` for the remote ref and the local one both, the
  branch name is built from the task row (`task/p<Phase>-<NN>-<name>`), the sync
  phase returns early, and a failure to delete is a log line and not a stopped
  run. A stale branch is untidy; a deleted unmerged one is lost work.
- **`docs/console.md` says what moved.** One paragraph beside the job log: an
  `acl` status read is 2 transactions the first time after a grant and after each
  day's refresh and 1 the rest of the time, nothing is logged when the request is
  skipped because nothing was sent, and a payload that says nothing at all — an
  older server — is two every time, as before.

## Not verified here (and why)

A session cannot flash a board or hear a radio. What this task adds to the bench
walk of `docs/console.md` is small and precise:

1. **An `acl`-class status read costs one transaction, not two, when the claim
   says so.** Walk step 8 (*Read now*) and then step 11 (the association's
   verify) against a repeater whose version the server already has: `jobs` must
   show that status job as **`ok after 1 transaction(s)`** and the job's log must
   have **no `owner info (firmware)` line** — nothing is logged, because nothing
   was sent. The first read after a grant, and the first of each day, must still
   be **2** with that line present and `firmware` in the result on the repeater's
   page. This needs **meshmaster.dk released first**: production is the phase-3
   build, which predates task p4.3-68 and sends no `version` field at all —
   against which every read is two transactions, correctly, and this part of the
   walk proves nothing.
2. **The day's arithmetic.** meshmaster.dk's task 68 states 167 transactions a
   day for one repeater at the defaults where it was 216. A night of probes with
   the association `active` (step 13) is where the board's own `jobs` count can
   be held against the server's Monitoring tab: 48 status reads at two
   transactions before, 48 at one plus a single second request after.
3. **The branch delete has not been seen to fire.** It is exercised the next time
   `tasks/run-all.ps1` runs a phase — task 08 is the first — and the log line to
   look for is `deleted origin/task/p1.1-08-the-host-harness (merged)`. The
   refusal paths were reasoned about and the script parses clean
   (`[Parser]::ParseFile`), but no run has gone through them.
4. Everything else on the phase-1 bench list is untouched by this task:
   `tasks/phase-1/FOLLOWUPS.md`'s first open item is still the whole of it.

Nothing here went near TLS, the token, NVS, the frame log or the
one-send-per-command rail; the greps and tests that hold those
(`test_tls_policy`, `test_credentials`) ran green with the rest.
