# p1.2-10 — The small ones

Three boxes from the first day on the air, and nothing else.

**The backoff no longer outlives the outage.** A 502, 503 or 504 that carries
`Retry-After` is now believed to the second, exactly as the 429 always was, and
once the board's own link is proven — WiFi associated *and* a clock that came off
the network — the doubling stops at **two minutes** instead of ten. The five
failed calls of 3 October would have been `30, 60, 120, 120, 120` rather than
`30, 60, 120, 240, 480`, and with a `Retry-After` on them they would have been
the server's own number each time.

**`neighbours` runs at a guest login.** `typeAllowsClass` puts it beside `status`
and `telemetry`, which is the rule the pinned firmware actually has: at
`d9296435`, `REQ_TYPE_GET_ACCESS_LIST` is guarded by `sender->isAdmin()` and
`REQ_TYPE_GET_NEIGHBOURS` by nothing at all.

**The README and the release notes say which image erases the settings.** The
merged image is the first flash and it takes NVS with it; the application image
at `0x10000` is the upgrade and keeps it. Task 11 makes the first half of that
sentence untrue in the good direction.

## Acceptance checklist

- [x] **A 503 with `Retry-After: 90` holds for 90 s and does not double; a 503 without one backs off, and with WiFi connected and SNTP answered the wait never exceeds two minutes; without a proven link it may reach ten.**

  which `AgentClient::Call::retryAfterS` already parsed — and returns
  `WaitRetryAfter` for the statuses of the new `saysWhenToComeBack()` (429, 502,
  503, 504) when it is non-zero. `AgentLoop::noteFailure` then takes the wait
  from `retryAfterMs()` and leaves `backoffMs_` untouched, so nothing doubles;
  the log line is `server: http 503; the wait is Retry-After's 90 s`. Without a
  header the same statuses are `BackOff` as before. The ceiling is
  `maxBackoffMs(linkProven)` — `kMaxBackoffWhenLinkUpMs` (120 000) against
  `kMaxBackoffMs` (600 000) — and `AgentLoop::linkProven()` is the picker:
  `wifi_->connected()` and `AgentClock::source()` being `Sntp` or `Server`.

## Deviations from the spec or the task

- **The policy was not untested.** The task says "`test_server_policy` (the
  policy is a pure function and has had none)"; it had five cases in
  `test/test_observations`, where task 02 left them. The new suite is what the
  task asks for and those five moved into it rather than being written twice,
  with `test_observations`' header saying where they went.
  `test_buffers`' `ServerPolicysOwnBackoffIsThatSequence` moved too, as
  `TheBackoffIsTheSharedSequenceAtTheServersNumbers`, and now holds both
  ceilings against `src/Backoff.h`'s three-argument form.
- **`nextBackoffMs(previousMs)` is gone, replaced by
  `nextBackoffMs(previousMs, bool linkProven)`.** The task says "`AgentLoop::noteFailure`
  picks the cap", and it does — but a second overload taking a `uint32_t` cap
  would sit beside `src/Backoff.h`'s `nextBackoffMs(previous, first, max)` and
  mean something different in the same position, which is a trap worth avoiding.
  The ceilings are named (`maxBackoffMs(bool)`) and `kMaxBackoffMs` still means
  what it meant.
- **The reboot guard needed the hour and a half writing down.** Task 06's
  twelve consecutive unanswered calls *was* about an hour and a half because the
  backoff doubled to ten minutes. At the new ceiling twelve of them is about
  twenty-one minutes — and twenty-one minutes of meshmaster.dk being away is a
  long deploy, not a wedged TLS stack, so the lower cap alone would have made
  the board restart itself through outages it used to ride out and throw away
  the ring and the buffered results, which are exactly what a server outage
  fills. `kRebootAfterFailingMs` (90 min) is now a condition beside
  `kRebootAfterFailures`, both must hold, and task 06's sentence is true of
  either backoff. `errors` prints how far along both are, and the RTC reason
  carries the minutes (`12 server calls unanswered in 94 min, wifi up`).
  Nothing else about the guard moved: the WiFi-up requirement, the counter and
  the number twelve are task 06's.
- **The spec is silent on `Retry-After` for a 5xx, and the .NET agent has no
  backoff at all.** Read at today's `master` (`828632e`): `spec/API.md` names
  `Retry-After` only on the 429 and on a 409 `idempotency-in-progress`, and
  `spec/EXIT-NODES.md` §6 says nothing about retries; `MeshMaster.Agent`'s
  `Uplink.cs` records a `ServerAnswer(Reachable, Status, Value, Problem)` and
  reads no header, and `AgentService.cs` contains no backoff, no retry and no
  mention of either. So this is the board's own policy, as `ServerPolicy.h` has
  always said in its header, and there is nothing in the other repository to
  disagree with. Worth the reviewer's eye for meshmaster.dk: if the server's
  deploy does **not** put a `Retry-After` on its 503s, the first half of this
  task does nothing and only the lower ceiling helps — see *Not verified here*.
- **Nothing else.** `spec/EXIT-NODES.md` §7's table reads
  `neighbours | **guest / acl / admin** | 1 per page of 9` at today's `master`,
  with the sentence the task quotes, so the firmware and the spec now agree. §10
  is the server's own `online` / `quiet` / `offline` and is untouched: what this
  task changes is how soon the board calls, not what the page derives from it.

## Decisions taken without asking

- **"SNTP has answered" is read as a clock whose source is `Sntp` *or*
  `Server`.** `AgentClock::hasTime()` was the obvious predicate and is the wrong
  one: it is true for `Source::Rtc`, a plausible time the RTC held across a
  software reset, which proves nothing about this board's network. `Sntp` and
  `Server` both mean a packet of ours left the board and something answered it,
  which is the whole content of "the link is proven"; `Server` is the stronger
  of the two and costs one comparison.
- **A believed 503 is not a consecutive failure.** "As the 429 path does" is the
  task's wording and it is taken at its word: a server that answered and named a
  time has not gone unanswered, so `consecutiveFailures` does not move, the
  reboot guard does not count it, and the OLED's second line can read
  `Online: yes` through a short deploy. `httpFailures` *does* move, so the call
  is not lost to the heartbeat's counters and `errors` shows it. The alternative
  — counting it — would have made twelve believed 503s a reboot trigger, which
  is the thing the paragraph above exists to prevent.
- **`saysWhenToComeBack` is four statuses and not every 5xx.** 502, 503 and 504
  are what a deploy and the proxy in front of it answer and they carry the
  header when the server knows the duration; a 500 is a bug, and a `Retry-After`
  on one would be a number nobody chose. The 429 is in the list so that the one
  predicate is the whole rule.
- **The notes print no `esptool` line for the application image.** The task asks
  for two sentences beside the two files; the upgrade's command is README's
  *Flashing it*, which already had it, and the release notes name the offset
  (`0x10000`) in the sentence. A second command block would have been the
  task's to ask for.
- **The `MANIFEST.txt` commit bump is kept.** No fixture byte changed, so the
  diff is one line — the meshmaster.dk commit the copy is recorded against,
  moved from `b04799f` to today's `828632e`. That line is the evidence that the
  check this task asks for was made.

## Not verified here (and why)

A session cannot make a server answer 503 and cannot put a repeater on the air.

1. **A real deploy's 503s.** The next release of meshmaster.dk is the test, with
   `pio device monitor -b 115200` open on the board. Two things to read:
   - if the server's 503 carries `Retry-After`, the log says
     `server: http 503; the wait is Retry-After's N s` and the board is back
     within N seconds of the deploy ending;
   - if it does **not**, the log says `server: next attempt in 88 s (the 120 s
     step, jittered)` and never a step above `120 s` — the board is back within
     two and a half minutes whatever the outage's length.
   The exit node's page should stay `online` through either (3× the poll
   interval is six minutes at the idle 120 s). **If the 503 carries no header,
   that is meshmaster.dk's to add** and it is one line in the deploy's proxy or
   in the app's shutdown path; the firmware is right either way, so this is a
   note for the other repository and not a bug here.
2. **The lower ceiling against an unproven link.** Set `wifi.ssid` to a network
   that associates and goes nowhere (a phone hotspot with mobile data off is the
   easy one), and watch the steps climb past 120 s to `600 s`: `status` says
   `time no time` or `from rtc`, which is what makes the difference. Then let
   SNTP answer and watch the next failure drop to `120 s`.
3. **The reboot guard.** `errors` now prints
   `httpFailures N (M in a row now, failing for K min; it restarts itself at 12
   in a row and 90 min)`. Pull the router's uplink and leave it: the board should
   *not* restart at twelve failures (about twenty-one minutes in) and should
   restart somewhere past ninety, with `reboots` showing
   `N server calls unanswered in 9x min, wifi up`. This is the slow one — an
   afternoon with the uplink out — and the thing that matters is the first half:
   no restart at twenty minutes.
4. **`neighbours` at a guest login.** A repeater this board holds **no** ACL
   entry on, associated through the guest door, with the server's neighbour-list
   job run against it: the job should come back `ok` with the list rather than
   `unsupported`, and `jobs` should count one login and one request per page of
   nine. A repeater where this board *does* hold a grant must still refuse the
   guest class with the demotion sentence — the server will not send it, but the
   board's own refusal is what the test holds and the bench can confirm it with
   a `cli` of `setperm` beforehand if it is worth the trouble.
5. **The merged image's erasure, deliberately this time.** The finding is
   already proven on the bench (4 October), so this is only the documentation
   being right: flash `-merged.bin` to a provisioned board without *erase first*
   and confirm the console comes up with `wifi off, wifi.ssid is unset` and
   `server not configured`, and that `status` shows the **same identity** as
   before. Then flash the application image at `0x10000` over it and confirm the
   settings survive.
