# p1.2-09 — The display

The OLED is lit at boot and **stays lit**. `display.timeout` is the number of
seconds without a button press after which it goes dark, and its default is
`0`, which never does; a click on PRG toggles it. The four lines are new, and
they are a pure function of a plain struct — `src/ui/DisplayLines.h`, with
`main.cpp`'s `fillOled` as the one place that gathers it — so the wording is
under native test and the only parts of the display that need a board are the
toggle and the timer:

```
ID: 46F6     12:03:14
WiFi: yes Online: yes
Heartbeat: 12:03:14
Idle, last 12:34:56
```

The reasons the board is *not* working, which line three carried since task 06,
have moved to line four with the rest of "what it is doing": line two's *no*
says something is wrong, line four says what. The four `oledLine` methods of
`WifiLink`, `AgentClock`, `AgentLoop` and `AgentClient` are gone.

## Acceptance checklist

- [x] **`display.timeout` is in `settings` with default `0`; `set display.timeout 300` takes effect without a reboot; `Oled::loop` never turns the display off at `0`.**
  `src/settings/Keys.cpp` has it as the twelfth key — `ValueKind::Int`, fallback
  `"0"`, range `0..86400`, NVS name `disp_timeout` (12 of the 15 characters NVS
  allows) — and its help line names `300` as what the firmware used to do.
  `main.cpp`'s `applyDisplaySettings()` reads it and calls `Oled::setTimeout`,
  called from `setup()` before the first frame and from `onSettingChanged` for
  any `display.*` key and from `onErased`, the way the radio and log settings
  are re-applied; `setTimeout` restarts the countdown when the panel is lit, so
  the new value is in force at once. `Oled::loop` guards the turn-off with
  `timeoutMs_ != 0`, so at `0` there is no `turnOff()` path at all. The key is
  in `test/test_console_parser`'s two tables (`set display.timeout 300` parses,
  `get display.timeout` prints `unset (0)`), in README's `get` block — which
  that test replays line for line — and in `docs/console.md`'s key table.
- [x] **A click toggles the display; nothing else about the button changed.**
  `Oled::loop` now compares `button_->check()` with `BUTTON_EVENT_CLICK`
  exactly (it was `!= BUTTON_EVENT_NONE`) and turns the panel off when it is on,
  on when it is off, restarting the timeout in the second case. `LONG_PRESS`,
  `DOUBLE_CLICK` and `TRIPLE_CLICK` fall through unhandled, as before. The
  button object, its pin and its construction are MeshCore's `user_btn`
  (`variants/heltec_v3/target.cpp`: `MomentaryButton(PIN_USER_BTN, 1000, true)`)
  and are untouched. `Oled.h`'s header says in one sentence that GPIO 0 held
  through a reset is the ESP32-S3's ROM bootloader, which a click in this loop
  cannot cause.
- [x] **`renderLines` produces exactly the strings above for each state, every line ≤ 21 characters, under `pio test -e native`.**
  `test/test_display_lines`, 14 cases, all `[PASSED]`: line one's

## Deviations from the spec or the task

- **The geometry constants moved, and `Oled::kLines`/`kCols` alias them.** The
  task writes the signature as
  `renderLines(const DisplayState&, char lines[Oled::kLines][Oled::kCols])`,
  but `Oled.h` includes `mesh/MeshCoreHeaders.h` for `DisplayDriver` and
  `MomentaryButton`, so a header that names `Oled::kLines` cannot be compiled on
  a host — and "as a pure function… with no dependency on the board" is the
  point of the deliverable. `kDisplayLines` (4) and `kDisplayCols` (22) are
  therefore declared in `DisplayLines.h`, and `Oled.h` includes it and defines
  `kLines = kDisplayLines`, `kCols = kDisplayCols`. The parameter's *type* is
  what the task asked for, `Oled::kLines` and `Oled::kCols` still exist and
  still mean 4 and 22, and `Oled::Fill` is unchanged, so `main.cpp`'s
  `fillOled` still has the task's signature.
- **Nothing else.** `docs/ops/agent.md` on meshmaster.dk (read at today's
  `master`) does not mention a display at all — the .NET agent is a service
  with a journal — so there was nothing there to agree or disagree with.
  `spec/EXIT-NODES.md` §10's `online` / `quiet` / `offline` are the *server's*
  derivation from heartbeat age and are untouched by this task; line two's
  *Online* is deliberately a different and simpler thing, "the last call to
  MeshMaster was answered", as the task defines it, and the README and
  `docs/console.md` say so in those words so that nobody reads the board's word
  as the page's.

## Decisions taken without asking

- **`display.timeout`'s range is `0..86400`.** The task fixes the units
  (seconds), the meaning of `0` and the default; it does not give a ceiling. A
  day is the largest value that is still a *timeout* rather than a clumsy way of
  writing `0`, and `Int` needs some bound.
- **The countdown on line four is clamped to `999s`.** `no server: retry ` is 17
  of the font's 21 characters, so four are left. The backoff's own ceiling is
  600 s and fits, but a 429's `Retry-After` is the server's to choose and could
  be any number of seconds; rather than let the line grow past the panel, a
  longer wait reads `no server: retry 999s`. A test covers it.
- **`Idle, last …` uses the newest remembered job's time whatever its
  outcome.** `JobRunner::Record` keeps the outcome, and line four could have
  said it (`Idle, last ok 12:34:56` fits). The task's wording is
  `Idle, last 12:34:56` exactly, so that is what it says; `jobs` on the console
  is where an outcome is read.
- **Line four says nothing special when the server is simply unconfigured.** The
  task enumerates three faults and `no server set` is not one of them. On a
  fresh board WiFi is off too, so the line reads `no wifi`, which is true and is
  the thing to fix first; `docs/field.md` §4 says so in a sentence. Adding a
  fourth fault would be the task's to ask for.
- **An open job wins over a fault on line four.** "Nothing runs in those
  states", so the two should not meet; the order is written down and tested
  anyway, because a job on the air is what a person at the window is looking
  for.
- **`status`'s `log` line still says only `oled on` / `oled off`.** Printing the
  timeout there would change a line the README's console session replays for no
  gain: `get display.timeout` is the question's own answer.

## New libraries (with the one-line justification)

None. `src/ui/DisplayLines.cpp` is added to `[env:native]`'s

## Not verified here (and why)

A session cannot light a panel or press a button: `Oled` needs MeshCore's
`DisplayDriver` and `MomentaryButton` and is not in `[env:native]`. With a V3
on USB and `pio device monitor -b 115200`:

1. **It stays on.** Flash, and leave the board alone for ten minutes. The panel
   is still lit, and the clock on line one is still ticking. (`status` says
   `log … oled on`.)
2. **Click off, click on.** One short press of PRG: the panel goes dark —
   `status` says `oled off` — and the board keeps working (`server` shows the
   heartbeats still going). One more short press: it comes back, with a fresh
   frame rather than the old one.
3. **The timeout.** `set display.timeout 10`, then don't touch the button. The
   panel goes dark about ten seconds later with no reboot in between. Click it
   on: lit, and dark again ten seconds after that click. `set display.timeout 0`
   and click it on: it stays.
4. **The four lines read right on the glass.** Line one's clock against the
   right edge and the four characters matching the prefix the exit node's page
   shows; line two `WiFi: yes Online: yes` filling the width exactly, no
   character clipped at either end; line three moving every poll interval. Then
   each of the faults: pull the router's uplink → `no server: retry Ns` counting
   down; pull the WiFi (or `set wifi.ssid` to something that is not there) →
   `no wifi`; `set meshmaster.token mma_wrongwrongwrong` → `token
   revoked/wrong`, and it stays until the real token goes back.
5. **A job on line four.** Run any job from the server against a test repeater
   and watch line four read `Job <id> <type>` for the length of it and then
   `Idle, last HH:MM:SS`. A `config.read` is the long one and the best to watch.
6. **Ghosting.** The Watch list's own item: an SSD1306 lit for a month may
   retain the static parts of these lines. If it shows, the fix is a pixel
   shift, not a timeout — the display is meant to be on now.

Not a bench check but worth saying: the four lines are redrawn once a second
whether anything changed or not, as before, and that is unchanged power and
unchanged I²C traffic from `v0.1.1` — what changed is that `turnOff()` is not
called.
