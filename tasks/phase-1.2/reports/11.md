# p1.2-11 — The partition table

NVS is above the application on both boards. A merged image — bootloader, partition
table and application as one file from `0x0` — ends where the application ends, and
from this table on it ends 1.9 MB (V3) and 5.2 MB (V4) before NVS begins, so the
settings it used to erase are out of its reach. Nothing else moved: `spiffs`, where
the identity lives, `app0`, `otadata` and `coredump` are byte-identical to the
framework's defaults in offset and size, `app1` is gone (this firmware does no OTA),
and the rest of its region and the gap at `0x9000` are left unallocated on purpose.
`tools/check-partitions.py` holds all of that against the installed framework and
the real merged image in CI, on every build of every board. No source file changed:
`SettingsStore` opens NVS by label, and the framework's own boot path re-initialises
a blank or foreign region before `setup()` runs — cited below from the installed
core and from ESP-IDF at the version it bundles.

And the merged images themselves, read byte by byte (`out/firmware-11-*-merged.bin`):
bootloader magic `0xE9` at `0x0`, partition-table magic `AA50` at `0x8000`,
`boot_app0` (`01 00 00 00`) at `0xE000`, application magic `0xE9` at `0x10000` — and
**every byte of `0x9000`–`0xDFFF` is `0xFF`** in both, which is the finding of
4 October demonstrated on the artefact: with the default table that span *was* NVS.
The header's fourth byte is `0x3F` (V3) and `0x4F` (V4): `esptool` wrote the
`--flash_size` it merged for into the image, `8MB` and `16MB`, which is where the
check reads the board's flash size from.

- [x] **The framework's `Preferences.begin` recovery on a blank or foreign NVS region is confirmed from its source and cited, or `SettingsStore::begin` does the erase-and-retry itself with a test of the decision.**
  Confirmed from source, and **not where the task expected it** — see *Deviations*.
  The chain, every file read on disk or at the IDF tag the core bundles:
  1. `Preferences::begin(name, readOnly, partition_label)` —
     `libraries/Preferences/src/Preferences.cpp:33–55` of the installed core — does
     **no** recovery: with `partition_label == NULL` (our call, `Store.cpp:13`) it is
     one `nvs_open(name, …)` and `return false` on error. The erase-and-retry lives in
     `initArduino()`, `cores/esp32/esp32-hal-misc.c:249–265`, which runs before
     `setup()`: `nvs_flash_init()`, and on `ESP_ERR_NVS_NO_FREE_PAGES` or
     `ESP_ERR_NVS_NEW_VERSION_FOUND` it finds the partition by
     `ESP_PARTITION_SUBTYPE_DATA_NVS`, `esp_partition_erase_range(partition, 0,
     partition->size)` and `nvs_flash_init()` again. So the two errors the task names
     are handled, for every sketch, by the core itself.
  2. **A blank region** (all `0xFF`, which is what the region at `app1`'s old offset
     is on a board that never ran OTA — and no firmware this board has run does): ESP-IDF
     v4.4.7 `components/nvs_flash/src/nvs_page.cpp:41–62`, `Page::load` reads the
     header, sees `PageState::UNINITIALIZED`, reads the whole sector to confirm it is
     empty; `nvs_pagemanager.cpp:24–47`, every such page fails `getSeqNumber`
     (`nvs_page.cpp:992–999`) and goes to the free list, `mPageList` is empty, and
     `activatePage()` (`:195–211`) makes the first one `ACTIVE`. `nvs_flash_init`
     returns `ESP_OK` without any erase; `Preferences::begin` opens the namespace;
     `isKey` says nothing is set. No error, no log line.
  3. **A foreign region** (whatever a previous firmware left at that offset — the
     repeater image Thomas's V3 came from is the realistic case): a page whose header
     is not all-`0xFF` and whose CRC does not match is `CORRUPT` (`nvs_page.cpp:64–65`
     and the `default:` arm at `:86–88`; `mState` starts as `INVALID`,
     `nvs_page.hpp:212`); a page that starts with `0xFF` but is not empty is `CORRUPT`
     too (`:57–60`). `CORRUPT` pages go to the free list like blank ones, and
     `activatePage()` **erases a `CORRUPT` page before using it**
     (`nvs_pagemanager.cpp:201–206`, `Page::erase()` at `nvs_page.cpp:1020`). Again
     `ESP_OK` from `nvs_flash_init`, and the region is reformatted sector by sector as
     it is used. The 1-in-2³² case of foreign bytes whose header CRC happens to match
     is what step 1's `NEW_VERSION_FOUND` / `NO_FREE_PAGES` arms catch.
  4. **The label.** `nvs_flash_init()` is `nvs_flash_init_partition(NVS_DEFAULT_PART_NAME)`
     (`nvs_api.cpp:132–167`, the `#else` of `CONFIG_NVS_ENCRYPTION`, which the bundled
     `sdkconfig` does not set), and `lookup_nvs_partition`
     (`nvs_partition_lookup.cpp:12–15`) is `esp_partition_find_first(DATA, NVS, label)`
     with `NVS_DEFAULT_PART_NAME` = `"nvs"` (`tools/sdk/esp32s3/include/nvs_flash/
     include/nvs.h:58`). The label is the lookup key and the offset is the table's,
     which is why `src/settings/Store.cpp` needed no change and got none.

## Deviations from the spec or the task

- **The recovery is not `Preferences.begin`'s.** The task says "`Preferences.begin`
  erases and re-inits on `ESP_ERR_NVS_NO_FREE_PAGES` and `ESP_ERR_NVS_NEW_VERSION_FOUND`
  — verify this in the framework source and say so". Verified, and it is `initArduino()`
  that does it (`esp32-hal-misc.c:249–265`), before `setup()`; `Preferences::begin` is
  a bare `nvs_open`. The outcome the task wants — a blank or foreign region is usable
  without `SettingsStore` doing anything — holds, and for the two cases that actually
  arise (blank, foreign) it holds one level lower still, in NVS's own page loader, with
  no error ever raised. Cited above with line numbers; nothing was added to
  `SettingsStore::begin`, so there is no decision of ours to test.
- **"Three fixture tables, one good and two wrong" is two wrong fixtures and the two
  shipped tables.** A good fixture that is a copy of `boards/partitions/meshmaster_8MB.csv`
  is a file that drifts from the one it copies the first time either is edited, and a
  self-test that then passes on the copy proves nothing about the table that ships.
  The self-test runs the real 8 MB and 16 MB tables as its good cases and
  `tests/fixtures/partitions/` holds only the two that must be refused, which its
  README says.
- **The check asserts a little more than the task lists**: `nvs` keeps the default's
  size and its `data/nvs` type (the deliverable says "with its default size"), no two
  partitions overlap, the merged image is at least long enough to contain an
  application (a zero-length file would otherwise pass "below nvs"), and the embedded
  defaults match the installed package's. Each is one line and each is a way the table
  could be wrong without the four named assertions noticing.
- **No meshmaster.dk spec section is linked by this task** — its spec list is this
  repository's own files — so there is nothing at `fbf4625` to disagree with today's
  `master`. The one thing read there is task 96 (`tasks/phase-4.7/96-a-new-token.md`,
  at `master`, 5 October): the button is *Generate a new token*, on the exit node's
  page, behind the re-authentication gate, old token dead the moment the new one is
  written — which is what README, `field.md` and the notes say.

## Decisions taken without asking

- **The flash size the check uses comes from the merged image's header**, not from the
  board definition. `esptool merge_bin --flash_size 8MB` (what `tools/pio/merge_bin.py`
  passes, from the board's `upload.flash_size`) writes that size into the bootloader
  header's fourth byte (`0x3F` and `0x4F` in the two images above, esptool's nibble
  3 = 8 MB, 4 = 16 MB), so the size checked is the size the image was merged for,
  read from the artefact rather than from a second parse of a board JSON that lives
  in the platform package for the V3 and in `boards/` for the V4. `--flash-size`
  overrides it, and is required when there is no merged image.
- **The csv is found through `platformio.ini`**, by reading `board_build.partitions`
  from `[env:<name>]` (following `extends` if it is not there), so that CI checks the
  table the build actually used and not a file name typed twice. `--csv` takes a file
  directly for the fixtures.
- **The self-test is Python and runs in CI's build job**, before the real check, rather
  than being a gtest under `test/`: the thing under test is a Python script, the native
  suite is C++, and shelling out to Python from gtest would make `pio test -e native`
  depend on something it does not otherwise need. It also ran in the container beside
  the native suite, so the no-framework path is exercised on Linux and the
  with-framework path on Windows and in CI.
- **The two wrong tables live in `tests/fixtures/partitions/`**, beside the contract
  and companion fixtures, with their own README saying they are this repository's and
  not meshmaster.dk's. `tools/sync-fixtures.ps1` is scoped to its two sets by name and
  does not see the new directory; `test_contract_fixtures` iterates its own directory
  only.
- **The tables keep `otadata` and `boot_app0`.** The task says `otadata` keeps its
  offset, and the merge script takes `FLASH_EXTRA_IMAGES` from PlatformIO, which always
  includes `boot_app0.bin` at `0xE000`. With one `ota_0` and no `ota_1` the bootloader's
  selection is `ota_seq 1 → index 0 → app0`; dropping `otadata` would have been a
  second change for no gain and a bootloader behaviour to verify on a bench.
- **"`v0.1.1` or earlier" is how the documents name the boards the exception
  applies to.** `v0.1.0` and `v0.1.1` are the two tags on this repository and both
  carry the default table; the next tag is the first with this one. Naming the old
  releases rather than the new one is what keeps the one text true after the next
  release and the one after that.
- **The table csvs carry their reasoning as comments** (why NVS moved, why `app1` is
  gone, why the rest of its region is unallocated, what must not move), so that the
  next person to open one with an editor reads the rails before the rows.
- **`ci.yml` only.** The task names `ci.yml`'s build job; `release.yml` builds the
  same commit after `ci-green` has waited for exactly that run, so the published
  image's table has been checked on that commit before it is built. Not added there a
  second time.
- **The images from task 10's checklist are the same bytes.** This task changed no
  source, and the build confirms it; nothing was done to make them differ.

## Not verified here (and why)

A session cannot flash a board, and a partition table is proved only by one. This is
the walk, in the order that costs least if something is wrong, with the identity's
first eight hex characters (`status`, or the OLED's `ID:` line's four) written down
before each step:

1. **The application image over the old table — nothing changes.** On the provisioned
   `v0.1.1` V3, `esptool.py --chip esp32s3 --port COM5 --baud 921600 write_flash
   0x10000 out/firmware-11-heltec_v3.bin` (or `pio run -e heltec_v3 -t upload`). The
   board must come back with its WiFi, URL and token, `status` the same identity, and
   `server` a heartbeat: the ESP32 reads the table from `0x8000` and the application
   image does not touch it, so NVS is still at `0x9000` and still full. This is the
   proof that an upgrade is still an upgrade.
2. **The first merged flash — the one exception, once.** `write_flash 0x0
   out/firmware-11-heltec_v3-merged.bin` *without* an erase. Expected on the console:
   the banner, `identity: <the same 64 hex>`, `wifi off, wifi.ssid is unset`, `server
   not configured`, and **no** `Failed to initialize NVS` or `nvs_open failed` line
   (those are the core's `log_e`, and they would mean the chain cited above did not
   hold). Then steps 4–7 of `docs/field.md` §2 with a token from *Generate a new
   token* on the exit node's page; the page must show the same companion key and the
   node back `online` **without** *companion changed*, and a job through a repeater
   whose ACL holds the board must still come back `ok`. If `status` shows a different
   identity at any point, stop: that is the one failure this task exists to prevent,
   and the table is wrong.
3. **The second merged flash — the settings now survive.** The same `write_flash 0x0`
   again, over the board provisioned in step 2. Expected: it comes back with its WiFi,
   URL and token intact and heartbeats within a poll interval, because NVS at
   `0x340000` is beyond the image's `0x15AF70` bytes. This is the whole point, and it
   is the one thing nothing but a board can show.
4. **`pio run -t upload` and the application image over the new table**, once each,
   keep the settings (same reasoning as step 1, now with NVS where this table puts it).
5. **`erase confirm` still keeps the identity** under the new table (it is `prefs_.clear()`
   on the namespace, not a partition erase, and SPIFFS is not touched — but the bench
   is where that sentence is checked after a table change).
6. **The V4**, steps 2 and 3 only, when there is one on the bench: same expectations,
   `0x650000` for `nvs` and `0x15A580` for the image.
7. **The region at `app1`'s old offset on Thomas's V3** was most likely blank, which is
   the easy case for the NVS loader. A board that came from a firmware that *did*
   write there (an OTA'd repeater image) is the foreign case, and the first merged
   flash of one such board is worth watching with `pio device monitor` open: the
   expectation is identical, and the only visible difference would be a one-time
   `log_e` from the core if the CRC coincidence of step 1 ever happened.

Still open from task 10, unchanged by this one: whether meshcore.io's web flasher can
take the application image at `0x10000`. With this table the question matters less
— the merged image no longer costs the settings after its first flash — but the
first flash of every board provisioned under `v0.1.1` is still the re-provisioning
above, whichever tool writes it.
