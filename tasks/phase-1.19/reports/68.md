# p1.19-68 — The observers stand down for a fetch

On 20 November Aarhus C refused 0.7.5 eight seconds into its fetch, with three ranges that
stopped short and nothing anywhere saying why. Three things come of that. **No observer slot is
connected while a release is fetched** — Thomas, 21 November: *it would be good for the exit nodes
to stop all observers before trying to update.* **A range that stops short says why**: what the
HTTP client returned, the TLS layer's own error, and the largest free block at that moment.
**And a failure is a request that brought nothing**: a range that brought bytes that were kept is
asked on from where it stopped and costs no try, and three requests in a row that bring nothing
end a fetch.

**What a person sees.** `get mqtt.status` while a fetch runs:

```
slot 1 meshview (wss://mqtt.meshview.dk:443/mqtt): standing down since 12:03:11 for a release being fetched; … gave way 0 time(s); last error: standing down while a release is fetched
slot 2 meshmapper (wss://mqtt.meshmapper.net:443/mqtt): standing down since 12:03:11 for a release being fetched; … gave way 0 time(s); last error: standing down while a release is fetched
```

and a range that stops short, now with its reason:

```
[12:03:19] I fetch: range 131072-196607 stopped at 48208 of 65536 bytes: client -5, tls -0x7f00, block 47092, no memory; asking on from 179280 (179280 of 1515024 held)
[12:03:21] E update: fetch: range 196608-262143 brought nothing: client -5, tls -0x7f00, block 47092, no memory (3 failure(s), which is all this fetch gets)
```

The second of those is also the last line of the journal on the board's *Firmware* tab, which is
the point: the figures that were missing on 20 November are now readable without a cable.

## Deviations from the spec or the task

- **The spec here is this repository.** Nothing of meshmaster.dk's contract, fixtures or wire
  shapes is read or changed. One thing is worth the server's notice all the same: a slot's
  `state` in the heartbeat's `observer.slots[]` has an **eighth** value, `standing-down`.
  `AgentObserverSlot.json` types it as a string and no fixture enumerates the set, so nothing of
  the contract breaks — but meshmaster.dk's Observer card will show a word it has not seen before.
  `docs/observer.md` said *those seven words are a contract*; it now says eight and names the new
  one. Nothing was renamed. `CHANGELOG.md` gets no line: nothing of `lib/agent-core`'s
  interfaces, constants or fixtures moved.
- **The tests of the slots' own state machine are in `test/test_fetch`, not `test/test_observer`.**
  The task names `test/test_observer` for *the scripted clients*, and that suite has none: it holds
  the dialect, the topics, the token, the console's lines and two greps, and the scripted client and
  the clock a test moves are `test/test_connection`'s. A fetch standing the slots down is one thing
  across two files, so it is tested where the fetch is, with a cut-down copy of that fake client —
  and with the **real** `observer::Connections` and the **real** adapter, which is why
  `src/update/FetchObservers.h` is a portable header and not four lines in `src/main.cpp` beside
  the other board-only seams. `test/test_observer` is unchanged; `test/test_connection` is unchanged
  and still green.
- **The task's line numbers have drifted** in `src/main.cpp` (the ask's seam to the fetch is at
  L269–272, `update fetch` at L797, the loop's step at L1348) and in `AgentClient.cpp` (the
  streamed body is L245–270). Everything the task names was read where it now is.
- **`kFileTries` keeps its name and its value and changes its meaning**, from *three in all* to
  *three in a row*. `Fetch.h`'s comment beside it says so and why; the result keeps `failures` as
  every request that brought nothing over the whole fetch and adds `failuresInARow`, which is what
  the ending's sentence prints.

## Decisions taken without asking

- **The reason's words are short because an ask's journal note is 96 characters.** The first
  wording was *the client returned -5, tls -32512 (-0x7f00), largest free block 47092, for want of
  memory*; with the range in front of it and the count of failures behind it, `largest free block`
  fell off the one line meshmaster.dk shows. So the phrase is four short words — `client N`,
  `tls -0xNNNN`, `block N`, `no memory` — the refusal's sentence leads with the reason and the
  failure count trails it, and `docs/field.md` §9 has a row per word spelling each out. Raising
  `kMaxNoteLen` was the alternative and was not taken: it is used by `Trial.cpp`, `Ask.cpp` and
  `UpdateRecord::why`, so it is .bss on every board for one sentence, and the journal's real bound
  (`kJournalMaxCharacters`, which **is** the contract's) would then drop entries sooner.
- **A *fetched* ending keeps the slots down; every other ending opens them at once.** The task
  asks for both, and the order of `src/main.cpp`'s loop decides where the choice has to live:
  `observer.loop()` runs **before** `asked.step()`, so a fetch that opened the slots at a *fetched*
  ending would have one of them in a TLS handshake a pass before the switch threw it away. So
  `Fetcher::end` passes `ending == Ending::Fetched` to `Observers::standUp`, and on that the slots
  hold.
- **…with a way back after a minute, so that a board is never left without its observers.**
  `kFetchedStandDownMs` is 60 s. An ask switches and restarts within a pass or two, so it is never
  waited out in the ordinary way; it is there for the board whose switch was refused and for a
  bench that ran `update fetch` and did not apply it. Without it, such a board would need a reboot
  to have its observers again, and nothing would say why they were gone.
- **The bound on one file's requests is twice its ranges, plus the tries** (`kFileRequestsPerRange`
  = 2; 0.7.5 is 1 515 024 bytes, which is 24 ranges of 64 kB, so its bound is 51). Where it comes from: Risskov's fetch of
  20 November was sent 1.6 MB for a file of 1.5 MB — 24 requests for 23 ranges, 1.04 a range — so
  twice the ranges is about double the worst a fetch of ours has ever cost. The only fetch it ends
  is one whose ranges each bring a handful of bytes, which is the fetch that could otherwise go on
  for ever now that such a range costs no try.
- **What bounds the wait for the sessions to be gone, and how it is known they are.** `allDown()`
  is *no slot is `connected` and none is `connecting`*, and `standDownForFetch` reaches that state
  **synchronously**: it calls `Client::close()`, and the board's is
  `esp_mqtt_client_destroy`, which stops the client's task, joins it and frees its TLS context
  before it returns (`src/net/MqttClient.cpp:246`). So the first look is true and the fetch asks
  for the manifest in the same pass it started; `result().standDownMs` is **0** on the board.
  `kStandDownMs` is 5 000 ms and is there for an implementation that one day closes in the
  background; reaching it does **not** end the fetch — a release that can be had with one slot
  still up is better than no release at all — and the line says it was reached.
  `TheObserversStandDown.TheFirstRequestWaitsForTheSessionsToBeGone` and
  `SlotsThatWillNotGoDoNotHoldAFetchUpForEver` hold both halves.
- **A slot standing down keeps what was left of its backoff.** `standUpAfterFetch` puts a slot
  that still has `nextAttemptAt` in the future back into `backing-off` rather than straight to
  `waiting-for-wifi`, so a fetch cannot be used to skip a broker's own wait. *Their ordinary rule*
  is read as the rule they were under.
- **A `set mqtt*` during a fetch does not open what the fetch closed.** `configure()` enters
  `StandingDown` instead of `WaitingForLink` while `fetching_` is true; the new settings take
  effect when the fetch has ended, like everything else about the slots.
- **`get mqtt.status`'s word is `standing-down`** (the state) and *standing down since 12:03:11 for
  a release being fetched* (the line), with *up again in N s* added only while the minute above is
  running. `gave way` is untouched, and the slot's `last error` reads *standing down while a
  release is fetched*, which is not an error and is the one field a person looks at for *why*.

## Not verified here (and why)

A session cannot flash a board or hear a radio. Every line below is Thomas's at the bench, and
each has a command and what its answer should be.

- ⚠ **Aarhus C, with both observer slots set: *Update* on its Firmware tab.** This is the one that
  matters, because it is the board the pile is made from. While it fetches, `get mqtt.status`
  should show **both slots `standing down … for a release being fetched`**, `0 connected`, and
  `gave way 0 time(s)` unmoved on both. Afterwards the journal on the Firmware tab says how it
  ended. **If a range still stops short, its last line now names the reason** — `client N`,
  `tls -0xNNNN`, `block N`, and `no memory` where it was memory — and *that line is what to send*:
  it is the first measurement anybody has of why those ranges stopped.
- ⚠ **The next update of Aarhus C is still fetched by 0.7.4's rules.** The firmware that fetches is
  the one the board runs, not the one it is given, so this task's behaviour only applies from the
  release *after* the one this merges into. Press *Update* again as it is; if it refuses again,
  `set mqtt2.preset none` at the board for the update, or the plain `.bin` over USB once. From the
  release that carries this task on, a board stands its observers down by itself.
- ⚠ **The `stack` line of `status` after an update**, which will be the first reading with a fetch
  in it (task p1.18-67's own bench item, and this task makes the fetch's deepest moment different).
  `status`, and send the line.
- ⚠ **That the slots really come back on their own after a refused fetch.** `get mqtt.status`
  within a few seconds of a refusal: both slots `connecting` or `connected` again, `gave way`
  still 0. The host test holds the state machine; only a board holds `esp_mqtt_client_destroy`
  giving the heap back and a handshake succeeding on it.
- ⚠ **That no slot reopens between a *fetched* ending and the restart.** `get mqtt.status` is of no
  use here (the window is a pass of the loop); the log is — there should be no
  `observer: slot N …: connecting` line between `update: fetched …` and the restart banner.
- ⚠ **What `client N` and `tls -0xNNNN` actually are on a board whose range stops.** The host test
  scripts them; nothing but a board can say which numbers the ESP32's HTTP client and mbedtls
  really produce in that moment. The first real line is the measurement, and `docs/field.md` §9's
  table of what to do about each reason is written from `HTTPClient`'s own codes and mbedtls's
  header, not from a board.
- ⚠ **A V4.** No V4 in the fleet has run 0.7.4 or anything after it (pile 1.19's follow-ups), so
  the standing down has not been seen on one. The code is the same on both boards and the native
  tests run the V3's profile and the V4's; nothing here is board-specific.
