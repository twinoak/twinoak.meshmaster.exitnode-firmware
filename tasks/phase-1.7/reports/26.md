# p1.7-26 — The observer dialect

The exit node now speaks the observer firmware's dialect — every byte an observer sends to
meshview.dk and meshmapper.net, and the token it signs in with — as portable, host-tested code
under `src/observer/`, with **no network in it**: task 27 puts it on the air. The dialect was
read from `agessaman/MeshCore`, branch `observer-firmware`, at
**`d664d89df66bdacc1319900a2e2d152fa31b9dc9`** (24 October 2026, the head of that branch on the
day), and every field and rule names its file and line there; the two computed numbers (the
packet hash and the rebroadcast score) were read from MeshCore at this firmware's pin,
`d9296435`, and cited the same way.

The Danish observer guide of the pile's README, typed line for line on this console, now ends in
the two slots it means: `wifi.pwd` is `wifi.pass`, `timezone` and `bridge.source` are answered
with one line each instead of an `error:`, the sixteen `mqtt` keys exist with the observer
firmware's names and sizes, and `set mqtt1.preset meshview` is the guide's four `custom` lines
as one name. A configured observer formats every frame the radio hears into the packet message
the brokers take, and `status` counts them; nothing leaves the board yet.

Presets 940, Config 869, Topics 568, Frame 111); the key table grew for sixteen keys and seven

settings copies and its one message buffer (`kPacketMessageCap` 1 280) plus the 255-byte raw

## What was built

- **`src/observer/`**, the portable half, compiled by `[env:native]` beside the key table and
  the parser:
  - `Frame.{h,cpp}` — where a frame's header, transport codes, path and payload are, as
    `Packet::readFrom` and `Dispatcher::tryParsePacket` read them; nothing looks inside the
    payload.
  - `Dialect.{h,cpp}` — `formatPacket` and `formatStatus`, field for field and in the order
    the observer firmware fills its ArduinoJson document, written with the library's
    `JsonWriter` (identical bytes for every string the keys admit; the header says why);
    `formatTimestamp` (`%Y-%m-%dT%H:%M:%S.%06u+00:00`, UTC), `formatRadio`
    (`%.6f,%.1f,%d,%d` of two *floats* and two ints — 869.618 is `869.617981` there, as it is
    on an observer), `formatClientVersion` (`meshcore/<firmware_version>`), and `packetScore`,
    MeshCore's `packetScoreInt` in the source's own float/double steps.
  - `Token.{h,cpp}` — the JWT exactly: base64url header and claims, `publicKey` uppercased,
    `aud`, `iat`, `exp`, `owner` (uppercased), `client`, `email` each only when set, and the
    Ed25519 signature as **128 uppercase hex** (not base64url — the firmware's "MeshCore
    Decoder format", `JWTHelper.cpp:91-110`); `usernameFor` (`v1_<HEX>`); the lifetime with the
    per-slot stagger (86 400 for slot 1, 86 100 for slot 2) and the renewal rule (lifetime / 10,
    60..300 s before `exp`; a token made without a clock is remade when there is one). The
    signer is an interface of one call; nothing of a token is ever logged.
  - `Presets.{h,cpp}` — two rows: `meshmapper` as `MQTTPresets.h:141` writes it (URL,
    audience, retain, keepalive 55) and `meshview` as the guide's four custom lines (no retain,
    default keepalive, as a custom slot gets); `custom` and `none`; `describePresets` for the
    console. No row carries a secret.
  - `Topics.{h,cpp}` — `meshcore/{iata}/{device}/{type}` with the iata check (three letters or
    digits, not `XXX`), and custom templates substituted as `mqttSubstituteTopic` does (an
    unknown `{...}` copied through; an overflow or an empty result is no topic).
  - `Config.{h,cpp}` — what the keys mean: a preset row, or `custom` with `server` required and
    `audience` meaning the token else `username`+`password`, else the slot says what is missing;
    `observerEnabled` over the two slots and the code.
- **`src/observer/Observer.{h,cpp}`**, the board half: reads the sixteen keys, resolves the
  slots, holds the `IdentitySigner` over `mesh::LocalIdentity::sign`, formats every frame the
  tap hands it into one buffer and counts (`status` prints the line), and `formatStatus` for
  27's connect-time status with uptime and the two heap figures filled.
- **The tap**: `AgentMesh::logRxRaw` stashes the radio's bytes, SNR and RSSI; `logRx` (called
  right after, for the same frame, only once `tryParsePacket` accepted it) hands them over with
  the dispatcher's score and `Packet::calculatePacketHash`. `RxFrame`/`RxTap` in
  `AgentMesh.h`; nothing of it is printed.
- **The keys** (`src/settings/Keys.{h,cpp}`): `mqtt.origin`, `mqtt.iata`, `mqtt.owner`,
  `mqtt.email`, `mqtt1.*`, `mqtt2.*` (preset, server, audience, topic, username, password),
  with the observer firmware's buffer sizes less one; seven value kinds (`Iata`, `Hex64`,
  `Email`, `Host`, `BrokerUrl`, `Topic`, `Preset`); `findKey("wifi.pwd")` is `wifi.pass`;
  `explainKey` for `timezone` and `bridge.source`; `normalizeValue` uppercases an IATA code as
  the observer firmware stores it. **Four secrets** now: the two passwords are `Secret`.
- **The parser and the console**: `Verb::Note` (accepted and answered with one line) and
  `Verb::Presets` (`get mqtt.presets`); the console's redaction on echo is now by the table
  (`isSecret` of the key being typed), so `set wifi.pwd …` and `set mqttN.password …` echo as
  asterisks; `help` lists the new keys and the alias; `status` gains an `observer` line.
- **`[env:native]`**: MeshCore installed as a `lib_deps` entry at the pin and `lib_ignore`d, and
  `tools/pio/meshcore_private_libs.py` — the board's own script — compiles its `lib/ed25519`
  into the host build, so the token test verifies with the library the board signs with and
  nothing is copied into this tree. The six `src/observer/*.cpp` of the portable half in
  `build_src_filter`.
- **Docs**: `docs/console.md` (the keys, `get mqtt.presets`, the two notes, `wifi.pwd`,
  `status`), `docs/library.md` §1 (the observer is the Heltec's, not the library's: the Walter
  has no use for it), `README.md` (the `get` block, which the parser test replays, and the
  `observer` line of `status`).

## Deviations from the spec or the task

- **The status message's `offline` is not something the observer firmware writes.** At
  `d664d89d` it publishes `"online"` only (`MQTTBridge.cpp:4100`, `:3182`) and sets no last
  will (no `setWill` call anywhere; the `"online|offline"` in `MQTT_IMPLEMENTATION.md` is the
  doc's, not the code's). `formatStatus` takes the status as a string and the test shows
  `offline` formats; whether 27 sets a retained `offline` will (its task file says so) is a
  choice beyond what the observer firmware does — noted for 27.
- **`mqtt.iata` takes three letters, not three letters or digits.** The observer firmware
  accepts digits (`MQTTObserverValidation.h:15-24`); the task says A–Z, and every code in its
  help is letters. The topic builder still accepts a digit (as the firmware does), so a code
  set by a future path is not refused there.
- **`mqttN.server` takes `wss://` and `mqtts://` only.** The observer firmware also takes
  `ws://` and `mqtt://` and skips certificate checks on them; this firmware verifies TLS on
  every connection (the rails), so those two are refused with a line that says why. 27 may use
  either TLS scheme through esp-mqtt.
- **The packet message's `origin`.** The observer firmware's is `mqtt.origin`, else the node
  name — and this firmware has no node name (an exit node adverts nothing). `mqtt.origin` is
  the key, and its fallback is `MeshMaster-` and the first four characters of the key, the
  prefix meshmaster.dk and the OLED show this node by. The table's help says so; the fallback
  cannot be in the table because it depends on the identity.
- **`firmware_version`** is this firmware's whole string (`meshmaster-agent 0.0.0-dev on
  MeshCore companion-v1.17.1` — what `status` and the log's first line print), so
  `client_version` is `meshcore/` + that; `model` is MeshCore's own board name (`Heltec V3`),
  as the observer sends it. `repeat` is always `off`.
- **Fixtures are `.fixture` files, not JSON.** The task asks for the citations in a header
  comment, and JSON has none; the format is `#` lines, then `key=value`, the last `expected=`
  with the exact message. A reader can diff the `expected` line against a broker's capture.
- **`agent-core` is unchanged** (0.3.1, no CHANGELOG entry): nothing of the observer is in the
  library, by the task's own ruling, and `test_library`'s boundary still holds.

## Decisions taken without asking

- **The hash is the board's `Packet::calculatePacketHash` and arrives at the formatter as
  bytes.** Computing it portably would need a SHA-256 on the host, and MeshCore's Crypto
  library cannot be built there whole (`RNG.cpp` needs Arduino); the fixtures' hashes were
  computed with Python's hashlib over exactly the bytes `Packet.cpp:41-50` hashes, and the
  header of each fixture says which. The board uses MeshCore's function, which is what the
  observer firmware calls too.
- **The score comes from the dispatcher**, which computes it for every received frame and
  hands it to `logRx`; the portable `packetScore` is the same arithmetic for the host, held to
  the fixtures and to the formula.
- **`meshview` is a preset with a custom slot's connection settings** (no retain, default
  keepalive), because that is what the guide's four lines configure on the observer firmware —
  not meshmapper's row with a different host. `Settings.TheMeshviewPresetIsTheGuidesFourCustomLines`
  holds the two equal field by field.
- **A custom slot whose own template has no `{iata}` needs no code** (`observerEnabled`), as
  the observer firmware's custom route substitutes an empty code without complaint.
- **`mqtt.email` is validated lightly** (one `@`, no spaces, 63 characters): the observer
  firmware stores any text; a claim that is not an email is useless to a broker, and the check
  costs one line.
- **The native environment downloads MeshCore's dependencies it never builds** (RadioLib,
  Crypto, RTClib, BusIO, RV3028, CayenneLPP): PlatformIO resolves a git library's manifest when
  it installs it, `lib_ignore` only keeps it out of the build. It is a few seconds of the native
  job and keeps the pin in one place (`${meshcore.pin}`); a script that cloned by hand would be
  a second download path. The per-suite `Library Manager: Installing SPI @ *` lines in the log
  are that resolution and are harmless.
- **No third-party notice was added.** Nothing was copied from the observer firmware: every
  function was written from the cited lines, and the only transcription of a formula is
  MeshCore's `packetScoreInt`, whose licence (MIT) already covers the dependency this firmware
  builds against. The repository has no third-party notices file yet (`LICENSE` only); the day
  something is copied, the notice goes beside `LICENSE` and the file says which lines.
- **The MeshCore pin's `Utils::toHex` is uppercase** (`hex_chars = "0123456789ABCDEF"`,
  `Utils.cpp:174`), so `public_key_hex` in `main.cpp` is already the `{device}` the brokers
  want; the observer uppercases its copy anyway and the comment in `main.cpp` that calls it
  lowercase is left for a task that touches that line.
- **`strftime` and `gmtime` were not used**: the timestamp, `time` and `date` are cut from the
  library's `formatUtc`, which is the same civil-date arithmetic without newlib's locale
  tables (the first build with `strftime` was 3.8 KB larger).

## New libraries (with the one-line justification)

None. MeshCore appears in `[env:native]`'s `lib_deps` at the pin it already has, install-only,
so that the token test verifies signatures with the Ed25519 the board signs with
(`tools/pio/meshcore_private_libs.py`, unchanged, does the compiling); no new package and no
new version anywhere.

## Not verified here (and why)

A session cannot flash a board, hear a radio or reach a broker. On the bench, with `v0.3.0`'s
heap figure already noted for the `[Thomas]` item of pile 1.6:

1. **The settings, as the Danish guide types them.** With this build flashed, type the pile's
   README guide line for line (an IATA code and your owner key in place of the placeholders).
   Expect: `set timezone CEST` and `set bridge.source rx` answer with one line each and no
   `error:`; `set wifi.pwd …` echoes asterisks and answers `ok wifi.pass`; every `set mqtt…`
   answers `ok <key>`; `get` lists the sixteen `mqtt` keys with `mqtt1.password unset`-style
   lines and never a value; `get mqtt.presets` prints the two rows, `custom` and `none`.
2. **`status`'s `observer` line.** Before any `mqtt` key: `observer  off: no slot configured
   (set mqtt1.preset ...); …; N frame(s) heard while off`, with N moving as adverts arrive. After
   `set mqtt1.preset meshview` alone: `off: mqtt.iata is unset`. After `set mqtt.iata AAR`:
   `slot 1 meshview, slot 2 none (preset is none); iata AAR, origin "MeshMaster-XXXX"; N packet
   message(s) made, 0 did not fit; nothing sent (task 27)` — N counting every frame heard, and
   `0 did not fit` staying 0 (a frame the radio can receive always fits `kPacketMessageCap`).
3. **Nothing new on the port.** With `log.level debug` and `log.frames on`, an hour at a window
   must print exactly what `v0.3.0` printed: no line from the observer at all (the rails test
   greps `src/observer/` for `LOG_` and `Serial`, but the bench is where a person reads it).
4. **The heap did not move.** `status`'s heap line before and after configuring both slots is
   the same figure: the observer allocates nothing. The static RAM is +2 624 bytes against
   `v0.3.0` (49.8 % of the V3's 320 KB), which is what the `[Thomas]` measurement of pile 1.6
   should be read against before 27 adds two TLS connections.
5. **`erase confirm`** forgets the sixteen keys too (`get` shows them unset) and `status`'s
   `observer` line goes back to `off: no slot configured`.

The messages themselves reaching a broker, and whether meshview.dk and meshmapper.net accept
the token, are task 27's bench.
