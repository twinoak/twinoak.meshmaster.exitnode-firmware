# p1.7-27 — The broker connection

Task 26's messages are on the air. Each of the two observer slots is a state machine over an MQTT
client (`src/observer/Connection.h`, host-portable, no network in it) that waits for WiFi, the clock
and the heap in that order, signs in with the node's own token, publishes every packet message the
radio produced and a retained status, renews the token before it expires, backs off from a refusal
or a loss with the reason, and gives way to the MeshMaster uplink when the uplink is short of
memory. The client is ESP-IDF's **esp-mqtt as the Arduino core at this pin ships it** - no library
added - behind an interface (`src/net/MqttClient.h`), with its own task per connection, so a publish
is an enqueue and the mesh loop and the agent loop never wait on a broker. Every connection verifies
the broker's chain against roots this firmware carries: **ISRG Root X2 joins ISRG Root X1** in
`TlsRoots.h`, read off the two brokers' live chains from this machine.

## What was built

- **`src/observer/Connection.{h,cpp}`** - the portable state machine: `Client` (the interface:
  `open`, `close`, `publish` as an enqueue, `takeEvent`, `outboxBytes`), `Environment` (millis,
  epoch, free heap, largest block, random, the roots), `StatusSource`, `ReportLine`; `Connections`
  over `kSlots` slots with the states *off, waiting-for-wifi, waiting-for-clock, waiting-for-heap,
  connecting, connected, backing-off*; `configure` re-resolves both slots from Config.h and restarts
  only a slot whose URL, sign-in, topics, owner or email changed (a hash of those); the per-slot
  byte queue (2 048, oldest dropped and counted; a slot not connected drops at once); the status at
  connect and every five minutes; the token through Token.h with the renewal rule; the backoff
  through agent/Backoff.h (5 s doubling to 10 min, jittered, cleared after two minutes up); the heap
  gate and the ten-minute yield; `view()` and `describe()` for the console. Every number is a named
  constant with its source beside it.
- **`src/net/MqttClient.{h,cpp}`** - the board half over esp-mqtt: one `esp_mqtt_client` per open,
  destroyed at close so the TLS context goes back to the heap; `cert_pem` the carried roots or the
  core's bundle through `arduino_esp_crt_bundle_attach` (never neither - a config with no CA store
  is refused in code, because esp-tls would then verify nothing); auto-reconnect off (the state
  machine's backoff is the policy); receive buffer 512, send buffer 1 536 (a packet message and its
  topic whole, by a `static_assert`), retransmit 15 s as the observer firmware's; events from
  esp-mqtt's task into a four-slot ring under a spinlock, read one per loop pass as a kind and one
  short reason (CONNACK code names, esp-tls error names, the mbedtls code as a number).
- **`src/agent/TlsRoots.h`** - ISRG Root X2 beside X1, `kCarriedRootsPem`, the evidence as a comment.
- **`src/agent/AgentClient.{h,cpp}`** - `memoryFailures()`: a call that got no reply where mbedtls
  reported an allocation failure or the largest free block after the call cannot hold a TLS content
  buffer, logged with the figures. `main.cpp` hands each increment to the observer.
- **`src/observer/Observer.{h,cpp}`** - owns the `Connections`, hands every packet message to them,
  is their `StatusSource` (the status message now carries `mqtt_slots_up`, `mqtt_slots_total` and
  `mqtt_connect_failures` when > 0) and their log; `reconfigure()` is live for every `mqtt` key.
- **`src/main.cpp`** - two `MqttClient`s, the `Environment`, `observer.setLinkUp(wifi.connected())`
  and `observer.loop()` every pass, the memory-failure hand-over, `printMqttStatus`, the display's
  two counts.
- **The console** - `get mqtt.status` (`Verb::MqttStatus`): the observer's summary line, one line
  per slot, and the memory rule with the heap as it is now. `status`'s `observer` line names each
  slot's state and how many are connected. `help` lists it.
- **The display** - line three is `HB 12:03:14  MQTT 2/2` while a slot is configured (exactly the
  font's 21), `Heartbeat: …` as before when none is.
- **Docs** - `docs/observer.md` (new: what it is, the lines to type, what is published and to whom,
  TLS, what it costs and the order of priority, what the console shows, privacy); `docs/console.md`
  (`get mqtt.status`, the live `mqtt` keys, the OLED's third line); `README.md` (the tree, the rails'
  TLS line, the display).

## Deviations from the spec or the task

- **The retained `offline` will is this task's, not the observer firmware's** - task 26 noted that
  firmware sets no will and writes `"online"` only. The task file asks for the will; it is the full
  status message with `"status":"offline"`, formatted at open, so its stats are the ones at connect
  time (a will is fixed at CONNECT). A clean `reboot` does not send MQTT's DISCONNECT, so the will
  fires on a reboot too and the brokers see `offline` rather than a stale `online`.
- **The status is retained where the preset allows and not retained for meshview**, which is a
  custom slot's settings in that firmware (task 26's reading); meshmapper's row allows it.
- **Keepalive is 75 s for every slot**, not the preset's 55 for meshmapper: the observer firmware
  on a board without PSRAM ignores the preset's value and uses 75 (Cloudflare closes an idle
  WebSocket at 100 s; `MQTTBridge.cpp:5125-5135`), to spare the TLS churn. `ResolvedSlot.keepalive`
  is still resolved for the day a board has PSRAM.
- **`mqtt.interval` is a constant, not a key**: five minutes, the observer firmware's default
  (`MQTTBridge.cpp:981`). The task names "every `mqtt.interval` (the observer firmware's default)";
  the Danish guide never sets it, and a 29th key for it would be scope beyond the guide.
- **A chain that ends at neither carried root is tried once against the core's bundle, then
  refused** - the task's "(or takes an explicit CA - say which and why)". The CA is the ESP32
  core's certificate bundle, the Mozilla roots, because that is the policy `AgentClient` already
  applies to meshmaster.dk, it is verification, and it needs no new key or file on the board; a
  custom broker with a private CA is refused with the reason and backs off. No `mqttN.ca` key.
- **The uplink's handshake was not measured on the host**: the host has no mbedtls and the task
  allowed the fallback. The reserve is the observer firmware's 40 KB per TLS connection plus 8 KB,
  with the reasoning at `kHeapReserve*` in `Connection.h`: a slot opens while free heap >= 90 112
  and the largest block >= 34 816 (two 17 KB content buffers).
- **Nothing needs a reboot**: every `mqtt` key takes effect live, as the observer firmware's do
  ("MQTT settings apply live"); the task asked which do not, and the answer is none.
- **Static RAM grew 7.9 KB**, which is more than task 26's 2.6 KB and is the queues: 4 KB of the
  7.9 is the two 2 048-byte packet queues, sized for about three packet messages each. A smaller
  queue drops more under a burst; the bench's figure for free heap decides whether this is the
  right trade, and the constant is one line.

## Decisions taken without asking

- **One handshake at a time**: a second slot does not open while the first is still connecting
  (state *waiting-for-heap*, reason "waiting for the other slot's handshake"), because two
  handshakes at once is twice the peak on a board whose heap is the constraint.
- **A user/password custom slot also waits for the clock**: its token needs none, but every packet
  message carries the wall clock, and publishing frames stamped 1970 helps nobody.
- **The client is destroyed at close, not kept**: the observer firmware keeps its client objects to
  avoid fragmentation churn; this firmware frees the ~40 KB because the uplink may need it, which
  is the whole point of the yield. `esp_mqtt_client_destroy` joins esp-mqtt's task, which can hold
  the loop task for as long as the client's current network operation (10 s at most); a renewal is
  once a day and a failure is rare.
- **The queue is a plain byte FIFO with a memmove on pop** (2 KB at most) so the front message is
  always contiguous and goes to the client straight from the queue - no second copy.
- **The uplink's memory failure is detected on the uplink's side** (`AgentClient::memoryFailures`):
  the five mbedtls `*_ALLOC_FAILED` codes, or a largest free block under one TLS buffer right after
  the failed call. Both are conservative: a failure for any other reason yields nothing.
- **The CONNACK, esp-tls and mbedtls codes are rendered as short phrases plus the number**
  (`bad username or password (CONNACK 4)`, `tls handshake failed (tls -0x7780, errno 104)`), the
  observer firmware's `MQTTErrorLabels.h` wording where it has one.
- **`arduino_esp_crt_bundle_set/attach` are declared in `MqttClient.cpp` rather than included**:
  the ESP-IDF ships an `esp_crt_bundle.h` of its own with a different symbol, and which header an
  include finds depends on the include order.
- **esp-mqtt's client id is its default** (`ESP32_<MAC>`), as the observer firmware's
  PsychicMqttClient leaves it.
- **The connections are pumped inside a job's waits too** (`pumpDuringAJob` in `main.cpp`,
  beside the console and the OLED): a thirteen-minute `config.read` would otherwise fill the
  two-kilobyte queue in a minute and drop everything heard after it. esp-mqtt's own tasks keep the
  sessions alive either way; this only keeps the frames flowing.
- **A link flap during a ten-minute yield ends the yield early**: when WiFi comes back the slot goes
  through the heap gate again rather than finishing the hold. The gate still protects the uplink;
  the hold is a courtesy on top, and the simpler rule won.
- **The `[Thomas]` measurement of pile 1.6 is still open** and this task does not depend on it;
  the reserve constant is where the number goes when it exists.

## New libraries (with the one-line justification)

None. esp-mqtt, tcp_transport and esp-tls are components of the ESP-IDF 4.4.7 inside the Arduino
core the pin already names (`framework-arduinoespressif32` 3.20017: `tools/sdk/esp32s3/include/mqtt/esp-mqtt`,
`libmqtt.a`, `CONFIG_MQTT_TRANSPORT_WEBSOCKET_SECURE=y` in its sdkconfig), linked by the core's own
`platformio-build-esp32s3.py` whether used or not; this task is the first to reference them.

## Not verified here (and why)

A session cannot reach a broker, flash a board or read its heap. On the bench, after the pile's
README's step 1 (the `v0.3.0` heap figure):

1. **One slot first.** With this build flashed and the guide typed (`mqtt.iata`, `mqtt.owner`,
   `set mqtt1.preset meshview`): within a few seconds of `status` showing a time, the log says
   `observer: slot 1 meshview: connecting to wss://mqtt.meshview.dk:443/mqtt with token, root ISRG Root X1/X2`
   and then `connected (root ISRG Root X1/X2; 1 connects)`. A `sign-in refused` or
   `tls handshake failed` line is the thing to copy into FOLLOWUPS.md verbatim; `get mqtt.status`
   has the same reason as `last error`.
2. **The node on meshview.dk** within a minute of adverts being heard: `get mqtt.status` shows
   `published` climbing with `status`'s `frames rx`, `dropped` staying near 0.
3. **The heap.** `status`'s `heap` line before `set mqtt1.preset`, after slot 1 connects, and after
   a heartbeat has gone through beside it: three figures, into FOLLOWUPS.md. Free heap after the
   TLS call minus free heap with the slot up is the slot's real cost; if `largest block` falls under
   ~35 000 the second slot will wait, and `get mqtt.status` will say so.
4. **Two slots.** `set mqtt2.preset meshmapper`: slot 2 connects after slot 1's handshake (the
   log shows the two `connected` lines seconds apart), the OLED's third line reads `HB … MQTT 2/2`,
   and the node is on meshmapper.net. An hour later: `status`'s heap line again, `get mqtt.status`
   (0 `gave way`, 0 errors, published counts in step with each other), and the heartbeat still
   answered (`server`).
5. **The uplink first.** With both slots up, press *Read now* on a repeater associated to this
   exit node: the jobs run as before. If the log ever says
   `server: the call failed for want of memory`, the next line is
   `observer: slot 2 meshmapper: closed for 10 min` and `get mqtt.status` counts `gave way 1 time(s)`;
   the call after it must go through. If that happens at all on a V3, the reserve constants in
   `Connection.h` are what to raise.
6. **Renewal** (a day later): the log says `the token is renewed before it expires (1 renewal(s))`
   once per slot, five minutes apart, and the node never leaves the maps.
7. **The will.** `reboot` on the console, then the retained status on the broker (meshmapper
   retains; `mosquitto_sub -h mqtt.meshmapper.net -p 443 ...` over WSS, or the map's node page)
   should read `offline` until the board is back and `online` again.
8. **`erase confirm`** closes both slots (`get mqtt.status`: both `off`) and the panel's third line
   goes back to `Heartbeat: …`.
