# p1.7-28 — The observer in the heartbeat

Two optional fields of the agent protocol, the fixtures that carry them, and the
pile closed. MeshMaster can now show an exit node's observer from what the
heartbeat says, and tell a silent login from a lost request by the result's
`failedAt`.

`tests/fixtures/contracts/AgentHeartbeatObserver.json` **is** on meshmaster.dk's

## Deviations from the spec or the task

- **The library has the observer's field names in it, and the task's "without
  the library knowing what an observer is" is satisfied a level up.** The task
  allows "a callback or an interface of one method ... that writes the object".
  Read strictly, *writes* could mean the provider hands over JSON that the
  heartbeat writer drops in with `raw()`, and then the field names would live in
  `src/observer/` alone. This task did **not** do that: `Envelopes.h` has
  `HeartbeatObserver` and `HeartbeatObserverSlot`, mirroring `AgentObserver` and
  `AgentObserverSlot` field for field, exactly as it mirrors every other record,
  and the provider fills a struct. Two reasons, and the second is the one that
  decided it. The file's own purpose is to be that mirror — *"structs that
  mirror MeshMaster.Contracts field for field"* is its first line — and the
  bytes have always been the library's to write, escaping included (clause 8,
  task 25). And a `raw()` of consumer-written JSON is a hole in exactly the place
  D-46 warns about: *a bad observer object must not take an exit node off the
  air*. A provider that writes a stray byte would make a heartbeat the server
  refuses, and an exit node whose heartbeat is refused is offline. With a struct
  the library writes the bytes and a provider cannot produce invalid JSON at all.
  What the task's sentence is actually about — the **loop** not knowing what an
  observer is — holds: `AgentLoop` has no notion of a broker, a slot's meaning,
  a topic or a key; it asks one method and writes what it gets.
- **The heartbeat body buffer moved, in `src/` and not in the library.**
  `AgentClient::postHeartbeat`'s `requestJson` is **2 048** bytes, up from 1 024.
  Two slots at the bounds the server accepts — a 63-character custom broker and
  a 95-character last error apiece — are about 700 bytes of `observer` on top of
  the ~720 this board's own fields come to, and `writeHeartbeat` returns 0
  rather than cutting a body. A heartbeat that does not fit is an exit node the
  server reads as **offline**, so the buffer is sized for the longest thing this
  firmware can produce and not for the common case. It is the whole of this
  task's RAM cost, and `CHANGELOG.md` names the number for a consumer who sizes
  buffers from this repository's.
- **`AgentTransportList.json` and `AgentHeartbeatNoKey.json` came with the sync
  and nothing here reads them.** They are not this task's and neither changes a
  byte this firmware writes. The one thing they did change is a **comment**:
  `test_envelopes`' transport test said "the fixtures carry **one** word
  (`onboard`)", which stopped being true the moment `AgentHeartbeatNoKey.json`
  (transport `native`) landed. The test's assertion was always *`onboard` is
  among the words the fixtures carry* and still passes; the comment was corrected
  rather than left to mislead the next reader.

## Decisions taken without asking

- **`failedAt` is the step the job *ended* at, tracked as a stage, rather than
  inferred from whether a session exists.** `Context::Stage` is `None`, `Login`
  or `Request`: `ensureSession()` sets `Login` the moment a session is wanted
  (a fresh login or a reused one), and `exchange()` sets `Request` at the top of
  **every attempt**. The last one reached is what the result names. The
  alternative — "`request` if `ctx.hasSession`, else `login`" — agrees on
  everything the field exists for, but the stage is what the record's own
  sentence says (*where a failed job failed*) and it gets the re-login case right
  without a special case: a request that lost its session, failed to get another
  and gave up names `login`, because that is where it stopped. A test holds
  exactly that.
- **Three cases carry no `failedAt`, and one of them is wider than the task's
  words.** The task says *absent on success and on results with no login
  (`trace`)*; this implementation also leaves it out when the job **put nothing
  on the air** — a type the mesh declines, a lease that had already run out, a
  `reportNotRun` for a wake with no room. Those are "results with no login" in
  substance, and the alternative is worse than silence: `failedAt: login` on a
  job that never sent a login would tell MeshMaster's page that a stored password
  is suspect on the strength of a packet nobody sent, which is the one reading
  the field exists to prevent. Where there was no login attempt there is no step
  to name.
- **An `unauthorized` whose login was answered below the class reads
  `failedAt: login`.** It is a refusal — `LoginSequence` reads it as one and no
  session is kept — and the field says *where*, not *why*; the outcome and the
  result's `loggedInAs`/`needed` say the rest. The server's own wording allows
  it: *`login` when no login was answered — silence to the password, or **a
  refusal***.
- **The board sends both slots, always, and an off slot names no preset and no
  broker.** `AgentObserverSlot.Preset` is documented as *"or absent when the
  exit node names none"*, so an empty slot could carry `"preset":"none"` or
  nothing; nothing was chosen, because the card's own words for it are *no
  broker* and because it is the record's "absent" case. Sending the slot at all
  is deliberate: *one entry per slot the exit node has*, and a card that shows
  **slot 2 · no broker — off** tells an owner with one slot configured that
  there is a second one and it is empty. `AgentObserverRules.IsConfigured` reads
  `state != "off"`, so an off slot is excluded from the *connected over
  configured* count either way.
- **The provider is handed over while the observer is `enabled_`**, which is the
  console's own answer — at least one slot resolved **and** a region code to
  build its topic from (`observerEnabled`). A board where `mqtt1.preset` is set
  but `mqtt.iata` is not is therefore *not* an observer in the heartbeat, and
  `get mqtt.status` is where its reason is read (*mqtt.iata is not set*). The
  alternative — reporting a half-configured observer so that MeshMaster could
  show the reason — would have put a configuration error on a page that D-46 says
  configures nothing, and the console is where the lines were typed.
- **`since` is the slot's `sinceEpoch` and is left out while it is 0**, which is
  exactly the `waiting-for-clock` case the record documents (*absent while it has
  no clock*). Nothing was invented to fill it.
- **The slot array lives in `Observer` and the loop copies nothing**, the rule
  `HeartbeatIdentity` already lives by. 96 bytes of static RAM, and no question
  about who owns a string.
- **The seven state words got a test of their own**
  (`Settings.TheSevenStateWordsAreTheOnesMeshMasterSpells`, in
  `test_connection`). They were a display string until this task and they are a
  contract now: the server **keeps** a word it has not heard of rather than
  refusing it, so renaming one would not break a heartbeat — it would quietly
  change what an owner's Observer card says, which is worse than a red build.
- **Nothing was bounded on this side.** The server bounds every field (preset
  32, host 64, state 32, lastError 120 characters, six slots) and refuses an
  over-long one *by name while still taking the rest of the heartbeat*.
  Everything this firmware can produce is inside those numbers — the longest
  preset name is `meshmapper` (10), `mqttN.server` holds 63 characters, a last
  error is `kReasonCap`'s 95 — so a bound here would be a second copy of the
  server's that could drift, and it would have nothing to do. `docs/library.md`
  §6.1 says the numbers for a consumer whose buffers are its own.

## Not verified here (and why)

A session cannot flash a board, reach a broker or reach meshmaster.dk. **The
bench list of task 27 stands in full and is where to start** — it is the one
that gets a slot connected at all. What this task adds to it, to be walked after
27's step 4 (two slots up):

1. **The Observer card exists.** Within one poll interval of the first heartbeat
   after `set mqtt1.preset meshview`, `/exit-nodes/{id}` shows an **Observer**
   card: the lead line, `slot 1 · meshview — connected since …`, the broker,
   *N published, N dropped*, and `slot 2 · no broker — off` under it. The list
   at `/exit-nodes` shows **1/1** in the Observer column. With slot 2 up as well:
   **2/2**, two rows. This end can show that the bytes are the fixture's; only
   meshmaster.dk can show that its page reads them.
2. **The numbers agree across the two ends.** `get mqtt.status`'s `published`
   and `dropped` for each slot against the card's, at the same minute. They are
   the same counters and they must not differ by more than the heartbeat's age.
3. **A refusal reaches the card.** With a deliberately wrong custom slot (`set
   mqtt2.preset custom`, `set mqtt2.server wss://mqtt.meshmapper.net:443/mqtt`,
   `set mqtt2.username nobody`, `set mqtt2.password wrong`): the console's `last
   error` and the card's amber line should be **the same phrase**, and the state
   `backing-off`. Put the phrase in FOLLOWUPS.md either way — it is the first
   real reading of a broker's own wording.
4. **Turning it off empties the card.** `set mqtt1.preset none` and `set
   mqtt2.preset none` (or `erase confirm`): the heartbeat stops carrying the
   object within one poll interval — `get mqtt.status` says `off` and why — and
   the card stays on the page for **a day** and then goes. That last part is a
   day of waiting and is nobody's job to watch; what the bench checks is that the
   heartbeat still goes and the exit node stays **online** with the observer off,
   which is the thing that would matter if it were wrong.
5. **`failedAt` on a real failure.** The field cannot be seen from this end on a
   real mesh at all. On the bench: a repeater with a **wrong stored guest
   password**, read on its schedule → the job's page should say the password is
   the thing to look at (`failedAt: login`). Then a repeater that is **on the air
   and answers a login but not the request** — hard to arrange deliberately;
   the honest way to see this one is to watch an ordinary week of job failures
   and check that `request` ever appears at all. If every failure a month of real
   use produces says `login`, that is worth a note in FOLLOWUPS.md: it would mean
   the second case is rarer than the server's page assumes.
6. **The heap, again, with the heartbeat beside it.** The heartbeat body buffer
   is 1 KB larger and the static RAM is 52.6 % of the V3's 320 KB. Pile 1.6's
   `[Thomas]` measurement is still the open one: `status`'s heap line (free,
   minimum ever, largest block) with WiFi, the uplink and both slots up, into
   `../phase-1.6/FOLLOWUPS.md`. If `largest block` sits near 35 000, the second
   slot will be waiting and `get mqtt.status` will say so — and the reserve
   constants in `src/observer/Connection.h` are what moves.
7. **Then tag `v0.4.0`** (the pile's README, *Before you flash it*, step 3).
