# p1.7-25 — The strings are UTF-8

Three defects the review of pile 1.6 found ([`../phase-1.6/FOLLOWUPS.md`](../phase-1.6/FOLLOWUPS.md),
its three `[1.7]` items), each in `lib/agent-core/` and each with a test that fails
first. The first of them is the one that matters: since task p1.6-24 `JsonWriter`
copies a character's own source bytes to the wire, and the decoder behind that
accepted an overlong form, a surrogate encoded as a character, a code point above
U+10FFFF and the lead bytes F5–FF — so a repeater whose name carries such bytes,
read back over its console rather than heard in an advert, made a result
**System.Text.Json refuses**, and a refused result is kept and retried at the
head of this agent's ordered queue, blocking the ones behind it until the buffer
evicts it. `string()` is now the decoder as well as the escaper:
one U+FFFD per **maximal subpart** of an ill-formed sequence, and no output of
this writer is ill-formed UTF-8 whatever came in.

**The Heltec's behaviour does not change.** RAM **±0** on both boards; flash
**+80** (V3) and **+76** (V4), named symbol by symbol below. Nothing it prints
moved, no console line moved, `docs/console.md` did not move, and the heartbeat
and every other envelope are the same bytes for every input that was valid
before.

`pio test -e native`: **392 cases in 23 suites, all passing** (387 in 24 before —
five new, in three existing suites). Both boards SUCCESS with `-Werror`; 20's
five-configuration host matrix, the component check and `-Verify` are green.
`agent-core` **0.3.1** in the three manifests, with a `CHANGELOG.md` section.

## Deviations from the spec or the task

- **Clause 8 is wider here than the spec states it, and says so.** Read at
  today's `origin/master` of meshmaster.dk — **`a9a18fa`** — the rule is
  `tests/fixtures/contracts/README.md`'s table ("8 | a lone surrogate | `\uFFFD`
  (it is not a character)") and `docs/dev/unit-protocol.md` §8's clause 7
  sentence, which says the same. **That is the whole of the clause from .NET's
  side, and it has to be:** its input is a UTF-16 `string`, so the only
  ill-formed value it can hold is a lone surrogate, and `System.Text.Json` never
  sees ill-formed UTF-8 at all — it refuses such a document at the reader. This
  writer's input is **bytes**, so the same clause has to answer a wider question,
  and the extra forms (overlong, above U+10FFFF, F5–FF, a cut sequence) and the
  maximal-subpart rule for them are this repository's, matched to what
  `Encoding.UTF8` does with the same bytes. Nothing of the spec disagrees; the
  spec is simply silent where only this end can be asked. `JsonWriter.h`'s clause
  table and header say so, and so does `docs/library.md` §9 for the Walter's
  writer. **Nothing for the reviewer to open in the other repository** — but if
  meshmaster.dk ever wants the clause stated for a byte reader, this is the
  wording to copy.
- **The replacement character is written `\uFFFD` and not as its own three
  bytes.** It is an assigned BMP character, so clause 5 would write it as
  `EF BF BD`, and `Clause7…` holds exactly that for a U+FFFD that **arrives** in
  the input. For a *replacement* the writer makes itself, the spec's own table
  says `\uFFFD`, which is what p1.6-24 wrote and what this task kept. The two
  forms are the same string to any reader.
- **`C0 80` is two U+FFFD and not `\u0000`.** p1.6-24 decided that "an overlong
  encoding of an ASCII byte goes through `escape()`" so that no path through
  `string()` could write a raw control byte. Table 3-7 makes that decision
  unnecessary — a sequence beginning C0 or C1 is ill-formed at the lead byte, so
  nothing decodes to a code point below 0x80 any more — and the task names
  `C0 80` as a `Clause8` case, so the old branch is gone. The rail it protected
  is stronger now, not weaker: the fuzz test holds *no unescaped byte below
  0x20*, over the whole input space rather than over one path.
- **A `v0.3.1` tag is not assumed.** The CHANGELOG's heading is `v0.3.1` because
  that is the number in the three manifests, and the section says in as many
  words that **there may never be such a tag**: pile 1.7 tags `v0.4.0` after task
  28 (`tasks/phase-1.7/README.md`), and 28 bumps the library to 0.4.0. So the
  `v0.3.0` pin examples in `docs/library.md` §2 and `docs/upstream.md` were left
  where they are — they name the last tag, which is still the last tag — and the
  section tells a consumer who wants this fix sooner to take the library at the
  commit, as §2.1 describes.

## Decisions taken without asking

- **The undatable advert is dropped, not carried.** The task allowed either:
  drop and count, "or carry their age and the sleep's length, if the image has
  room — say which". **Dropped**, and the image's layout is untouched. Carrying
  an age needs a duration the unit cannot measure: `millis()` restarts at zero,
  nothing in the image or in `WakeState` bounds how long a deep sleep actually
  lasted (that is why `heardAtEpoch` exists at all, p1.6-22), and the restore
  would have to add an unknown to a known. An advert with a plausible-looking
  wrong time is worse than a counted loss: it is the one record the server draws
  a coverage map from. A unit with an RTC, or one whose first heartbeat has
  answered, never reaches this path.
- **The read end drops such an advert too.** `restoreKept()` refuses an advert
  whose `heardAtEpoch` is 0 and counts it, with a log line of its own. The write
  end cannot produce one any more, but `v0.3.0` is tagged and pinned by another
  firmware, and the kept image's version did not change — so an image written by
  a build before this one and read by this one is a real case, exactly once, on
  the first boot after an update. Three lines closed it rather than leaving the
  defect alive in the one window where it can still happen.
- **`WakeReport::observationsNotKept` counts both kinds**, with the log line
  saying which. A second field would have been a third name for "an advert this
  wake lost", and a consumer that reports the figure wants the sum; the
  heartbeat's `observationsDropped` is the sum either way, because
  `ObservationRing::dropped()` is where both go.
- **The decline is one method, `JobRunner::meshDeclines()`**, asked by `runJob()`
  and by `AgentLoop::wakeJobs()`. The alternative was to repeat
  `extension_ != nullptr && !isKnownJobType(...)` in the loop, which is the half
  of the question that is easy to get wrong (an extension's own type is **not**
  the mesh's to decline) and would have been two copies to keep in step. A seam
  test holds the method's body and that the wake asks it before it prices.
- **A declined job goes through `runClaimed()`**, not through a new path.
  `report.jobsRun` counts it and the runner writes the result, which is what the
  same job gets in `loop()` — one answer for one job, whichever way the caller
  drives the library. `reportNotRun()` is for a job the **wake** could not fit;
  this one is a job the **unit** will never run.
- **The two fuzz tests live in `test_json_escaping`** rather than in a suite of
  their own: they hold clause 8, and the clause is what that file is for. Each is
  seeded with a constant, so CI and this machine run the same cases and a failure
  is reproducible.
- **The sharper fuzz generator was kept after the first one proved toothless.**
  The uniform version was written first, passed against the buggy writer, and was
  replaced rather than merely added to — a test that cannot fail for the defect it
  is named after is worse than no test, because it reads like a guarantee. Both
  runs are in `out/` (`25-before.log`, `25-before-fuzz.log`).

## Not verified here (and why)

Nothing the Heltec *does* changed, so 1.5's, 20's, 21's, 22's and 24's bench lists
stand as they were. What this task leaves for the bench:

1. **A result with an ill-formed name, read by the real server.** This end can
   show that the bytes it writes are UTF-8 and parse; only meshmaster.dk can show
   that `System.Text.Json` takes them and that the job's page renders the
   `\uFFFD`. The board cannot even be asked for the interesting case directly —
   `validUtf8PrefixLength` cuts an advert name before the writer sees it — so the
   path to walk is a **CLI reply**: `cli` with a command whose answer carries a
   byte that is not UTF-8 (a repeater name set from another tool, an `owner.info`
   with a stray byte), and the raw result body pasted into the next bench note.
   Nothing on a healthy mesh produces one; this is the case that was blocking a
   queue when it did.
2. **The kept-advert drop on a unit that sleeps.** The Heltec passes no
   `IRetained` store, so `keepAcrossSleep` is not on its path at all — this is the
   Walter's to see, on a unit with no RTC whose first heartbeat has not answered:
   one wake with the server away, the log line *nothing can date them*, and
   `observationsDropped` on the exit node's page after the next heartbeat. The
   native tests hold it with a fake clock and a fake store.
3. **A declined type on a unit whose mesh declines one.** Also the Walter's (its
   p4-02, a UART link with no trace request): a bound `trace` in a tight wake
   should come back `unsupported` with *this mesh cannot carry a 'trace' job* in
   its log. This board's mesh carries all thirteen, so nothing here can answer
   `false` outside a test.
4. **`v0.3.1` is not tagged** and is not planned to be (above). The library's
   version in the three manifests is 0.3.1; the repository's next tag is pile
   1.7's `v0.4.0`.
