# p1.11-52 — A release from the button

A release of this firmware needed four things done by hand or by a task: the
*What's new* text edited inside `release.yml`, the changelog's heading, the
library's version in three manifests, and a tag pushed. It now needs one press.

**What changed, in one view.**

| | Before | Now |
|---|---|---|
| the trigger | a pushed tag `vX.Y.Z`; *Run workflow* was a dry run | *Run workflow* publishes; a **dry run** tick box rehearses; **the tag trigger is gone** |
| the version | typed into the tag, and copied by hand into three manifests | [`VERSION`](../../../VERSION) at the root, one line, naming the release that comes **next** (`0.7.1`); the three manifests copy it and CI fails when one does not |
| *What's new* | a block of prose edited inside `release.yml` by the task that shipped the tag | `release-notes/unreleased/<task>.md`, one line per task, compiled in **merge order** |
| the changelog at the tag | `## Unreleased` | `## v0.7.1` — the version that is coming |
| after a release | nothing; the next task moved the version | one pull request, opened and merged by the workflow |
| the decisions | shell inside the workflow | [`tools/release.ps1`](../../../tools/release.ps1), with a 19-case self-test CI runs against scratch repositories |

[`docs/release.md`](../../../docs/release.md) is the page. **Nothing was
published and no tag was pushed by this task.**

## What a press does now

1. **`gate`** — checks out `master`'s head (a dry run may name another ref, and a
   dry run that names none rehearses the ref it was pressed from), fetches the
   tags and `origin/master`, and runs `release.ps1 -Action plan`: the version,
   the tag, and the three refusals, each one sentence, **before the `build` job
   exists**. Then `-Action ci-commit` names the commit `ci`'s verdict is read
   from, and the twenty-minute wait for that run, as before.
2. **`build`** — unchanged: both boards, the version baked in as
   `-D MESHMASTER_AGENT_VERSION`, `-t mergebin`, the images named after the
   release.
3. **`publish`** — `SHA256SUMS`; *What's new in vX.Y.Z* from the waiting lines;
   the standing parts of the notes (the flasher, the table of files, the console
   lines) unchanged below it; `gh release create` with the tag on that commit, as
   **Latest**; and then the pull request that files the notes and moves the
   version on.

A **dry run** does the same build, publishes nothing, says `0.0.0-dryrun+<sha7>`
and keeps the images as artifacts — and refuses nothing, printing instead what a
real release *would* have refused.

## Deviations from the spec or the task

- **None of substance.** Two readings the task left open are recorded under
  *Decisions* below rather than as deviations: what a dry run refuses, and what
  happens to the run when the pull request after a release cannot be merged.
- **The task's *First* is satisfied.**
  `gh api repos/twinoak/twinoak.meshmaster.exitnode-firmware/actions/permissions/workflow`
  answers `{"default_workflow_permissions":"write","can_approve_pull_request_reviews":true}`
  — the workflow's own token may create pull requests — so no `logs/STOPPED-52.md`
  was written and the task ran.
- **The spec for this task is this repository's own files and meshmaster.dk's
  `release.yml` as the model**, and the two did not disagree. Where this
  repository's shape differs, it differs for a reason worth naming: meshmaster.dk
  compiles its notes into `release-notes/releases.json` **before** it builds,
  because its site *embeds* the file and must show what it ships, and it looks up
  each bullet's pull request number with `gh`. This repository's notes go into a
  GitHub release that is written at publish time and read by people who can see
  every pull request anyway, so the lines are compiled in the `publish` job, the
  archive is one markdown file per version (`release-notes/vX.Y.Z.md`) rather than
  a JSON history, and no pull request is looked up. The rest — a line per task,
  one pull request afterwards opened and merged by the job's own token, three
  merge attempts ten seconds apart, the state of the pull request deciding rather
  than `gh`'s exit code — is meshmaster.dk's, deliberately.

## Decisions taken without asking

- **`VERSION` at the root, one line, as the one place.** Not `platformio.ini`
  (which a board build parses and a consumer does not read), not `library.json`
  (one of the three manifests it has to govern). A file called `VERSION` is read
  by `bash`, `pwsh`, Python and a C++ test in one line each, which is what the
  four rails needed.
- **It names the release that comes *next*.** The task says so for the version;
  the consequence it does not spell out is the changelog's. Deliverable 5 asked
  how the top section should be headed so the file reads right *at the tag*, and
  the answer falls out: head it with the version `VERSION` names. At `v0.7.1` the
  first heading of `CHANGELOG.md` is `## v0.7.1`, where it would have said
  *Unreleased*; the release's own pull request opens `## v0.7.2` above it.
  `tools/release.ps1 -Action check` fails in CI when the heading and `VERSION`
  disagree. **What reads that file by machine, and still works**:
  `twinoak.meshcore.walter-firmware`'s `.github/workflows/upstream.yml` takes
  `git show <tag>:CHANGELOG.md | sed -n "/^## /,/^## /p"` — the **first** `## `
  section at the tag — into its bump pull request's body, and now quotes that
  release's own four answers instead of *Unreleased*. Its
  `tools/upstream-check.ps1` reads `AGENT_CORE_VERSION` out of its copy and this
  repository's `v*` tags, and never the changelog. **`tools/new-sync-task.ps1` in
  this repository reads nothing from `CHANGELOG.md` at all** — it reads
  `[meshcore].pin` from `platformio.ini` and the tag it is given — so there was
  nothing there to keep working.
- **A release note is one paragraph of at most 400 characters**, where
  meshmaster.dk's bound is one line of 120. Its notes are a list on a web page;
  these are read inside a GitHub release beside a flashing table, and the lines
  `v0.7.0` actually shipped are two sentences with a bold lead. No heading, no
  list marker, no quote — the release makes the bullet. Emphasis and code spans
  are allowed, which is why the bound is on characters and not on lines.
- **A dry run refuses nothing.** The task's four refusals are written as a
  release's ("there is nothing to *release*"), and only the third names the dry
  run explicitly. A dry run that refused *the tag already exists* could not be
  pressed at all between a release and its pull request landing, which is exactly
  when a rehearsal is wanted. So a dry run prints `would refuse a release: …` for
  each one and carries on; the self-test asserts that (*and a dry run may name
  one, and refuses nothing*).
- **A dry run's `ci is green` does not filter on `push`.** `ci.yml`'s push
  trigger is `master`'s alone, so a dry run of a branch has no push run and the
  old gate would have waited twenty minutes for one that was never coming. For a
  dry run the event filter is dropped and the branch's own pull-request run
  answers; a real release still reads a **push** run of `master`, as it always
  has.
- **A pull request that cannot be merged turns the run red.** The task says it is
  left open and that the summary says so, and does not say whether the run
  passes. It goes red, with a summary naming the branch, the setting that is the
  usual cause, and what the next press will say — because pile 1.11 exists
  precisely because two green runs published nothing, and a green run that left
  the version unmoved is that same failure again. The release itself stands and
  nothing is undone.
- **`ci-commit` insists on the bot *and* the paths.** The commit the workflow's
  own pull request puts on `master` gets no `ci` run (GitHub raises no workflow
  from an event made with the job's token), so the gate walks the head back over
  it. The walk steps over a commit only when it is `github-actions[bot]`'s **and**
  every file in it is `VERSION`, `CHANGELOG.md`, `release-notes/` or one of the
  three manifests, it is not a merge, and at most five in a row. A person's commit
  stops it even when it touches only those files — a person's push *does* start a
  `ci` run, so that one must be waited for. Two self-test cases hold each half.
  The build and the tag still use `master`'s head; only *which run was green* is
  asked of the commit below.
- **The notes' standing text keeps `v0.7.0`'s observer and flood-scope
  paragraphs**, minus the two sentences that were that release's own (*An upgrade
  … this release adds none*, and *the status message **now** carries…*). The task
  says the standing parts stay where they are; a line that a later release makes
  wrong is that release's line to fix.
