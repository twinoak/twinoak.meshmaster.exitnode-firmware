# v0.7.3

Released 2026-11-19 19:41 UTC from `b6d4cfb`. These are the bullets of that release's *What's new*, as published.

- **A neighbour listing now says how many neighbours the repeater has.** When a reading comes back with only part of the list, because a page was lost on the air, meshmaster.dk can tell: before, the part that arrived was taken for the whole list and the neighbours missing from it were reported as lost until the next listing found them again.
- **A board can now be given a second place to keep firmware, which is what a future update will be fetched into.** On the console, `update` says whether this board has one yet and `update slot` adds it, once, followed by `reboot`; the WiFi, the token and the board's identity are untouched.
- **A release is now signed, and every image says inside itself what it is.** The release page carries `manifest.json` and `manifest.json.sig` beside the images: one signature covering every file, which is how meshmaster.dk will know a release is really this firmware's. On the console, `update` now prints what the running image says it is and which release keys the board trusts.
- **A board can now fetch a release from meshmaster.dk into its second slot and check it there.** On the console, `update fetch <release id>` downloads the image into the slot that is not running and refuses it in a sentence if the signature, the manifest or the bytes do not add up; `update` then says what the slot holds, and still says so after a reboot. Nothing is switched yet.
- **A board can now switch to the firmware it fetched, and it undoes it by itself if the new one does not work.** On the console, `update apply` restarts into the fetched image, which then has ten minutes to start the mesh, join the WiFi and reach meshmaster.dk; if it does not, the firmware that was running comes back without anybody's help, and `update` says what was missing.
- **An update can now be started from meshmaster.dk.** One press on an exit node's page and the board fetches the release, switches to it and keeps it only if the new firmware reaches the mesh, the WiFi and the server within ten minutes; the page follows each step and says how it ended. A board that had no room for a second firmware makes room itself. Nothing updates a board unless a person asks.
- **Making room for a second firmware no longer risks the board.** The one write of the partition table is now tried again when it fails, and if the new table still will not hold, the one the board came with is put back, so the board goes on running as before. A board left with neither keeps trying once a minute and says in plain words, every time you ask it anything, that its power must stay on.
- **A board that has been updated can now be put back on the firmware it came from.** On the console, `update back` switches to whatever is in the board's other slot and gives it the same ten minutes to prove itself; flashing the older release over USB never did that, and the board now says at every start which release it is holding but not running.
